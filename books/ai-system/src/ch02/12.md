# 2.4 软件栈：框架、编译器、推理引擎与服务系统

打开手机里的 AI 助手，输入一句“帮我把这段话改得更礼貌一些”，不到一秒，屏幕上开始一个字一个字地冒出回答。上一节讲过，回答背后是数据中心里成排的 GPU 服务器。但 GPU 本身只是一块会做大量乘法加法的硅片，并不认识你那句话，也不知道该调用哪个模型。它和你的提问之间，隔着好几层软件。这几层软件叠在一起，工程师称为“软件栈”（Software Stack）。

## 2.4.1 一摞软件，像一栋楼的不同楼层

可以把软件栈想象成一栋楼：最底层是地基和管线，最上层是对外开放的大堂。越往下越贴近硬件，越往上越贴近用户。人工智能系统的软件栈大致可以分成下面几层：

| 层次 | 主要任务 | 常见例子（写作时的情况） | 类比 |
|---|---|---|---|
| 服务系统 | 接收用户请求、排队、分配机器、计费与限流 | 各家云平台的模型服务、API 网关 | 酒店前台与调度 |
| 推理引擎 | 让训练好的模型高效地生成回答 | vLLM、TensorRT-LLM、llama.cpp 等 | 专业后厨 |
| 深度学习框架 | 描述模型结构，组织训练与计算 | PyTorch、TensorFlow、JAX | 菜谱与厨房流程 |
| 编译器与算子库 | 把计算翻译成芯片能高效执行的指令 | XLA、TVM、Triton、cuDNN 等 | 把菜谱拆成具体刀工火候 |
| 驱动与运行时 | 管理芯片、内存和任务的执行 | 英伟达的 CUDA、AMD 的 ROCm | 水电燃气管线 |

表中的具体名字变化很快，几年后可能换了一批，但“从用户请求到芯片指令要经过多层翻译和调度”这个结构基本不会变。下面从下往上逐层看。

## 2.4.2 底层：驱动、算子库与编译器

芯片厂商会提供驱动程序和编程平台，让软件能把计算任务交给芯片。英伟达的 CUDA（统一计算设备架构，Compute Unified Device Architecture）是其中最有代表性的一个。它是英伟达 GPU 专用的平台，并不是所有 AI 芯片通用的标准。AMD、谷歌和国内各家加速器厂商，都有各自对应的软件平台。

模型里的计算可以拆成许多基本动作，比如矩阵乘法、加法、求最大值。每一种基本动作叫作一个“算子”（Operator）。同样是矩阵乘法，写法不同，速度可能差出好几倍。原因在于芯片的计算单元很快，而从内存搬数据相对慢，好的实现要尽量让数据少搬几趟。所以厂商和社区会为常用算子写好高度优化的版本，集中放在“算子库”里。

“编译器”（Compiler）再往前走一步。它不只是挑一个现成的算子，而是把整个模型的计算看成一张图，自动做优化。例如，它可以把“先乘、再加、再取激活”三步合并成一步执行，这叫“算子融合”（Operator Fusion），好处是中间结果不必写回内存再读出来。像谷歌的 XLA（加速线性代数，Accelerated Linear Algebra）、开源的 TVM 都属于这一类。编译器的价值还在于“一次描述、多处运行”：同一个模型，经编译后可以跑在不同厂家的芯片上。这对想摆脱单一硬件依赖的企业很重要。

## 2.4.3 中层：深度学习框架

研究者和工程师很少直接写芯片指令，他们用“深度学习框架”（Deep Learning Framework）来搭模型。框架就像一套标准化的积木和说明书：用几十行代码声明“这里是一层注意力，那里是一层全连接”，框架就会自动安排计算，并且自动算出训练所需的梯度。这一功能叫“自动微分”（Automatic Differentiation），第六章讲训练机制时还会再遇到它。

写作时，学术界和工业界最常见的框架是 PyTorch，最初由 Meta（原 Facebook）主导开发，现由 Linux 基金会旗下的 PyTorch 基金会托管。另外还有谷歌开发的 TensorFlow 和 JAX。框架之所以关键，是因为它把“想法”和“硬件”分开了。研究者只需关心模型怎么设计，至于数千块 GPU 怎么协同、内存怎么分配，交给框架和底层去处理。

## 2.4.4 上层：推理引擎与服务系统

训练好的模型要变成每天服务海量用户的产品，还需要专门的“推理引擎”（Inference Engine）。训练时追求的是把数据一遍遍“喂”进去、把参数调好；推理时追求的是又快又省地生成回答。两者的优化重点不同，所以推理往往有专门的软件。推理引擎常见的本领包括：

- **缓存中间结果**：生成每个新词时，复用前面已经算过的内容，不必从头算一遍（即第六章将详细介绍的 KV 缓存）；
- **合并请求**：把许多用户的请求凑成一批一起算，提高芯片利用率，这叫“批处理”（Batching）；
- **降低精度**：用更少的位数表示数字，以换取速度和内存（第七章的“量化”）。

写作时，开源推理引擎 vLLM 在业界使用广泛；英伟达提供了面向自家 GPU 的 TensorRT-LLM；llama.cpp 则以能在普通笔记本电脑上运行模型而闻名，第九章动手实验时会用到这类工具。

再往上是“服务系统”（Serving System）。它是整个软件栈对外的门面，负责的事情和模型本身关系不大，却决定了用户体验：

1. 接住全球各地同时涌来的请求，检查身份和调用额度；
2. 决定把请求派给哪个机房、哪台机器；
3. 某台机器出故障时自动切换，保证服务不中断；
4. 记录每次调用消耗了多少令牌，用于计费和监控。

你在 App 里感受到的“偶尔排队”“提示请求过多请稍后再试”，通常就是服务系统在做限流和调度。

## 2.4.5 为什么软件栈常被称为“护城河”

看算力新闻时，常能读到这样的说法：某家公司芯片的纸面性能已接近领先者，但用户迁移意愿不高。原因多半在软件栈。多年积累下来的算子库、框架适配、调试工具和开发者习惯，形成了一张很难迅速复制的网。硬件决定的是理论上能跑多快，软件栈决定实际能跑出多快、开发者用起来顺不顺手。一位工程师有个形象的说法：芯片是发动机，软件栈是变速箱、传动轴和方向盘，少了后者，发动机再强，车也开不起来。

回到你那句“帮我把这段话改得更礼貌一些”。它先经过服务系统排队分派，再由推理引擎组织生成，框架和编译器把模型计算翻译成算子，最后由驱动交给 GPU 执行。生成的文字再沿原路返回你的屏幕。软件栈把硬件的算力变成了产品的能力，而这些能力最终要通过某个“入口”交到用户手上，这就是下一节要讲的应用与接口。
