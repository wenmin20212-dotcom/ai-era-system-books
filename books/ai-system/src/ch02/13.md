# 2.5 应用与接口：App、API 与智能体

打开手机里的 AI 助手，你看到的是一个输入框、一个发送按钮，也许还有一个麦克风图标。前面几节讲过的数据、模型、芯片和软件栈，用户一样也看不见。用户能直接接触的只有最外面这一层：**应用与接口**。它是整个人工智能系统和人打交道的地方，也决定了模型的能力能以什么形式、多少成本、多大范围被用起来。

## 2.5.1 App：给普通人用的“前台”

我们常说的 AI 产品，比如聊天助手、写作工具、拍照识物、输入法里的智能补全，在系统里属于**应用层（Application Layer）**。一个对话类 App 大致做这几件事：

- **收集输入**：接收文字，也接收语音、图片、文件，把它们转换成后台能处理的格式。语音通常先经过语音识别，转成文字或特定编码。
- **组织上下文**：把你这次的问题、之前的聊天记录、你设置的偏好整理到一起，再交给后台。
- **呈现输出**：把后台一点一点传回来的文字实时显示出来，就是你看到的“逐字打出”效果；也可能把它渲染成表格、代码块或朗读出来。
- **管理账号与权限**：登录、额度、历史记录、隐私设置，都在这一层处理。

可以把 App 看作餐厅的前厅和服务员。点菜、上菜、结账都在这里完成，真正做菜的是后厨。同一个后厨可以同时供应堂食、外卖和团餐，同一个模型也可以同时支撑手机 App、网页版和办公软件里的插件。

## 2.5.2 API：给程序用的“窗口”

很多 AI 能力并不出现在独立 App 里，而是藏在别的软件中，比如客服系统自动回复、文档软件一键总结、购物平台生成商品描述。这些软件之所以能调用模型，靠的是**应用程序编程接口（Application Programming Interface，API）**。

API 是一套事先约定好的“点菜单格式”。开发者的程序按格式发出一个**请求（Request）**，里面写明要用哪个模型、输入内容是什么、最多生成多长；服务器处理后返回一个**响应（Response）**。在写作时，主流大模型服务商普遍通过网络 API 对外提供服务，请求和响应常用 JSON 这种文本格式书写，并通过一串**API 密钥（API Key）**识别调用者、统计用量。

| 对照项 | App | API |
|---|---|---|
| 使用者 | 普通用户 | 开发者编写的程序 |
| 交互方式 | 点击、输入、说话 | 按格式发送请求 |
| 常见计费 | 免费额度或按月订阅 | 多按输入、输出的令牌数量计费 |
| 典型用途 | 个人问答、创作 | 嵌入其他产品、批量处理 |

计费单位“令牌（Token）”是模型处理文本的基本单位，大致相当于一个词或词的一部分，中文里常常一两个字对应一个令牌，具体换算因模型而异。第五章讲价值流时会再回到它。这里先记住：**API 把模型变成了一种可以按量购买、随处接入的基础服务**，就像自来水管道把水厂接进千家万户。

除了云端 API，还有一类接口在本地运行。手机厂商在系统里集成的小模型、电脑上运行的开源模型，可以通过本机接口被调用，不必把数据发到远方的数据中心。哪些任务在端侧做、哪些上云，是各家厂商不同的设计取舍，第七章讲端侧部署时再展开。

## 2.5.3 智能体：会自己“跑腿”的应用

普通对话是一问一答：你问，模型答，结束。**智能体（Agent）**更进一步。它让模型根据目标自己拆分步骤，调用外部工具，看结果，再决定下一步，直到任务完成或需要人来确认。

举个场景：你说“帮我查一下下周末北京的天气，如果下雨就把周六的户外聚会改到周日”。一个智能体可能会依次做这些事：

1. 理解目标，判断需要天气信息和日历操作两样工具；
2. 调用天气查询接口，拿到预报；
3. 判断周六是否有雨；
4. 如果有雨，调用日历接口修改日程，或者先请你确认；
5. 把执行结果汇报给你。

这里的关键机制是**工具调用（Tool Calling / Function Calling）**：开发者事先向模型描述有哪些工具、每个工具需要什么参数；模型并不亲手执行操作，而是输出一段结构化的“调用意图”，由外层程序真正去执行，再把结果交回模型。写作时，多家模型服务商都在 API 中提供了这类功能，业界也出现了一些试图统一模型与工具连接方式的开放协议，例如 Anthropic 提出的模型上下文协议（Model Context Protocol，MCP）。具体规范仍在演进，名称和细节以各方最新文档为准。

智能体能“办事”，带来的风险也比聊天大：查错一次天气无关紧要，误删一份文件、误发一封邮件就麻烦了。所以设计良好的智能体会限制工具权限，在关键操作前请求人工确认，并保留操作记录。第六章会专门剖析它的规划与执行机制。

## 2.5.4 接口层为什么重要

从系统角度看，应用与接口层至少承担三种作用：

- **翻译**：把人的意图和其他软件的需求，转换成模型能接收的输入，再把模型输出转换成人和程序能用的结果。
- **把关**：在请求进入模型之前、输出返回用户之前，做身份验证、限流、内容安全过滤。很多安全措施在这一层生效，不只靠模型本身。
- **放大**：同一个模型，通过不同的应用和接口，可以变成翻译工具、编程助手或客服系统。模型能力相同，不同的组织方式会让它在用户那里显得很不一样。

所以评价一个 AI 产品好不好用，不能只看背后用的是哪个模型。上下文怎么组织、工具接得是否可靠、出错时怎么提示和回退，这些接口层的工程细节同样影响体验。

到这里，第二章的五个组成部分已经全部出场：数据是原料，模型是凝结下来的能力，算力是动力，软件栈是调度体系，应用与接口是面向人的出口。下一节我们把它们收拢成一张完整的结构骨架图，再动手去找找它们在你身边留下的痕迹。
