# 4.4 数据中心与用户之间：云服务、API 网关与终端设备

前面三节，我们从芯片内部一路走到集群：张量核心挨着高带宽内存，八张 GPU 挤在一台服务器里，成千上万台服务器靠高速网络连成一体。可是这些机器都锁在远方的机房里，你手里只有一部手机。你在聊天 App 里输入“明天去爬山要带什么”，按下发送，一两秒后答案就一行行出现在屏幕上。从你的指尖到那座数据中心，中间隔着几百甚至几千公里，还要经过运营商网络、互联网骨干网、云平台的层层关口。这一节要回答的问题是：**用户和数据中心之间，靠什么连起来？**

## 4.4.1 一条请求的“出门路线”

先按顺序看一条请求走过的地方。下面的路线是对常见在线大模型服务的概括，各家公司的具体实现不同。

1. **终端设备**：手机或电脑上的 App、网页把你的文字打包成一条网络请求。请求通常使用 HTTPS（超文本传输安全协议），内容在传输途中是加密的。
2. **接入网络**：请求经过 Wi‑Fi 路由器或蜂窝基站，进入运营商网络，再走上互联网骨干网。
3. **边缘入口**：大型服务往往在多个地区设有接入点，常借助 CDN（内容分发网络）或类似的边缘节点，让你先连上离你较近的入口，缩短建立连接的时间。
4. **API 网关**：请求进入服务商的“大门”，接受身份检查、限流和路由。
5. **推理集群**：请求被分配到某组 GPU 服务器上，模型逐个生成令牌。
6. **原路返回**：生成的文字以流式方式一段段传回，屏幕上就出现了“打字机”效果。

整条路线可以类比成寄快递：手机是寄件人，运营商网络是城际公路，边缘节点是离你家最近的营业点，API 网关是总仓的安检和分拣中心，推理集群才是真正“加工”包裹的车间。

## 4.4.2 API 网关：数据中心的“前台”

API（应用程序编程接口）是一套约定好的“提问格式”：发什么字段、用什么地址、返回什么结构，双方事先说清楚。在 AI 服务里，App 和第三方开发者都通过 API 调用模型。**API 网关**（API Gateway）就是所有调用的统一入口，它本身不做推理，只负责几件管理性的事情：

| 网关职责 | 通俗理解 | 为什么必要 |
|---|---|---|
| 身份认证 | 核对“API 密钥”或登录凭证 | 确认是谁在调用，便于计费和追责 |
| 限流 | 规定每分钟最多多少次请求、多少令牌 | 防止个别用户挤占 GPU，抵御恶意刷量 |
| 路由 | 决定送往哪个模型、哪个地区的集群 | 不同模型、不同负载需要分流 |
| 计量 | 统计输入、输出令牌数 | 按量计费的依据 |
| 安全过滤 | 部分系统在入口处做内容审查 | 与第三章讲的安全模块配合 |

网关后面通常还有一层**负载均衡**（Load Balancing），它把请求分摊给当时较空闲的推理服务器，就像银行大厅的叫号机，不让某个窗口排长队而另一个窗口闲着。

## 4.4.3 云服务：把算力变成“按需取用”

绝大多数企业和开发者并不自建万卡集群，而是通过**云服务**（Cloud Service）使用 AI。按照用户“自己管多少”，常见形态可以分成三层：

- **租用算力**：在云平台上按小时租 GPU 虚拟机或整台服务器，模型和软件由用户自己部署。这接近 IaaS（基础设施即服务）。
- **托管平台**：云厂商提供训练、部署工具，用户上传模型即可上线服务，近似 PaaS（平台即服务）。
- **模型 API**：直接按调用付费使用现成的大模型，用户只写几行调用代码。这是写作时最普遍的使用方式，一些提供商把它称为“模型即服务”（MaaS）。

写作时，国内外主要云厂商和大模型公司都提供以上一种或几种形态，具体产品名称和价格变化很快，读者以各家官网为准。系统层面值得记住的是：**云把“拥有机器”变成了“租用能力”**，于是一家几个人的小公司也能调用由大型集群支撑的模型，而集群的建设、维护和电费由云厂商承担，再分摊到每次调用的价格里。这一点会在第五章的“价值流”里展开。

## 4.4.4 时延从哪里来

用户最直接的感受是“快不快”。一次对话的等待时间大致由三段组成：

- **网络往返时间**：信号在光纤中传播一千公里约需 5 毫秒量级，加上路由转发，跨地区往返常在几十到上百毫秒。服务商在多个地区部署机房，就是为了缩短这一段。
- **排队时间**：高峰期请求多，网关和调度器需要让请求等待空闲的 GPU。
- **生成时间**：这往往是大头。模型需要先读完你的输入，再逐个生成令牌，回答越长耗时越久。业内常用“首令牌延迟”（TTFT，Time To First Token）衡量多久开始出字，用每秒输出令牌数衡量出字速度。

流式输出之所以普遍，正是因为它让第一段文字尽早到达，虽然总时间没变，人的主观等待感明显减轻。

## 4.4.5 终端设备：不只是“显示屏”

手机并非只负责收发。写作时，主流手机芯片大多集成了 NPU（神经网络处理器），一些手机厂商已在设备上本地运行参数规模较小的模型，用于语音识别、照片处理、文字摘要等任务。这就形成了**端云协同**的分工：

| 在终端运行 | 在云端运行 |
|---|---|
| 小模型，响应快，不依赖网络 | 大模型，能力强，可随时更新 |
| 数据不出设备，隐私更易保护 | 需要上传数据 |
| 受电池、内存、发热限制 | 受网络和服务费用限制 |

不少系统的做法是：简单任务在手机上就地完成，复杂任务再发往云端，由系统或用户选择。具体怎样分工，各家厂商的设计不同。第七章讲模型压缩时，我们会看到小模型是怎样被“塞进”手机的。

## 4.4.6 小结：一条从指尖到机房的链

把第四章四节连起来，就得到一条完整的连接链：芯片内的张量核心与高带宽内存 → 服务器内的多 GPU 互连 → 集群内的高速网络 → 云平台与 API 网关 → 互联网 → 你手里的终端。每一级都有自己的“接口”和“瓶颈”，任何一环变慢，你看到的就是转圈的加载图标。理解了这条链，下次遇到“服务繁忙，请稍后再试”，你就能大致判断：问题多半不在你的手机，而在网关限流或推理集群排队。下一节，我们把本章的连接关系整理成骨架，并到身边去找它们的实物踪迹。
