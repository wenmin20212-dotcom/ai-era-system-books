# 3.2 推理系统：把能力变成回答

你在手机上问助手“明天去杭州要带伞吗”，按下发送，不到一秒，第一个字就出现了，随后文字一个接一个地“流”出来。这段几秒钟的体验背后，是一套专门负责“把训练好的能力变成具体回答”的系统，叫作**推理系统**。这里的“推理”（Inference）不是逻辑学里的演绎推理，而是工程术语，指用已经训练好的模型去处理新的输入、产生输出。上一节讲的训练系统像是“读书”，推理系统则像是“上岗答题”。读书一次要花很久，答题却要每天面对成千上万的人。

## 3.2.1 训练和推理：一次性投入与天天运营

训练与推理用的是同一个模型，但两者的工作性质差别很大，可以用下表对照：

| 对比维度 | 训练系统 | 推理系统 |
|---|---|---|
| 目标 | 调整参数，让模型学会能力 | 参数固定，用模型回答问题 |
| 发生频率 | 一个模型通常只做一次大规模训练（后续可再微调） | 模型上线后持续发生，每次提问都要做一次 |
| 最关心的指标 | 总耗时、总成本、训练是否稳定 | 响应速度、并发能力、每次回答的成本 |
| 计算特点 | 前向加反向传播，计算量大且集中 | 只有前向计算，但请求零散、时刻变化 |
| 类比 | 厨师在学校学艺几年 | 餐厅每天接待一拨又一拨客人 |

这张表里最重要的一点是：训练是“一次性的大投入”，推理是“长期的流水账”。一个面向大众的 AI 应用，每天可能收到海量请求，累计起来，推理消耗的算力和电费在许多公开分析中被认为可以与训练相当，甚至超过训练。所以，推理系统的设计核心不是“能不能算出来”，而是“能不能又快又省地算出来”。

## 3.2.2 一个回答是“一个字一个字”生出来的

为什么回答是逐字出现的？这不是界面特效，而是大语言模型的工作方式决定的。

模型处理文字的基本单位叫**令牌**（Token），可以理解为“词块”：一个常见汉字、一个英文单词或单词的一部分，都可能是一个令牌。推理时，模型每次只预测“下一个令牌最可能是什么”，选出一个后，把它接到已有文字后面，再预测下一个。这个过程叫**自回归生成**（Autoregressive Generation），像接龙一样，直到模型输出“结束”标记，或达到长度上限。

因此一次回答可以分成两个阶段：

1. **预填充阶段**（Prefill）：模型一次性读完你的问题以及系统附加的提示，把它们“消化”成内部状态。问题越长，这一步越费时。
2. **解码阶段**（Decode）：模型一个令牌一个令牌地往外“吐”字。回答越长，这一步循环的次数越多。

这两个阶段对应着用户能感受到的两个指标：**首令牌延迟**（Time to First Token，TTFT，也常叫“首字延迟”），即按下发送到看见第一个字要等多久；以及**生成速度**，常用“每秒输出多少令牌”衡量。把文字边生成边推送给手机，叫作**流式输出**（Streaming），它不会让总时间变短，却让人不必干等，体验好得多。

## 3.2.3 推理系统里的几个关键部件

把模型权重文件放到一块 GPU 上，写几行代码，就能做最简单的推理。但要同时服务大量用户，就需要一整套部件协同工作：

- **请求入口与调度器**：接收来自各地的请求，排队、分配给合适的机器，类似餐厅的前台和领位员。
- **推理引擎**（Inference Engine）：真正驱动模型计算的软件，负责把计算高效地安排到 GPU 上。写作时开源社区常见的有 vLLM、SGLang，英伟达也提供 TensorRT-LLM 等工具；各大公司内部还有自研系统。
- **KV 缓存**（Key-Value Cache，键值缓存）：模型在生成每个新令牌时，需要回看前面所有内容。如果每次都从头重算，浪费极大。KV 缓存把已经算过的中间结果存在显存里，下一步直接取用。它让生成速度大幅提高，代价是占用大量显存——对话越长，缓存越大。
- **批处理**（Batching）：GPU 擅长“一次算很多份”。把多个用户的请求合在一起计算，能显著提高硬件利用率。现代推理引擎普遍采用**连续批处理**（Continuous Batching）：有人的回答写完就离开，新请求随时补进来，像一辆不停站、随时上下客的公交车。
- **输出后处理与安全检查**：把令牌还原成文字，有些系统还会在输出前后做内容审核，这部分将在下一节展开。

这些部件的工作原理，第六章 6.3 节会进一步讲解；这里只需记住它们各自“负责什么”。

## 3.2.4 快、多、省：推理系统的三角难题

推理系统的工程师常在三个目标之间权衡：

- **快**：单个用户等得少，首令牌延迟低、生成速度高；
- **多**：同一批机器能同时服务更多用户，即吞吐量高；
- **省**：每生成一百万个令牌的成本更低。

这三者经常互相牵制。比如把更多请求塞进同一批次，吞吐量上去了，单个用户却可能等得更久；为了速度使用更大更快的芯片，成本又会上升。常见的折中手段包括：用**量化**（Quantization）把模型参数从高精度数字压成低精度数字，减少显存和计算量；用较小的模型处理简单问题，复杂问题再交给大模型；对重复出现的提示内容复用缓存。这些技术在第七章 7.4 节还会详细介绍。

你在新闻里看到的“某某模型降价”“输出速度提升”，背后往往就是推理系统在这个三角上找到了新的平衡点，而不一定是模型本身变聪明了。

## 3.2.5 推理发生在哪里：云端与手机

推理不一定都在远方的数据中心完成。写作时的情况大致是：

| 部署位置 | 典型场景 | 优点 | 局限 |
|---|---|---|---|
| 云端数据中心 | 大型对话助手、复杂写作和编程 | 可运行大模型，能力强 | 依赖网络，有延迟和服务成本 |
| 手机、电脑等终端 | 输入法联想、相册识别、离线翻译、部分系统助手功能 | 响应快、可离线、数据不必出设备 | 只能运行较小的模型 |
| 端云协同 | 简单请求本地处理，复杂请求转发云端 | 兼顾隐私、速度与能力 | 系统设计更复杂 |

手机芯片里的**神经网络处理器**（Neural Processing Unit，NPU）正是为端侧推理而设计的。一些手机厂商已采用端云结合的方式，但具体如何分工，各家做法不同，不能一概而论。

## 3.2.6 小结

训练系统让模型“学会”，推理系统让模型“会用”。从你按下发送键起，请求被调度、模型逐个令牌地生成、KV 缓存和批处理在幕后节省算力，文字再流回你的屏幕——每一个环节都在和时间、显存与成本赛跑。不过，一个只会“接龙”的模型，并不天然知道哪些话该说、哪些不该说，回答也未必符合用户的真实意图。让系统按人类意图行事，正是下一节对齐与安全模块要解决的问题。
