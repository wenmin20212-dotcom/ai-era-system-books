# 7.2 Tool and Context Protocols: Making Tools Plug-and-Play

Suppose you are using a coding agent on your computer to modify code, and you also want it to read your company's internal requirements documents and check the status of tasks in your project management system. Many people setting this up for the first time discover that "connecting the agent to a system" usually isn't done by typing a sentence into the chat box. Instead, you add a "server" in a settings file, fill in a name and a launch command or URL, and sometimes go through an authorization step. Once that's done, a few new capabilities appear in the agent's tool list.

The thinking behind this process resembles the way computer ports moved from assorted proprietary plugs to a unified standard. That thinking is the subject of this section: using a shared **protocol** (a set of communication rules agreed on in advance by both sides) to turn tool integration from one-off custom handiwork into plug-and-play standard parts.

## 7.2.1 Without a Protocol: The M×N Problem

Chapter 4 explained that a model "speaks" an action through function calling, and the orchestration program then actually carries it out. The trouble is that each agent application may use its own format for describing tools, passing parameters, and returning results. If M agent applications need to connect to N external systems (files, databases, calendars, code repositories, and so on), the worst case requires writing M×N pieces of adapter code. Each one is maintained separately, and whenever either side releases a new version, a batch of integrations may break.

A protocol places a layer of shared conventions in the middle that everyone follows. Each agent application only needs to implement "speaking this protocol" once, and each external system only needs to implement "providing capabilities according to this protocol" once, reducing the workload from M×N to roughly M+N. The internet has long since proven this approach works: browsers and websites can interoperate precisely because of public protocols like HTTP, not pairwise negotiations.

## 7.2.2 A Representative Example: The Model Context Protocol

At the time of writing, one of the more influential open standards in this area is the **Model Context Protocol** (MCP), released and open-sourced by Anthropic in November 2024. The company uses the USB-C port as an analogy: just as different devices connect through the same port, different tools and data sources connect to agents through the same protocol. Since then, agent products and developer tools from a number of companies have announced support for the protocol. However, the exact level of support and configuration methods vary from product to product and change quickly, so consult each product's official documentation when using it.

The basic structure of MCP can be summarized with three roles:

| Role | English | What It Does | Analogy |
|---|---|---|---|
| Host | Host | The agent application the user interacts with directly, such as a desktop assistant or coding tool | The computer itself |
| Client | Client | The component inside the host responsible for maintaining a connection to one particular server | A port on the computer |
| Server | Server | A program that exposes an external system's capabilities according to the protocol | A plugged-in peripheral |

What servers provide to agents falls into three main categories: **Tools**, which are actions that can be executed, such as "create a task" or "run a query"; **Resources**, which are data that can be read, such as file contents or database records; and **Prompts**, which are pre-written task instructions that users can invoke directly. The advantage of this division is that "what can be done" and "what can be seen" are separated at the interface level, which makes permission control, discussed later, easier to manage.

At the communication level, MCP messages use the JSON-RPC 2.0 format. JSON is a structured text format, and RPC stands for "Remote Procedure Call," meaning asking another program to do something as if calling a local function. A server can run as a process on the local machine, communicating with the host via standard input and output, or it can be deployed remotely and accessed over HTTP.

## 7.2.3 How Plug-and-Play Happens

Connecting a new server to an agent generally involves the following steps:

1. **Connection and handshake**: The client and server tell each other their protocol version and the features each supports, much like two devices confirming "which language we both speak" after being plugged in.
2. **Capability discovery**: The client asks the server, "What tools do you have?" and the server returns each tool's name, description of its purpose, and parameter format.
3. **Placement into context**: The host passes these tool descriptions to the model, so the model "knows" what new capabilities it has.
4. **Invocation and return**: When the model decides to use a tool, the host sends a request through the client, the server executes it and sends back the result, and the result then feeds into the next round of reasoning.

Step 2 is the key. The tool list is fetched dynamically at runtime rather than hard-coded into the agent program, so adding a new server requires no changes to the agent itself. That is exactly what "plug-and-play" means.

## 7.2.4 What Protocols Solve, and What They Don't

A unified protocol brings interoperability, but it does not automatically bring reliability or security. Three points deserve attention:

- **How well descriptions are written still determines how well tools are used.** The model relies on tool descriptions to decide when to call a tool and how to fill in parameters; vague descriptions lead to faulty calls.
- **More tools mean a more crowded context.** Every tool description consumes tokens. Connecting dozens of servers at once both raises costs and interferes with the model's choices. The context flow discussed in Chapter 5 applies here as well.
- **A third-party server is third-party code.** The content it returns may carry malicious instructions, and the actions it performs may exceed its authority. The protocol specifies "how to talk," while "whether to trust it and whether it may act" must be guarded by sandboxes, permissions, and human confirmation—the topics of the next section and Section 7.5.

Beyond "agents connecting to tools," the industry is also exploring protocols for "agents connecting to agents." For example, Google proposed the Agent2Agent (A2A) protocol in 2025 to let agents from different sources discover one another and delegate tasks. Such standards are still evolving, and the landscape may shift, but the underlying logic stays the same: **replace pairwise custom connections with connections built on shared conventions.**

Once you understand this, whenever you encounter the name of a new protocol, you can break it down with the same set of questions: Who does it connect to whom? What messages does it define? How does each side discover the other's capabilities? And to whom does it leave the security problems?
