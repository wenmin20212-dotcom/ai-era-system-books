# 7.1 Agent Frameworks and Development Tools

Suppose you're in charge of a small project at your company: have an AI read the previous day's sales spreadsheet automatically every morning, flag any anomalies, and post a short write-up to the team chat. You've tried it in a chat window, and the model can indeed understand the spreadsheet and write the summary. But the moment you want it to "run on its own every day," problems pop up immediately. Where does it read the spreadsheet from? Who retries when something fails? How do you hook up the messaging interface? And how do you check afterward what each step actually did?

These questions have little to do with how smart the model is. They are engineering problems. Earlier chapters took the agent apart into its components: the model, instructions, tools, memory, the runtime environment, and the orchestration program. Assembling those parts into a machine that runs reliably takes a great deal of repetitive "plumbing work." Agent frameworks and development tools emerged to standardize that work.

## 7.1.1 What a Framework Is: A Prefabricated Set of "Frames and Fittings"

An **agent framework** is a type of software library or platform that pre-writes the code you would otherwise write over and over when building agents, so developers only need to fill in their own task logic. Think of it like building a home. Building from scratch means pouring the foundation, laying the walls, and running the plumbing and wiring yourself. With an unfinished apartment, the load-bearing walls and utility lines are already in place, and all you decide is how to lay out the rooms.

A typical framework usually provides the following kinds of "prefabricated parts":

| Prefabricated part | Problem it solves | Related section in this book |
|---|---|---|
| Model access layer | Calls models from different vendors with a unified syntax | 2.1 The Brain |
| Prompt templates | Assembles system prompts, roles, and task descriptions into a fixed format | 2.2 Instructions |
| Tool registration and invocation | Registers a function as a "tool," auto-generates its description, and parses the model's call requests | 2.3 The Hands, 6.3 Tool Calling |
| Memory module | Stores conversation history, compresses it into summaries, and connects to vector retrieval | 2.4 Memory, 6.4 Memory Management |
| Loops and orchestration | Implements the "reason–act" loop, or schedules multiple steps and multiple agents according to a flowchart | 6.1, 4.3 |
| Logging and tracing | Records the input, output, latency, and token usage of each step | 5.5 Cost Flow |

As you can see, a framework does not bring any new "intelligence" of its own. It turns the structures and mechanisms discussed earlier into reusable parts. Once you understand the frame, you can look at any framework and recognize where it saves you effort.

## 7.1.2 Three Common Organizational Patterns

Frameworks differ widely in their design philosophy, but they fall roughly into three organizational patterns.

**The first is the chain or pipeline pattern.** The task is written as a fixed sequence of steps: retrieve first, then summarize, then output. The flow is clear and easy to debug, which suits tasks whose steps are largely fixed, such as the sales report above. The cost is low flexibility. When something unexpected happens, it won't reroute on its own.

**The second is the graph or state-machine pattern.** Each step is treated as a node on a graph. The edges between nodes can carry conditions, and the flow can return to earlier nodes to form loops. This pattern can express both a "fixed flow" and branches such as "retry on error" or "continue after human approval." At the time of writing, several popular frameworks in the open-source community follow this approach, such as LangGraph from the LangChain team.

**The third is the conversational multi-agent pattern.** You define several agents, each with its own role, such as a "researcher," a "writer," and a "reviewer," and they collaborate on a task by sending messages to one another. AutoGen, launched by Microsoft Research, is built mainly around this pattern. It has since entered maintenance mode, and Microsoft recommends its successor, Microsoft Agent Framework, instead. The open-source project CrewAI also centers on this pattern. It mirrors how human teams divide labor, and its advantage is that it is intuitive. The difficulty is that as messages pile up, so do costs and the risk of losing control (see Sections 4.3 and 5.5).

These three patterns are not mutually exclusive. Many frameworks support all of them, and developers choose based on the nature of the task.

## 7.1.3 From Code Libraries to "Out of the Box": The Spectrum of Development Tools

Beyond frameworks, there is a large category of development tools. Ordered by barrier to entry, they fall roughly along a spectrum:

- **Official toolkits from model vendors.** At the time of writing, OpenAI, Anthropic, Google, and others have each released their own agent development kits, such as OpenAI's Agents SDK and Anthropic's Claude Agent SDK. They are tightly integrated with their own models and usually also support general-purpose tool protocols (covered in the next section).
- **General-purpose open-source frameworks.** These are not tied to any particular model. They have active communities and rich component libraries, and they suit developers who need flexible combinations.
- **Low-code or visual platforms.** You build flows by dragging blocks and connecting them, with little coding required. Platforms like these exist both in China and abroad, and they let business staff prototype quickly.
- **Ready-made agent products.** Examples include coding agents and assistants that can operate a browser. Users assign tasks directly, with no assembly involved.

The further down the spectrum, the less effort required. The further up, the more control you have. When adopting these tools, managers often need to weigh "launching quickly" against "being able to see and modify every step."

## 7.1.4 What Really Matters When Choosing a Framework

Frameworks evolve extremely fast. Their names and features can change within a few months. For that reason, this book does not recommend specific choices. It offers only a few criteria that are unlikely to go out of date:

1. **Transparency.** Can you see the full prompt sent to the model at each step, along with the results the tools return? With frameworks that hide too much behind abstractions, problems are hard to pin down.
2. **Observability.** Is there built-in tracing and logging? Can you track latency and token usage?
3. **Control points.** Can you easily insert human confirmation, permission checks, and timeout aborts? This bears directly on the safety issues discussed in Sections 7.3 and 7.5.
4. **Replaceability.** How much code do you have to change to switch to a different model or tool? Does the framework support open tool protocols?
5. **Task fit.** Using a heavyweight multi-agent framework for a simple task often costs more than it's worth. Many experienced engineers take this approach: write it first with the plainest possible loop, confirm that a framework is truly needed, and only then bring one in.

The last point deserves a bit more discussion. A framework saves you repetitive work, but it also adds a layer of abstraction. An agent's core loop is essentially nothing more than "send the context to the model, parse which tool it wants to call, execute it, and put the result back into the context." You can write a working prototype in a few dozen lines of code (Section 9.2 will walk you through it hands-on). Understand this core first, and then use a framework. Only then can you strike the right balance between the framework's convenience and your own control.

## 7.1.5 Summary

Agent frameworks turn components such as model access, prompts, tools, memory, loops, and logging into standard parts. Development tools extend from code libraries to visual platforms and ready-made products. What they solve is the question of "how to assemble an agent reliably." But for the parts to plug into one another, there also needs to be a unified interface standard: how tools describe themselves and how context is passed along. That is exactly the question the next section, "Tool and Context Protocols," will answer.
