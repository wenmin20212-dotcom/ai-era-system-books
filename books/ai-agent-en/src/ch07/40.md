# 7.3 Sandboxes, Permissions, and Security Isolation

Suppose you ask a coding agent to fix an error in your project. It reads the code, decides a dependency package is missing, and types an install command into the terminal. Then, to "clean up the environment," it prepares to delete a folder it considers useless. At that moment a prompt pops up on the screen: "The agent wants to run the following command. Allow?" You pause, take a look, and realize that the folder holds experimental data you haven't backed up yet.

Behind that brief pause lies a whole body of engineering design. An agent that can take action can also take the wrong action. So we first need to define where it may act, what it may touch, and how much damage a mistake could cause. That design is the subject of this section: sandboxing, permissions, and security isolation.

## 7.3.1 From "Trusting the Model" to "Limiting the Consequences"

As earlier chapters explained, the output of a large language model is probabilistic. It may misunderstand the task, it may be manipulated by malicious text on a web page (Section 7.5 discusses this "prompt injection" in detail), or it may gradually drift off course during a long task. Expecting a model never to make mistakes is unrealistic. The prevailing engineering approach is to accept that the model will make mistakes and then confine the consequences of those mistakes to a tolerable range.

This approach has long been mature in the field of computer security, and it is often summarized in a few principles:

| Principle | Meaning | Applied to agents |
|---|---|---|
| Principle of Least Privilege | Grant only the permissions needed to complete the task | A read-only task gets no write permission |
| Defense in Depth | Multiple layers of protection, so if one fails, another remains | Combine sandboxes, permission rules, and human confirmation |
| Default Deny | Any operation not explicitly allowed is blocked | Commands not on the allowlist require confirmation |
| Auditability | Every operation leaves a record that can be traced afterward | Keep logs of every tool call |

These principles were not invented for agents; operating systems, banking systems, and cloud services all use them. What makes agents special is that the party issuing the operations is not an employee who can sign a contract and be held accountable, but a program that makes on-the-fly decisions based on text. That is why these old principles must be enforced even more strictly.

## 7.3.2 Sandboxes: Giving the Agent an "Isolated Workshop"

The name sandbox comes from the children's sandpit: kids can dig however they like inside it, and the sand won't spill into the living room. In computing, a sandbox is a restricted execution environment separated from the real system, so nothing a program does inside it can affect the outside.

Common isolation techniques can be arranged from weakest to strongest:

1. **Directory restrictions**: The agent may read and write only within a particular project folder; all other paths are denied. This is simple to implement but offers the least isolation.
2. **Containers**: Using isolation features provided by the operating system, the agent gets its own file system, process space, and network settings. Docker is a common container tool. Containers start quickly and have low resource overhead, and many coding agent products use them as execution environments.
3. **Virtual Machines (VMs)**: A VM emulates an entire computer with its own operating system kernel. Isolation is more thorough, at the cost of slower startup and higher resource consumption. Some providers use lightweight virtual machine technology to strike a balance between isolation strength and speed.
4. **Remote cloud environments**: The agent doesn't run on your computer at all; it works on a temporary machine operated by the provider, which is destroyed when the task ends. As of this writing, cloud-based coding agents from several companies take this approach: they modify code and run tests in a temporary environment, then hand the results to the user for review in the form of code changes.

Beyond isolating files, a sandbox must also isolate the **network**. An agent that can freely connect to the internet, once manipulated, might send keys or private data it has read to an outside party. So a common practice is to cut off network access by default, or to allow access only to a few trusted addresses, such as official package repositories.

Sandboxes have another advantage: they are **disposable**. If the environment gets messed up, just delete it and rebuild. This contrasts with the opening scenario: deleting the wrong folder on your real computer is often irreversible.

## 7.3.3 Permissions: Writing "What It Can Do" as Rules

The sandbox determines where the agent operates; permissions determine what it can do there. Many agent tools classify operations by risk, roughly as follows:

- **Low risk, can run automatically**: reading files, searching code, viewing directories.
- **Medium risk, decided by rules**: modifying files within the project, running test commands.
- **High risk, requires human confirmation**: deleting files, installing software, pushing code to a remote repository, sending email, making payments.

Users or administrators can usually configure these rules, for example: "Allow running test commands, but ask me before any deletion." As of this writing, most mainstream coding agent products offer similar permission modes, with several levels ranging from "ask at every step" to "run automatically within a defined scope." The specific names and levels vary by product, but they are all making trade-offs on the same question: each additional prompt adds a bit more interruption for the user, and each prompt skipped adds a bit more chance that something goes wrong.

Permissions have one more easily overlooked source: **credentials**, meaning accounts, passwords, and access tokens. When an agent calls an external service, it always has to use some identity. Good practice is to give it a dedicated identity with limited permissions, rather than handing over your own administrator account. It's the same logic as a company giving an intern an account that can access only certain systems.

## 7.3.4 Human Confirmation: The Last Gate, With Its Own Limits

The pop-up in the opening scenario is human confirmation, an instance of the "Human-in-the-Loop" approach discussed in Section 4.4. It is the last line of defense, but relying on it alone is not dependable.

The first problem is **confirmation fatigue**. If an agent asks for confirmation dozens of times an hour, people soon start clicking "Allow" without reading, and the gate becomes useless. The second problem is **comprehension**. Faced with a complex command or a large block of code changes, an ordinary user may not be able to judge the risk.

So human confirmation must work together with the earlier layers: the sandbox catches most mistaken operations, permission rules filter out actions that are clearly safe or clearly dangerous, and only the few critical operations that truly require human judgment are passed to a person. The confirmation interface should also translate operations into plain language, such as "This will delete the data folder, which contains 312 files," rather than just displaying a raw command.

## 7.3.5 Summary: Stability Comes From Stacking the Layers

Stacking up the content of this section gives a simple model:

> The **sandbox** limits the scope of damage, **permissions** limit the kinds of actions, **human confirmation** guards a small number of critical decisions, and **logs** make everything traceable afterward.

None of these layers guarantees perfect safety, but they are independent of one another, so when one fails, the others still work. Next time you use an agent, pay attention to three things: what environment it runs in, what it is allowed to do, and when it will stop to ask you. Once you see these three clearly, you'll know how much risk you are taking on when you let it loose.

Isolation, however, is only one side of the security question. To judge whether an agent deserves trust, we also need a yardstick to measure its capability and reliability. That is the subject of the next section: evaluation benchmarks.
