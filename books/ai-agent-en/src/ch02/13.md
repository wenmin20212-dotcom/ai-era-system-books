# 2.5 Runtime Environment and Orchestration: Where the Agent Lives and What Drives It

Suppose you ask a coding agent on your computer to "change every date format in this project to year-month-day, then run the tests." A few minutes later, a stream of log entries scrolls across the screen: it opened several files, edited a dozen or so lines of code, ran the test command, saw two failure messages, went back to fix one spot, and finally told you, "All tests pass."

Several things in this sequence of actions deserve a closer look. Where were the files opened? On which machine did the test command run? A large language model can only output text. So what turned the sentence "run the tests" into a real command and sent the results back to the model? These two questions point to the last two components of an agent: the **runtime environment**, which answers "where," and the **orchestrator**, which answers "what drives it."

## 2.5.1 Runtime Environment: The Agent's "Workbench"

The runtime environment is the computing space where an agent's actions actually take place. It includes the files the agent can see, the programs it can run, the networks it can reach, and the operating system all of this sits on. To use an analogy: the model is a hired craftsman, the tools are the hammer and wrench in his hands, and the runtime environment is the workshop where he does the job. What materials the workshop holds, and whether its doors are locked or open, determine what the craftsman can actually accomplish and what he might break.

Common runtime environments fall roughly into the following categories:

| Type of runtime environment | Typical scenario | Characteristics |
|---|---|---|
| User's local machine | Using a coding agent in the terminal or editor on your own computer | Reads and writes your real files directly; convenient, but mistakes affect you directly too |
| Cloud container or virtual machine | A web-based assistant "running code" or analyzing a spreadsheet in the background | Isolated from your computer; can be thrown away as a whole when the task ends |
| Browser environment | An agent opening web pages and filling in forms on your behalf | Deals with real websites; actions can have real consequences |
| Internal enterprise systems | A business agent connected to a company database or ticketing system | Permissions and data are governed by organizational rules |

As of this writing, many vendors run code execution in temporary cloud containers, while some coding agents run directly in the command line on the user's own machine. Specific approaches vary from vendor to vendor and change quickly. One thing stays the same, though: every action has to land in some concrete environment.

The runtime environment matters to an agent in two ways. First, it is the **stage for action**: without an environment that can execute commands, "run the tests" remains only words. Second, it is the **source of observation**: test errors, file contents, and web page text are all information the environment feeds back to the agent, which relies on that information to decide its next step. Because actions in the environment have real consequences, people often add a layer of isolation called a sandbox: a restricted space, cut off from the outside world, where problems won't spill over into real systems. We'll leave the technical details of sandboxes and permissions for Chapter 7. For now, remember this: **how much an agent can do is often capped by its runtime environment, not just by the model's capabilities.**

## 2.5.2 Orchestrator: The "Dispatcher" That Keeps the Loop Turning

Now for the second question. A large language model is essentially a "text in, text out" function. It doesn't wake up on its own, and it doesn't type commands on its own. What actually keeps an agent cycling through its loop is an ordinary piece of software called the orchestrator, sometimes also called the agent framework or the "harness."

If you break down a single task, the orchestrator repeatedly does roughly the following:

1. **Assemble the input**: Combine the system prompt, the user's task, descriptions of the available tools, and the earlier conversation and tool results into one complete context, and hand it to the model.
2. **Parse the output**: Read the model's reply and determine whether it is answering the user directly or requesting a tool call, such as "run the command `npm test`."
3. **Execute the action**: If it's a tool request, actually carry it out in the runtime environment, pausing first to ask the user for confirmation when necessary.
4. **Return the results**: Write the command output, error messages, and other results back into the context, then call the model again.
5. **Decide when to stop**: End the loop when the model declares the task done, a step or time limit is reached, an unrecoverable error occurs, or the user calls a halt.

Think of it as a restaurant. The model is the head chef, who stays in the kitchen thinking about the menu. He says "I need two eggs," but he doesn't go out himself. The orchestrator is the waiter who also does the shopping: he passes the customer's requests to the kitchen, turns the chef's words into actual actions, and brings back the groceries along with the customer's new feedback. However brilliant the chef, without this waiter the food never reaches the table.

It's worth stressing that the orchestrator itself is **usually not artificial intelligence** but deterministic code written by developers. It doesn't do the "thinking," only the "turning." Even so, it sets many of the key rules: how much history the model sees, which tools it may call, which actions need human confirmation, and how many steps it may take at most. The same model placed in two different orchestrators can behave very differently.

## 2.5.3 How the Two Work Together: The Full Picture of a Task

Let's put the components from the previous sections together and return to the date-format example from the beginning:

- The **model** reads the context and decides, "First, search the project for every way dates are written";
- The **orchestrator** recognizes this as a search tool request and hands it to the runtime environment for execution;
- The **runtime environment** performs the search in the project folder and returns the results;
- The **orchestrator** puts the results back into the context and wakes the model again;
- This repeats until the tests pass and the model gives a summary, at which point the orchestrator ends the loop and presents the result to you.

| Component | Its role in one sentence | Without it |
|---|---|---|
| Model | Decides what to do next | No judgment, only a fixed script |
| Instructions | Define identity, goals, and rules | Doesn't know what to do or what rules to follow |
| Tools | Provide available actions | Can only talk, not act |
| Memory | Preserves process and knowledge | Starts from scratch at every step |
| Runtime environment | Where actions actually happen | Actions have nowhere to land |
| Orchestrator | Drives the loop and enforces rules | Components can't be connected |

This table also points to a common misconception. People tend to say "the AI completed the task on its own," but from a systems perspective, the task is completed by **a combination of model, program, and environment**. The model provides judgment, the orchestrator provides order, and the runtime environment provides the stage and the feedback.

## 2.5.4 Summary: Seeing the Two Components "Behind the Scenes"

When you use an agent, the model's replies are what stand out most, while the runtime environment and the orchestrator often stay hidden behind the scenes. The next time you look at an agent's execution log, ask two questions. Where was this step executed: on my computer, in a cloud container, or on some website? And what decided to ask for my approval first, and what decided it should stop? If you can answer these two questions, you can see the bridge that takes an agent from "able to talk" to "able to act."
