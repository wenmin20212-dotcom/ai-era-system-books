# 2.3 The Hands: Tools, Functions, and External Services

Suppose you say to an agent: "Check tomorrow's weather in Shanghai for me. If it's going to rain, move my afternoon outdoor run in my calendar to an indoor workout." A few seconds later, it replies: "Light rain is expected in Shanghai tomorrow. I've changed your 15:00 run to a gym session."

At no point did the large language model itself "see" the weather or "touch" your calendar. It cannot go online, and it cannot modify any file. All it does is read text in and write text out. The parts that actually query the weather service and change the calendar are a separate set of components, the agent's "hands": tools, functions, and external services.

## 2.3.1 Why the Brain Needs Hands

The previous section described the large language model (LLM) as the agent's "brain." This brain has three built-in limitations:

- **Its knowledge has a cutoff date**: Its training data stops at a certain point, so it doesn't know today's weather or stock prices.
- **It can only produce text**: It cannot actually send an email, create a file, or click a button.
- **Its exact calculations are unreliable**: Ask it to work through a long string of numbers in its head, and it may get them wrong. For the reasons inside the model, see Volume 18, *Large Language Models*.

Tools are attached to make up for these three gaps. Here is an analogy: the model is like a consultant sitting in an office, well-informed and capable of good judgment, but with no phone and no computer at hand. Tools are like giving that consultant a phone, a calculator, and a key to the office. The consultant is still responsible for deciding "what should be done," while these instruments carry out the actual actions.

## 2.3.2 What a Tool Is: A "Manual" Plus a "Real Program"

In engineering terms, a tool usually has two parts.

**The first part is a manual written for the model**, which generally includes:

| Item | Example | Purpose |
|---|---|---|
| Name | `get_weather` | Lets the model call it by name |
| Description | "Get the weather forecast for a given city on a given day" | Helps the model decide when to use it |
| Parameter format | City (text), date (year-month-day) | Specifies what must be filled in when calling it |

The parameter format is commonly described in JSON (JavaScript Object Notation, a structured data format). Think of it as an application form with fixed fields.

**The second part is the program that actually runs**. A developer writes it in advance. It runs outside the model, sends requests to the weather API or reads and writes the calendar database, and then hands back the result.

"Function calling" means that after reading the manual, the model outputs a neatly formatted piece of text, such as "call get_weather, city=Shanghai, date=tomorrow." The orchestration program outside the model recognizes this text, runs the corresponding program on the model's behalf, and sends the result, "light rain, 18°C," back to the model as a new message. From the model's point of view, it is only ever writing and reading text. The "doing" step is carried out by an external program. How a model "speaks" an action is covered in detail in Section 6.3 of Chapter 6.

## 2.3.3 Common Kinds of "Hands"

There are many kinds of tools. By function, they fall roughly into the following categories:

1. **Information retrieval**: web search, reading web pages, querying databases, reading local files. These bring back information the model doesn't have.
2. **Computation and code**: calculators and code interpreters (environments that can run a piece of code). These handle exact calculation and data processing, such as producing summary statistics from a spreadsheet.
3. **Action and writing**: sending email, changing calendars, committing code, filling in forms on web pages. These tools make real changes to the outside world.
4. **Interface operation**: Some systems let the model "see" the screen through screenshots and then output mouse-click and keyboard-input commands, so it can operate software that has no API. At the time of writing, companies such as Anthropic and OpenAI have publicly released this kind of "computer use" capability, but it is still maturing and is slower and less reliable than calling an API directly.
5. **External services**: maps, payments, internal enterprise systems, and the like, connected through application programming interfaces (APIs, the agreed-upon ways software programs talk to each other).

These categories carry very different levels of risk. If a weather lookup goes wrong, the only consequence is an inaccurate answer. If the agent sends the wrong email or deletes the wrong file, it is often hard to undo. That is why Section 4.4 and Chapter 7, which cover permissions and sandboxing, focus heavily on the third category.

## 2.3.4 Three Simple Principles of Tool Design

When equipping an agent with tools, more is not always better. Judging from the development experience that various companies have shared publicly, a few principles hold up well and are unlikely to go out of date:

- **Write clear descriptions**: The model can rely only on the manual to decide which tool to use. If the descriptions are vague, for example if two tools are both called "query," the model can easily pick the wrong one. It's the same as handing off work to a new colleague.
- **Keep the number down**: Every manual takes up space in the model's context. With too many tools, costs go up and confusion becomes more likely. A common practice is to select a small set of tools relevant to the task at hand.
- **Keep the output concise**: Whatever a tool returns is sent back to the model. If an entire web page is stuffed back in as-is, the model may struggle to find what matters. A good tool filters first and returns only the key information.

In addition, when every system writes its own version of the same kind of tool, the cost of integration is high. This led the industry to develop unified protocols for connecting tools, such as the Model Context Protocol (MCP), introduced by Anthropic in late 2024. Its goal is to make tools plug-and-play, like USB devices. The details are left for Sections 4.1 and 7.2.

## 2.3.5 Summary: The Hands Are Outside the Brain

Back to the weather-and-calendar task from the opening: the model judges that it first needs to check the weather, so it writes a call request, which the weather tool executes. After seeing "light rain" come back, the model decides to change the schedule, and the calendar tool executes that. Throughout the process, the model does the judging, the tools do the executing, and the orchestration program passes messages between the two.

Once you understand this, agents seem much less mysterious: what an agent can do depends largely on which tools it has been connected to and how much permission it has been granted. On the other hand, once a tool has finished running, where should the result be stored, how long should it be kept, and will the model be able to recall it next time? That is the subject of the next section: "memory."
