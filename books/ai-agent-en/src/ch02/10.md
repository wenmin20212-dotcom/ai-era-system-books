# 2.2 Instructions: System Prompts, Role Definitions, and Task Descriptions

Suppose you open a coding agent and type a single sentence: "Change all the date formats in this project to 'year-month-day'." A few minutes later it has read the files, edited the code, and run the tests. You said only one sentence, yet it seems to know many things you never told it: read the code before making changes, don't delete files on a whim, and report back on what was changed.

Where do these unspoken rules come from? Before you said a word, someone had already written a long passage for it. The previous section covered the agent's "brain," the large language model. This section covers the "job manual" that brain reads before every task: the instructions.

## 2.2.1 Instructions Usually Come in Three Layers

The model itself doesn't remember who it is, nor does it know what it's supposed to do today. On each call, all it reads is the text passed in, called the context. Instructions are the part of that text devoted to "setting the rules and assigning the work." By source and stability, they fall roughly into three layers:

| Layer | Usually written by | Example content | How often it changes |
|---|---|---|---|
| System prompt | Product developer | You are a coding assistant; read files before modifying them; do not run dangerous commands | Rarely; included in every conversation |
| Role definition (persona / role) | Developer or user | Answer in the voice of a senior data analyst; respond only in Chinese | Configured per scenario |
| Task instruction | User | Change all date formats to "year-month-day" | Different every time |

Think of it as starting a new job. The system prompt is like the company's employee handbook, the role definition is like the job description, and the task instruction is like the specific thing your manager asked you to do this morning. A new employee gets the job done because all three work together.

In the APIs of mainstream large models, this layering takes a concrete technical form. At the time of writing, the chat APIs from OpenAI, Anthropic, Google, and others distinguish content from different sources. The common categories are system instructions, user messages, and model (assistant) replies, and tool results are marked separately as well, though the exact field names vary by vendor. During training, models learn that content in the system message should generally take priority over ordinary user messages. This is only a trained tendency. It is not an unbreakable hard rule, and we will return to it in Chapter 7 on safety.

## 2.2.2 What Goes into a System Prompt

An agent's system prompt is often much longer than a chatbot's. Public materials and several open-source projects show that the system prompts of coding agents often run to several thousand words. Their contents fall roughly into these categories:

- **Identity and goals**: who you are, whom you serve, and what counts as done.
- **Descriptions of available tools**: which tools exist, what each is for, and when to use them. The detailed tool formats are usually defined separately, as the next section explains.
- **Working methods**: for example, "make a plan before executing," "run the tests after changing code," "ask the user when unsure."
- **Boundaries and prohibitions**: don't access certain directories, don't delete data without confirmation, don't leak secret keys.
- **Output format**: what language to reply in, how long the reply should be, whether to list the changes made.
- **Environment information**: the current date, operating system, working directory, and so on. The model has no way of knowing these on its own, so they must be written in.

The last category is often overlooked, but it is telling. The model's knowledge stops at its training cutoff. It doesn't know what day "today" is, nor what's on your computer. Here the system prompt works like a sticky note on a desk: "Today is such-and-such a date, and you're working in this folder on this machine."

## 2.2.3 Why Words Alone Can Work

Traditional software sets rules in code, such as "if the filename ends in .exe, reject it," and the computer follows them to the letter. Many of an agent's rules, however, are written in natural language, such as "be cautious with operations that could cause damage." This works because the large language model has seen vast amounts of text during training and has gone through dedicated instruction-following training (instruction tuning). That training taught it to treat such sentences as behavioral constraints. The training process itself is covered in Volume 18.

This cuts both ways. The upside is flexibility: write "be cautious" once, and the model can generalize it to hundreds or thousands of concrete situations without each one being coded. The downside is imprecision. The model may misread the instruction, may "forget" an earlier rule in a very long context, or may be led astray by a malicious line on a web page. For this reason, mature agent systems never rely on prompts alone for the limits that really matter. Programs enforce those limits too. For example, a confirmation dialog must appear before a file is deleted, and the orchestration program guards that step instead of relying on the model's self-discipline. A handy way to remember it: **prompts guide; programs provide the safety net.**

## 2.2.4 Task Instructions: The Layer Users Control

The system prompt is usually written by the developer, and ordinary users can neither see nor change it. What users actually control is the task instruction. Even for the same job of tidying up a spreadsheet, the following two phrasings produce very different results:

- Vague version: "Tidy up this spreadsheet for me."
- Clear version: "Summarize the sales sheet by month, one row per region; keep amounts to two decimal places; don't modify the original file, save a new copy instead; list any rows with missing data separately for me to review."

The clear version spells out four things: the **goal** (summarize by month), the **format** (two decimal places), the **constraint** (don't modify the original), and the **deliverable** (list the missing data). Agents need clarity even more than chatbots do, because agents actually take action. When a chatbot misunderstands, the worst outcome is an off-topic answer. When an agent misunderstands, it may already have overwritten the original file.

Many agent products also let users write a long-lived "project instructions" file. At the time of writing, some coding agents read an instructions file with an agreed-upon name from the project folder, such as CLAUDE.md, used by Anthropic's Claude Code, or AGENTS.md, supported by multiple tools. The agent automatically merges the file's contents into its instructions, for example "this project uses four-space indentation" or "run a certain test command before committing." This amounts to the user writing a supplementary employee handbook for their own project, something that sits between the system prompt and a one-off task.

## 2.2.5 Summary: Instructions Are the Agent's "Factory Settings" Plus "Today's Task"

To pull this section together: the model provides capability, and the instructions decide where that capability is applied and how far. The system prompt sets identity and bottom lines, the role definition sets style and perspective, and the task instruction sets what needs doing this time. Only when the three are combined do they form the complete "job manual" the model reads at every step it takes.

Still, no matter how well the manual is written, an employee can't get anything done without tools. What carries out actions like "run the tests," "read the file," or "search the web"? The next section looks at the agent's hands: tools, functions, and external services.
