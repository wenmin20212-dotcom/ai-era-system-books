# 2.4 Memory: Short-Term Context, Long-Term Memory, and Knowledge Bases

Suppose that in the morning you ask an agent to tidy up a sales spreadsheet. It reads three files, notices that the dates in the second file use inconsistent formats, and converts them first. In the afternoon you say, "Pick up where we left off this morning and draw the summary chart too." Whether it can carry on depends on what it "remembers." If it has completely forgotten the morning's work, you have to explain everything again from the start. If it still remembers where the files are and that the dates have already been converted, a single sentence is enough.

People often say that agents "have memory," but an agent's memory is very different from a human brain's. It is not a single unified organ. It is several storage methods pieced together. This section takes up three questions: where information is kept, how long it lasts, and how it is retrieved. Using them, it divides an agent's memory into three layers: short-term context, long-term memory, and knowledge bases.

## 2.4.1 First, Understand This: The Model Itself Does Not Remember

The large language model that serves as the "brain" usually has fixed parameters during use once training is complete (for the model's internal workings, see Volume 18). When you finish a round of conversation with it, its parameters do not change as a result. On the next call, it does not "know" what happened the previous time.

So why can a conversation stay coherent? Each time the model is called, an external program hands it the earlier conversation history, the results returned by tools, and relevant materials all over again. The model is "rereading," not "recalling." Think of the model as a consultant who loses his memory every time he walks through the door. The stack of papers on the desk determines what he knows at that moment. What we call an agent's memory is really the management of that stack: which papers go on the desk, which get filed in the cabinet, and where to look when they are needed again.

## 2.4.2 Short-Term Context: The Materials on the Desk

Everything the model can read in at once is called its **context**, and the maximum it can hold is called the **context window**. This limit is measured in **tokens**, the basic units in which a model processes text. One Chinese character corresponds roughly to one or two tokens. According to public information at the time of writing, mainstream models commonly have windows ranging from tens of thousands to around a million tokens, and the figure varies widely between products.

Within a single task, short-term context usually includes the following:

- The system prompt and task instructions (covered in the previous section);
- The back-and-forth between you and the agent;
- The request and returned result of each tool call, such as file contents that were read, web page text, and command output;
- The plans and intermediate conclusions the agent writes down for itself.

This layer can be seen most clearly but also fills up most easily. When an agent reads a large file or fetches a few web pages, a big chunk of the window is quickly used up. Once the window is full, the orchestration program has to delete older content or compress it into summaries. When the content is very long, the model may also overlook details buried in the middle. Researchers call this phenomenon "lost in the middle." So no matter how big the desk is, you cannot pile everything onto it.

## 2.4.3 Long-Term Memory: Notes Kept Across Tasks

**Long-term memory** refers to information stored outside the model that persists across multiple conversations or multiple tasks. It is not in the window. It lives in files, databases, or dedicated storage services, and it is pulled into the context only when needed.

There are several common approaches:

- **Note files**: Some coding agents read an agreed-upon instruction file in the project directory. The file contains project conventions and frequently used commands, and the agent loads it automatically at every startup. At the time of writing, coding tools from several companies use this approach, with varying file names and formats.
- **User preference records**: Some conversational assistants offer a "memory" feature that records how you like to be addressed, your usual language, and your writing preferences, and lets you view and delete them.
- **Task logs and summaries**: Partway through a long task, the system writes the completed steps into a summary and saves it, so that later steps or the next session can read it back.

Long-term memory solves the problem of continuing in the afternoon what was started in the morning, but it also raises new problems. What if something is remembered wrongly? What if it goes out of date? Should privacy-sensitive content be remembered at all? A well-designed system therefore lets people see these memories, correct them, and delete them, rather than letting them quietly accumulate in the background.

## 2.4.4 Knowledge Bases: The Filing Cabinet You Can Consult Anytime

A **knowledge base** is another kind of external storage. What it holds is usually not "what this agent has experienced" but "what this work requires looking up": company policies, product manuals, past years' reports, code repositories.

Knowledge bases are often too large to fit into the context in full, so the relevant passages must be picked out through **retrieval**. A common technique is called **Retrieval-Augmented Generation (RAG)**. First, the materials are split into small chunks, and the gist of each chunk is recorded as a numerical representation called a "vector" (an embedding). When a question is asked, the chunks closest in meaning are found and placed into the context, and then the model answers. Besides this kind of semantic retrieval, the system can also search directly by keyword, query a database, or have the agent search through folders with commands, as a person would. These retrieval mechanisms are covered in detail in Chapters 4 and 6.

## 2.4.5 The Three Layers Compared: Desk, Notebook, and Filing Cabinet

| Layer | Analogy | Where It Is Stored | How Long It Lasts | Main Challenges |
|---|---|---|---|---|
| Short-term context | Materials on the desk | Content the model reads in this time | One call or one session | Limited capacity, easily pushed out |
| Long-term memory | Pocket notebook | Files, databases, memory services | Across sessions and tasks | What to record, when to update, privacy |
| Knowledge base | Filing cabinet in the archive room | Document stores, vector databases, business databases | Long-term, maintained by people | Retrieval accuracy, freshness of materials |

Back to the spreadsheet task from the beginning. The file contents read in the morning sit in short-term context. If the conclusion that the dates were converted was written into the task log, it has become long-term memory. The report format the company requires comes from the knowledge base. Each layer handles its own part, and the orchestration program moves the right content onto the desk at the right time.

How much an agent remembers, and how accurately, is therefore not determined entirely by the model. It depends largely on this external system for storing and retrieving information. Where that system runs and what drives it are the subject of the next section: the runtime environment and the orchestration program.
