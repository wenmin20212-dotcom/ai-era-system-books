# 4.5 Chapter Skeleton Summary and Hands-On Exploration Tasks

In the previous four sections, we shifted our gaze from the "inside" of an agent's body to the "outside." Take the same task we handed it before: look up a few sources, organize them into a table, and tweak a statistics script along the way. To get this done, the agent has to call search and spreadsheet tools, dig through your folders and knowledge base, perhaps hand part of the work off to another agent, and finally pause at a critical step to wait for your go-ahead. The agent cannot complete the task on its own; it deals with the outside world through four connecting lines. This section first gathers those four lines into a single picture, then invites you to go find them in a real system you have on hand.

## 4.5.1 One Picture of the Four Connections

Think of the agent as a person standing at the center of an intersection, with a road leading off in each of four directions:

| What it connects to | What the connection relies on | What gets exchanged | Where things most often go wrong |
|---|---|---|---|
| Tools | Function Calling, tool descriptions, tool protocols | Call requests and execution results | Unclear descriptions, wrong parameters, unvalidated results |
| Knowledge | Retrieval-Augmented Generation (RAG), file reading, database queries | Text snippets, table records | Inaccurate retrieval, outdated material, treating irrelevant content as evidence |
| Other agents | Delegation, message passing, shared state | Subtasks and sub-results | Overlapping responsibilities, information lost in handoffs, agents waiting on each other |
| People | Interfaces, permission settings, human confirmation | Goals, authorization, feedback | Too many confirmations numb people; too few and things spin out of control |

All four lines have one thing in common: **each one is an "agreed-upon interface" plus a "round trip that can be inspected."** Tools have parameter formats, knowledge has retrieval entry points, agents exchange task instructions and delivery formats, and people and agents share confirmation buttons and permission boundaries. The clearer the interface, the more reliable the system. The more complete the record left by each round trip, the easier it is to trace problems when something goes wrong.

## 4.5.2 Review of the Chapter's Key Points

- **Tool connections**: The model doesn't actually "press the button." It simply writes out a call request in an agreed format; an outside program performs the actual execution and sends the result back to the model. The point of a tool protocol is to standardize this agreement. As of this writing, the Model Context Protocol (MCP) proposed by Anthropic is one of the more frequently discussed open protocols, and other companies and open-source communities have their own interface specifications. The specific standards are still evolving, but the structure of "describe—request—execute—return" is fairly stable.
- **Knowledge connections**: What a model remembers has a cutoff date, and it knows nothing about your private materials. Retrieval means first finding the relevant snippets, then placing them in the context for the model to consult. Retrieval quality often determines answer quality, and it matters more directly than how powerful the model itself is.
- **Connections between agents**: Multi-agent systems trade coordination cost for focus through division of labor. Common forms include "supervisor—subordinate" delegation as well as multiple roles passing work along a pipeline. More participating agents don't necessarily make a better system. Whether the task can be cleanly divided is the real key to whether the work can be split up.
- **Connections between people and agents**: Permissions determine what an agent can touch; confirmation points determine where it must stop. Good design lets it complete low-risk actions automatically while leaving irreversible actions—deleting, paying, sending things externally—for a human to decide.
- **The one sentence running through this chapter**: Half of an agent's capability comes from the model, and half comes from how well it connects to the outside world.

Flowing along these four connecting lines are tasks, messages, context, permissions, and costs. In the next chapter, we'll follow these "flows" further.

## 4.5.3 Hands-On Exploration Tasks

The tasks below require no programming; the AI assistant or coding agent you already use will do. Before you begin, make sure nothing involves work secrets or personal privacy.

1. **Count its tools**: Open the agent product you use most often, and in its settings, plugins, or "connectors" page, list the tools it can call. Label each one "read-only" or "makes changes." See which of the tools that make changes require your confirmation before they're called.
2. **Look at the traces of a retrieval**: Upload a document you know well and ask a question whose answer can only be found in that document. Observe whether it marks where it's citing from. Then ask a question the document doesn't answer, and see whether it admits "the document doesn't contain this" or makes up an answer.
3. **Track a delegation**: If your system supports subtasks or multiple roles (as of this writing, some coding agents dispatch "subagents" to search through code), give it a task that can be broken apart. Record how many subtasks it dispatched, what each one brought back, and whether anything was missed when the results were combined.
4. **Test the confirmation boundary**: In a safe test folder, ask the agent to "organize and delete duplicate files." Record at which steps it stopped to ask for your confirmation and which steps it just carried out. Then compare this against its permission settings and consider whether the design makes sense.
5. **Draw your own connection map**: With the real task you gave it at the center, draw the connections in all four directions on paper. Mark what travels along each line and the risk points that concern you, and save it to add the "flow" arrows in Chapter 5.

## 4.5.4 Questions You Can Ask AI Directly

- "Using an example of looking up information and making a table, explain step by step what the model outputs during a function call, what the program executes, and how the result returns to the model."
- "What kinds of tasks suit a single agent, and what kinds suit multiple agents dividing the work? Give two examples of each, and explain what extra costs multiple agents introduce."
- "If I want to bring an agent that can read and write a shared folder into my team, which operations should require human confirmation? List them from highest to lowest risk, with reasons."

Once you get the answers, check them against this chapter's four connecting lines: Which line is it talking about? What's the interface? Where is the round-trip record? Reading AI answers this way is also practice in the systems-level X-ray vision this book keeps emphasizing.
