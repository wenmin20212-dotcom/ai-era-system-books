# 4.2 Agents and Knowledge: Retrieval, Files, and Databases

Suppose you hand an agent your company's fifty-page expense reimbursement policy along with a spreadsheet of the past year's expense claims, and ask it: "How many times did hotel costs on business trips exceed the limit? Which rule did each one violate?" It won't answer from memory. In the interface you can often watch it first "read the file," then "search the document," then "query the spreadsheet," and finally give an answer that quotes the policy text. Behind these steps lies a basic fact: your reimbursement policy is not in the large model's "head." To answer the question, the agent must first bring the relevant knowledge in from outside. This section is about that connection between agents and knowledge.

## 4.2.1 What the Model "Knows" and What the Task "Needs" Are Two Different Things

A large language model's knowledge comes from its training data. You can think of it as a person who has read a vast amount of public text and is speaking from memory. That memory has three built-in limitations:

- **It has a cutoff date**: the model does not know about anything that happened after training ended;
- **It has never seen private material**: your company's policies and the spreadsheets on your computer never made it into the training data;
- **Its memory is imprecise**: the model may mix up details and still state them with confidence. This is what is commonly called "hallucination."

So when an agent handles a specific task, the reliable approach is an "open-book exam": whatever material it needs, it looks up on the spot, places what it finds into the context, and only then answers. This approach has a specific name: **Retrieval-Augmented Generation** (RAG), meaning retrieve first, then generate. Volume 18, *Large Language Models*, discusses in detail why models hallucinate; this section is concerned only with how the "open book" is put into practice.

## 4.2.2 Three Sources of Knowledge: Files, Knowledge Bases, and Databases

The external knowledge an agent can access falls roughly into three categories by form. Each is accessed differently and suits different kinds of questions.

| Knowledge source | Typical examples | How the agent obtains it | Questions it answers well |
|---|---|---|---|
| Files | PDFs, Word documents, code files, logs | Reads the full text or reads by line or page; searches by keyword | "What does clause three of this contract say?" |
| Knowledge bases | Corporate document collections, product manuals, help centers | Semantic retrieval, finding the several passages closest in meaning | "What are the rules on business-trip accommodation?" |
| Databases | Sales records, inventory tables, expense ledgers | Generates query statements; the database performs exact calculations | "How many over-limit expense claims were there last quarter?" |

Back to the reimbursement example: the policy text belongs in a knowledge base and is pulled in through retrieval, while the expense records are a structured table and should be handed to a database or spreadsheet tool for counting. A well-designed agent handles these two kinds of questions separately rather than having the model "count" a thousand rows on its own. Models are good at understanding and organizing language; precise counting and aggregation should be left to programs built for the job.

## 4.2.3 Semantic Retrieval: Finding the Right Passage Among Thousands of Pages

When there are only a few files, the agent can read them straight into its context. Once there are hundreds or thousands of documents, the context window can no longer hold them, and retrieval becomes necessary. The common approach has two stages.

**Preparation stage (building the store)**:

1. **Chunking**: split long documents into paragraph-sized pieces;
2. **Vectorization**: use a dedicated embedding model to convert each piece into a string of numbers called a vector. Text with similar meaning produces vectors that sit close together in mathematical space;
3. **Indexing**: store these vectors in a vector database, recording which file and which page each piece came from.

**Usage stage (lookup)**: the agent converts the question into a vector as well, finds the closest pieces in the store (usually anywhere from a few to a dozen or so), and hands them to the model together with the question.

A library makes a useful analogy. Traditional keyword search is like consulting a title index: you only find a book if its title contains the word you looked up. Semantic retrieval is more like asking a librarian who knows the collection well. Ask about "the cap for hotel stays on business trips," and they can still find the chapter titled "Travel Expense Standards." Real systems often combine the two, an approach called hybrid search: keyword search is precise for ID numbers, names, and specialized terms, while semantic search is thorough for questions phrased in different words.

## 4.2.4 More Retrieval Steps Mean More Places to Go Wrong

Retrieval brings knowledge in, but it also introduces new points of failure. When using an agent, readers can watch for several common situations:

- **Not found**: the truly relevant passage ranks too low and is not selected, so the model must answer from incomplete material;
- **Cut off**: a rule is split across two chunks and only the first half is retrieved, while the exception clause happens to fall in the discarded second half;
- **Out of date**: the knowledge base holds both the old and new versions of a policy, and retrieval returns the old one;
- **Database query error**: the model writes the query conditions wrong, say, a date range that is one month short, and the spreadsheet tool still returns a number that looks perfectly normal.

For this reason, a reliable agent **cites its sources**, noting which file and which clause an answer comes from so that a person can check it. For database queries, good practice is to keep the query statement and, when necessary, ask a person to confirm it. Permissions also matter: once a knowledge base is connected, whatever the agent can retrieve is what it can "see," and sensitive tables such as employee personal information should not be open to it by default. Chapter 5, "Permission Flows and Data Flows," expands on this issue.

## 4.2.5 Summary: Knowledge Is "Looked Up," Not "Remembered"

The relationship between agents and knowledge can be summed up in one sentence: **the model handles understanding and expression, retrieval supplies the evidence, and the database does the exact calculation.** Only by combining files, knowledge bases, and databases can an agent answer questions that its training data does not cover. Every step of retrieval can go wrong, so citing sources and keeping query records deserve more attention than the answer itself.

Tools let an agent take action; knowledge connections let its answers be traced back to evidence. The next section turns to another kind of connection: when a task is too large for one agent to handle alone, how multiple agents divide the work and delegate to one another.
