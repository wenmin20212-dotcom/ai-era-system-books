# 4.4 Agents and People: Interfaces, Permissions, and Human Confirmation

Suppose you ask a coding agent to fix an error in your project. It reads a few files and proposes a change. Then it stops and shows a prompt on screen: "About to run the command `rm -rf build/`. Allow?" Below are three buttons: "Allow once," "Always allow," and "Deny." Many people find this screen a little redundant the first time they see it. If I've already handed the job over, why is it asking me?

That pause is what this section is about. The agent connects to tools, to knowledge, and to other agents, and all of these connections eventually lead back to a human. The human starts the task and also bears its risks. Three things hold the connection between human and agent together. The **interface** determines how the two communicate. **Permissions** determine how far the agent can go. **Human confirmation** determines which critical moments require a human decision.

## 4.4.1 Interfaces: The Layer Humans Can See

At the time of writing, the interfaces through which people work with agents fall roughly into the following categories:

| Interface Type | Typical Scenario | What the Human Can See |
|---|---|---|
| Chat window | AI assistants on the web or a phone | The reply text; some products also show steps such as "Searching" or "Reading file" |
| Command line or editor plugin | Coding agents | Which files it read, which lines it changed, and which commands it ran |
| Browser or desktop control | "Computer use" agents | Screenshots and where the mouse clicked |
| Background automation | Scheduled report compilation, ticket handling | Run logs, result notifications, and error alerts |

These interfaces differ widely in how transparent they are. Chat windows are the friendliest, but they often show only the conclusion and not the process. Background workflows are the most efficient, but they leave the human farthest from the scene. A well-designed interface lets a person see three things clearly whenever they need to: **what the agent intends to do, what it is doing now, and what it has done**. Coding agents commonly show code changes in a "diff view," which marks deleted and added lines in red and green. This puts all three things in front of the human. People can supervise only what they can see.

## 4.4.2 Permissions: How Big a Key to Give the Agent

Permissions answer a simple question: what can the agent see, and what can it touch? A hotel key card is a useful analogy. It opens only your own room, and it works only during your stay. The front desk never hands a guest the master key. Agent permissions follow the same idea, which computer security calls the **Principle of Least Privilege**: grant only the permissions the task requires, and nothing more.

In practice, permissions are usually divided along several dimensions:

- **Scope**: The agent can read and write only a specific project folder, not the whole disk. It can visit only designated websites and cannot connect to the internet freely.
- **Action type**: Reading and writing are separate. "View email" is separate from "send email," and "query the database" is separate from "delete records."
- **Duration**: Permissions apply only to the current task and are revoked automatically when it ends.
- **Identity**: The agent acts through its own restricted account rather than borrowing an administrator's identity.

Why not simply open everything up? Because the agent's "brain" is a probabilistic model, and it makes mistakes. It may misread an instruction, or it may be manipulated by malicious text hidden in a webpage (Chapter 7 discusses this kind of "prompt injection" in detail). Permissions set an **upper limit on the damage when something goes wrong**. Reading the wrong file costs very little. An agent with the power to delete an entire database can cause irreversible harm with a single mistake.

## 4.4.3 Human Confirmation: A Gate Where Actions Can't Be Undone

Permissions alone are not enough. Some actions fall within the agent's permissions but have a large impact and cannot be undone. These call for **human confirmation**, which the industry often calls "Human-in-the-Loop" (HITL). Three questions help decide whether an action needs confirmation:

1. **Is it reversible?** Deleting files, transferring money, and sending emails are hard to undo once done.
2. **Is its impact broad?** Editing a draft and changing the configuration of a live system carry very different weight.
3. **Does it have an external effect?** A trial run on your own computer is harmless. Once the agent sends messages, submits forms, or makes payments on your behalf, your name and your responsibility are on the line.

If the answer to any of these questions is "yes," it is usually worth pausing to ask a human. The confirmation prompt for the delete command at the start of this section was designed this way. At the time of writing, many coding agent tools offer several modes, such as "ask at every step," "ask only before running commands or editing files," and "run automatically inside a sandbox." Users choose a mode according to the task's risk.

The timing of confirmation also matters. Ask too rarely, and risk gets out of control. Ask too often, and people fall into "confirmation fatigue," clicking "Allow" without reading, and the gate stops doing its job. A better approach is to **concentrate confirmations at a few key points**: have the human approve the overall plan first, intercept only high-risk actions during execution, and have the human review the result at the end.

## 4.4.4 The Division of Labor Between Humans and Agents at a Glance

Taken together, interfaces, permissions, and confirmation form a layered relationship between human and agent:

- **Before**: The human sets the goal and defines the permissions, much like signing a contract and issuing a key card.
- **During**: The agent acts autonomously within its permissions. The interface shows progress in real time, and the agent pauses for approval before high-risk actions.
- **After**: The human reviews the results and the action log, then decides whether to accept, modify, or roll back.

One principle in this structure never changes: **capability can be delegated, but responsibility cannot**. An email the agent writes for you still represents you once it is sent. If code the agent changed for you causes problems after release, the team is still responsible. Because responsibility stays with the human, the human must keep the ability to see clearly, to stop the agent, and to say no. Interfaces, permissions, and confirmation are designed to preserve that ability.

So that seemingly redundant confirmation prompt is really the smallest possible collaboration agreement between human and agent. The agent's job is to get things done quickly. The human's job is to hold the direction and the bottom line at the critical points. With this, we have covered all four kinds of connections: agents with tools, with knowledge, with other agents, and with humans.
