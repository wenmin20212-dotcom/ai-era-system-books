# 4.3 Agents and Agents: Division of Labor, Delegation, and Multi-Agent Systems

Suppose you give a coding agent a task: "Replace every outdated date function in the project, then add tests." In some coding tools, you might see a line like this in the execution log: "Starting a subtask to search the codebase for all relevant calls…" A little later, the subtask hands back a list, and the main agent works through the list making changes one by one. At that point, more than one agent is working behind the screen: one agent has handed part of the job to another. This section is about that relationship: how agents divide work, delegate, and collaborate with one another.

## 4.3.1 Why Have Multiple Agents Work Together

A single agent can do a job from start to finish, so why split it among several? There are three common reasons.

First, **context is limited**. As Chapter 2 explained, there is a ceiling on how much a model can "see" at once. If a single conversation involves searching hundreds of files, reading web pages, writing code, and running tests, the flood of intermediate information crowds the available space, and earlier key points may get pushed out. Handing the "search" to a subagent that returns only its conclusions keeps the main agent's context clean.

Second, **specialization**. Give different agents different system prompts and tools: one only retrieves information, one can only write code, one is dedicated to review. Each role's instructions are more focused and its toolset smaller, so there are fewer chances to go wrong.

Third, **parallel speedup**. Subtasks that don't depend on one another can run at the same time, such as investigating three competitors' websites simultaneously and then compiling the findings.

The logic is the same as in a human team: a project manager doesn't need to look up every document personally, but must assign tasks clearly, collect the results, and take responsibility for the whole.

## 4.3.2 Several Common Collaboration Structures

The concept of a Multi-Agent System (MAS) has existed in artificial intelligence research for decades, and large models have given it new ways to be implemented. Classified by "who directs whom," common structures fall into the categories in the table below:

| Structure | Analogy | How It Works | Suitable Scenarios |
|---|---|---|---|
| Supervisor–subordinate (hierarchical) | A project manager leading team members | A coordinator breaks down tasks, delegates, and compiles results | Most complex tasks; the most common |
| Pipeline (sequential) | A factory assembly line | A's output goes to B, B's output goes to C | Fixed steps, such as "retrieve → draft → proofread" |
| Handoff | A customer service rep transferring you to a specialist | The current agent decides, then transfers the whole conversation to another | Routing by problem type |
| Debate/review | Author and reviewer | One side proposes a solution, the other finds faults, with repeated revisions | Writing and code review that need quality control |

At the time of writing, many publicly available agent frameworks and coding tools offer mechanisms such as "subagents" or "handoffs." The names vary from vendor to vendor, but the structures largely fall into the categories above. Specific product features change quickly, so readers should consult each vendor's current documentation.

## 4.3.3 The Key to Delegation: A Clearly Written "Task Brief"

Delegation sounds simple, yet the handoff is where things most often go wrong. A subagent usually doesn't share the main agent's full memory; it can see only the instructions passed to it at the moment of delegation. If the main agent writes only "go check the date functions," the subagent won't know which directory to search, whether to make changes once it finds them, or what format to report back in.

A good delegation's task brief generally includes:

- **Goal**: what to accomplish, and what counts as done;
- **Background**: information the subagent needs but cannot see on its own;
- **Boundaries**: which tools it may use and what it must not do (for example, "read only, do not modify files");
- **Deliverable format**: whether to return a list, a summary, or structured data.

When a subagent finishes, it usually hands back a compressed result rather than the whole process. This is both a strength of multi-agent systems and a risk: the main agent sees only the conclusions, not the reasoning, so if the subagent missed something or misjudged, the error may be carried straight into the final result. The coordinator therefore needs to check what comes back, spot-checking or assigning another agent to verify when necessary. This is the same principle as the "reflection and error correction" discussed in Chapter 3, simply extended from inside a single agent to across a team.

## 4.3.4 More Agents Aren't Always Better

Seeing the benefits of division of labor, people readily assume that more agents means more intelligence. In reality, multi-agent systems carry real costs:

1. **Costs multiply**. Every agent calls the model and consumes tokens; with several agents running in parallel, the cost may be several times that of a single one (the "cost flow" discussion in Chapter 5 works through these numbers).
2. **Communication loss**. Each time information is passed along, it may be compressed or misunderstood, just like in a game of telephone.
3. **Coordination difficulties**. Several agents editing the same file at once may overwrite one another; inconsistently stated goals can send them off in different directions.
4. **Harder debugging**. When something goes wrong, you may have to comb through several execution logs to pinpoint which link failed.

The safer engineering approach, therefore, is to first get the task working with a single agent, and to split work off only when the context truly isn't enough, the subtasks can truly be done independently, or an independent review is truly needed. Parallelizable "read-only" tasks (searching, research) are the safest to split off; tasks that require frequent edits to the same material are often more reliably handled by a single agent.

## 4.3.5 Summary

Moving from one agent to many essentially repeats the "plan–execute–check" loop at the team level: the coordinator handles breakdown and compilation, subagents handle their specialized segments, and quality at the handoffs depends on clear task briefs and verification of results. No matter how many agents are on the team, someone still needs to be accountable for the final result.
