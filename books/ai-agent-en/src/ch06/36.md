# 6.5 Failure Modes and Recovery: Getting Stuck, Drifting Off Course, and Making Wrong Moves

You ask a coding agent to fix a failing test. Ten minutes later you come back to find it has run the same test command more than twenty times. The error is identical every time, and every time it says "Let me try again." Another time, you ask it to tidy up a sales spreadsheet. Along the way it "improves" the headers and renames every column that your downstream formulas depend on. On yet another occasion, while cleaning up temporary files, it comes close to deleting your entire project directory. Only a confirmation prompt stops it.

These three scenarios correspond to the three most common kinds of agent failure: **getting stuck**, **drifting off course**, and **harmful actions**. The previous section covered how memory is summarized and compressed. This section turns to the most practical runtime question: how agents go wrong, and what the system relies on to pull them back.

## 6.5.1 What the Three Failures Look Like and Why They Happen

Laying out common failures by symptom, typical cause, and consequence makes the picture clearer:

| Failure type | Typical symptoms | Common causes | Nature of consequences |
|---|---|---|---|
| Getting stuck (stuck) | Repeats the same action, apologizes and retries over and over, never finishes | The error message isn't actually understood; there is no trigger to "try a different approach"; the tool keeps returning the same result | Wastes time and tokens, but usually causes no direct damage |
| Drifting off course (drift) | Wanders away from the original goal partway through, or expands the task scope on its own | The context grows too long, so the original goal gets pushed out or diluted; misleading information appears midway; the task boundaries are poorly understood | The result "looks like hard work" but isn't what you wanted |
| Harmful action (harmful action) | Mistakes in irreversible actions such as deleting, overwriting, sending, or paying | Excessive permissions; misjudging the state of the environment; being manipulated by malicious instructions in web pages or files | Can cause real losses; the most important to guard against |

Two other phenomena often show up alongside these. The first is **hallucinated success**: the agent reports "Done," but the tests were never run or the file was never saved. The second is **malformed tool calls**: missing parameters or wrong types cause the call to fail. Section 6.3 explained how a model "speaks" its actions, and this step goes wrong more often than you might expect.

These failures share a common root. At every step, a large language model makes a probabilistic judgment based on its current context (Volume 18 covers how models work internally). It has no built-in awareness that "I'm going in circles" or "this step can't be undone." The surrounding orchestration program has to provide that awareness.

## 6.5.2 Detecting Failure: Fitting the Loop with "Sensors"

Recovery starts with noticing that something is wrong. Common detection techniques in engineering practice include:

- **Step and time limits**: Set a maximum number of iterations, a maximum running time, and a token budget for the reason–act loop. When a limit is exceeded, force a stop or ask a human. This is the simplest and most reliable way to prevent getting stuck.
- **Repetition detection**: The orchestration program compares the last few tool calls and their results. If "the same command with the same error" keeps appearing, it flags a likely stuck state.
- **Objective verification**: Don't take the agent's word that it's "done." Check with external signals instead, such as whether the tests actually pass, whether the file actually exists, and whether the spreadsheet's row count adds up. This is why coding agents rely so heavily on test and compiler results.
- **Goal review**: Periodically put the original task back into the context so the model can check whether "what I'm doing now is still within the scope of the task." This counters drift.

You can think of these as an engineering version of the cybernetic "negative feedback" discussed in Chapter 8. The system continuously measures the gap between output and goal, and triggers a correction when that gap crosses a threshold.

## 6.5.3 Recovery Strategies: A Ladder from Retrying to Asking for Help

Once a problem has been detected, recovery measures fall roughly into several levels, from light to heavy:

1. **Informed retry**: Feed the full error message back to the model with an explicit prompt such as "The last approach failed; please try a different one," instead of simply rerunning the same thing.
2. **Roll back to a checkpoint**: Save state before key steps, for example with a commit in the code repository or a backup copy of a file. After an error, restore the last clean state and continue from there. At the time of writing, many coding-agent tools offer something like an "undo this round of changes" feature.
3. **Replan**: Abandon the current sub-plan and go back to the task-decomposition level (Section 6.2) to take a different path.
4. **Narrow the scope**: Break the large task into smaller pieces. Finish the parts that can be done with confidence, deliver them, then deal with the rest.
5. **Hand back to a human**: Explain where it got stuck, what it has tried, and what information or authorization it needs, and let a person decide the next step.

A good agent system treats level 5 as a normal exit, not a failure. An agent that can say "I can't do this, because…" is far more useful than one that forges ahead and makes blind changes.

## 6.5.4 Preventing Harmful Actions: Making Mistakes "Undoable" or "Unable to Get Through"

The cost of getting stuck or drifting is mostly time and money. Harmful actions, on the other hand, may be impossible to reverse. That is why prevention comes first, and after-the-fact repair serves only as a safety net. Common practices include:

- **Least privilege**: Grant only the permissions the task requires. An agent that tidies spreadsheets doesn't need the ability to send email.
- **Sandbox isolation**: Run code and commands in an isolated environment. Even if something goes wrong, the impact on real systems stays limited (detailed in Section 7.3).
- **Human confirmation for high-risk actions**: Pause before deleting, overwriting, sending externally, or making payments, and wait for a person's approval. The confirmation prompt in the opening example is exactly this mechanism.
- **Dry run**: First show "what is about to happen," such as a list of files that will be deleted, and only execute after confirmation.
- **Distinguish reversible from irreversible**: The orchestration program assigns risk levels to tools. Reversible operations run freely, while irreversible ones pass through multiple checks.

The thinking here resembles workplace safety in a factory. Nobody expects workers never to make mistakes. Instead, the goal is that a mistake can either be undone or be stopped before it happens.

## 6.5.5 Summary

Agent errors can't be eliminated entirely, so reliability comes mainly from the surrounding design. Limits and detection catch an agent that is stuck. Goal review and objective verification prevent drift. Permissions, sandboxes, and confirmations block harmful actions. A recovery ladder, from light measures to heavy ones, brings the task back on track. For everyday use, keep one rule of thumb in mind: **watching how an agent fails and how it asks for help tells you more about whether it's dependable than watching it succeed once.** The next section reviews the core mechanisms of this chapter and offers hands-on tasks for observing these failure and recovery processes.
