# 6.4 Memory Management: Summarization, Compression, and Retrieval

You ask a coding agent to fix a bug. It reads a dozen or so files, runs several rounds of tests, and scrolls through screen after screen of error messages. Partway through, you may see a line on the screen saying something like "Compacting context." After that it keeps working as before. Occasionally, though, it forgets a requirement you specifically gave it half an hour earlier.

Behind that message is the agent's memory management. Section 5.3 of Chapter 5 described how context flows in, stays, and gets pushed out. This section goes one level deeper. Once running out of room becomes the normal state, what mechanisms does an agent use to decide what to keep, what to discard, and how to get information back when it needs it?

## 6.4.1 The Root of the Problem: The Workbench Has a Fixed Size

Each time a large language model generates a response, it can only "see" what is in a single input. That space is called the context window. Its length is measured in tokens, the basic units of text a model processes. According to public sources, at the time of writing the windows of mainstream models commonly range from tens of thousands to over a million tokens. The model itself remembers nothing between calls. For why it works this way, see Volume 18.

The window is usually large enough for chat, but agents are different. At every step, an agent appends more to its context: the model's reasoning, the tool calls it issues, and the results those tools return. A single web page fetch, a log file, or a large source file can take up thousands or even tens of thousands of tokens. After a few dozen turns of the loop, the window will fill up sooner or later.

Even before the window is full, there is trouble. Researchers and engineers have widely observed that the longer the context and the more irrelevant material it contains, the more likely the model is to overlook key information buried in the middle. Responses also get slower and more expensive. Memory management therefore has two jobs. The first is to keep the window from overflowing. The second is to make sure that what the window holds is as useful as possible.

Think of the context window as a workbench of fixed size. Only a limited number of documents can be spread out on it. The rest must either be condensed into a summary pinned in one corner or filed in a cabinet nearby and pulled out when needed. The three mechanisms below correspond to these three options: delete, summarize, and archive for later retrieval.

## 6.4.2 Trimming: The Simplest and Crudest Approach

The most direct approach is to throw things away. Common variants include:

- **Sliding window**: Keep only the most recent several turns and delete everything earlier.
- **Truncating tool output**: When a tool returns too much, keep only the beginning and the end, with a note in between such as "N lines omitted."
- **Clearing old results**: Once a file has been read and dealt with, remove the raw text of that read from the context. Leave only a record noting that the file was read.

Trimming is cheap and predictable, and it requires no extra model calls. The cost is that information is lost for good. Suppose the instruction "don't modify the test files" from your first turn happens to fall in the deleted portion. Then the agent really will forget it. Well-designed systems therefore place long-lived constraints like this in the system prompt, or they pin the original task description so that it never slides out.

## 6.4.3 Summarization and Compression: Letting the Model Write Itself a Memo

A smarter approach is to have the model summarize older content. That "Compacting context" message from the opening is usually doing exactly this. When the orchestration program notices that the window is nearly full, it hands the earlier history to the model. It asks the model to write a condensed version covering several points: what the goal is, which steps have been taken, what conclusions have been reached, what remains unfinished, and what requirements the user has stated. The summary then replaces the original history, and the loop carries on.

| Approach | What is kept | Cost | Typical risk |
|---|---|---|---|
| Trimming | Recent raw text | Almost none | Key early information lost wholesale |
| Summarization and compression | Condensed key points | One extra model call | Summary omits details or gets them wrong |
| External storage plus retrieval | All raw text, stored outside | Requires storage and retrieval systems | Fails to find content or retrieves irrelevant material |

Compression is inherently lossy. It is like turning a two-hour meeting into one page of minutes: whatever the note-taker considers unimportant disappears. For this reason, some engineering practices require summaries to follow fixed sections, such as "Current goal / Completed / To do / Key constraints / Known errors," to reduce omissions. Another approach has the agent actively maintain a notes file as it works, such as a to-do list or a progress log. This file is an externalized version of "working memory." After compression happens, the agent can reread its notes and pick up where it left off. At the time of writing, some coding agent products take exactly this kind of approach.

## 6.4.4 Retrieval: Putting a Filing Cabinet Next to the Workbench

The third mechanism does not rush to delete anything. Instead, it stores content outside the context and fetches it back when needed. This follows the same idea as the long-term memory discussed in Section 2.4 and the knowledge bases in Section 4.2. The only difference is that it now serves the agent's own experience.

There are two main ways to do this:

1. **On-demand reading**: Large files and long logs are not stuffed into the context in full. The model is simply told, "There is a file here, at such-and-such path." When it needs the file, it calls a read or search tool and fetches only the few dozen relevant lines. This is why coding agents often use text search tools to locate things in a codebase.
2. **Semantic retrieval**: Past conversations, user preferences, and task experience are split into small chunks. Each chunk is converted into a vector, called an embedding, which represents the meaning of the text as a series of numbers. The vectors are stored in a vector database. When a new task arrives, the system retrieves the few most relevant chunks by similarity of meaning and places them in the context. This kind of "retrieval augmentation" is commonly abbreviated as RAG (Retrieval-Augmented Generation).

Retrieval turns "remembering" into "being able to find." A person need not memorize an entire manual, only know which page to look things up on. Its weakness lies in that same act of finding. A poorly worded query, or relevant content scattered across different chunks, may mean the right material never comes back. Sometimes the system even retrieves old records that look relevant but are out of date.

## 6.4.5 Putting It Together: A Layered Memory System

Real agents rarely rely on a single mechanism. Most combine them in layers:

- **Innermost layer**: The system prompt and task description, always retained and never compressed.
- **Middle layer**: The raw text of the last few turns, kept in full detail so the model can continue reasoning.
- **Outer layer**: Earlier history, compressed into summaries or written to a notes file.
- **Outermost layer**: Files, databases, and long-term memory, retrieved on demand.

This structure closely resembles the storage hierarchy of a computer: registers, RAM, and disk. The closer a layer is to the processor, the faster, smaller, and more expensive it is. For an agent, "closer" means closer to the model's attention.

Back to the opening scenario: you can help, too. Write important constraints into a project instructions file, or restate them at key moments. Split long tasks into several stages and start a fresh session for each, accompanied by a handoff summary. When an agent seems to "forget" something, first ask whether that information has already been pushed off the workbench.

Memory management determines whether an agent can see a long task through to the end. Yet even with memory handled well, agents still get stuck, drift off course, or even take the wrong action. The next section looks at these failure modes and at how systems recover from them.
