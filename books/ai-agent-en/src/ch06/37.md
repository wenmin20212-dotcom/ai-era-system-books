# 6.6 Chapter Skeleton Summary and Hands-On Exploration Tasks

Over the past five sections, we have been looking at what happens inside an agent while it "runs." You hand it a task, say, "Compile the thirty expense reports in this folder into a single table and flag the ones with unusual amounts." It does not produce the answer in one go. Instead, it reads one report, makes a note, does a calculation, and tries a different approach when it finds a format it cannot handle. This chapter has broken that seemingly haphazard series of actions down into five mechanisms. This section first assembles them into a single skeleton, then asks you to return to the agent you have on hand and see these mechanisms for yourself.

## 6.6.1 Chapter Skeleton Review: Five Mechanisms, One Loop

If we treat the components in Chapter 2 as a "parts list" and the various flows in Chapter 5 as "what moves through the pipes," then this chapter is about "how the engine turns." The five mechanisms can be condensed into the following comparison table:

| Mechanism | Core Question | Key Approach | What Happens If Unaddressed |
|---|---|---|---|
| Reasoning–action loop (ReAct-style approaches) | What to do next | Think a step, take a step, look at the result, then decide the next step | Answers come from imagination alone, detached from the real environment |
| Planning and task decomposition | How to break down a large goal | Draft a plan first, adjust along the way, or combine both | Missed steps, jumbled order, getting lost midway |
| Tool calling | How the model actually "takes action" | The model outputs a structured call request; the orchestration program executes it and returns the result | The model can only "talk," not "do" |
| Memory management | What to do when there is too much information to fit | Summarize, compress, store externally, retrieve on demand | Context overflows; earlier instructions are forgotten |
| Failure and recovery | What to do when something goes wrong | Set limits, run checks, enable rollback, hand back to a human | Getting stuck, drifting off course, taking harmful actions |

These five mechanisms are not five building blocks sitting side by side. They are nested within the same loop:

- **The loop is the backbone.** The reasoning–action loop is the basic rhythm of an agent's operation, and the other four mechanisms all take place within this rhythm.
- **Planning determines where the loop goes.** The plan gives each round of "thinking a step" a direction. Observations made during execution, in turn, revise the plan.
- **Tool calling is the "doing" beat of the loop.** Keep one key fact in mind: the model itself does not perform any actions. It only generates text that describes an action, and an external program carries it out. This dividing line is also where permissions and safety controls apply.
- **Memory management lets the loop keep running.** With each turn, the context grows a little longer, and something has to be responsible for "tidying the desk."
- **Failure recovery equips the loop with brakes and guardrails.** The loop will not stop on its own. Stopping conditions, retry limits, and human confirmation all need to be designed in advance.

To sum it up in one sentence: **an agent is a feedback loop that is driven by a model, reaches the world through tools, maintains continuity through memory, keeps its direction through planning, and avoids losing control through guardrails.** When we discuss cybernetics in Chapter 8, you will find that this structure has deep theoretical roots.

## 6.6.2 A Few Common Points of Confusion

When reviewing, it is worth distinguishing a few pairs of concepts once more:

1. **The "thinking process" is not the same as the actual execution record.** The reasoning text the model writes is text it generates, and it may not correspond exactly to the tools it actually calls. To judge what an agent did, look at the tool call logs and results.
2. **"Remembering" is not the same as "understanding."** Content compressed into a summary loses detail, and retrieved snippets may not be the most relevant ones. When a long task "forgets" its original constraints midway, the cause is often memory management, not the model "getting dumber."
3. **"Retrying" is not the same as "recovering."** Trying the same method over and over often just means going in circles. Real recovery requires changing strategy, backing up a step, or bringing in a human.
4. **"Done" is not the same as "done right."** When an agent reports that a task is complete, that only means the loop has stopped. The result still needs to be checked.

## 6.6.3 Hands-On Exploration Tasks

You can complete the following tasks with any AI assistant or coding agent that has tool capabilities. At the time of writing, many products display steps such as "Searching," "Running code," or "Reading file" in their interfaces. The exact names and presentation vary from product to product, so go by the version you are using. Do not experiment with files that contain private or important data.

1. **Count the turns of the loop.** Give the agent a small task that takes several steps to complete, such as "Look up a piece of public data, convert it into a different unit, and explain your calculation." Record each "think–act–observe" cycle, count how many turns it took in total, and note which turn's observation changed its next step.
2. **Compare two planning approaches.** Submit the same task twice. The first time, give it directly. The second time, ask it to "list your plan first and wait for my confirmation before executing." Compare the number of steps, any omissions, and your opportunities to intervene.
3. **Find the boundary of a tool call.** Locate a tool call in the interface or logs, and distinguish which part is the "call request" written by the model and which part is the "result" returned by the tool. If you cannot see these details, write that down too: it tells you what information this product hides from users.
4. **Test the limits of memory.** At the start of a very long conversation, state a clear constraint (such as "round all amounts to two decimal places"), then keep giving it task after task, and observe at which task it stops following the constraint. Then remind it once midway and see how well that works.
5. **Cause a controlled failure.** Ask it to read a file name that does not exist, or to open a spreadsheet with a corrupted format. Observe whether it reports the problem honestly, tries another approach, retries repeatedly, or pretends to succeed. Classify its response using the failure modes from Section 6.5.

We suggest recording your observations in a simple table: task, number of turns, which tools were called, what kind of failure occurred, and how it recovered. This table will come in handy in Chapter 9, "Reading Every Step of Its Record."

## 6.6.4 Questions You Can Ask an AI Directly

- "Using the example of organizing expense reports, walk through each round of the reasoning–action loop step by step: what you would think, which tool you would call, what result you would see, and how you would adjust the next step. Also point out which step is most likely to go wrong."
- "When a conversation gets too long and the context can't hold it all, what are the common memory management methods? For each, explain what information it loses and what kinds of tasks it suits."
- "When an agent gets stuck in a loop of repeated retries, what are the widely accepted protective designs? Distinguish which ones the model handles itself and which must be handled by an external program or a human."

After asking, try following up with: "Which parts of your answer are common practice, and which are specific to certain products?" This habit helps you separate stable principles from product details that change quickly.

## 6.6.5 Looking Back and Looking Ahead

This chapter answered the question "How does an agent run?" But real systems also depend on a whole set of engineering foundations: what frameworks they are built with, how tools connect through standardized protocols, how dangerous operations are isolated in sandboxes, how quality is measured, and who is responsible when something goes wrong.
