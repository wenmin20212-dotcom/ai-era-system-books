# 6.3 How Tool Calling Works: How a Model "Speaks" an Action

You ask an agent to "check tomorrow's weather in Shanghai and add it to the notes in my calendar." A few seconds later, a line of small gray text appears on the screen: "Calling: weather lookup…", followed by "Calling: calendar write…". Behind these two lines lies a fact that is easy to overlook. A large language model can do only one thing: continue text based on its input. It has no hands, and it cannot connect to a weather server. So where does the act of "calling a tool" come from? The model "speaks" a strictly formatted piece of text, and an outside program turns that text into a real action on its behalf. This section takes apart what it means to "speak an action."

## 6.3.1 From a Sentence to a "Work Order": Structured Output

In Chapter 4 we looked at function calling (also commonly called tool use) from the perspective of connectivity. Now we shift to the level of mechanism and look at what a single call actually looks like.

When the agent needs to check the weather, the model does not output natural language such as "Let me go check the weather." Instead, it outputs structured text that a machine can read directly. The most common format is JSON (JavaScript Object Notation, a general-purpose format that represents data using curly braces and key-value pairs). Here is an example:

```json
{
  "tool": "get_weather",
  "arguments": { "city": "Shanghai", "date": "tomorrow" }
}
```

Think of it as a "work order." It states which department to contact (the tool name) and what needs to be done (the arguments). The model only fills out the work order. The orchestration program does the actual legwork. This division of labor matters. What the model generates is always just text, and every effect on the outside world has to pass through the program first. That checkpoint is also where the sandboxing and permission controls discussed in Chapter 7 can be placed.

## 6.3.2 How the Model Knows Which Tools Are Available

The model can fill out the work order correctly because, with every request, the orchestration program places a "tool manual" in the context. Each tool's description generally contains three parts:

| Component | Purpose | Weather tool example |
|---|---|---|
| Name | Lets the model call the tool by name | `get_weather` |
| Description | Tells the model in natural language when to use it | "Look up the weather forecast for a given city on a given day" |
| Parameter schema | Specifies which fields to fill in, their types, and which are required | city: string, required; date: string |

The parameter schema is usually written in JSON Schema, a specification for describing data formats. Reading this manual, the model is like a new employee who has been handed a department phone list along with instructions for filling out forms.

This leads to a practical conclusion: **how well a tool is described directly affects whether the model uses it, and whether it uses it correctly.** If the description is vague, the model may use the tool when it shouldn't. If the parameters are poorly explained, the model may turn "tomorrow" into a date in the wrong format. Many developers have found that refining tool descriptions often pays off more than switching models.

The model can produce this format reliably mainly because of training. Major model providers include large amounts of demonstration data in training that show the model reading descriptions, choosing tools, and filling in arguments. Training details belong to the topic of models themselves; see Volume 18. At the time of writing, the APIs from OpenAI, Anthropic, Google, and others all offer similar tool-calling features. Their field names differ, but the basic structure of name, description, and parameters is largely the same.

## 6.3.3 The Full Round Trip of a Single Call

If we pull the camera back, a tool call turns out to be a round trip driven by the program. It maps directly onto the reasoning–action loop from Section 6.1:

1. **Present the menu**: The orchestration program sends the user's task, the conversation history, and the tool descriptions to the model together.
2. **The model decides**: The model judges that it needs external information, so it outputs a call work order instead of answering directly. The API marks this output with a special flag indicating "this is a call request," which lets the program tell an ordinary reply apart from an action.
3. **The program validates**: The program checks whether the tool name exists, whether the arguments match the schema, and whether the action requires human confirmation.
4. **Real execution**: The program calls the weather service and gets the result, for example "Cloudy, 18–24°C."
5. **Feed back the result**: The program appends the result to the context as a "tool message" and sends another request to the model.
6. **Continue or finish**: After reading the result, the model can issue the next call (writing to the calendar) or give its final answer.

Two points are worth noting. First, the model is "disconnected" between Step 2 and Step 6. It does not wait. Each time, the program feeds the full context back in, and the model picks up its reasoning from there. Second, some APIs allow the model to issue several work orders in a single output, which is known as parallel calling. For example, the model can check the weather in Beijing and Shanghai at the same time. The program executes the calls concurrently and then feeds back all the results together, which saves time.

## 6.3.4 When the Work Order Is Filled Out Wrong

Since actions are "spoken," they can also be misspoken. Common problems fall into the following categories:

- **Format errors**: A missing bracket or a field of the wrong type. Some APIs offer a "strict mode" or constrained decoding (restricting the model during generation so it can only output content that conforms to the schema), which greatly reduces these problems.
- **Fabricated arguments**: The user never provided an order number, yet the model fills in a plausible-looking one out of thin air. This is hallucination showing up at the level of action, and it does more harm than a wrong sentence.
- **Choosing the wrong tool**: Two tools have similar descriptions, and the model picks the less suitable one.
- **Calling when it shouldn't**: The model could have answered directly but takes a detour instead, adding cost for no benefit.

The corresponding engineering practices are straightforward. After the program validates the format, it feeds any error message back verbatim so the model can correct itself. When required information is missing, the program steers the model to ask the user first. Any irreversible action, such as a payment, a deletion, or sending a message, always goes to a human for confirmation. Section 6.5 on failure and recovery expands on these practices.

## 6.3.5 Summary: A Program Stands Between Saying and Doing

The mechanics of tool calling come down to one sentence: **the model "speaks" a properly formatted work order, and the program validates it, executes it, and returns the result to the model.** Once you understand this, you won't picture an agent as a "ghost" that reaches out and operates the computer by itself. Every action it takes leaves a written record, and every step can be inspected, intercepted, and reproduced. In the next section, we will see that as tool calls pile up, the context grows long quickly, and the agent has to manage its memory through summarization, compression, and retrieval.
