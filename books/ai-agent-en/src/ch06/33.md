# 6.2 Planning and Task Decomposition: Plan First, or Think While Doing?

Suppose you tell a coding agent: "Replace every use of the old date function in this project with the new approach, and make sure the tests pass." Some agents will first reply with a checklist: step one, search for all call sites; step two, modify them one by one; step three, run the tests; step four, fix whatever fails. Others will simply start searching and decide what to do next once they see the results. Both approaches can get the job done, but they take different paths. The previous section covered the loop of "think a step, act a step, observe a step." This section answers a question that comes earlier: how does a large goal become a series of small, executable steps? Should an agent lay out the full plan first, or think as it goes?

## 6.2.1 Why Decomposition Is Necessary: A Large Goal Cannot Be Executed in One Step

Each time, a model can only "say" one or a few concrete actions, such as calling a search tool, reading a particular file, or writing a piece of code. A goal like "make sure the tests pass" is not an action and cannot be executed directly. Task decomposition means breaking the goal into subtasks that are concrete enough that each step corresponds to a tool call or a piece of text output.

Home renovation offers an analogy. You can't start work on "fix up the house," but you can start on "first strip the old wall plaster, then run the plumbing and wiring, then lay the tiles." How fine-grained the decomposition needs to be depends on what tools you have. The lower-level the tools an agent can call, the more finely the plan must be broken down. The more powerful the tools, for example a tool that can directly "run all tests and produce a summary report," the coarser the plan can be.

Decomposition has another, easily overlooked benefit: it confines the model's attention to the current subtask. As Volume 18 explained, models tend to miss details when handling long, cluttered contexts. Breaking a large task apart lets each step focus on a small piece, which lowers the chance of error, and when errors do happen, they are easier to pinpoint.

## 6.2.2 Two Basic Approaches: Plan Then Execute, or Think as You Go

Common practice in industry and academia falls roughly into two categories.

| Aspect | Plan-and-execute | Think as you go (interleaved, e.g., ReAct-style) |
|---|---|---|
| Method | Generate a complete list of steps first, then execute them one by one | Decide each next step based on the observations from the previous one |
| Strengths | Clear global picture, easy for humans to review, low cost when there are few steps | Flexible, able to handle surprises |
| Weaknesses | The plan rests on guesses made before execution and easily breaks when something unexpected happens | Prone to focusing only on the immediate step, taking detours or even going in circles |
| Best for | Tasks with fixed workflows and predictable environments | Tasks with incomplete information that require figuring things out along the way |

"Plan then execute" is like setting your entire navigation route before departure; "think as you go" is like asking for directions at every intersection in an unfamiliar city. The risk of the former is that the plan depends on assumptions made before execution. For instance, the plan says "modify five files," but the search turns up twenty, three of which are auto-generated and should not be edited by hand. The original plan can no longer be followed as written. The risk of the latter is the lack of a global view: after fixing one spot, the agent might wander off to deal with an unrelated warning and forget the original goal.

## 6.2.3 The Practical Compromise: Plans Can Change, Progress Must Be Visible

At the time of writing, most mainstream coding agents and research agents adopt a compromise: draft a rough plan first and revise it at any point during execution. Common engineering techniques include the following.

- **To-do list**: Some coding agents write the plan as a checklist with completion status and display it in the interface, checking off each item when done and adding or removing items when new information comes up. The list lets the user see progress, and because it is fed back to the model repeatedly with the context, it also reminds the model where it is and what remains.
- **Replanning**: At key milestones, or when a step fails, the orchestrator asks the model to re-examine the remaining plan against the goal rather than sticking rigidly to the old list.
- **Hierarchical planning**: The top level lists only three phases, "search, modify, test," and each phase is subdivided internally. Some multi-agent systems have a "planner" handle the high-level plan and hand subtasks to "executors," which is the same structure as the delegation discussed in Section 4.3 of Chapter 4.

Taking the date-function task from the opening, a sounder process looks like this: first sketch four rough steps; after executing the first step, the search, refine "modify" into a set of specific files based on the actual results, and flag the generated files that should not be edited; when tests fail, insert an "analyze the cause of failure" step instead of rushing to the next item. The plan is continually revised during execution, and each revision is based on what was actually observed at each step.

## 6.2.4 Three Things That Determine Whether a Plan Is Good

No matter how polished a plan looks, that doesn't mean the job will get done. When reviewing a plan produced by an agent, readers can check three things.

1. **Is each step executable and verifiable?** "Optimize the code" is too vague; "change the loop in function A into a batch query and run the relevant tests" can be executed, and its result can be checked.
2. **Is the dependency order correct?** You must back up before deleting, and read a file before modifying it. A plan with the wrong order easily leads to mistaken operations during execution.
3. **Is there a clear completion criterion?** Criteria such as "all tests pass" or "the table contains data for twelve months" let the agent know when to stop. A missing completion criterion is a common reason agents spin idly or over-modify; Section 6.5 will discuss this in detail.

These three points apply equally to the person assigning tasks to the agent. If you spell out the completion criteria in your task description, the decomposition the model produces is usually more solid. As Chapter 2 explained, instructions are a component of the agent, and the quality of planning depends in part on how well the instructions are written.

## 6.2.5 Summary: The Plan Is a Hypothesis, Execution Is the Test

Planning first and thinking as you go are not mutually exclusive. A plan provides direction and amounts to a hypothesis; execution brings back real information that tests and corrects that hypothesis. A good agent combines the two into a loop: plan, execute, observe, revise the plan. Chapter 8 will show that this approach is grounded in the theory of search and planning and in the principle of feedback from cybernetics.
