# 5.3 Context Flow: How Information Enters, Persists, and Gets Pushed Out

You ask an agent to organize a thirty-page market research report. In the first half it does well. It reads files, pulls out key points, and builds tables in a clear order. Then, somewhere past step forty, it suddenly asks you: "What format would you like the report in?" You told it that at the very start. It isn't being "forgetful" or "lazy." The sentence you gave it at the beginning has most likely dropped out of what it can see right now.

To understand why, you need to look at the third kind of flow in an agent system: context flow.

## 5.3.1 A Workbench That Fills Up

Each time a large language model generates a response, it can directly "see" only one stretch of text, called the **context**. How much that text can hold is set by the **context window**. Its unit of measure is the **token**, the basic unit a model splits text into. One Chinese character corresponds to roughly one or two tokens. At the time of writing, publicly reported window sizes range from tens of thousands to over a million tokens, and they vary widely between models.

Think of the context window as a workbench of fixed size. The model is a craftsman sitting at the bench, and it can only work on what is laid out on the surface. Anything off the bench does not exist for it at that moment, even if it sits in the storeroom next door. Book 18, *Large Language Models*, explains why models are limited to working this way. Here we look only at how an agent system puts things on this bench, keeps them there, and clears them away.

## 5.3.2 Where Information Comes From

In a typical agent run, the material on the bench comes from roughly these sources:

| Source | Examples | Characteristics |
|---|---|---|
| System prompt | Role definition, behavioral rules, tool descriptions | Usually included every turn, in a fixed position |
| User input | Task goals, additional requirements, confirmation replies | Small in volume but carries the most weight |
| Tool returns | Web page text, file contents, command output, error messages | Largest in volume and the most likely to get out of hand |
| The model's own output | Reasoning, plans, call requests | Grows linearly with the number of steps |
| Retrieval results | Snippets fetched from a knowledge base or long-term memory | Injected on demand and selected by the orchestrator |

One point deserves emphasis: the model itself has no memory of "the previous turn." On every call, the orchestrator reassembles all of the above into a single stretch of text and hands it to the model. What we call "conversation history" is really a stack of pages the program hands over again each time. The orchestrator decides which pages to hand over and in what order. The model has no say.

## 5.3.3 How Information Stays, and How It Gets Pushed Out

What most distinguishes an agent from ordinary chat is **tool returns**. In a chat, each turn is only a few hundred words. An agent that reads one web page may bring back several thousand tokens, and running a single test may produce tens of thousands of lines of logs. After a few dozen steps, the bench fills up fast.

Once the bench is full, the orchestrator has to make trade-offs. Common approaches include:

- **Truncation**: Simply discard the oldest content. It is the easiest to implement, and it is often how the format requirement you gave at the start disappears.
- **Sliding window**: Keep only the most recent turns, plus the fixed system prompt.
- **Summary compression**: Have the model condense the previous few dozen steps into a summary, and replace the original text with it. The key points survive and the details are lost.
- **Offloading**: Write large blocks of content to files or a memory store, leave only an "index" on the bench, and retrieve the content when needed.
- **Trimming tool output**: When a tool returns, keep only the first few lines, or only the parts relevant to the task.

Each of these methods has a cost. Truncation can lose the goal, summarization can lose detail, and offloading depends on whether the content can be retrieved accurately later. Chapter 6, "Memory Management," covers how they work in detail. For now, remember one conclusion: **context is a resource that gets used up, and the longer an agent runs, the more often it has to make trade-offs.**

There is also a subtler kind of "pushing out": the information is still on the bench, but the model fails to notice it. Some published research has found that when the context is very long, models make less use of information buried in the middle than of information at the beginning and end. This is often called being "lost in the middle." How strong the effect is varies by model, but the logic holds: when the bench is piled too high, things get buried.

## 5.3.4 Quality Matters More Than Quantity

This leads to a very practical rule of thumb: more is not better. When a long, irrelevant web page enters the context, it takes up space and can also pull the model's attention off course. There is a bigger concern too. Content brought back by tools was written by the outside world, and it may contain text such as "ignore all previous instructions." This is exactly where the prompt injection risk discussed in Chapter 7 gets in. Context flow carries information, and it also carries risk.

For these reasons, well-designed agent systems usually do the following:

1. Put the most critical constraints (goals, format, off-limits areas) somewhere that won't get cut off, such as the system prompt or a separately maintained "task memo";
2. Filter tool output before adding it to the context;
3. On long tasks, produce progress summaries at regular intervals, so that each fresh context starts from the summary;
4. Hand subtasks to a separate sub-agent with a clean context, and bring back only its conclusions. At the time of writing, some coding agent products already work this way.

As a user, you can help too. Partway through a long task, restate the key requirements. Or have the agent write the task goal into a file and reread it every so often.

## 5.3.5 Summary: Keep an Eye on the Workbench

Back to the report task from the opening. When the agent asked you about format, it showed that your original sentence had been pushed off its workbench. Understanding context flow means understanding what goes onto that bench, what stays, and what gets cleared away, and when. Task flow tells us what the agent has to do. Message flow tells us where information travels and between whom. Context flow determines how much the model actually "knows" at each step.

But deciding what goes on the bench is not just a question of whether there is enough room. It is also a question of what *should* be there. Which files is the agent allowed to read? Which data must not leave? Which actions require asking a person first? That brings us to the next section: permission flow and data flow.
