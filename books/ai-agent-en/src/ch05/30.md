# 5.5 Cost Flow: Time, Tokens, and Call Counts

You ask an agent to "turn these thirty supplier quotes into a comparison table." It works for a few minutes and hands back a respectable-looking table. On screen, that is one task. The bill tells a different story. The model was called dozens of times and read several hundred thousand "tokens" of text, and partway through it retried twice because one file was in the wrong format. On a pay-as-you-go service, all of that becomes money. Even on a monthly subscription, it becomes waiting time and usage caps. The previous sections covered how tasks, messages, context, and permissions flow. This section looks at the last flow, and the one most easily overlooked: the cost flow.

## 5.5.1 Three "Currencies": Time, Tokens, and Call Counts

An agent's costs can be counted in three units.

| Cost unit | What it is | What the reader experiences |
|---|---|---|
| Time (Latency) | Total time from issuing a task to receiving the result | Spinning icons, waiting, tasks running for ten-plus minutes |
| Tokens | The unit for measuring the text a model reads and writes. One token is roughly one Chinese character or a fraction of one; in English, about three-quarters of a word (a common estimate in public sources) | Pay-as-you-go bills, consumption of usage quotas |
| Call counts | The number of requests made to the model, plus calls to search, databases, and external APIs | Rate-limit warnings, third-party service fees |

The three are linked. More calls usually mean more tokens, and more tokens mean the model takes longer to process and generate. Volume 18, *Large Language Models*, explains in detail how a model generates tokens one by one. Here you only need to remember one point: **every extra word the model reads or writes costs computation.**

## 5.5.2 Why Agents Cost Far More Than Chat

Ordinary chat is "one question, one answer," and a single call finishes the job. An agent runs a "reason–act loop," and every step sends **the entire context so far** back to the model.

A small scenario makes the arithmetic concrete. Suppose the system prompt and tool descriptions take up 3,000 tokens, the agent takes 20 steps, and each step's tool results add an average of 2,000 tokens. At step 1 the model reads 3,000, at step 2 it reads 5,000, at step 3 it reads 7,000, and by step 20 it reads 41,000. Across all 20 steps, the model reads about 440,000 tokens in total, even though the useful output may be a table of a few thousand words.

This reveals a structural feature of agent costs: **input cost grows roughly quadratically with the number of steps, not linearly.** No particular product is badly designed. The cost comes from the shape of the loop itself, because each step "rereads" the history before it. So the context compression discussed in Section 5.3 does more than make things fit. It also keeps them affordable.

Several other amplifiers are often overlooked:

- **Large tool results**: A single web fetch or log read can run to tens of thousands of tokens, most of them irrelevant.
- **Retries and detours**: When a tool errors and the agent tries again, the failed steps are billed too.
- **Multiple agents**: When a main agent delegates to several sub-agents, each one has its own context and loop, and the total multiplies.
- **Reasoning**: Some models produce lengthy internal reasoning text before answering, and this usually counts toward output usage as well. Whether and how it is billed depends on each service's terms at the time of writing.

## 5.5.3 Where the Cost Flow Goes: What the Money Is Spent On

If you break down the costs of a single task, the flow looks roughly like this:

1. **Fixed overhead**: The system prompt, role definition, and tool list. These are carried along at every step, so they add up as the number of steps grows.
2. **Task overhead**: Results from reading files, looking things up, and calling APIs, all of which enter the context.
3. **Generation overhead**: The reasoning, tool-call instructions, and final answer the model writes. Pay-as-you-go services generally charge more per output token than per input token, which is common practice in public price lists.
4. **External overhead**: Third-party calls such as search services, map APIs, and paid databases, each billed separately.

For the first item, some model providers offer "Prompt Caching." If the opening portion of multiple requests is identical, the repeated part can be billed at a lower rate and processed faster. At the time of writing, Anthropic, OpenAI, and others offer this kind of mechanism, with differing details. The principle is easy to grasp. Since every step rereads the same opening, the results of computing that opening are stored and reused.

## 5.5.4 Keeping the Cost Flow Under Control

In engineering practice, the common ways to manage the cost flow fall into three groups: "set limits, move less data, and choose the right model." A fourth habit, making costs visible, ties them together.

- **Set limits**: Give a task a maximum number of steps, a time limit, or a token budget. When it exceeds the limit, the agent stops and reports back instead of looping forever. This also works as a safety valve against getting "stuck," which Chapter 6 returns to in its discussion of failure recovery.
- **Move less data**: Have tools return only what is needed, such as the few dozen relevant lines of a file rather than the whole thing. Summarize old history before handing it to the model.
- **Choose the right model**: Give simple classification and extraction to smaller, faster models, and save complex planning for more capable ones. Many frameworks support assigning different models to different steps.
- **Make it visible**: Record how many tokens and how much time each step uses. Costs you cannot see cannot be managed, which matters especially for teams adopting agents.

For everyday users, the most practical habit is to **state the task clearly and narrow its scope**. "Take a look at what's wrong with this project" may send the agent rummaging through the entire folder. "Check the function that computes totals in report.py" takes only a few steps. A good instruction is itself a way to save money.

## 5.5.5 Summary: Cost Is Part of the System

Time, tokens, and call counts are not a "billing issue" tacked onto an agent. They follow directly from how it runs. The longer the loop, the larger the context, and the more the work is divided up, the heavier the cost flow. Once you understand this, you can see why agents compress their memory, why frameworks impose step limits, and why the same task can cost very different amounts depending on how it is phrased. That completes all five flows: tasks, messages, context, permissions and data, and cost.
