# 5.1 Task Flow: From a One-Sentence Goal to a Chain of Actions

Suppose that on a Monday morning you say one sentence to a coding agent: "Change every place in the project that reads a configuration file so it reads from environment variables instead, and run the tests when you're done." A dozen or so minutes later, you see a long record on your screen. The agent first searches the code, then opens five files and modifies three of them. It runs the tests, two of which fail, so it goes back to make more changes and runs the tests again. Finally it gives you a summary. You said only one sentence, yet dozens of actions took place inside the system.

Where this chain of actions comes from, the order in which it unfolds, and where it branches, loops back, and ends make up the first kind of flow this chapter traces: the task flow. Earlier chapters took the agent apart into its components and covered its connections to the outside world. This section shifts perspective and keeps its eye on the "task" itself, watching how it is processed step by step within the system.

## 5.1.1 Where the Task Flow Begins: What a Single Sentence Contains

A task flow usually begins with a goal stated in natural language. The sentence looks simple, but it actually mixes several different kinds of information:

| Component | How it appears in the example above | What the agent needs to do |
|---|---|---|
| Goal | Configuration is read from environment variables | Understand what "done" looks like |
| Scope | "Every place in the project" that reads configuration | Search on its own rather than changing just one spot |
| Additional step | Run the tests when done | Remember it and schedule it for the end |
| Implicit constraint | Don't break existing functionality | Not stated, so it must be filled in with common sense |

A human colleague given this sentence would naturally fill in the implicit constraints. Whether an agent can do so depends on the comprehension ability of the large language model, and also on whether the system prompt clearly spells out working norms (see Section 2.2). So the first step of the task flow is to turn a vague sentence into a **verifiable goal**: what degree of completion counts as done, and what counts as failure. The vaguer the goal, the more easily the subsequent actions drift off course.

## 5.1.2 From Goal to Actions: A Three-Stage Process

Turning a goal into a chain of actions roughly involves three stages of processing.

1. **Decomposition**: Break the large goal into several subtasks, such as "find all the code that reads configuration," "modify each one," "run the tests," and "report the results." Some systems first write out an explicit plan checklist, while others think as they go (the pros and cons of each approach are discussed in Section 6.2).
2. **Grounding**: Turn each subtask into concrete tool calls. Once grounded, "find all the code that reads configuration" might become a single full-text search with a particular keyword as its parameter.
3. **Verification**: After each action completes, check the result and decide the next step. If the search returns five matches, five inspections need to be scheduled; if the tests fail, new modification steps need to be inserted.

One point here deserves attention: **a task flow is not a fixed flowchart laid out in advance**. In a traditional automation script, the flow is hard-coded by the programmer; what happens first and what happens second are settled before the program runs. An agent's task flow "grows" during execution, and what it does next depends on what it saw in the previous step. You can compare it to driving with a navigation app: the starting point and destination are fixed, but the route is continually recalculated based on real-time traffic.

## 5.1.3 The Shapes of a Task Flow

If you draw each step an agent records as a diagram, the following shapes are common:

- **Linear**: One step follows another with no backtracking. Suited to small tasks with clear goals and fixed steps, such as "sort this table by date and then export it."
- **Looping**: Do, check, revise, do again, until a condition is met. The "modify code, run tests, modify again" cycle in the example above is a typical loop. Loops need an upper limit; otherwise they may keep going indefinitely.
- **Branching**: One task is split into several independent subtasks that can be processed in parallel and then combined at the end, for example querying three sources at once and merging the results. In multi-agent systems, branching often means delegating subtasks to different agents (see Section 4.3).
- **Interrupted**: The flow stops at a certain step and continues only after a human confirms or supplies additional information, for example asking you to click "Approve" before deleting files or sending an email (see Section 4.4).

Real tasks are often combinations of these shapes: branching first to gather information, then looping through modifications, with pauses at key steps to wait for human confirmation.

## 5.1.4 Who Moves the Task Forward

A task flow advances step by step through the cooperation of the orchestrator and the model. The division of labor can be understood as follows:

| Role | Responsibilities |
|---|---|
| Large language model | Decides "what to do next" and expresses the intended action |
| Orchestrator | Executes actions, collects results, tracks progress, decides whether to stop |
| Tools and environment | Actually perform operations such as searching, reading and writing files, and running programs |
| Human | Sets the goal, confirms at key points, and accepts the results |

The most easily overlooked element is the **stopping condition**. When does a task flow end? Common cases include: the model judges that the goal has been achieved; a preset limit on steps, time, or cost is reached; an error is encountered that the agent cannot resolve on its own; or a human calls a halt. A well-designed system spells these conditions out clearly. Missing stopping conditions are one of the common reasons an agent gets "stuck" or "spins idly," which Section 6.5 analyzes in detail.

## 5.1.5 Reading the Task Flow Means Understanding What the Agent Is Doing

For users, learning to read a task flow is genuinely useful. Many agent products now display the execution process to users. At the time of writing, a common approach is to list steps in the interface one by one, such as "Searching," "Reading a file," or "Running a command," though the exact form varies by product. Once you understand these records, you can judge: Did it misunderstand the goal? Is it going around in circles in some loop? Did it take an action you didn't intend to authorize?

This also gives us a simple principle for using agents well: **when assigning a task, state the goal, scope, and completion criteria clearly; during execution, watch whether the task flow drifts; at the end, check the result against the completion criteria**. The task flow is the skeleton of an agent's work, but something else also flows along this skeleton: the messages passing back and forth among the model, the tools, and the user.
