# 1.3 The Boundaries of an Agent: Model, Program, Environment, and People

Imagine telling a coding agent: "Change all the outdated date formats in this project to a consistent style, then run the tests when you're done." A few minutes later, it reports: "Modified 12 files; all tests passed." It's worth stopping to ask: who exactly did the work just now? Was it the large model? Or some program running on your computer? Who ran the tests? And if it had mistakenly deleted a file, where would the responsibility lie?

These questions all point to the same thing: **the boundaries of an agent**. When we say "the agent did something," it sounds like a single, complete entity. Take it apart, though, and the work is actually done jointly by four parties: the model, the program, the environment, and the human. If you can't tell these four apart, it's easy both to overestimate the agent and to blame it unfairly.

## 1.3.1 The Model: It Can Only "Speak," Not "Act"

Start with the core component, the Large Language Model (LLM). Its job is just one thing: take in a piece of text and output a piece of text. How the model predicts the next word from the preceding context is explained in detail in Volume 18, *Large Language Models*. Here you only need to remember one key fact: **the model by itself cannot open files, cannot run tests, and certainly cannot go online.**

When the agent "modified 12 files," what the model actually did was write out a properly formatted piece of text that said, in effect: "Please call the editing tool, open such-and-such file, and change line 30 to the following." This is merely a "request for action," not yet the action itself. The model is like a staff officer sitting in a command room: it can read the map, offer ideas, and issue orders, but it holds no real equipment in its hands.

This distinction matters. Many people think "the AI deleted my file." Strictly speaking, the model submitted a request to delete; the part that actually carried out the deletion was something else.

## 1.3.2 The Program: The Intermediary That Turns "Speaking" into "Doing"

What turns the model's text into real actions is an ordinary piece of software, usually called the **orchestrator**, which some also call the "agent runtime framework" or the "harness." It does roughly the following:

1. Bundles your task, the system instructions, and the list of available tools, and sends them to the model;
2. Reads the model's reply and identifies any tool-call requests within it;
3. Checks whether the request is permitted, asking you first if necessary;
4. Actually invokes the tool, such as reading or writing files or executing commands;
5. Sends the execution results back to the model and waits for it to decide the next step.

This process loops repeatedly until the model declares "task complete." The orchestrator is written using traditional programming methods; its rules are explicit and its behavior is deterministic: given the same input, it handles it the same way every time. The model, by contrast, is probabilistic; the same question may yield slightly different answers. **A somewhat "uncertain" brain paired with a highly "certain" execution framework**: this is the basic structure of most agents today. Chapters 2 and 6 will break this loop down in finer detail.

## 1.3.3 The Environment: The "Site" Where the Agent Gets Its Hands Dirty

The actions the program executes always land somewhere, and that somewhere is the **environment**. It might be your computer's terminal, a browser, a temporary container in the cloud, or your company's database or email.

The environment determines what the agent "can touch." The same instruction, "clean up unused files," executed inside an isolated test container, has a worst-case outcome of rebuilding the container; executed on your personal computer full of work files, the consequences are entirely different. That is why engineers commonly use a **sandbox** to confine the agent to a restricted space, limiting the directories, network access, and commands available to it. Chapter 7 is devoted to sandboxes and permissions.

The environment has another side: it "talks back." Whether tests pass or fail, whether a webpage opens or throws an error, this feedback flows back through the program to the model and forms the basis on which the agent decides its next step. The environment itself is not under the agent's control; it is the outside world the agent must perceive and adapt to.

## 1.3.4 The Human: Source of Goals and Final Gatekeeper

The last party is you. Humans play at least three roles in an agent system:

- **Setting goals**: The task begins with a sentence from you. If you phrase it vaguely, the agent may misunderstand it;
- **Setting boundaries**: You or your administrator decide which tools it can use, which files it can touch, and which operations require your approval first;
- **Doing acceptance**: "All tests passed" is the agent's report; whether the result truly matches your intent must ultimately be judged by a human.

Many agent products pop up a confirmation prompt before irreversible operations such as deleting, making payments, or sending email. This is precisely a design that places the human at critical junctures. It is not a needless nuisance but a deliberately reserved link in the chain of responsibility.

## 1.3.5 A Comparison Table: Who Is Responsible for What

| Party | Good at | Not good at | Typical symptoms when things go wrong |
|---|---|---|---|
| Model | Understanding intent, generating plans, writing code and text | Acting directly, guaranteeing consistency every time, knowing the latest facts | Plans going off track, fabricating nonexistent files or functions |
| Orchestrator | Looping by rules, invoking tools, checking permissions | Understanding vague requirements | Overly broad permission settings, loops that won't stop |
| Environment | Providing real data and execution results | Proactively correcting errors | Network outages, missing files, command errors |
| Human | Setting goals, judging value, bearing responsibility | Watching every small step | Vague instructions, excessive authorization, careless acceptance |

With this table in hand, the next time "the agent made a mistake," you can ask more precisely: Did the model reason wrongly? Did the program let through an action it shouldn't have? Did the environment give unexpected feedback? Or did we ourselves describe the task unclearly? Quite often, the problem lies in the gaps where these parties meet.

## 1.3.6 Summary: An Agent Is a System, Not an "It"

The word "agent" easily conjures up the image of an independent little robot. A more accurate view is this: **it is a system formed by the model, the program, the environment, and the human collaborating in a loop.** The model does the thinking, the program relays and executes, the environment provides the site and the feedback, and the human is responsible for goals and gatekeeping. Once you understand these boundaries, you'll know which capabilities you can expect from it and which responsibilities cannot be pushed onto it.

So how did this kind of system, one that "can both think and act," come about step by step? Long before large models, people had already tried to get machines to complete tasks autonomously. In the next section, we'll follow the history and trace the evolutionary path of agents.
