# 8.2 Cybernetics: The Perception–Decision–Action Feedback Loop

Suppose you ask a coding agent to fix a piece of code that throws an error. It changes a few lines, runs the tests, and sees that two tests still fail. It reads the error messages, edits again, and runs the tests again. It keeps going until every test passes. Readers already met this "edit, test, inspect, edit again" process in Chapter 6, where it was called the reasoning–action loop. This section asks a different question: why does checking the result and then adjusting work so well? People studied that question systematically more than eighty years ago, and the field they built is called cybernetics.

## 8.2.1 From Thermostats to Agents: What Feedback Is

The American mathematician Norbert Wiener coined the term *cybernetics* in his 1948 book of the same name, drawing on the Greek word for "steersman." The field covers a lot of ground. It studies how machines, animals, and organizations use information from their environment to regulate their own behavior and reach a goal.

The easiest example to grasp is the thermostat on a home air conditioner or electric water heater:

1. **Set the goal**: You set the temperature to 26°C.
2. **Sense**: A temperature sensor measures the room at 29°C.
3. **Compare**: The controller computes the error, which is the 3°C difference between the target and the current state.
4. **Act**: The compressor starts cooling.
5. **Sense again**: After a while the room reaches 27°C. The error has shrunk, so the system keeps adjusting. Near 26°C it slows down or stops.

Step 5 is the key. The system measures the result of its action and sends it back to shape the next action. This is called **feedback**. Feedback that shrinks the error and pushes the system toward its goal is **negative feedback**. Feedback that amplifies the error is **positive feedback**. The squeal that keeps getting louder when a microphone gets too close to a speaker is an example.

Engineers distinguish two approaches, **open-loop control** and **closed-loop control**:

| Approach | Checks results? | Everyday example | Agent counterpart |
|---|---|---|---|
| Open-loop control | No; runs the preset action to the end | An old toaster set to a 3-minute timer | Generating an entire block of code in one shot and delivering it without running it |
| Closed-loop control | Yes; measures results and adjusts based on the error | An air conditioner with a temperature sensor | Writing code, running the tests, and revising based on the errors |

Open-loop control is simple and fast, but it only works when you understand the environment well. Closed-loop control holds up better, because the real world always brings unexpected disturbances. Agents work in environments where web pages get redesigned, file formats vary widely, and code dependencies are complex. For them, the closed loop is close to mandatory.

## 8.2.2 Drawing an Agent as a Control Loop

Viewed through the lens of cybernetics, an agent's components map one-to-one onto a control system:

- **Goal (setpoint)**: the user's task description and acceptance criteria, such as "all tests pass" or "the table is sorted by date with no duplicate rows."
- **Sensors**: the information that tools return, such as command-line output, web page content, file contents, and screenshots.
- **Controller**: the large language model plus its orchestration program. It compares how things are with how they should be and decides the next step.
- **Actuators**: the tools and function calls, such as writing files, clicking buttons, and sending requests.
- **Controlled system**: the external environment, meaning the code repository, spreadsheet, browser, or database.

Drawn this way, the "perception, planning, execution, and reflection-and-correction" described in Chapter 3 stop looking like separate features. They form a single loop. Reflection and correction matter because they are the "compare the error" step. Without them, the agent degrades into an open-loop machine that makes mistakes without ever noticing.

This mapping is an analogy, not a strict mathematical equivalence. Classical control theory usually deals with continuous quantities such as temperature or speed, and engineers can write exact equations for them. An agent's "error" is often a block of error text or a remark like "the result doesn't meet the requirements," and the model has to interpret it in language. Still, the measure-compare-correct structure is the same in both cases, which is why ideas from cybernetics remain useful today.

## 8.2.3 Three Classic Problems with Feedback Loops

Control engineers have long known that having feedback does not solve everything. Several classic problems have direct counterparts in agents.

**First, inaccurate measurement.** If the sensor breaks, the air conditioner keeps cooling forever. For an agent, incomplete tests mean that "all tests pass" doesn't prove the code is correct. If a web scrape comes back incomplete, the agent will reason from partial information. The quality of the feedback sets an upper limit on how well the agent can correct itself. Giving an agent clear, verifiable acceptance criteria is like fitting it with a reliable sensor.

**Second, oscillation.** If a controller adjusts too aggressively, it overshoots, then overshoots again on the way back, and swings back and forth. A common version in agents goes like this: fixing spot A breaks spot B, and fixing B breaks A again, round and round. Many of the cases of "getting stuck" from Chapter 6 fall into this category. Engineers respond by making each adjustment smaller and keeping records. For agents, that means making small edits, keeping a history, and not repeating an attempt that already failed.

**Third, delay and cost.** The slower the feedback signal returns, the harder the system is to control. Every round costs an agent time and tokens, because it has to call the model and run tools. Real systems therefore usually set a maximum number of rounds, timeouts, and budget caps. These limits act as a fuse on the loop and keep it from running forever.

## 8.2.4 Humans Are in the Loop Too

Cybernetics also makes a point that people often overlook. The controller can itself be part of the system, and loops can nest inside one another. Inside the agent there is a small loop of editing code and running tests. Outside it there is a larger loop: the user reviews the results, decides something is off, and asks for changes. From a cybernetic perspective, the human confirmation steps described in Chapter 4 put a person at key points to serve as a more reliable sensor and a higher-level controller.

This also explains a practical rule of thumb. The more important a task is, and the harder it is to check automatically, the more often a human should step in. Let the agent fix the errors it can measure on its own. Have a human review the ones it can't measure, or can only measure at too high a cost.

## 8.2.5 Summary

Cybernetics shows that acting on its own is only part of what makes an agent useful. The more important part is that it checks the result before acting again. Goal, perception, comparison, action, and renewed perception form a closed negative-feedback loop. How reliable that loop is depends on three things: whether the feedback is accurate, whether the adjustments are steady, and whether the loop has limits. Once you understand this, you know where to put your effort when working with agents: state the goal clearly, provide thorough acceptance criteria, and set sensible limits on rounds and permissions. The next section turns to a different question: before it acts, how does an agent find a path among the many possible steps? That is the subject of search and planning.
