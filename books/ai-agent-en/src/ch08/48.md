# 8.5 Uncertainty and Computability: What Agents Cannot Do

You ask a coding agent to fix a bug in a program. It changes the code, runs the tests, and reports back: "All tests passed." You breathe a sigh of relief, yet something still nags at you. Does passing the tests mean the program will never fail again? If you follow up with "Can you guarantee this program will never hang on any input?", a trustworthy agent should answer, "No, not completely." That is not modesty. Some things are impossible not because the model is too small or the tools too few, but because they are mathematically impossible.

This section turns things around. Instead of what agents can do, it looks at where their limits lie. These limits come in two kinds. One comes from **uncertainty**: information is incomplete, and the world changes. The other comes from **computability**: some problems have no general algorithm that can solve them at all. Once you can tell these two kinds of limits apart, you can judge when to trust an agent and when a human must step in.

## 8.5.1 A World Only Partly Seen: Uncertainty from Incomplete Information

Return to the book's anchor task: having an agent look up information and organize it into a table. All it can see are search results, fragments of web pages, and the files you give it. Web pages may be out of date, two sources may contradict each other, and what you actually want may not have been spelled out clearly.

Decision theory calls this situation **partially observable**. The agent cannot see the full state of the world and can only infer it from observations. The classic mathematical model for such problems is the **Partially Observable Markov Decision Process** (POMDP). Here is one way to think about it: the agent holds only a "distribution of guesses" about the state of the world, and after each action it revises those guesses based on what it newly observes.

Uncertainty comes from roughly three sources:

| Source | How it shows up in agent tasks | Common responses |
|---|---|---|
| Environmental uncertainty | Web pages get redesigned, APIs time out, files are modified by someone else | Retry, validate returned results, record timestamps |
| Informational uncertainty | Sources contradict each other, credibility is unclear | Cross-check multiple sources, cite where information came from |
| Intent uncertainty | What exactly does "tidy this up" mean? | Ask clarifying questions first, or show a sample for the person to confirm |

A fourth source lies within the model itself. A large language model outputs the most probable text, which is not necessarily true. This is what people usually call "hallucination"; for its causes inside the model, see Volume 18. That is why the reflection and self-correction covered in Chapter 3 and the human confirmation covered in Chapter 4 are not optional extras. They are essential feedback loops for acting in an uncertain world.

## 8.5.2 A Program That Can Never Be Written: The Halting Problem

The second kind of limit is more fundamental. In 1936, the British mathematician Alan Turing proved that **no general program can determine, for an arbitrary program and input, whether that program will eventually stop or run forever**. This is the **Halting Problem**.

The idea behind the proof can be told as a short story. Suppose there is an "oracle" program H: give it any program, and it can tell you whether that program will stop. Now build a "troublemaker" program D specifically to foil it. D first asks H, "Will I stop?" If H says yes, D deliberately loops forever; if H says no, D stops immediately. D always does the opposite of what H predicts, so H cannot be right about every program. Such an oracle simply cannot exist.

Later, **Rice's Theorem** extended this result much further: for any "non-trivial" property of a program's behavior, such as "Will it leak data?" or "Is its output always correct?", there is no general algorithm that can decide it.

For agents, this means three things:

1. **A coding agent cannot, in general, prove that code is correct.** It can run tests, but tests cover only a finite number of cases. Tests can reveal bugs, but they cannot prove the absence of bugs.
2. **An agent cannot determine in advance that its task will definitely be completed.** The reason–act loop can get stuck going in circles, which is why engineering practice sets a maximum number of steps, timeouts, and cost limits, as seen in Chapters 5 and 6. These are not crude workarounds; they are the right response to undecidability.
3. **Security review cannot be foolproof either.** Trying to have a program automatically decide whether "this code is absolutely safe" is, in general, just as undecidable. This is why Chapter 7 emphasizes sandbox isolation: since safety cannot be proven in advance, you limit how far the damage can spread when something goes wrong.

## 8.5.3 Computable, but Too Slow to Wait For: Computational Complexity

Some problems can be solved in principle, but the time required grows explosively with their size. Section 8.3 covered search and planning; in problems like scheduling or route selection, the number of possible combinations grows exponentially with the number of tasks. Computer science classifies such hard problems as **NP-hard**, and no efficient general solution for them is currently known.

So when an agent plans, it aims not for the optimal solution but for a "good enough" one. This corresponds directly to **bounded rationality**, the idea proposed by the economist Herbert Simon: when time, information, and computing power are all limited, the rational approach is to find a satisfactory solution rather than exhaust every possibility. An agent's context window has a length limit, and every call costs money; these constraints make it all the more a "boundedly rational" actor.

## 8.5.4 Turning Limits into Design Principles

Knowing what an agent cannot do helps you use it better. The conclusions of this section can be turned into a few practical principles:

- **Require verifiable output**: Have the agent include sources, test results, and action logs, so that you check the evidence rather than simply taking its word for it.
- **Set guardrails**: Put limits on steps, time, and budget, and require human confirmation for high-risk actions.
- **Leave responsibility for correctness with people**: For decisions involving money, privacy, or production systems, the final sign-off should belong to a human.
- **Accept "good enough"**: Complex planning need not insist on the optimum; focus instead on making sure key constraints are never violated.

Uncertainty tells us that an agent is always "guessing" about the world; computability tells us that some problems cannot be solved in general by any machine, however powerful. These two limits will not disappear with the release of the next generation of models. Together with the decision-making, feedback, search, and learning covered in Sections 8.1 through 8.4, they form the complete foundation of how agents work.
