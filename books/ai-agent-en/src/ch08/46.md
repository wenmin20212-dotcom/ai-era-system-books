# 8.3 Search and Planning: From Solving Mazes to Scheduling

Suppose you tell an agent: "Next Wednesday afternoon, set up a one-hour meeting with Manager Zhang and Professor Li, and book a meeting room with a projector while you're at it." It first checks all three people's calendars and then the room's availability. It finds that a room is free at 2 p.m. on Wednesday, but Professor Li has a class at 2:30. So it backs up and tries 3 p.m., only to find that Manager Zhang will be traveling from 3 to 4. In the end it finds the 4-to-5 slot, when all three are free and a room is also available, and sends out the invitations.

The process looks unremarkable, but behind it lies one of the oldest kinds of problems in artificial intelligence: **search** and **planning**. When an agent tries a plan, hits a wall, backs up, and tries another, it is doing something structurally similar to a mouse running a maze or a computer playing chess.

## 8.3.1 Drawing the Problem as a "State Graph"

When computer science tackles problems like this, the first step is to formalize them. That means describing the problem clearly using a fixed set of elements:

| Element | Meaning | Solving a maze | Scheduling a meeting |
|---|---|---|---|
| State | What the world looks like right now | Which square the person is standing on | Which times, people, and rooms have been settled |
| Initial state | Where you start | The maze entrance | Nothing settled yet |
| Action | A single step you can take | Move one square up, down, left, or right | Pick a time slot, pick a meeting room |
| Transition | How an action changes the state | Move to an adjacent square | One more item gets settled |
| Goal test | What counts as done | Reaching the exit | Everyone is free and a room is available |
| Cost | How much each step costs | Number of steps taken | Number of queries, quality of the time slot |

Treat every state as a point and every action as a line connecting two points, and you get a **state-space graph**. Solving the problem means finding a path on this graph from the start to the goal. The sequence of actions along that path is a "plan."

The appeal of this view is that it unifies very different problems. Mazes, puzzles, navigation, scheduling, and editing code look nothing alike, yet once abstracted they all come down to "finding a path on a graph."

## 8.3.2 Blind Search and Heuristic Search

There are two basic ways to find a path.

- **Breadth-First Search (BFS)**: First look at every place reachable in one step from the start, then every place reachable in two steps, expanding outward ring by ring. It finds the path with the fewest steps, but it has to remember a great deal.
- **Depth-First Search (DFS)**: Follow one path all the way to the end, and if it's a dead end, back up to the previous fork and try another direction. It saves memory, but it can waste a long time in a very deep dead end.

The meeting example at the start is a depth-first search with "backtracking": try 2 p.m., and if that fails, back up and try 3 p.m.

The trouble is that the state spaces of real problems are often staggeringly large. Just the combinations of a few dozen time slots in a week, several people, and several meeting rooms number in the thousands. For chess or writing programs, the possibilities are astronomical. This is known as **combinatorial explosion**. Trying options one at a time without guidance is hopeless, no matter how fast the computer.

Hence **heuristic search**. A "heuristic" is a rule of thumb that estimates "how far you still are from the goal." In a maze, people instinctively head toward where the exit seems to be. When a map app calculates a route, it favors roads that run roughly toward the destination. The **A\* algorithm**, introduced in 1968, adds "how far you've already come" to "how far you estimate you still have to go" and always expands the point with the smallest total first. As long as the estimate never exceeds the true distance, it is guaranteed to find the optimal path while avoiding many needless detours. A\* remains a foundational algorithm in navigation, game pathfinding, and other fields.

## 8.3.3 From Pathfinding to Planning: Classical Planning

Search asks "how do I get there?" Planning asks "what do I do first, and what next?" In 1971, researchers at the Stanford Research Institute developed the **STRIPS** planning system for the robot Shakey. Its core idea is still used today: every action specifies its **preconditions** and its **effects**.

Take "booking a meeting room" as an example:

- Action: Book a meeting room
- Preconditions: The meeting time has been settled, and the room is free during that slot
- Effects: The room is occupied, and the meeting has a location

With descriptions like these, a planner can automatically work out the order of actions. You can't book a room before the time is settled, so the calendars must be checked first. Later came methods such as the **Hierarchical Task Network (HTN)**, which breaks a large task like "organize a meeting" down, level by level, into smaller tasks such as "settle the time," "book the room," and "send invitations." This is a different implementation of the same idea as the task decomposition discussed in Chapter 6.

Classical planning has one requirement: the rules of the world must be spelled out in advance. That works well in domains with clear rules, such as factory production scheduling and logistics dispatching, but it falls short in an open world. No one can write out in advance, as rules, every action and condition involved in "look up some material and write me a report."

## 8.3.4 LLM Agents: Common Sense Instead of Rules, Trial Instead of Exhaustive Search

Today's agents built around large language models make a key substitution in search and planning: **instead of needing humans to write action rules ahead of time, they rely on the common sense the model has learned from vast amounts of text to propose a "reasonable-looking next step" directly.** Here the model acts as a very powerful heuristic function. It can't guarantee the best answer, but it usually steers attention in a promising direction.

Here is a side-by-side comparison:

| Aspect | Classical search and planning | LLM agents |
|---|---|---|
| Where actions and rules come from | Written by hand | Generated by the model from common sense |
| How the next step is chosen | The algorithm expands systematically | The model "thinks up" the most likely step |
| Is finding a solution guaranteed? | Yes, when conditions are met | No |
| Scope of use | Closed problems with clear rules | Open-ended, fuzzy everyday tasks |
| How errors are corrected | Backtrack to the previous fork | Observe tool results and rethink |

Researchers are also trying to combine the two. For example, in 2023 researchers proposed the "Tree of Thoughts" method, in which the model generates several lines of reasoning at once, evaluates which looks more promising, and backs up when necessary. In essence, it moves tree search into the model's thinking process. Another common approach has the model translate a natural-language task into a formal description and then hand it to a traditional planner to solve, letting each do what it does best. At the time of writing, these directions are still under active research, and results vary by task.

Once you understand this, some of an agent's everyday behavior makes sense. It sometimes takes detours because it is "guessing" rather than "calculating." On problems with strict rules, such as producing a class timetable that satisfies a dozen or more constraints, it may be less reliable than a dedicated solver. Giving it a clear goal and explicit constraints is like drawing the boundaries of its state graph for it, and this often greatly reduces wasted attempts.

## 8.3.5 Summary: Good Plans Come from "Narrowing the Field"

From mazes to scheduling, the core challenge of search and planning has always been the same: too many possibilities, too little time. A major thread of progress in artificial intelligence has been finding ever better ways to "try fewer things," from hand-designed heuristics, to hand-written action rules, to drawing on the common sense of large models to propose workable steps directly.

Still, every one of these methods assumes that the outcome of each action is certain and can be worked out in advance. In reality, a meeting invitation may be declined and a web page may fail to load. An agent needs to learn which approach works better from feedback on result after result. This ability to improve one's actions through trial and error is exactly what the next section covers: reinforcement learning.
