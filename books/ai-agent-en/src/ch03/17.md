# 3.3 Execution: Calling Tools, Writing Code, and Operating Software

Suppose the task you give an agent is: "Merge the thirty sales spreadsheets in this folder into one master table, calculate quarterly totals for each region, and then draw a bar chart." The planning covered in the previous section would break this down into a few steps: "read the files, merge, calculate, chart, save." But a plan on paper does not merge spreadsheets by itself. What actually makes things happen is execution: the agent has to open the files, run the calculations, generate the image, and put the results where you asked.

This is also the dividing line between a chatbot and an agent. The former gives you a passage of text saying "I suggest you do it this way"; the latter does it itself. This section explains what forms execution takes, how a model "reaches out its hand," and why execution must be constrained.

## 3.3.1 Three Common Ways of "Taking Action"

From an engineering perspective, agent execution takes roughly three forms, with difficulty and risk rising at each level.

| Execution method | Typical examples | Strengths | Limitations |
|---|---|---|---|
| Calling tools | Searching the web, checking the weather, reading and writing files, sending email | Clear structure, explicit parameters, easy to check | Can only do what the tools provide in advance |
| Writing and running code | Writing a Python program to merge spreadsheets and draw charts | Flexible; can perform almost any computation | Code may contain errors; running it requires an isolated environment |
| Operating software interfaces | Viewing screenshots, moving the mouse, clicking buttons, filling in forms | Can use legacy software and web pages that lack interfaces | Slow, prone to misclicks, breaks when the interface changes |

**Calling tools** is the most orderly. The system registers a set of tools in advance, each with a name, a description of its purpose, and a parameter format, such as "Read file: requires a file path." When the model needs one, it fills out a "request slip" in that format, and a program carries it out. This approach is usually called function calling; Chapters 4 and 6 cover its interface and internal mechanisms, respectively.

**Writing code** is a more general-purpose tool. Rather than preparing separate tools for "merge spreadsheets," "compute averages," and "draw a bar chart," you can give the agent a code interpreter, that is, a small environment that can run programs. The model writes a few lines of code, and the environment runs them and hands the output back. Many data-analysis assistants and coding agents take this approach. Faced with thirty sales spreadsheets, the agent's most likely move is exactly this: write one script that handles them all at once, rather than shuttling through the files one by one by hand.

**Operating software interfaces** is closest to how people work. The agent "sees" the screen through screenshots and then outputs actions such as "click at a certain coordinate" or "type a certain piece of text." At the time of writing, companies including Anthropic and OpenAI have publicly released this kind of "computer use" capability and labeled it in their release notes as a feature still being refined. Its value lies in handling systems that lack programmatic interfaces; the cost is reliability noticeably lower than the other two methods.

## 3.3.2 The Model Doesn't Act Directly

One common misunderstanding: a large language model never touches your files directly. The model does only one thing, which is generate text. Execution happens thanks to a division of labor:

1. The model outputs a piece of structured text, for example "call read_file, parameter path = sales/beijing.xlsx";
2. The orchestration program (Chapter 2, Section 2.5) recognizes this as an action request and checks its format and permissions;
3. The program actually performs it in the runtime environment and reads the file contents;
4. The result (successful data or an error message) is written back into the conversation and handed to the model for its next judgment.

Think of the model as a dispatcher sitting in a control room: it can only give orders over a walkie-talkie, while the workers and machines on site do the actual moving. This division is deliberate. Because every action passes through a program checkpoint, the system has a chance to intercept dangerous operations, record logs, and, when something goes wrong, report the error back to the model exactly as it occurred.

## 3.3.3 The Result of Execution Is New Information

Execution is not a one-shot deal. Every action brings back an "observation": what was read from the file, what the code printed, what the web page displayed, or what error occurred.

Back to the spreadsheet-merging example. The first time the agent runs its script, it may well hit an error like this: "Spreadsheet 17 has no column named 'Quarter'." On inspection, it turns out that spreadsheet labeled the column "Qtr." This error is not the end of the road but the basis for the next step. The agent revises its code to handle the variant column name and runs it again. This is what "take a step, look, take another step" means, and the reflection and error correction covered in the next section are built on exactly these observations brought back by execution.

This leads to a practical rule of thumb: **how well the execution stage is designed depends largely on whether the information it returns is clear.** A tool that replies only "failed" leaves the agent nowhere to start; a tool that returns the specific location and cause of the error lets it actually fix the problem.

## 3.3.4 Why Execution Must Be Constrained

The greater the ability to act, the higher the cost of mistakes. A wrong search at most yields an inaccurate answer; deleting the wrong file may be irreversible. Mature agent systems therefore typically place several constraints on execution:

- **Scope of capability**: expose only the tools the task requires; an agent that organizes spreadsheets does not need permission to send email;
- **Isolated environments**: code runs in a sandbox, so even if it writes a harmful command, it cannot reach the rest of the system;
- **Tiered confirmation**: read-only operations can run automatically, while irreversible ones such as deleting, paying, or sending externally pause and ask a person to confirm;
- **Keeping records**: every action and result is written to a log so it can be checked step by step afterward.

The details of these constraints are covered in Chapter 4, Section 4.4, and Chapter 7, Section 7.3. For now, remember one principle: **design execution capability and constraint mechanisms together.** Don't just ask "what can it do?" Also ask "what is it allowed to do, and what happens if it gets it wrong?"

## 3.3.5 Summary

Execution is the stage where an agent turns plans into reality, and it commonly takes three forms: calling tools, writing code, and operating interfaces. The model is responsible only for "stating" the action; the orchestration program and runtime environment actually carry it out and send the result back to the model as a new observation. Precisely because every step produces new information, the agent has the chance to discover its own mistakes. The next section looks at how it uses that information to check results, correct errors, and try again.
