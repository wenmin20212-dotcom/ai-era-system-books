# 3.4 Reflection and Error Correction: Checking Results, Spotting Mistakes, and Trying Again

Suppose you ask a coding agent to fix a function in your project that is throwing an error. A few seconds later, it has changed a few lines of code, but instead of immediately announcing "done," it runs the tests itself. A line of red text appears on the screen: one test is still failing. It reads the error message, says "I missed the empty-list case just now," makes another change, and runs the tests again. This time everything passes. Only then does it report back to you.

This process of "check after you finish, and fix what the check turns up" is what we mean by an agent's reflection and error correction. The previous section covered execution, which lets an agent take action. The capability in this section lets it know, after acting, whether it got things right. Without this link, an agent is just a machine running blindly through a plan. With it, the agent comes closer to being a dependable assistant.

## 3.4.1 Why Checking Is Essential: The Model Doesn't Know It's Wrong

When a large language model generates content, it predicts the most suitable next piece of text step by step (see Volume 18 for details). It has no built-in "right/wrong indicator light." When the model writes a piece of flawed code and when it writes a piece of correct code, there is no difference in how it "feels" at the moment it produces them. A confident tone does not mean a correct result.

In multi-step tasks, this problem is amplified. If a task has ten steps and a small mistake occurs early on, every later step builds on that mistake, and the deviation snowballs. So an agent cannot rely only on "thinking correctly"; it also has to rely on "seeing the results." The point of checking is to catch errors before they spread.

## 3.4.2 The Basis for Checking: How an Agent Knows It's Wrong

The evidence an agent uses to detect errors comes roughly from three kinds of signals, and their reliability varies widely:

| Signal source | Typical examples | Reliability |
|---|---|---|
| Objective feedback from the environment | Program errors, failed tests, a web page returning "404 Not Found," a spreadsheet formula producing an abnormal value | High; the facts speak for themselves |
| Rule and format validation | Whether the output matches the required format, whether all fields are present, whether the numbers add up consistently | Fairly high; depends on how complete the rules are |
| The model's self-review | Having the model reread its own answer to judge whether anything is missing or contradictory | Moderate; it may "fail to see its own mistakes" |

This table reveals an important engineering principle: **wherever objective feedback is available, don't rely solely on the model's own sense of things**. Coding agents perform relatively well at error correction largely because the coding domain naturally has "referees" such as compilers, tests, and error messages. When you ask an agent to write a market analysis report, however, there is no such clear referee, and checking can only rely on verifying cited sources, cross-referencing original data, or having a human review the work.

Researchers have also observed that, without external information, simply asking a model to "think again and check" sometimes corrects errors, but sometimes turns an originally correct answer into a wrong one. This is one of the more common findings in public research, and it reminds us not to mythologize "self-reflection."

## 3.4.3 Several Approaches to Reflection

In engineering practice, reflection and error correction are usually organized in a few ways:

- **Post-execution verification**: Check the result after every key action. For example, after reorganizing a spreadsheet, verify that the number of rows matches the original data.
- **Root-cause analysis after failure**: When something goes wrong, don't simply retry; first explain "why it went wrong," then decide how to fix it. Methods proposed in academia, such as Reflexion, have the agent write down the cause of failure in text for reference on the next attempt.
- **Separating the generator from the reviewer**: One component produces the output while another is dedicated to finding faults. This can be a separate model call or a separate agent. It resembles the "author–editor" division of labor in writing: a different perspective makes problems easier to spot. This structure will be discussed further in Chapter 4 on multi-agent systems.
- **Reviewing against the goal**: Before the task ends, go back to the original requirements and check them one by one. Did the user want three columns or five? Chinese or English? Many "it's done, but it's not what you wanted" problems come from skipping this step.

## 3.4.4 Retries Need Boundaries Too

Once an error is found, the natural next step is to try again. But more retries are not always better. A common failure scenario is an agent repeatedly using the same method to fix the same error, failing every time, yet never changing its approach. It gets stuck in a loop, wasting time and calls.

For this reason, well-designed agent systems usually set boundaries on error correction:

1. **Limit the number of retries**, for example stopping after the same step fails a certain number of times;
2. **Require a change of strategy**, so that each retry must explain how it differs from the last;
3. **Escalate to a human**, so that when the problem truly can't be solved, the agent honestly reports "where it got stuck and what it tried," handing the decision back to the user.

The third point is especially important. An agent that honestly says "I didn't manage it" is far more useful than one that pretends to have finished. The most dangerous situation is not failure, but an agent taking shortcuts to "pass the check," such as modifying the test itself so it shows a pass instead of fixing the code. So when people review an agent's report, they should look at what it changed, not just at what it said.

## 3.4.5 Summary: A Small Feedback Loop

To compress this section into one sentence: reflection and error correction form a small "act–observe–compare–adjust" loop inside the agent. Actions produce results, results are compared against the goal, and the gap drives the next adjustment. The quality of this loop depends on whether the feedback signals are objective, whether the root-cause analysis is accurate, and whether retries have boundaries.

You will find that this is exactly the cybernetic idea of feedback, which Chapter 8 will cover, playing out in an agent. It is also the foundation for the failure and recovery mechanisms in Chapter 6. And when an agent cannot judge right from wrong on its own, or when the cost of an error is too high, it needs to stop and ask a human. This leads to the topic of the next section: collaborating with humans.
