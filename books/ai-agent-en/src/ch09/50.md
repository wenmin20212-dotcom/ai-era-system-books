# 9.1 Using an Agent to Dissect an Agent: Reading Every Step of Its Log

Suppose you ask a coding agent to fix a bug where dates turn into garbled text when a spreadsheet is exported. A few minutes later it reports "Fixed." In the interface there is a long, expandable record with line after line of entries such as "Read file," "Run command," "Modify line 42," and "Rerun tests." Most people skip right past it. The point of this section is that this record is the on-the-ground evidence for everything in the first eight chapters of this book. Once you can read it, the agent stops being a black box you judge only by its results and becomes a machine you can inspect step by step.

## 9.1.1 What's in a Record: The Basic Components of a Trajectory

In engineering practice, the complete process an agent goes through for a single task is usually called a **trajectory**, and the saved text is called a **log** or a **trace**. Different products present it differently. Some collapse it into small "Thinking…" text, some lay it out as a timeline, and development frameworks often export it as structured files. Taken apart, though, the basic components are much the same:

| Entry in the record | Corresponding system component | Related sections of this book |
|---|---|---|
| User goal, system prompt | Instructions | 2.2 |
| The model's reasoning or planning text | Brain, planning | 2.1, 3.2, 6.2 |
| Tool call (name + parameters) | Hands, function calling | 2.3, 6.3 |
| Tool result | Perception, message flow | 3.1, 5.2 |
| Request for confirmation, waiting for the user | Human–AI collaboration, permissions | 3.5, 4.4 |
| Context summary, "Compacted" | Memory management | 6.4 |
| Token count, elapsed time | Cost flow | 5.5 |

With this table in hand, you can find where every line of that long record sits on the skeleton. The first step in reading a record is exactly this kind of sorting: label each line as "thinking," "doing," or "seeing." String them together and you'll find it is almost exactly the reason–act loop described in Chapter 6.

## 9.1.2 Let Another AI Be Your "Commentator"

Records tend to be long, full of command-line output, error stack traces, and code snippets, which makes them hard going for beginners. This is where a conversational AI can help, in other words, using an agent to learn about agents. In practice, you copy the record out, first remove sensitive content such as passwords, keys, and customer information (see Section 5.4 for why), and then ask questions in this order:

1. **Segment**: "Please split this record into rounds following the reason–act–observe loop, and summarize each round in one sentence."
2. **Locate**: "Which round is the turning point? At which step did the agent discover the real cause?"
3. **Question**: "Are there any redundant steps, repeated attempts, or places where it drew conclusions without verification?"
4. **Compare**: "If it had instead listed a complete plan first and then executed it, how would this trajectory differ?"

Keep in mind that the commentator is also a model, and it too may misread the record or invent details that aren't there. So have it note which line supports each conclusion, and check the original yourself. Doing this is itself an exercise in the "reflection and error correction" covered in Section 3.4, except that the checker is now you.

## 9.1.3 Spotting Common Problems in a Record

After reading enough records, you'll start recognizing the failure modes discussed in Section 6.5. Each leaves fairly distinctive traces:

- **Getting stuck**: The same command appears again and again with nearly identical parameters and the same error, while the planning text just rephrases itself.
- **Drifting off course**: Partway through, it starts modifying files unrelated to the goal, or expands "fix the date format" into "refactor the whole module."
- **Declaring completion without verification**: After the last modification it neither runs the tests nor rereads the output, and simply writes "Fixed."
- **Being led astray by external content**: After reading a web page or document, the plan suddenly changes direction and it starts doing things the user never asked for. This is a possible sign of the prompt injection described in Section 7.5.
- **Losing context**: After a "Compacted" or "Summary" entry, the agent forgets constraints the user stated earlier, such as "don't change the interface."

Being able to point out these traces means you are checking the process as well as the result. For workplace users this matters especially: the result may happen to be correct, but overreach or luck in the process could turn into an incident next time.

## 9.1.4 Why Records Deserve to Be Taken Seriously

In principle, the record corresponds to **observability** in the cybernetics of Chapter 8: a system's internal state must be visible from the outside before it can be regulated and corrected. An agent's decisions come from a probabilistic model, so running the same task twice may produce different trajectories (see Section 8.5). That means a single result cannot tell you whether the agent is reliable; you have to look at the process. This is why many teams save trajectories for evaluation and auditing (see Sections 7.4 and 7.5). A complete record can serve at once as learning material, a basis for debugging, and evidence for accountability.

Records do have limitations, of course. The reasoning text shown in the interface may not fully reflect the model's actual internal computation, and some products display only a summary. Book 18 in this series, *Large Language Models*, discusses this in more depth. So when judging what an agent actually did, rely on the tool calls and their results, and treat the reasoning text as a reference only.
