# 8.3 Graph Theory and Routing Algorithms: Shortest Paths and Distance Vectors

Open a map app on your phone, enter a destination, and the software returns the "fastest route" almost instantly. It does not try every possible way of getting there one by one. Instead, it treats the city as a "graph" made of intersections and roads, then uses an algorithm to pick out the route with the lowest cost. Routers on the internet do the same thing every day: they treat thousands upon thousands of routers and the links between them as a graph, and work out which direction a data packet should travel. Chapter 3 explained how routers "look up a table and forward," and Chapter 5 described how routing protocols exchange "maps." This section digs one layer deeper to look at the mathematics behind that table: graph theory and two classic families of routing algorithms.

## 8.3.1 Drawing the Network as a Graph

A "graph" in graph theory is not a picture. It is an abstract structure with only two kinds of elements:

- **Node (also called a Vertex)**: a router in the network, or an entire autonomous system;
- **Edge**: a link connecting two nodes, such as a fiber-optic cable or a leased line.

Each edge can carry a number called its **weight** or **cost**, which represents how much "expense" it takes to traverse that edge. Network administrators decide how cost is defined. Common bases include:

| Basis for cost | Meaning | Typical use |
|---|---|---|
| Hop count | Each router passed through counts as 1 | The early RIP protocol |
| Bandwidth | The higher the bandwidth, the lower the cost | The usual default approach in OSPF |
| Latency | The slower the link, the higher the cost | Some networks set cost from measured latency |
| Administrative policy | Manually raised or lowered | Steering traffic away from an expensive line |

With such a weighted graph, "finding a route" becomes a clearly defined mathematical problem: **from the starting point to the destination, which path has the smallest sum of edge costs?** This is the **Shortest Path Problem**. Here "shortest" does not necessarily mean the shortest physical distance. It means the lowest total cost.

A small example: home router A needs to send data to D. A–B costs 1, B–D costs 5, A–C costs 2, and C–D costs 1. Going through B might seem fine at first glance, but its total cost is 6. Going through C costs only 3. The job of an algorithm is to reach conclusions like this reliably and quickly in large-scale networks.

## 8.3.2 Link State: Everyone Holds the Full Map and Computes Independently

The first approach is called **Link State**. It works in three steps:

1. Each router first discovers which neighbors it has and what each link costs;
2. It broadcasts this "self-introduction" to every router in the network, a process called **flooding**;
3. Once each router has collected everyone's introductions, it assembles a complete map of the whole network internally, then independently computes the shortest path to every destination.

The third step uses the algorithm published in 1959 by computer scientist **Edsger W. Dijkstra**, usually called **Dijkstra's algorithm**. Its logic can be compared to ripples spreading on water. Starting from the origin, it first settles the node closest to itself. Then, building on the nodes already settled, it advances outward ring by ring. Each time, it picks the unsettled node with the lowest currently known total cost, fixes that node's shortest path, and uses it to update its neighbors' estimates. Once every node has been settled, a "shortest path tree" rooted at the router itself is complete.

Representative protocols using this approach are **OSPF (Open Shortest Path First)** and **IS-IS (Intermediate System to Intermediate System)**. They are mostly used inside a single carrier's or enterprise's network. The advantage is that every router "has the whole picture in mind." When a link fails, the news floods quickly, everyone recomputes, and the network converges relatively fast. The cost is that every router must store the full map and run the algorithm, so the larger the network, the heavier the memory and computing load. Large networks therefore usually divide themselves internally into several **areas**. Each area knows its own details, and areas exchange only summarized information with one another.

## 8.3.3 Distance Vector: Listening Only to Neighbors, Passing Word Along

The second approach is called **Distance Vector**, and its style is entirely different. A router needs no full map. It needs to know only one thing: **how far each of my neighbors says it is from each destination.**

Each router maintains a table listing "the distance to each destination, and which neighbor to hand traffic to," and periodically tells its neighbors about this table. When it receives a neighbor's table, it does a simple addition:

> Cost to reach destination D via neighbor X = my cost to reach X + the cost X claims it takes to reach D

For each destination, it picks the neighbor with the smallest sum as the next hop. The mathematics behind this is the **Bellman-Ford algorithm**, named after Richard Bellman and Lester Ford Jr. It is like asking for directions in an unfamiliar city. You don't look at a map. You simply ask the people near you, "How many stops to the train station?", add the distance it takes you to reach each of them, and follow whichever one is closest.

The representative protocol is **RIP (Routing Information Protocol)**. It uses hop count as its cost and sets the maximum hop count at 15, with 16 treated as "unreachable." It is therefore suited only to small networks (see RFC 2453).

The strength of distance vector is that it is simple and places a light load on each device. Its weakness is that information travels one layer at a time, so bad news spreads slowly. The classic flaw is called **Count to Infinity**. When a link fails, A believes B can still reach the destination, and B believes A can. Each cites the other's stale information, and the distance figure climbs round after round while neither admits that the destination is "unreachable." RIP defines 16 as "infinity" precisely to put a ceiling on this process. There are also remedies such as **Split Horizon**: a route learned from a particular neighbor is never advertised back to that same neighbor.

## 8.3.4 Comparing the Two Approaches, and Where BGP Fits

| Comparison | Link State | Distance Vector |
|---|---|---|
| Information held | Full network topology | Distances reported by neighbors |
| Core algorithm | Dijkstra | Bellman-Ford |
| Representative protocols | OSPF, IS-IS | RIP |
| Convergence speed | Faster | Slower; count to infinity may occur |
| Resource overhead | More storage and computation | Less |
| Typical scenario | Medium to large networks inside a carrier or enterprise | Small networks |

So which category does **BGP (Border Gateway Protocol)**, which connects autonomous systems, belong to? It is often called a **Path Vector** protocol and can be seen as an improved version of distance vector. When it advertises a route, it says not only "how far," but also attaches the complete list of autonomous systems the route passes through. If a router sees its own number in that list, it knows a loop has formed and discards the route outright, which avoids count to infinity at the root. More importantly, BGP chooses routes mainly on the basis of business relationships and administrative policy, not simply the shortest path, as Section 6.3 explained. This shows that while mathematics supplies the "optimum," engineering still has to answer to reality.

## 8.3.5 Summary: Algorithms Determine How the Network "Thinks"

Given the same graph, link state makes each router an "all-knowing calculator," distance vector makes them "neighbors passing word to one another," and path vector attaches a complete travel record to the word being passed. The internet keeps finding routes even as nodes come and go and links drop in and out, and it does so thanks to these algorithms grown from graph theory. Internal networks mostly use link state for speed and accuracy, while connections between networks use path vector for stability and policy.

Finding a route, however, solves only the question of "how to connect." The next section turns to a different question: once networks are connected, why does their value grow as the number of nodes increases? That is where we will discuss Metcalfe's Law and network effects.
