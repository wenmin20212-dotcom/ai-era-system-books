# 4.3 Client–Server, Peer-to-Peer, and Edge Computing

Open a video app on your phone, tap on a series, and within seconds it starts playing. Video-call a friend, and their face appears on your screen almost in sync. On your computer, a download tool pulls an open-source system image; the speed rises and falls, and the interface shows "connected to several peers." All three happen over the internet, but the relationships behind them (who talks to whom, and who provides the content) are not the same. The previous section looked at how carriers interconnect. This section takes a different angle: from the application's point of view, how are the two communicating parties organized? There are three common arrangements: client-server, peer-to-peer, and edge computing, which moves servers closer to users.

## 4.3.1 Client-Server: One Side Asks, the Other Answers

The most common relationship is the client-server model (C/S). Browsers and mobile apps are clients: they send requests. The machines behind a website are servers: they wait for requests and send back responses. When you open a web page, your browser sends an HTTP request to the server, and the server returns the page's content. The two roles stay the same from start to finish.

Think of a restaurant. Customers order, the kitchen cooks, and the kitchen never phones a customer on its own initiative. This division of labor brings several engineering advantages:

- **Centralized management**: Data and programs live on the server. Fix a bug or change a feature once, and every user gets it at the same time.
- **Stable addresses**: A server has a fixed domain name and a public address, so clients can always find it. Clients, by contrast, can sit behind the network address translation (NAT) of a home router, because nobody needs to find them.
- **Easy control and billing**: Logins, permissions, and payments are all handled in one place on the server side.

The drawback is just as obvious: every request lands on the server side. As users multiply, the server's computing power and outbound bandwidth become bottlenecks, and if the server fails, nobody can use the service. That is why large websites never rely on a single machine. They run clusters of hundreds or thousands of servers, with load balancers in front to spread the requests. From the client's point of view, though, it is still talking to "one service," and the basic nature of the relationship has not changed.

## 4.3.2 Peer-to-Peer: Everyone Is Both Customer and Cook

Another relationship is peer-to-peer (P2P). The participants are called peers, and each one both requests data from others and supplies data it already has to others.

BitTorrent is the most frequently cited example in public sources. A large file is split into many small pieces. A downloader fetches different pieces from several peers while uploading the pieces it already has to others. The more people download, the more sources there are to share from. The system's overall capacity grows with the number of participants, instead of getting more crowded the way a single server does.

P2P has its own difficulties:

| Problem | Cause | Common approach |
|---|---|---|
| How to find other peers | No central directory | Use a "tracker" server or a distributed hash table (DHT) to record who has which data |
| Home devices are hard to reach directly | Most sit behind NAT with no public address | "Hole punching"; when that fails, relay traffic through a server |
| Peers can go offline at any time | Users shut down or disconnect | Store copies of the data across multiple peers |
| Trustworthiness of content | Anyone can supply data | Verify every piece and discard any that has been tampered with |

As a result, pure P2P is rare. Most real systems are hybrids: servers handle "finding people" and authentication, and peer-to-peer connections carry the heavy data traffic. Video calling is a typical case. WebRTC (Web Real-Time Communication), a browser technology standardized jointly by the W3C and the IETF, first uses a server to exchange each side's connection information. It then tries to have the two devices send audio and video to each other directly, and only falls back to a relay server when a direct connection cannot be made. Direct connections avoid detours, which lowers latency and also saves the service provider bandwidth.

## 4.3.3 Edge Computing: Moving the Server Into Your Neighborhood

The client-server model also runs into a physical limit it cannot avoid: distance. Light travels roughly 200,000 kilometers per second in optical fiber, so a single round trip between continents takes over a hundred milliseconds, before any queuing or processing time. That delay is tolerable for web pages but too long for cloud gaming, real-time interaction, or industrial control.

The idea behind edge computing is not to concentrate all computation in a few large data centers. Instead, some servers are placed at the "network edge," such as city-level facilities, carriers' aggregation points, or even sites near cell towers. A request can then be handled a few dozen kilometers from the user rather than thousands.

The content delivery networks (CDNs) introduced in Chapter 2 can be seen as an early form of the edge idea: they cache static content at the edge first. Today, some cloud providers and CDN vendors (as of this writing) go further and let developers run small programs directly on edge nodes for tasks such as authentication and content rewriting. The telecommunications industry is also promoting Multi-access Edge Computing (MEC), with frameworks developed by organizations such as the European Telecommunications Standards Institute (ETSI), to place computing resources inside mobile networks. This topic is closely tied to mobile communications and will be covered in more depth in the *Mobile Communications* and *Data Centers* volumes of this series.

It is worth stressing that edge computing does not overturn the client-server relationship. The client still sends requests and the server still answers them. The only change is where the server is located.

## 4.3.4 The Three Relationships Side by Side

| Dimension | Client-server | Peer-to-peer | Edge computing |
|---|---|---|---|
| Who provides the service | Central servers | All participants | Edge servers close to users |
| How it scales | Add servers | More participants means more capacity | Add edge nodes |
| Main advantages | Easy to manage and control | Saves central bandwidth; no single point of failure | Low latency; less load on the backbone |
| Main difficulties | Heavy load on the center | Finding peers, traversing NAT, trustworthiness | Many scattered nodes; complex operations |
| Typical uses | Web, email, online shopping | File distribution, direct video-call connections | Cloud gaming, real-time interaction, CDNs |

Back to the three scenes from the start. Streaming a series is mainly client-server, plus edge caching. A video call is "the server makes the introduction, then peer-to-peer carries the traffic." Downloading an open-source image may genuinely use P2P. Nearly every real application mixes all three relationships, combining them according to its needs for latency, cost, and control.

These arrangements can be combined freely because the internet itself only delivers packets from one end to the other; it does not dictate who must be the server. As for who assigns network addresses and domain names and who sets protocol standards, that is the question the next section, "Internet Governance," will answer.
