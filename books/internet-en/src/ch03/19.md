# 3.5 Application Services: Web, Email, Instant Messaging, and Video

Before heading out in the morning, you may have done all of this within a few minutes: checked the weather in your browser, replied to a work email in your inbox, sent a photo to your family in a chat app, and then scrolled through a few short videos on the subway. All four tasks used the same phone and the same network, yet each of them "speaks" in its own way. The addressing, naming, routing, and reliable transport covered in the previous sections all exist to deliver data to the right place; what actually makes you feel that you are "online" are the application services running on top of these basic functions. This section looks at how the web, email, instant messaging, and video each make use of this underlying infrastructure.

## 3.5.1 The Web: Question and Answer with HTTP

When you type a URL into the address bar and press Enter, what the browser does can be summed up as "ask the server a question and wait for its answer." The rules for this exchange are called the HyperText Transfer Protocol (HTTP). A typical request roughly says, "Please give me the page at such-and-such a path"; the server's answer carries a status code and the page content. The "404" you may have seen is the status code a server returns to say "this page cannot be found."

Today's web pages are rarely just a single file. A news homepage often needs dozens or even more than a hundred resources: the page skeleton (HTML), style sheets (CSS), scripts (JavaScript), images, and fonts. After the browser receives the skeleton, it sends further requests based on the references inside it, and finally assembles everything into the view you see. To protect what is being transmitted, websites now commonly use HTTPS, which wraps HTTP inside an encrypted TLS connection; the small padlock icon in many browsers' address bars indicates exactly this. The TLS handshake process is covered in detail in Chapter 6.

HTTP itself keeps evolving. The table below gives a brief comparison of three generations; the details are explored in Chapter 7:

| Version | Underlying transport | Main features |
|---|---|---|
| HTTP/1.1 | TCP | Text format; requests on a single connection largely have to wait in line |
| HTTP/2 | TCP | Binary framing; multiple requests can run simultaneously on one connection |
| HTTP/3 | QUIC (based on UDP) | Less waiting during connection setup; when packets are lost, requests don't hold each other back |

However the versions change, the basic pattern of "the client requests, the server responds" has never changed.

## 3.5.2 Email: "Store and Forward," Like Sending a Letter

Email is even older than the web, and its design closely resembles the postal system. When you click "Send," the message does not fly straight into the other person's phone. Instead, it is first handed to the outgoing mail server of your email provider, which then passes it on, using the Simple Mail Transfer Protocol (SMTP), to the server of the recipient's email provider, where it is stored in the recipient's "mailbox." Only when the recipient opens their client does the client fetch the message using IMAP (Internet Message Access Protocol) or the older POP3 (Post Office Protocol 3).

Two details here are worth noting:

- **How does the outgoing mail server know where the recipient's mailbox is?** Through the Domain Name System. Each mail domain can register a special MX (Mail Exchange) record that specifies "mail sent to this domain should be handed to this server." The DNS covered in the previous section comes into play once again here.
- **Why is email allowed to be "a bit slow"?** Because it uses store and forward: when the recipient's server is temporarily unreachable, the outgoing server holds on to the message and retries after a while. So email does not aim for real-time delivery; it aims for "eventual delivery."

Many people now send and receive email through web pages or mobile apps, which on the surface use HTTPS, but mail transfer between providers is still based on SMTP.

## 3.5.3 Instant Messaging: Long-Lived Connections That Stay "Open"

Instant messaging apps such as WeChat, QQ, and Telegram need to achieve "the moment they send it, you receive it." The difficulty is that your phone usually sits behind a home router or a carrier's address translation equipment, so servers on the outside cannot reach it whenever they like. A common solution is for the phone itself to establish a long-lived connection to the server and periodically send a tiny bit of "heartbeat" data, so that the connection and the address translation records along the way are not cleared. When a new message arrives, the server pushes it down along this already-open connection.

Instant messaging software from different companies mostly uses its own proprietary protocols, and the specific methods are neither public nor unified. On the open-standards side, there is XMPP (Extensible Messaging and Presence Protocol), among others, which some systems have used in the past. Voice and video calls are more sensitive to latency; they commonly carry real-time media over UDP and may try to let the two devices communicate directly, falling back to relaying through a server when a direct connection cannot be established. This trade-off between "peer-to-peer" and "relay" is discussed again in Chapter 4.

In addition, to save battery, mobile operating systems usually do not allow every app to keep its own connection open. Both Apple's and Google's mobile operating systems provide a unified push channel, in which the system maintains a single connection and receives notifications on behalf of all apps. This is common practice among mainstream mobile operating systems at the time of writing.

## 3.5.4 Video: Cut into Small Pieces, Chosen on Demand

Video is one of the largest categories of internet traffic today, and public industry reports often describe it as "the lion's share." Online on-demand video (such as watching shows or short videos) is usually not downloaded as a complete file in one go. Instead, the video is cut into small segments a few seconds long each, and the same content is prepared in multiple quality levels—high, medium, and low. While playing, the player estimates the current network speed and then decides which quality level to request for the next segment. This approach is called Adaptive Bitrate Streaming; common standard solutions include HLS (HTTP Live Streaming, proposed by Apple) and MPEG-DASH (developed by the International Organization for Standardization). When you see the picture suddenly turn blurry on the subway and then gradually sharpen again, that is the player adjusting quality according to network conditions.

These segments are essentially just ordinary HTTP files, so they can be cached on content delivery network nodes very close to you—this is precisely the point of the CDN mentioned in Chapter 2. Live streaming has stricter latency requirements, so it shortens segment lengths as much as possible or adopts dedicated low-latency transport methods.

## 3.5.5 Summary: One Network, Four "Personalities"

Placing the four kinds of applications side by side makes the differences clear:

| Application | What it cares about most | Typical approach |
|---|---|---|
| Web | Fast loading, complete content | HTTP request-response, encrypted transport |
| Email | Eventual delivery | SMTP store and forward, DNS MX records |
| Instant messaging | Real-time arrival | Long-lived connection plus heartbeat, server push |
| Video | Smooth playback | Segmentation, multiple quality levels, nearby caching |

They share the same set of addressing, naming, routing, and transport capabilities, and simply combine these capabilities at the top layer according to their own needs. This also reflects an important idea in internet design: the network itself is only responsible for making a best effort to deliver data, while how that data becomes a web page, an email, or a video is left for the applications at the two ends to decide. This division of labor is exactly the subject of the next chapter, "Layered Models."
