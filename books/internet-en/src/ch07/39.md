# 7.2 QUIC and HTTP/3: Making the Web Faster

You scroll through your phone on the subway while the signal comes and goes. You walk from your home down to the street, and your phone switches from Wi-Fi to the cellular network. At moments like these, you may notice that video in some apps stalls briefly before resuming, while in others you barely notice anything. Part of the difference lies in the transport protocol. As earlier chapters explained, the web has long relied on the combination of TCP plus TLS plus HTTP for transport. QUIC and HTTP/3 replace the foundation of that combination, with the goal of making the web faster and network switches smoother. This section explains what problems they solve and how they solve them.

## 7.2.1 Three Sources of "Slowness" in the Old Stack

Recall Chapter 6: to open an HTTPS web page, the browser first performs a TCP three-way handshake with the server, then a TLS handshake to negotiate keys, and only then can it send the first HTTP request. This approach has three problems.

1. **Too many handshake round trips.** The TCP handshake costs one round-trip time (RTT). TLS 1.2 adds two more round trips; TLS 1.3 reduces that to one. If the server is across an ocean, a single round trip is often on the order of one or two hundred milliseconds. Stack several of them together and the user can feel the wait.
2. **Head-of-line blocking.** HTTP/2 allows multiple files, such as images, scripts, and stylesheets, to be transferred simultaneously over a single TCP connection, with each file traveling on its own "stream." But TCP recognizes only a single ordered byte stream. If any one packet is lost, all subsequent data must wait for it to be retransmitted, even if that later data belongs to other files and has already arrived. It is like a car breaking down on a single-lane road: every car behind it has to stop.
3. **Connections are tied to addresses.** A TCP connection is identified by four values: source IP, source port, destination IP, and destination port. When a phone switches from Wi-Fi to cellular, its IP address changes, the old connection becomes invalid, and a new handshake is required.

These problems are hard to fix inside TCP itself. TCP is implemented in the operating system kernel, and the network is full of firewalls and NAT devices that recognize TCP's old format. Any change to the packet format risks having packets dropped by these middleboxes, a phenomenon known as protocol "ossification."

## 7.2.2 QUIC: Rebuilding the Transport Layer on Top of UDP

QUIC was originally designed by Google and trialed in the company's own browser and services. It was later handed over to the Internet Engineering Task Force (IETF) for standardization and published in 2021 as RFC 9000 and a set of related documents. In the standard, its name is no longer an acronym; it is simply QUIC.

QUIC's approach is to carry its data inside UDP datagrams. UDP (User Datagram Protocol) is very simple: it only handles delivery and guarantees neither ordering nor reliability. Most middleboxes let UDP through, so QUIC can be deployed directly on most networks without modifying existing equipment. QUIC reimplements reliable delivery, congestion control, and encryption on its own on top of UDP, and it usually runs inside the application rather than in the kernel. This way, when browsers and servers update their software, the protocol can improve along with them, without waiting for operating system upgrades.

The table below compares QUIC's design against the three problems above:

| Problem | Old stack (TCP+TLS+HTTP/2) | QUIC + HTTP/3 |
|---|---|---|
| Connection handshake | 1 round trip for TCP + 1–2 round trips for TLS | Transport and encryption combined; about 1 round trip for a first connection; 0-RTT can be attempted for previously visited servers |
| Effect of packet loss | One lost packet makes every stream wait | Each stream is ordered independently; a loss affects only the stream it belongs to |
| Switching networks | An IP change breaks the connection; reconnection required | Connections are identified by a connection ID and can migrate to a new address |
| Encryption | TLS sits on top of TCP; header information is in plaintext | TLS 1.3 built in; most header fields are also encrypted |

## 7.2.3 Three Key Mechanisms

**Combined handshake.** QUIC builds TLS 1.3 key negotiation directly into its own handshake (RFC 9001), settling transport parameters and cryptographic parameters in one pass. If the browser has visited the server before, it can use information saved from the previous session to include request data in the very first packet. This is called 0-RTT. 0-RTT comes at a cost: this early data could be intercepted and resent by someone else (a replay), so the standard recommends using it only for requests that are harmless if executed more than once, such as ordinary page reads.

**Independent streams.** QUIC natively supports multiple streams within a single connection, each with its own number and its own ordering. If a packet carrying an image is lost, only that image's stream has to wait for the retransmission; scripts and text being transferred at the same time are delivered to the browser as usual. The single-lane road from before has become a multi-lane highway.

**Connection migration.** Every QUIC connection has a connection ID. When a phone switches networks and its IP changes, as long as the connection ID in the packets stays the same, the server knows it is still the same client. After address validation, both sides can continue transferring data without a new handshake.

## 7.2.4 HTTP/3: HTTP Running on QUIC

Semantically, HTTP/3 (RFC 9114) is the same as HTTP/1.1 and HTTP/2: request methods, status codes, headers, and so on are unchanged. The difference is that it hands multiplexing over to QUIC's streams and no longer manages it itself. HTTP/2's original header compression algorithm depended on strict ordering, which would reintroduce blocking in an environment where streams are independent of each other, so HTTP/3 comes with a separate compression scheme called QPACK (RFC 9204).

How does a browser know that a website supports HTTP/3? A common approach is for the browser to first connect over HTTP/2, and the server uses the Alt-Svc header in its response to tell the browser "I also have HTTP/3 available." On its next visit, the browser switches to QUIC. Another approach is to announce support in advance in a DNS HTTPS record. If UDP is blocked on a given network, the browser falls back to TCP, so users generally don't notice any of this.

At the time of writing, major browsers and large content delivery networks widely support HTTP/3. Public measurement data shows that it already accounts for a substantial share of global web traffic, though the exact figure varies considerably depending on the measurement method.

## 7.2.5 Benefits and Costs

QUIC's benefits show up mainly in scenarios with high latency, frequent packet loss, and frequent network switching, such as mobile networks and intercontinental access. On stable wired networks, the difference between it and TCP is often negligible.

It has costs as well. Because encryption, sending, and receiving happen in user space, server CPU overhead is usually higher than with TCP, which has benefited from years of optimization inside the kernel. In addition, since most of each packet is encrypted, network operators find it hard to capture and analyze traffic in the middle of the path the way they used to—one of the measurement challenges discussed in Section 7.5. Some enterprise networks also block UDP port 443 for management reasons.

You can open your browser's developer tools and show the "Protocol" column in the Network panel to see which resources are loaded over h3. QUIC demonstrates something important: even with TCP itself left unchanged, the transport layer can be rebuilt between endpoints, allowing the whole stack to keep evolving. Content delivery networks, the subject of the next section, are one of the main forces bringing HTTP/3 close to you.
