# 6.1 虚拟化与容器：一台机器当多台用

在云服务商的控制台上点几下，一两分钟后你就“拥有”了一台云服务器：有自己的操作系统、IP 地址和硬盘空间，可以远程登录、安装软件。可是，并没有人为你搬一台新机器进机房。第二章里那台插在机柜里的服务器，此刻很可能同时“扮演”着几十台互不相识的机器，其中一台归你。你上传的那张照片，处理它的程序多半也运行在这样一台被“切开”的服务器里，可能只占用其中很小的一角。

本节解释这种“一台机器当多台用”的机制：虚拟化（Virtualization）与容器（Container）。

## 6.1.1 为什么要把一台机器“切开”

早年的企业机房常常“一个应用一台服务器”：邮件一台，财务系统一台，网站又一台。这样做简单，彼此也不打扰，但浪费很大。多数业务大部分时间都闲着，业界公开资料中常见的说法是，传统物理服务器的平均利用率往往只有百分之十几甚至更低。

联系第五章讲过的电力流就能明白这笔账：服务器闲着也要耗电，按经验约为满载功耗的三到六成，耗掉的电最终都变成要被空调搬走的热。机器越多，占用的机柜、电力和冷却容量也越多。把多个业务合并到一台机器上，让它“忙起来”，是提高数据中心整体效率最直接的办法。

难点在于“合住”的业务不能互相干扰。一个程序崩溃不能拖垮邻居，A 公司也不能看到 B 公司的数据。虚拟化和容器解决的，正是共享与隔离如何兼顾的问题。

## 6.1.2 虚拟机：在硬件上“模拟”出多台完整的电脑

虚拟化的核心部件叫虚拟机监视器（Hypervisor），也称虚拟化管理程序。它运行在物理服务器上，把 CPU、内存、硬盘、网卡等真实硬件切分成若干份，再“包装”成一台台虚拟机（Virtual Machine，VM）。每台虚拟机都以为自己独占一台完整的电脑，可以装自己的操作系统，比如一台装 Linux，另一台装 Windows。

可以用公寓楼来类比：

- 物理服务器是整栋楼；
- Hypervisor 是物业，负责分配水电、管理门禁；
- 每台虚拟机是一套带独立厨房和卫生间的公寓，住户关上门就自成一体。

现代 CPU 一般带有硬件虚拟化支持，例如英特尔的 VT-x 和 AMD 的 AMD-V，所以虚拟机的性能损耗已经比早年小得多。常见的 Hypervisor 有开源的 KVM、Xen，以及 VMware 的 ESXi 等商业产品（写作时的情况）。云服务商卖给你的“云服务器”，大多就是这样一台虚拟机。

虚拟机还有一个特性对运维很重要：它本质上是一组文件和运行状态，可以“搬家”。在线迁移（Live Migration）技术能把正在运行的虚拟机从一台物理机挪到另一台，用户通常只会感到极短的停顿。物理机需要维修时，运维人员先把上面的虚拟机迁走再动手，业务基本不受影响。这一点会在 6.3 节讲冗余与容错时派上用场。

## 6.1.3 容器：共用一个内核的“合租房间”

虚拟机隔离得彻底，但比较“重”。每台虚拟机都要带一整套操作系统，启动往往要几十秒到几分钟，还要占用不少内存。很多时候，我们只是想让某个程序有一个干净、独立的运行环境，用不着整套操作系统。

容器就是更轻的方案。同一台机器上的所有容器共用宿主操作系统的内核，各自只打包应用程序和它依赖的库文件。在 Linux 上，隔离主要依靠内核提供的两类功能：

- **命名空间（Namespace）**：让每个容器看到的是“自己的”进程列表、网络和文件系统，看不到别人的；
- **控制组（Control Groups，cgroups）**：限制每个容器最多能用多少 CPU、内存和磁盘读写。

延续前面的类比，容器像同一套大房子里隔出的合租房间：卧室各自上锁，厨房、水管和电表是共用的。

| 对比项 | 虚拟机 | 容器 |
|---|---|---|
| 隔离层次 | 硬件层，每台有独立操作系统 | 操作系统层，共用宿主内核 |
| 启动时间 | 通常几十秒到几分钟 | 通常不到一秒到几秒 |
| 单个体积 | 常见为数 GB | 常见为数十 MB 到数百 MB |
| 一台物理机可容纳 | 几台到几十台 | 几十到上百个甚至更多 |
| 隔离强度 | 较强 | 较弱，内核漏洞会影响所有容器 |

表中数字是公开资料中的典型范围，实际情况取决于配置。2013 年发布的 Docker 让“镜像打包、到处运行”变得简单，容器从此迅速普及。

## 6.1.4 成千上万个容器谁来管：编排

一家大公司可能同时运行数万乃至更多的容器，靠人工逐个启动显然不现实，于是有了容器编排（Orchestration）系统。目前最常用的是 Kubernetes（常简写为 K8s），它源于谷歌内部集群管理的经验，后来开源，写作时已成为事实上的主流。它的工作方式可以概括为“声明你想要的状态”：

1. 你告诉它“这个照片处理服务要保持 10 个副本”；
2. 它自动挑选有空余资源的机器把容器放上去；
3. 某台机器宕机、某个容器挂掉，它会发现数量少了，自动在别处补上。

这样一来，单台服务器从“需要精心照料的宠物”变成了“可以随时替换的牲畜”，这是运维圈里一个流行的比喻。

容器的隔离不如虚拟机彻底，所以很多公有云采用两层叠加的做法：先用虚拟机把不同客户隔开，再在每个客户自己的虚拟机里运行容器。也有更轻量的“安全容器”或微型虚拟机方案，例如 AWS 开源的 Firecracker，试图兼顾两者的长处。

## 6.1.5 小结：从“物理的一台”到“逻辑的很多台”

虚拟化和容器在物理服务器与应用之间加了一层软件，“一台机器”从此成了可以切分、组合、搬迁的资源池。它带来的变化落在数据中心的各个层面：服务器利用率提高了，同样的业务需要的机柜、电力和冷却更少；新业务几分钟就能上线；硬件故障可以靠迁移和重建来消化。

资源被切成成千上万份之后，一个新问题随之出现：每个请求、每个新容器应该放到哪台机器上？这就是下一节要讲的负载均衡与调度。
