# 6.2 负载均衡与调度：把请求分到合适的机器

晚上九点，你打开相册应用，点了“上传到云端”。同一秒钟，可能还有成千上万的人在做同样的事。你的手机并不知道该把照片交给机房里的哪一台服务器，它只认得一个网址。从这个网址到某一台具体的机器之间，有一套专门“分活”的机制在工作，这就是负载均衡与调度。上一节讲到，虚拟化和容器把一台物理机切成许多份。这一节要回答的问题是：请求和任务越来越多，机器也越来越多，系统靠什么把每一份活交给合适的机器。

## 6.2.1 一个网址背后的“前台”

可以把数据中心想成一家大型银行营业厅。顾客进门先到取号机，取号机看哪个窗口空闲，就把号分过去。顾客不用知道窗口后面坐着谁，只要窗口在办事就行。

负载均衡（Load Balancing，常简写为 LB）的作用和取号机差不多。你访问的网址先经过域名系统（DNS）解析，得到的往往不是某台服务器的地址，而是一个“虚拟地址”（VIP，Virtual IP）。这个地址挂在负载均衡器上，负载均衡器再把请求转给后端某一台真实服务器。后端的机器可以随时增加或减少，用户看到的地址始终不变。

分发通常分几层完成：

| 层次 | 做什么 | 类比 |
|---|---|---|
| DNS / 全局负载均衡 | 把用户引向某个地区或某个数据中心 | 先决定去哪个城市的分行 |
| 四层负载均衡（L4） | 只看 IP 地址和端口，转发速度快 | 门口按号码分流 |
| 七层负载均衡（L7） | 能看懂请求内容，比如网址路径，再决定发给谁 | 大堂经理问清业务再引导 |

“四层”“七层”指的是网络分层模型里的传输层和应用层，第二十五册《互联网》对分层模型有专门介绍。你上传照片时，七层负载均衡可以认出这是一个“上传”请求，把它交给专门处理上传的服务器组；浏览相册的请求则交给另一组。

## 6.2.2 怎么分：几种常见算法

取号机最简单的做法是轮流叫号。负载均衡常用的分配方法有这几种：

- **轮询（Round Robin）**：按顺序一台一台轮着分，适合各台机器能力相近的情况。
- **加权轮询**：性能强的机器权重大，多分一些。
- **最少连接（Least Connections）**：哪台机器手上正在处理的请求最少，就交给哪台，适合处理时长差别大的业务。
- **哈希（Hash）**：按用户或请求的某个特征计算出一个固定结果，同一用户总落到同一台机器上，便于利用缓存。“一致性哈希”是它的改进版，机器增减时只有一小部分请求需要换去别的机器。

真实系统一般会把几种方法组合使用。不管用哪种算法，负载均衡器都要做健康检查（Health Check）：每隔几秒向后端机器发一个探测请求，没有正常回应的机器会暂时从名单里拿掉。所以单台服务器宕机时，用户一般察觉不到，后面的请求已经被转到其他机器上了。这也是下一节“冗余与容错”的一个具体体现。

## 6.2.3 调度：给任务找一个“座位”

负载均衡处理的是不断到来的短请求，以毫秒计。数据中心里还有另一类工作，比如给新上传的照片批量生成缩略图、做人脸聚类，或者启动一个新的容器。这类工作需要先决定“在哪台机器上运行、占用多少资源”，这件事叫调度（Scheduling）。

调度器手里有一张全局资源表，记录每台机器还剩多少处理器核、内存、显卡，以及它们位于哪个机柜、挂在哪一路电源上。来了一个任务，调度器大致分两步处理：

1. **过滤**：排除资源不够、型号不符或者正在维护的机器；
2. **打分**：在剩下的机器里按规则打分。有的规则希望把任务挤在少数机器上，让其余机器省电或空出来；有的规则希望把同一服务的多个副本分散到不同机柜和故障域，避免一个机柜断电就全部停掉。

写作时最常见的开源例子是 Kubernetes。它的调度器按“过滤—打分”的流程给容器（在 Kubernetes 中称为 Pod）挑选节点。谷歌公开发表过其内部集群管理系统 Borg 的论文，Kubernetes 的设计在很多方面借鉴了 Borg 的思路。各家云服务商也有自己的调度系统，细节并不统一。

## 6.2.4 弹性：机器不够了怎么办

晚上的上传高峰和凌晨的低谷相比，流量可以差好几倍。如果按最高峰准备固定数量的机器，平时就有大量机器闲着。于是负载均衡和调度常常与自动伸缩（Auto Scaling）配合使用：监控系统发现某组服务器的平均处理器占用持续偏高，就让调度器多启动几个实例，并把它们登记到负载均衡器的后端名单里；流量回落以后再逐步收回。

整个过程形成一个循环：

> 监控发现负载变化 → 调度器分配资源、启动或回收实例 → 负载均衡器更新名单 → 请求重新均匀分布

这个循环说明，负载均衡和调度都需要第五章讲过的运维流提供实时数据，也依赖虚拟化和容器能够快速创建、销毁实例。少了其中任何一环，“弹性”就做不起来。

## 6.2.5 小结：从一张照片看“分活”

你的照片从手机出发，经过 DNS 被引到某个数据中心，在四层和七层负载均衡器上被转给某台健康的上传服务器；后续的缩略图生成、识别分类等任务由调度器安排到合适的机器上运行。负载均衡管的是请求怎么分，调度管的是任务放在哪里，两者合起来，才能让几十万台机器像一台机器那样对外提供服务。

分活有一个前提：总得有备用的机器可以分。备用要准备多少，哪些部件必须成对配置，故障发生时影响能被限制在多大范围，这些是下一节“冗余与容错”要讨论的内容。
