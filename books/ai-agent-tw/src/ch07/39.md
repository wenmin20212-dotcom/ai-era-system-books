# 7.2 工具與上下文協議：讓工具即插即用

假設你在電腦上用一個程式設計智能體改程式碼，同時希望它能讀公司內部的需求文件，再查一下專案管理系統裡的任務狀態。很多人第一次做這類配置時會發現，「讓智能體連上某個系統」往往不是在聊天框裡說一句話，而是要在設定檔案裡添加一個「伺服器」，填上名稱、啟動命令或網址，有時還要授權一次。添加完成後，智能體的工具列表裡就多出幾項新能力。

這個過程背後的思路，和電腦介面從各式專用插頭走向統一標準很相似。本節要講的就是這種思路：用一套公共的**協議**（Protocol，即雙方事先約定好的通信規則），把工具接入從逐個定制的手工活，變成即插即用的標準件。

## 7.2.1 沒有協議時：M×N 的麻煩

第四章講過，模型通過函式呼叫「說出」一個動作，再由編排程式真正去執行。問題在於，每種智能體應用描述工具、傳遞參數、返回結果的格式都可能不一樣。如果有 M 個智能體應用，要接入 N 個外部系統（檔案、資料庫、日曆、程式碼倉庫……），最壞情況下需要寫 M×N 份適配程式碼。每份程式碼各自維護，任何一方改版，都可能有一批接入失效。

協議的作用，是在中間放一層大家共同遵守的約定。智能體應用只需要實現一次「會說這套協議」，外部系統也只需要實現一次「按這套協議提供能力」，工作量就從 M×N 降到大約 M+N。網際網路早已證明過這條路走得通：瀏覽器和網站之所以能互通，靠的正是 HTTP 這類公共協議，而不是兩兩談判。

## 7.2.2 一個代表性例子：模型上下文協議

寫作時，這一方向上影響較大的一個開放標準，是 Anthropic 公司在 2024 年 11 月發布並開源的**模型上下文協議**（Model Context Protocol，MCP）。該公司用 USB-C 介面作比方：不同設備用同一種介面連接，不同的工具和資料源也通過同一種協議接入智能體。此後，多家公司的智能體產品和開發工具陸續宣佈支援這一協議。不過各產品的具體支援程度和配置方式變化較快，使用時應以對應產品的官方文件為準。

MCP 的基本結構可以用三個角色來概括：

| 角色 | 英文 | 做什麼 | 類比 |
|---|---|---|---|
| 宿主 | Host | 使用者直接使用的智能體應用，如桌面助手、程式設計工具 | 電腦本身 |
| 客戶端 | Client | 宿主內部負責與某一個伺服器保持連接的組件 | 電腦上的一個介面 |
| 伺服器 | Server | 把某個外部系統的能力按協議暴露出來的程式 | 插上去的外設 |

伺服器向智能體提供的內容主要有三類：**工具**（Tools），是可以執行的動作，例如「創建任務」「執行查詢」；**資源**（Resources），是可以讀取的資料，例如檔案內容、資料庫記錄；**提示模板**（Prompts），是預先寫好的任務說明，方便使用者直接呼叫。這樣劃分的好處是「能做什麼」和「能看什麼」在介面層面就分開了，後面講權限控制時更容易管理。

在通信層面，MCP 的訊息採用 JSON-RPC 2.0 格式。JSON 是一種結構化文本格式，RPC 是「遠程過程呼叫」（Remote Procedure Call）的縮寫，意思是像呼叫本地函式一樣請求另一個程式辦事。伺服器可以作為本機上的一個進程，通過標準輸入輸出與宿主通信；也可以部署在遠端，通過 HTTP 訪問。

## 7.2.3 即插即用是怎樣發生的

把一個新伺服器接進智能體，大致會經過以下幾步：

1. **建立連接與握手**：客戶端和伺服器互相告知協議版本和各自支援的功能，類似兩台設備插上後先確認「彼此會說哪種話」。
2. **能力發現**：客戶端詢問伺服器「你有哪些工具」，伺服器返回每個工具的名稱、用途說明和參數格式。
3. **放入上下文**：宿主把這些工具說明交給模型，模型因此「知道」自己多了哪些能力。
4. **呼叫與返回**：模型決定使用某個工具時，宿主通過客戶端發出請求，伺服器執行後把結果送回，結果再進入下一輪推理。

關鍵在第 2 步。工具清單是執行時動態獲取的，而不是寫死在智能體程式裡，所以新增一個伺服器不需要修改智能體本身。這正是「即插即用」的含義。

## 7.2.4 協議解決了什麼，沒有解決什麼

統一協議帶來的是互通性，但它不會自動帶來可靠性和安全性。有三點需要注意：

- **說明寫得好不好，仍然決定用得好不好**。模型靠工具說明來判斷何時呼叫、怎樣填參數，說明含糊，呼叫就容易出錯。
- **工具越多，上下文越擠**。每個工具的說明都要佔用令牌，一次接入幾十個伺服器，既增加成本，也會干擾模型的選擇。第五章講的上下文流在這裡同樣適用。
- **第三方伺服器就是第三方程式碼**。它返回的內容可能夾帶惡意指令，它執行的動作可能越權。協議規定的是「怎麼說話」，而「該不該信、能不能做」需要靠沙箱、權限和人工確認來把關，這是下一節和 7.5 節的主題。

另外，在「智能體連接工具」之外，業界也在探索「智能體連接智能體」的協議。例如谷歌公司在 2025 年提出了 Agent2Agent（A2A）協議，用於讓不同來源的智能體互相發現並委派任務。這類標準仍在發展中，格局可能變化，但背後的邏輯不變：**把兩兩定制的連接，換成公共約定上的連接**。

理解了這一點，再看到任何新協議的名字，你都可以用同一組問題去拆解它：它連接的是誰和誰，約定了哪些訊息，怎樣發現對方的能力，又把安全問題留給了誰。
