# 6.3 工具呼叫的機制：模型怎樣「說出」一個動作

你讓 AI 代理「查一下明天上海的天氣，再寫進我的日程備註裡」。幾秒鐘後，介面上出現一行灰色小字：「正在呼叫：天氣查詢……」，接著又是「正在呼叫：日曆寫入……」。這兩行字背後有一個容易被忽略的事實：大語言模型本身只會做一件事，就是根據輸入續寫文字。它沒有手，也連不上天氣伺服器。那麼「呼叫工具」這個動作是從哪裡來的？答案是模型「說」出了一段格式嚴格的文字，由外面的程式替它把這段文字變成真正的動作。本節就拆開這句「說出一個動作」。

## 6.3.1 從一句話到一張「工單」：結構化輸出

在第四章我們從連接的角度認識了函式呼叫（Function Calling，也常稱工具呼叫 Tool Use）。現在換到機制層面，看清一次呼叫的具體樣子。

當 AI 代理需要查天氣時，模型並不會輸出「我去查一下天氣」這樣的自然語言，而是輸出一段機器能直接讀懂的結構化文本，最常見的格式是 JSON（JavaScript 對象表示法，一種用花括號和鍵值對表示資料的通用格式）。示意如下：

```json
{
  "tool": "get_weather",
  "arguments": { "city": "上海", "date": "明天" }
}
```

可以把它看成一張「工單」：寫明要找哪個部門（工具名）、辦什麼事（參數）。模型只負責填工單，真正跑腿的是編排程式。這種分工很關鍵：模型生成的內容始終只是文字，所有對外部世界的影響，都必須經過程式這道關口。這也是第七章討論沙箱與權限時，能在這裡設卡的原因。

## 6.3.2 模型怎麼知道有哪些工具可用

模型之所以能填對工單，是因為每次請求時，編排程式都會把一份「工具說明書」放進上下文。每個工具的說明一般包含三項：

| 組成部分 | 作用 | 天氣工具的例子 |
|---|---|---|
| 名稱 | 讓模型點名呼叫 | `get_weather` |
| 描述 | 用自然語言告訴模型何時該用 | 「查詢指定城市某天的天氣預報」 |
| 參數結構 | 規定要填哪些字段、什麼類型、哪些必填 | city：字元串，必填；date：字元串 |

參數結構通常用 JSON Schema（JSON 模式，一種描述資料格式的規範）來寫。模型讀到這份說明，就像新員工拿到一張部門電話表加填表須知。

由此可以推出一個實用結論：**工具描述寫得好不好，直接影響模型會不會用、會不會用對**。描述含糊，模型可能在不該用的時候亂用；參數說明不清，模型可能把「明天」填成格式錯誤的日期。許多開發者的經驗是，調好工具描述往往比更換模型更見效。

至於模型為什麼能穩定地輸出這種格式，主要來自訓練：主流模型廠商在訓練中加入了大量「看說明、選工具、填參數」的示範資料。訓練細節屬於模型本身的話題，可參閱第十八冊。寫作時，OpenAI、Anthropic、Google 等公司的介面都提供了類似的工具呼叫功能，字段名稱各不相同，但「名稱—描述—參數」這一結構基本一致。

## 6.3.3 一次呼叫的完整往返

把鏡頭拉遠，一次工具呼叫是一個由程式驅動的往返過程，和 6.1 節的推理—行動循環正好對應：

1. **提供選單**：編排程式把使用者任務、對話歷史和工具說明一起發給模型。
2. **模型決策**：模型判斷需要外部資訊，於是輸出一張呼叫工單，而不是直接回答。介面會用特殊標記表明「這是一次呼叫請求」，程式據此區分普通回覆和動作。
3. **程式校驗**：程式檢查工具名是否存在、參數是否符合格式、這個動作是否需要人工確認。
4. **真實執行**：程式呼叫天氣服務，拿到結果，比如「多雲，18—24℃」。
5. **結果回填**：程式把結果作為一條「工具訊息」追加進上下文，再次請求模型。
6. **繼續或結束**：模型讀到結果後，可以再發起下一次呼叫（寫入日曆），也可以給出最終答復。

有兩點值得注意。第一，模型在第 2 步和第 6 步之間是「斷開」的：它不會等待，每次都是程式把完整上下文重新送進去，它再接著往下想。第二，有些介面允許模型在一次輸出裡同時發出多張工單，即並行呼叫，比如同時查北京和上海的天氣，由程式併發執行後再統一回填，從而節省時間。

## 6.3.4 當工單填錯時

既然動作是「說」出來的，就會有說錯的時候。常見的問題有以下幾類：

- **格式錯誤**：少了括號、字段類型不對。部分介面提供「嚴格模式」或約束解碼（在生成時限制模型只能輸出符合格式的內容），可以大幅減少這類問題。
- **參數編造**：使用者沒提供訂單號，模型卻憑空填了一個看似合理的號碼。這是幻覺在動作層面的表現，危害比說錯一句話更大。
- **選錯工具**：兩個工具描述相近，模型選了不合適的那一個。
- **不該呼叫卻呼叫**：本可以直接回答，卻多繞一圈，白白增加成本。

對應的工程做法也很樸素：程式校驗格式後把錯誤訊息原樣回填，讓模型自己修正；必填資訊缺失時，引導模型先向使用者提問；涉及付款、刪除、發送等不可逆的動作，一律交給人確認。這些做法會在 6.5 節的失敗與恢復中繼續展開。

## 6.3.5 小結：說與做之間隔著一個程式

工具呼叫的機制可以濃縮成一句話：**模型負責「說」出一張格式規範的工單，程式負責校驗、執行，並把結果送回給模型。**理解了這一點，就不會把 AI 代理想成一個自己伸手去操作電腦的「幽靈」。它的每一個動作都留有文字記錄，每一步都可以檢查、攔截和復現。下一節我們將看到，隨著工具呼叫越來越多，上下文會迅速變長，AI 代理需要靠總結、壓縮和檢索來管理自己的記憶。
