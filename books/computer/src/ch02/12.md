# 3.2 从指令到执行：取指、译码、运算与提交

双击一个应用图标后，屏幕上的程序不会被“整块”送进 CPU。可执行文件中的机器指令先由操作系统装入内存，处理器再以很细的步伐不断取得、识别并执行这些指令。教科书常把这一过程概括为“取指—译码—执行”，但现代 CPU 为了提高效率，还会让多条指令重叠前进，并在最后确认哪些结果真正生效。理解这条流水线，是从“CPU 会计算”走向“CPU 如何组织计算”的关键一步。

## 3.2.1 取指：找到下一条要处理的指令

处理器内部有一个用于指示执行位置的状态，通常称为程序计数器或指令指针。取指单元依据它所给出的地址，请求下一段指令字节。理想情况下，所需内容已经在靠近核心的指令缓存中；若没有命中，就需要从更远的缓存层乃至主存调入。由此可见，取指并不只是“读一下内存”，它依赖地址、缓存层次、互连和主存共同配合。

顺序执行时，下一地址通常紧接当前指令；遇到条件分支、函数调用或返回时，执行方向可能改变。为了不让后续部件空等，现代处理器会预测分支更可能走向哪里，并提前取得相应路径上的指令。预测正确，流水线可以继续推进；预测错误，提前做的部分工作就要被撤销，再从正确地址重新开始。预测改变的是执行效率，不应改变程序最终应有的语义。

取回的指令字节还要被切分成可识别的指令边界。不同指令集的编码方式不同：有的指令长度较为规则，有的长短不一；因此，处理器前端不仅要搬运字节，还要判断一条指令从哪里开始、到哪里结束。

## 3.2.2 译码：把机器编码变成内部操作

机器指令由一串二进制编码构成，其中通常包含操作类型、操作数位置以及寻址方式等信息。译码单元要回答几个问题：这是什么指令？需要读取哪些寄存器？是否要访问内存？结果写到哪里？它还可能把一条较复杂的机器指令拆成若干更便于内部执行的微操作。

这里可以把“指令”与“微操作”区分开来。指令是软件能够观察和使用的体系结构接口，例如加法、加载、跳转；微操作则是某种处理器实现内部的工作单元。相同指令集的两款 CPU 可以运行同一程序，却采用不同的译码、调度和执行设计。软件看到的是相对稳定的指令语义，硬件内部则可以持续演进。

译码之后，处理器还需准备依赖关系。若后一条指令需要前一条指令的结果，它就不能贸然运算。现代 CPU 常通过寄存器重命名消除一部分由名称复用造成的“假依赖”，再把微操作送入等待区，由调度逻辑寻找已经具备输入条件的任务。这一步使后续执行不必机械地按照原始顺序逐条开始。

## 3.2.3 运算：让可执行的工作进入不同单元

准备就绪的微操作会被派发到适合的执行单元。整数加减可能进入整数运算单元，浮点或向量计算进入相应的数据通路，地址计算协助加载与存储单元确定内存位置，分支单元则判断控制流方向。所谓“CPU 核心”并不是一个万能计算器，而是一组功能不同、可并行工作的结构。

以一个简化表达式 `c = a + b` 为例，若 `a` 和 `b` 已在寄存器中，加法微操作可以直接等待整数执行单元；若数据尚在内存里，就要先完成地址计算和加载，之后才能相加，最后还可能把结果存回内存。任何一次缓存未命中，都可能拉长等待时间。与此同时，只要别的指令与这份数据没有依赖关系，调度器就可能先安排它们执行，用并行工作填补空隙。这种方式称为乱序执行：改变的是内部完成工作的先后，不是软件所观察到的程序顺序。

| 阶段 | 核心问题 | 常见影响因素 |
|---|---|---|
| 取指 | 下一条指令在哪里 | 指令缓存、分支预测、指令边界 |
| 译码 | 指令要求做什么 | 编码格式、微操作、数据依赖 |
| 运算 | 哪个单元何时执行 | 执行端口、操作数就绪、缓存命中 |
| 提交 | 结果能否正式生效 | 原始顺序、异常、预测正确性 |

## 3.2.4 提交：把推测结果变成程序状态

如果处理器只追求“谁先准备好谁先做”，就可能出现一个问题：后面的指令已经算完，前面的指令却发生异常；或者分支预测错误，使后面的工作原本就不该发生。因此，许多现代处理器会把执行结果暂存在内部结构中，等到确认它们位于正确路径且前面的指令没有阻断性问题后，再按程序顺序提交。

提交可以理解为结果获得“正式身份”的时刻。寄存器状态在体系结构层面更新，存储操作按规则对外可见，已完成的内部资源得到释放。若某条较早的指令触发异常，处理器可以丢弃尚未提交的后续结果，把系统恢复到一个精确边界，再交由操作系统处理。分支预测失败时，也会清除错误路径上的推测工作。正因为存在提交阶段，内部的乱序、预测和并行才能与外部所要求的有序语义兼容。

不过，“按顺序提交”不意味着所有内存访问在多核系统中都天然呈现最直观的全局顺序。缓存、一致性协议和内存模型还会规定不同核心如何观察读写结果，这将在后文继续讨论。此处应抓住的边界是：单个核心内部可以大胆优化，但必须遵守指令集和系统规定的可观察行为。

## 3.2.5 用一次条件计算串起流水线

设想程序执行“如果库存大于零，就把库存减一”。处理器先取入比较、条件跳转和减法等指令，并预测条件是否成立；译码阶段识别各指令所需的寄存器和依赖；执行阶段读取库存值、完成比较，再决定分支方向。如果预测正确，减法可能已经提前完成；如果预测错误，错误路径结果会被丢弃。最后，只有位于正确路径、且没有异常的结果才能提交。看似简单的一句高级语言，背后已经牵动指令缓存、预测器、寄存器、调度器、执行单元与提交结构。

观察 CPU 时，我们很难直接看见这些纳米尺度上的动态过程，但可以从公开的架构框图、性能计数器和实验现象间接建立证据。例如，让程序处理规则分支和难预测分支，比较执行时间；或改变数据规模，观察缓存命中状况对延迟的影响。需要注意，具体流水线级数、微操作拆分和内部队列属于特定微架构，不能从一个型号直接推广到所有 CPU。

你也可以让 AI 辅助推演，但应把条件说清楚：**“请以一颗具有分支预测、乱序执行和按序提交能力的通用 CPU 为抽象模型，逐阶段解释‘加载两个数、相加并按条件写回’的取指、译码、调度、执行与提交过程；分别说明缓存未命中和分支预测错误会造成什么影响，并区分通用机制与依赖具体微架构的细节。”** 对 AI 给出的流水线级数、周期数或型号特征，应再查阅对应厂商文档或可靠测量资料。

从取指到提交，CPU 的关键能力不仅是进行算术运算，更是持续发现可并行的工作，同时维持程序应有的秩序。下一步再看 GPU 和 NPU 时，可以用同一组问题比较：任务怎样被分解，数据怎样到达执行单元，并行性又受到哪些结构约束。
