# 5.5 更新流：系统补丁怎样下载、安装与生效

很多人都见过这样的提示：电脑右下角弹出“需要重启以完成更新”，手机在深夜自动安装系统更新，第二天早上开机看到“正在完成更新”。更新看上去只是“下载一个文件、点一下安装”，实际上它要修改操作系统自己的核心文件，而操作系统此时正在运行这些文件。这是一项在运行中替换自身部件的工作。本节沿着一次补丁的路径，看它怎样从厂商的服务器出发，最后在你的设备上生效。

## 5.5.1 第一站：发现与下载——补丁从哪里来

更新流的起点在设备之外。系统里有一个后台服务定期联系厂商的更新服务器，报告本机的系统版本、硬件型号等信息，询问有没有适合自己的新补丁。Windows 中负责这项工作的是 Windows 更新服务（Windows Update），多数 Linux 发行版由包管理器（Package Manager，如 apt、dnf）向软件仓库查询，Android 和 iOS 则由系统设置里的更新组件完成。

下载有两个特点：

- **增量更新**：厂商通常只发送新旧版本之间的差异部分，即“差分包”或“增量包”（Delta Update），不必把整个系统重新下载一遍。
- **分批推送**：许多厂商采用分阶段发布（Staged Rollout），先推给一小部分设备，确认没有严重问题再逐步扩大范围。所以你和同事用同一款手机，收到更新的时间可能前后相差几天。

## 5.5.2 第二站：验证——确认补丁没有被调包

补丁要改写系统最核心的文件，一旦被人篡改，后果比普通病毒更严重。因此下载完成后，系统首先检查**数字签名**（Digital Signature）。厂商用只有自己掌握的私钥给补丁签名，设备用预先内置的公钥验证。签名对不上，补丁就会被拒绝安装。

这和收快递时核对封条相似：封条完好、印章正确，才说明包裹在路上没被拆开。签名验证依赖的是第三章讲过的密码学与信任链，也和 2.1 节固件中的安全启动是同一套思路，都是“先验证，再信任”。

## 5.5.3 第三站：安装——在运行中替换自身

真正的难点在这里。正在被使用的文件，不能像普通文档那样直接覆盖。不同系统采用了不同的办法：

| 做法 | 基本思路 | 典型例子 |
|---|---|---|
| 重启时替换 | 先把新文件准备好，等下次启动、旧文件尚未被加载时再换上 | Windows 的“重启以完成更新” |
| 包管理器替换 | 逐个替换软件包的文件，正在运行的程序继续使用旧文件，重启该程序后改用新版本 | 多数 Linux 发行版 |
| A/B 分区 | 系统有两套分区，在当前不用的那一套上安装新版本，重启时切换过去 | 部分 Android 设备的“无缝更新”（Seamless Update） |
| 只读系统卷与快照 | 系统文件放在只读、带校验的卷上，更新时生成新的系统卷快照，启动时改用新快照 | macOS（自 macOS 11 Big Sur 起） |
| 内核热补丁 | 在不重启的情况下替换内核中有问题的函数 | Linux 的 livepatch 等机制，多用于服务器 |

这些办法要解决的是同一个问题：**更新过程中断电、出错，设备也不能变成“砖头”**。A/B 分区和快照的思路是“旧版本先不动，新版本单独准备好”，新版本启动失败，还能退回旧版本。Windows 在更新失败时也会尝试撤销更改、恢复到更新前的状态。这与 6.3 节将要讲的文件系统日志思想相通：先把“要做什么”安排妥当，确认可以完成再正式切换。

## 5.5.4 第四站：生效——为什么常常要重启

安装完成不等于补丁生效。新代码要被加载进内存，才会真正运行。普通应用重新打开一次就能用上新版本；内核、驱动和核心系统服务从开机起就驻留在内存里，替换它们最稳妥的方式就是重启，让启动流（5.1 节）从头走一遍，加载新的版本。

所以你会看到这样一条规律：**补丁离内核越近，越可能需要重启**。浏览器、办公软件的更新往往只需重开程序；系统安全补丁、驱动更新则常常要求重启。服务器上的热补丁可以减少重启次数，但适用范围有限，大版本升级仍需要重启。

重启之后，系统通常还会做一些收尾工作：迁移设置、重建缓存、清理旧文件。手机升级后第一次开机较慢、“正在优化应用”，就是这一步。

## 5.5.5 小结：更新流的完整链条

把四站连起来，一次系统更新的路径是：

### 5.5.5.1 检查 → 下载（增量、分批）→ 验证签名 → 准备新版本（保留旧版本）→ 重启或重载 → 收尾与清理

理解这条链条，就能读懂日常的更新提示：“需要重启”说明补丁触及了正在运行的核心部件；“更新失败，正在撤销更改”说明回退机制在起作用；同一型号设备更新时间不同，是分阶段推送的结果。对管理者来说，及时安装安全补丁、在重要工作前留出重启时间，也是基于这条链条的合理安排。
