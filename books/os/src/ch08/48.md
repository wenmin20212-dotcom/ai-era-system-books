# 8.5 可靠性与形式化验证

你的手机可能连续几周不关机，电脑偶尔弹出“系统遇到问题，需要重新启动”，汽车里的控制系统则被要求在整个使用寿命中几乎不出错。同样是操作系统，人们对它的期待差别很大。软件不会像轴承那样磨损，它为什么还会“坏”？工程师又怎样让它少坏、坏了也能恢复，甚至在数学上证明它“不会以某种方式坏掉”？这一节回到原理层面，看可靠性这门学问，以及形式化验证（Formal Verification）这件严格的工具。

## 8.5.1 软件为什么会“坏”：故障、错误与失效

可靠性工程里有一组常用的区分，读者可以对照自己遇到的蓝屏或闪退来理解：

| 概念 | 含义 | 操作系统中的例子 |
|---|---|---|
| 故障（Fault） | 潜藏的缺陷或异常原因 | 驱动代码里一处没检查的空指针；内存条一个比特被宇宙射线翻转 |
| 错误（Error） | 故障被触发后，系统内部状态出了偏差 | 内核某个数据结构被写坏 |
| 失效（Failure） | 偏差暴露到外部，服务不再符合预期 | 蓝屏、内核崩溃（Linux 中称 kernel panic）、应用闪退 |

软件不老化，但它的状态空间极其庞大。前面讲过的并发、中断、缓存、调度交织在一起，同一段代码在绝大多数时序下都没问题，只在某个罕见的先后顺序里出错。测试只能覆盖其中一小部分情形，这就是计算机科学家迪杰斯特拉（Edsger Dijkstra）那句常被引用的话：测试能证明错误存在，却不能证明错误不存在。

衡量可靠性，常用两个指标：平均无故障时间（MTBF，Mean Time Between Failures）和平均修复时间（MTTR，Mean Time To Repair）。可用性大致取决于二者的比例——要么少出故障，要么出了故障赶紧恢复。服务器领域常说的“几个 9”（如 99.9%、99.99%）就是可用性的表达方式，具体数字依场景而定。

## 8.5.2 让系统“扛得住”：隔离、冗余与恢复

操作系统并不指望代码完美无缺，而是层层设防，前面几章的许多机制在这里汇合：

- **隔离**：用户态与内核态分开，每个进程拥有独立的虚拟地址空间。一个应用崩溃，通常只关掉它自己，不会拖垮整台电脑。微内核设计更进一步，把驱动、文件系统放到用户态进程中，某个驱动出错可以单独重启。
- **冗余**：服务器用磁盘阵列（RAID）在多块硬盘上保存冗余数据，用纠错码内存（ECC）自动修正单个比特错误；云平台在多台机器、多个机房部署同一服务。
- **一致性与恢复**：第六章讲的文件系统日志，保证突然断电后元数据能回到一致状态；系统更新失败时，部分手机和电脑会保留旧系统分区或还原点，以便回滚。
- **监控与重启**：看门狗定时器（Watchdog Timer）是嵌入式系统常见做法——系统要定期“报平安”，超时未报就被强制复位；桌面系统的服务管理器也会在后台服务崩溃后自动拉起它。

这些手段的共同思路是：承认故障必然发生，把失效的影响范围限制住，并缩短恢复时间。

## 8.5.3 形式化验证：用数学证明代替“多测几遍”

对于飞行控制、医疗设备、汽车电子这类场合，“基本不出错”还不够。形式化验证的做法是：先用精确的数学语言写出规格说明（Specification），即“系统应当满足什么性质”，再用数学推理证明实现确实满足它。常见路线有两类：

1. **模型检验（Model Checking）**：把系统抽象成有限状态的模型，由工具自动穷举所有可能状态，检查是否会出现死锁、违反安全性质等情况。它擅长发现并发中罕见的交错时序问题，局限是状态数量会随规模迅速膨胀。
2. **定理证明（Theorem Proving）**：借助 Isabelle、Coq 等证明辅助工具，由人构造证明、机器逐步检查每一步推理是否严密。它能处理更一般的问题，但需要大量专业人工。

最常被引用的例子是 seL4 微内核。公开资料显示，研究团队用定理证明的方法，证明了它的 C 语言实现符合抽象规格，从而排除了缓冲区溢出、空指针访问等一大类错误。值得注意的是证明工作量：一般认为，证明本身的篇幅和投入远超内核代码本身。这也说明了为什么形式化验证多用于小而关键的部分，而不是整个 Windows 或 Linux。工业界也有局部应用，例如一些公司用 TLA+ 等规格语言检查分布式协议的设计，微软曾用静态验证工具检查 Windows 驱动是否正确使用内核接口。

## 8.5.4 证明了什么，没证明什么

“经过形式化验证”不等于“绝对安全”。证明总是建立在假设之上：规格写得对不对？编译器和硬件是否按预期工作？证明之外的部分（如启动代码、硬件本身）有没有问题？例如，2018 年前后公开的“幽灵”（Spectre）等处理器漏洞，利用的正是硬件推测执行的行为，而许多软件验证的模型并不包含这类细节。因此更准确的说法是：形式化验证把“相信整段代码”缩小为“相信规格、工具和少量假设”，让信任的基础更小、更清楚。

可靠性与形式化验证在一起，构成一条从工程到数学的谱系：日常系统主要靠隔离、冗余和快速恢复；关键系统在此之上再加数学证明。这与本章前面的抽象与分层、并发理论一脉相承——正因为系统被分层、接口被清晰定义，才有可能对其中一层单独下“它不会出错”的结论。下一节，我们把第八章的五条原理收拢成一张骨架。
