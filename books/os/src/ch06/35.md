# 6.4 同步与死锁：多个程序抢同一样东西

你在手机上一边用网盘同步相册，一边打开相册删掉几张照片。按理说，两件事同时动同一批文件，很容易出乱子：网盘刚上传到一半，照片被删了；或者你刚删掉的照片，又被同步程序“好心”恢复回来。多数时候这些事并没有发生，或者应用会提示“文件正在使用中”。在 Windows 上删除一个正被 Word 打开的文档，系统会弹出“操作无法完成，因为文件已在另一程序中打开”。这些提示背后，就是操作系统处理“同步”问题的一套机制。

## 6.4.1 竞争条件：同时动手为什么会出错

先看一个最简单的例子。银行账户里有 100 元，两个程序同时各存入 50 元。每次存款在计算机里其实分三步：读出余额、加上 50、写回余额。如果两个程序交错执行，就可能出现这样的顺序：

| 时刻 | 程序 A | 程序 B | 内存中的余额 |
|---|---|---|---|
| 1 | 读出 100 | | 100 |
| 2 | | 读出 100 | 100 |
| 3 | 算出 150，写回 | | 150 |
| 4 | | 算出 150，写回 | 150 |

两次存款结果只多了 50 元，有一次存款丢了。这种结果取决于执行先后顺序的错误，叫作**竞争条件**（Race Condition）。在第 3 章里我们看到，调度器随时可能打断一个线程、换另一个上来；在多核处理器上，两个线程甚至真的在同一瞬间运行。所以只要多个执行流共享同一份数据，竞争条件就可能出现，而且往往很难复现：一万次运行里可能只错一次。

被多方共享、一次只能由一方安全操作的那段代码，称为**临界区**（Critical Section）。同步要解决的核心问题，就是保证同一时刻只有一个执行流进入临界区，这个性质叫**互斥**（Mutual Exclusion）。

## 6.4.2 锁、信号量与原子操作：操作系统提供的工具

日常生活中，公共卫生间门上的“有人/无人”标志就是一种互斥工具。操作系统和处理器提供了几类类似的工具：

- **原子操作**（Atomic Operation）：处理器提供的特殊指令，能把“读—改—写”作为不可分割的一步完成，中途不会被别的核心插进来。它是所有更高级工具的地基。
- **互斥锁**（Mutex，Mutual Exclusion 的缩写）：进入临界区前“上锁”，出来后“解锁”。如果锁已被别人拿走，后来者要么原地反复检查（称为自旋锁，Spinlock，适合极短的等待），要么让操作系统把自己挂起、等锁释放后再唤醒（适合较长的等待）。
- **信号量**（Semaphore）：由荷兰计算机科学家迪杰斯特拉（Edsger Dijkstra）在 20 世纪 60 年代提出，可以理解为“剩余名额计数器”。停车场入口显示“剩余车位 5”，进一辆减一，出一辆加一，为零时后来的车排队等候。名额为 1 的信号量就相当于一把互斥锁。
- **读写锁**（Read-Write Lock）：允许多个读者同时读，但写者必须独占。很多人同时看一份公告没有问题，有人修改时则要暂停大家阅读。

前面提到的“文件已在另一程序中打开”，就是 Windows 对文件加锁的表现：打开文件的程序可以声明“不许别人删除或写入”，系统据此拒绝其他请求。Linux 等类 Unix 系统的默认做法不同，文件锁多是“建议性”的，需要各程序主动遵守；另外，在 Linux 上删除文件只是去掉它的目录项，所以通常可以删除一个正被打开的文件，等最后一个使用它的程序关闭后，文件才真正被释放。这是两类系统设计取向上的差异，并非对错之分。

## 6.4.3 死锁：互相等待，谁也走不了

锁解决了竞争，却带来了新麻烦。设想一条窄巷两头各开进一辆车，谁都不肯倒车，两辆车就会永远堵在那里。程序里也一样：程序 A 拿着锁 1、等锁 2；程序 B 拿着锁 2、等锁 1。双方都在等对方先放手，结果都卡住不动，这就是**死锁**（Deadlock）。用户看到的现象可能是某个应用“未响应”、界面冻结，而任务管理器里它的处理器占用却接近零，因为它不是在忙，而是在等。

1971 年，科夫曼（E. G. Coffman）等人总结出死锁发生的四个必要条件，至今仍是教科书中的标准说法：

1. **互斥**：资源一次只能被一个程序占用；
2. **占有并等待**：程序拿着已有资源不放，同时等待新的资源；
3. **不可剥夺**：别人不能强行夺走它手里的资源；
4. **循环等待**：若干程序形成一个首尾相连的等待环。

四个条件同时满足才会死锁，所以只要打破其中任何一个，死锁就不会发生。

## 6.4.4 预防、避免、检测：三种应对思路

| 思路 | 做法 | 生活类比 | 代价 |
|---|---|---|---|
| 预防 | 规定所有程序按统一顺序申请锁，打破“循环等待”；或要求一次申请全部资源 | 窄巷规定单向通行 | 编程约束多，资源利用率可能下降 |
| 避免 | 每次分配前计算是否仍有安全的完成顺序，不安全就暂不分配，经典方法是迪杰斯特拉的“银行家算法” | 银行放贷前确认现金足够周转 | 需要预先知道各程序的最大需求，实际系统中难以满足 |
| 检测与恢复 | 允许死锁发生，定期检查等待关系中是否出现环，发现后终止或回滚某个程序 | 交警发现堵死后指挥一方倒车 | 需要额外的检查开销，被牺牲的程序要重做 |

现实中，通用操作系统内核主要靠第一种：内核开发者遵守严格的加锁顺序规则，Linux 内核还提供名为 lockdep 的调试工具，在开发测试阶段检查加锁顺序是否可能形成环。数据库系统则常用第三种，检测到事务互相等待时，会选一个事务回滚，让它稍后重试。至于普通应用之间的死锁，桌面操作系统通常并不替它们“解围”，而是交给用户处理：Windows 标记“未响应”并提供“结束任务”，macOS 提供“强制退出”，本质上就是用剥夺资源的方式打破僵局。

## 6.4.5 小结：秩序的代价

同步机制让多个程序能安全地共享数据和设备，但每一把锁都意味着有人要排队，加锁过多会拖慢系统，加锁顺序不当还会造成死锁。操作系统设计者始终在“正确”与“高效”之间权衡：粗粒度的大锁简单可靠，但并发度低；细粒度的小锁并发度高，却更容易出错。这些等待与切换最终都要穿过用户程序与内核之间的边界。下一节我们就来看这道边界本身：用户态与内核态，以及程序怎样通过系统调用请求内核为它办事。
