# 6.3 文件系统机制：目录、索引与日志

打开电脑里的“文档”文件夹，双击一份上周写的报告，几乎不到一秒它就出现在屏幕上。可是在硬盘或固态硬盘（SSD）的内部，并没有“文件夹”，也没有“报告”，只有一长串编了号的存储块，每块通常几千字节。你看到的层层文件夹和文件名，是文件系统在这串编号块之上搭建的一套“图书馆管理制度”。第三章讲过文件管理“做什么”，这一节打开这套制度，看它怎样做到：找得到、放得下、断电也不乱。

## 6.3.1 从路径到数据块：目录其实是一张“名字对照表”

设想你要打开路径为“/home/xiaoming/报告.docx”的文件（Windows 上类似“C:\Users\xiaoming\报告.docx”）。文件系统不会扫遍整个磁盘，而是逐级查表：

1. 从根目录出发，根目录本身也是一个特殊文件，里面记录着“名字 → 编号”的对照，例如“home → 编号 2048”；
2. 按编号找到 home 目录，再在其中查“xiaoming”；
3. 一级级查下去，最后得到“报告.docx”对应的编号。

所以**目录（Directory）本质上是一张名字到文件编号的对照表**。文件名只是写在这张表里的标签，而不是文件本身的一部分。这解释了一个日常现象：在同一个分区里把一个几 GB 的视频从一个文件夹“移动”到另一个文件夹，几乎瞬间完成，因为系统只是把一行对照记录从一张表挪到另一张表，数据本身一个字节都没动。而跨磁盘移动要真正复制数据，就慢得多。

为了避免每次都从根目录逐级查找，操作系统会把最近查过的路径结果缓存在内存里，Linux 中称为目录项缓存（dentry cache）。这正是第八章将讲到的局部性原理的一个应用。

## 6.3.2 文件的“档案卡”：索引节点与数据块地图

拿到编号之后，系统要找的是这个文件的“档案卡”。在 Linux 常用的 ext4 等类 Unix 文件系统中，它叫**索引节点（index node，简称 inode）**；Windows 的 NTFS 则把类似信息记录在主文件表（Master File Table，MFT）的条目中。档案卡上一般记着：

| 记录项 | 作用 |
|---|---|
| 文件大小 | 读到哪里结束 |
| 所有者与权限 | 谁能读、写、执行（呼应 3.5 节） |
| 时间戳 | 创建、修改、访问时间 |
| 数据位置 | 文件内容存放在哪些存储块 |

最关键的是最后一项。一个文件的内容往往分散在磁盘的许多块里，档案卡要像一张地图一样把它们串起来。常见做法有两种：

- **块指针表**：逐个记录块编号，大文件则用“指针指向一张存满指针的表”的多级间接方式扩展，早期 Unix 文件系统和 ext2/ext3 采用这种思路；
- **区段（Extent）**：只记“从第几块开始、连续多少块”，一条记录就能描述一大片连续空间。ext4、NTFS、苹果的 APFS 等现代文件系统都采用了区段或类似思路，对大文件更省空间、读取也更快。

此外，文件系统还要维护一张“空闲块账本”（常用位图，Bitmap，每一位表示一块是否已占用），新写数据时从这里分配空间。

## 6.3.3 断电的风险：一次写入要改好几处

现在问题来了。保存一个新文件，至少要改动三处：空闲块账本（占用新块）、档案卡（记录位置和大小）、目录（加入名字）。这三处分布在磁盘不同位置，不可能同时写完。如果写到一半突然断电，可能出现：

- 块被标记为已占用，但没有任何文件指向它——空间白白“丢失”；
- 目录里有了名字，档案卡却还是空的——文件打开就出错。

早年的系统遇到异常关机，开机时要运行检查工具（如 Linux 的 fsck、Windows 的 chkdsk）把整个磁盘的账目对一遍。磁盘越大，检查越久，大容量磁盘可能要花很长时间。

## 6.3.4 日志：先写“备忘录”，再动正式账本

现代文件系统普遍采用**日志（Journaling）**机制，思路借鉴自数据库：动正式账本之前，先把“我打算改哪几处”完整写进磁盘上一块专门的日志区，并在末尾记一条“提交”标记；然后才去修改真正的位置；全部完成后，再把这条日志标为作废。

断电后重启时，系统只需看日志：

| 断电时机 | 重启后的处理 |
|---|---|
| 日志没写完（无提交标记） | 丢弃这条日志，当作操作从没发生 |
| 日志已提交，正式修改未完成 | 按日志“重放”一遍，补完修改 |

这样，一次操作要么完整生效，要么完全没发生，这种性质称为**原子性（Atomicity）**。检查时间从“扫描全盘”缩短为“读一小段日志”。ext4 和 NTFS 都使用日志。为了兼顾速度，许多系统默认只把元数据（档案卡、目录、账本）写入日志，文件内容本身不全部记录；这意味着文件系统结构不会乱，但断电时正在写的那份文件内容仍可能不完整。这就是为什么编辑软件仍会提醒你“及时保存”。

另一条路线是**写时复制（Copy-on-Write，CoW）**：从不覆盖旧数据，而是把修改写到新位置，最后一步再把“根指针”切换过去。苹果的 APFS、Linux 上的 Btrfs 以及源自 Solaris 的 ZFS 都采用这一思路，它顺带让“快照”（瞬间保存整个文件系统某一时刻的状态）在创建时几乎不额外占用空间。

## 6.3.5 小结：一套分工明确的管理制度

把这一节串起来，打开一个文件的过程是：**目录把名字翻译成编号 → 索引节点给出数据地图 → 按地图读出数据块**；而保存文件时，**日志或写时复制保证几处修改要么全成、要么全不成**。名字、档案、数据、记账各自分开，正是第八章“抽象与分层”思想的一个缩影。

不过，日志只解决了“一个人改账本时断电”的问题。如果两个程序同时要改同一个文件、同一张表，又该听谁的？这就是下一节要讨论的同步与死锁。
