# 7.4 量化与本地部署：模型文件格式与推理工具

打开一个开源模型的下载页面，你常会看到同一个模型摆着好几个版本：文件名后缀写着“FP16”“Q8_0”“Q4_K_M”之类的字样，体积从十几 GB 到几 GB 不等。同一个模型，为什么能“变小”？变小之后还是不是原来那个模型？要回答这些问题，需要先弄清模型文件里装的是什么数字，再看人们怎样压缩这些数字，最后看哪些软件能把压缩后的文件在你自己的电脑上跑起来。

## 7.4.1 模型为什么这么“重”：参数与数字精度

第一章说过，模型文件的主体是权重，也就是几十亿乃至更多个参数。每个参数是一个带小数的数字，用多少个二进制位（bit）来存它，叫作**数值精度**。

| 精度格式 | 每个参数占用 | 说明 |
|---|---|---|
| FP32（32 位浮点数） | 4 字节 | 训练中常用的“全精度” |
| FP16 / BF16（16 位浮点数） | 2 字节 | 发布开源模型时最常见的原始格式 |
| INT8（8 位整数） | 1 字节 | 常见的量化格式 |
| INT4（4 位整数） | 0.5 字节 | 本地部署中很流行的格式 |

估算体积有个简单办法：**参数量 × 每个参数的字节数**。一个约 70 亿参数（7B）的模型，用 16 位存储约需 14 GB；压到 4 位，约 3.5–4 GB。这个量级差别，决定了它是只能放在服务器显卡上，还是能装进一台普通笔记本的内存。

运行时占用的还不止权重。第七章 7.3 节提到的键值缓存（KV Cache）会随上下文变长而增长，所以实际所需内存通常比文件体积再多出一截。

## 7.4.2 量化：用更少的位数近似原来的数字

**量化**（Quantization）就是把高精度的数字映射到低精度的格子里。可以类比为把一张照片从上千万种颜色压成 256 种：每个像素的颜色都被“就近取整”，细看有偏差，整体画面仍然可辨。

最基本的做法是：把一组参数的取值范围找出来，均匀切成若干档（4 位只有 16 档），每个参数记下自己落在第几档，再额外存一个**缩放因子**（scale），用来在计算时还原出近似值。工程上为了减少误差，又发展出一些常见技巧：

- **分组量化**：不是整张权重矩阵共用一个缩放因子，而是每几十个参数一组，各算各的范围，离群的大数只影响自己所在的小组。
- **混合精度**：对误差更敏感的部分（如部分注意力层或输出层）保留较高位数，其余部分压得更狠。前面提到的“Q4_K_M”这类命名，就是 llama.cpp 项目定义的一类混合方案。
- **训练后量化与量化感知训练**：前者在模型训练完成后直接压缩，成本低、最常用；后者在训练中就模拟低精度，效果更好但需要重新训练。GPTQ、AWQ 是社区中常见的训练后量化方法名称。

量化的代价是精度损失。公开资料中较常见的经验是：8 位量化与原模型几乎难以区分；4 位在多数日常任务上仍可用，但在数学、代码和长推理上可能更容易出错；再往下到 3 位、2 位，质量下降通常会明显起来。具体影响因模型和任务而异，最可靠的办法是用自己关心的任务实际对比。

## 7.4.3 模型文件格式：同一份权重的不同“包装”

权重要存成文件，就需要约定格式。写作时开源社区中最常见的几种如下：

| 格式 | 主要来源与用途 | 特点 |
|---|---|---|
| PyTorch `.bin` / `.pt` | PyTorch 框架的传统存储方式 | 基于 Python 序列化，加载不受信任的文件存在执行恶意代码的风险 |
| Safetensors（`.safetensors`） | Hugging Face 推出 | 只存张量数据和元信息，不能夹带代码，更安全，加载也快；目前是开源模型发布的主流格式 |
| GGUF（`.gguf`） | llama.cpp 项目定义 | 单个文件内打包权重、配置和分词表，原生支持多种量化等级，面向本地 CPU/GPU 推理 |

注意格式与精度是两件事：Safetensors 文件可以是 16 位，也可以存放量化后的权重；GGUF 则最常与量化一起出现，但也可以存放 16 位等未量化的权重。下载时，从官方或可信的发布者处获取，并优先选用 Safetensors、GGUF 这类不含可执行代码的格式，是一个值得养成的习惯。

## 7.4.4 推理工具：让模型文件真正“开口”

文件本身不会说话，需要**推理引擎**（Inference Engine）读入权重、执行第二章讲过的逐层计算，并按第六章的采样策略一个个生成令牌。写作时较常见的几类工具：

- **llama.cpp**：用 C/C++ 编写的开源推理库，能在普通 CPU 上运行，也支持多种显卡和苹果芯片，是 GGUF 格式的“原产地”。
- **Ollama、LM Studio 等桌面工具**：在 llama.cpp 等底层之上做了封装，提供一键下载、命令行或图形界面，适合入门者。
- **vLLM 等服务端引擎**：面向多用户并发的服务器场景，重点优化批处理和键值缓存管理，追求吞吐量而非单机便捷。
- **Hugging Face Transformers**：研究和开发中最常用的 Python 库，灵活但对硬件要求通常更高。

本地部署的好处很实在：数据不离开自己的电脑，可离线使用，可自由调整参数和系统提示词。代价同样实在：受限于自己的内存与算力，能跑的模型规模有限，速度也可能不如云端服务。至于显卡显存、内存带宽为何决定生成速度，属于硬件层面的话题，可参阅丛书第十七册《人工智能系统》。

## 7.4.5 小结：从“文件大小”读出系统取舍

下次看到一个模型的多个版本，你可以这样读它：参数量决定“原料”有多少，精度决定每份原料占多大，格式决定它怎样打包、用什么工具打开。量化不是魔法，而是在体积、速度与质量之间做交换。理解了这一点，你就能根据自己的设备和任务，挑出合适的那一个文件。下一节我们将转向另一个选择题：开源模型与闭源模型各自意味着什么，以及怎样读懂一份模型卡。
