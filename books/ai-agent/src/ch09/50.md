# 9.1 用智能体拆解智能体：读懂它的每一步记录

假设你让一个编程智能体修复表格导出时日期变成乱码的问题。几分钟后它报告“已修复”。界面上那条可以展开的长记录里，有“读取文件”“运行命令”“修改第 42 行”“重新运行测试”等一行行条目，大多数人会直接跳过它。这一节要说明的是，这份记录正是本书前八章内容的现场证据。读懂它，你就能把智能体从一个只看结果的黑箱，变成一台能逐步检查的机器。

## 9.1.1 一份记录里有什么：轨迹的基本构成

工程上通常把智能体一次任务的完整过程叫作**轨迹**（trajectory），把保存下来的文本叫作**日志**（log）或**追踪记录**（trace）。不同产品的呈现方式不一样：有的折叠成“思考中”的小字，有的列成时间线，开发框架则常常导出结构化文件。不过拆开来看，基本构成大同小异：

| 记录中的条目 | 对应的系统部件 | 本书相关章节 |
|---|---|---|
| 用户目标、系统提示词 | 指令 | 2.2 |
| 模型的推理或计划文字 | 大脑、规划 | 2.1、3.2、6.2 |
| 工具调用（名称+参数） | 双手、函数调用 | 2.3、6.3 |
| 工具返回结果 | 感知、消息流 | 3.1、5.2 |
| 请求确认、等待用户 | 人机协作、权限 | 3.5、4.4 |
| 上下文摘要、“已压缩” | 记忆管理 | 6.4 |
| 令牌数、耗时 | 成本流 | 5.5 |

有了这张表，再看那条长记录，每一行都能找到它在骨架上的位置。读记录的第一步就是做这种归类：把每一行标上“这是想”“这是做”“这是看”。连起来以后，你会发现它几乎就是第六章讲的推理—行动循环。

## 9.1.2 让另一个 AI 当你的“解说员”

记录往往很长，里面有命令行输出、报错堆栈和代码片段，新手读起来吃力。这时可以请一个对话式 AI 来帮忙，也就是用智能体来学习智能体。具体做法是把记录复制出来，先去掉密码、密钥、客户信息等敏感内容（理由见 5.4 节），再按顺序提问：

1. **分段**：“请把这份记录按推理—行动—观察的循环切成若干轮，每轮用一句话概括。”
2. **定位**：“哪一轮是转折点？智能体在哪一步发现了真正的原因？”
3. **质疑**：“有没有多余的步骤、重复的尝试，或者没经过验证就下结论的地方？”
4. **对照**：“如果换成先列完整计划再执行的方式，这份轨迹会有什么不同？”

需要注意，解说员本身也是模型，也可能读错或编出记录里没有的细节。所以要让它在每个结论后面注明依据的是哪一行，自己再回原文核对。这样做本身就是一次 3.4 节讲的“反思与纠错”练习，只不过检查者换成了你。

## 9.1.3 从记录里认出常见问题

读多了以后，你会在记录里认出 6.5 节讲过的几类失败模式，它们各有比较明显的痕迹：

- **卡死**：同一个命令带着几乎相同的参数反复出现，报错一样，计划文字也只是换了说法。
- **跑偏**：中途开始修改与目标无关的文件，或者把“修日期格式”扩成了“重构整个模块”。
- **未验证就宣布完成**：最后一次修改之后没有运行测试，也没有重新读取输出，就直接写“已修复”。
- **被外部内容带走**：读完某个网页或文档后，计划突然转向，去做用户没有要求的事。这正是 7.5 节说的提示词注入可能留下的迹象。
- **上下文丢失**：在“已压缩”或“摘要”条目之后，智能体忘了用户早先提出的约束，比如“不要改接口”。

能指出这些痕迹，说明你检查的不再只是结果，还包括过程。对职场使用者来说这一点尤其重要：结果可能碰巧是对的，但过程里的越权或侥幸，下次就可能变成事故。

## 9.1.4 记录为什么值得认真对待

从原理上看，记录对应的是第八章控制论里的**可观测性**：系统的内部状态必须能从外部看见，才谈得上调节和纠正。智能体的决策来自概率模型，同样的任务跑两次，轨迹也可能不同（见 8.5 节）。所以单看一次结果判断不了它是否可靠，必须看过程。许多团队把轨迹保存下来用于评测和审计，原因就在这里（见 7.4、7.5 节）。一份完整的记录同时可以当作学习材料、调试依据和追责凭证。

当然，记录也有局限。界面上显示的推理文字未必完整反映模型内部真实的计算过程，有些产品只展示摘要。关于这一点，第十八册《大语言模型》有更深入的讨论。因此，判断智能体实际做了什么，应以工具调用和返回结果为准，推理文字只作参考。

从下一次任务开始，不妨把那条折叠的记录展开读一遍。读懂别人搭好的智能体之后，下一节我们动手搭一个最小的智能体，从写记录的一方去理解它。
