# 2.5 运行环境与编排程序：智能体在哪里、由谁驱动

假设你在电脑上让一个编程智能体“把这个项目里的日期格式统一改成年-月-日，然后跑一遍测试”。几分钟后，屏幕上滚过一串记录：它打开了几个文件，改了十几行代码，运行了测试命令，看到两条失败信息，又回头改了一处，最后告诉你“全部通过”。

这串动作里有几件事值得追问。文件是在哪里被打开的？测试命令是在哪台机器上运行的？大模型只会输出文字，是谁把“运行测试”这句话变成了真实的命令，又把结果送回给模型？这两个问题分别指向智能体的最后两个组成部分：**运行环境**，回答“在哪里”；**编排程序**，回答“由谁驱动”。

## 2.5.1 运行环境：智能体的“工作台”

运行环境（runtime environment）是智能体执行动作时实际所处的那片计算空间，包括它能看到的文件、能运行的程序、能访问的网络，以及这一切所在的操作系统。打个比方，模型是请来的师傅，工具是他手里的锤子和扳手，运行环境就是他干活的那间车间。车间里有什么材料、门锁着还是开着，决定了师傅实际能干成什么、可能弄坏什么。

常见的运行环境大致有下面几类：

| 运行环境类型 | 典型场景 | 特点 |
|---|---|---|
| 用户本机 | 在自己电脑的终端或编辑器里使用编程智能体 | 能直接读写你的真实文件，方便，但出错影响也直接 |
| 云端容器或虚拟机 | 网页版助手在后台“运行代码”、分析表格 | 与你的电脑隔开，任务结束可整体丢弃 |
| 浏览器环境 | 智能体代你打开网页、填写表单 | 面对的是真实网站，动作可能带来真实后果 |
| 企业内部系统 | 接入公司数据库、工单系统的业务智能体 | 权限和数据受组织规则约束 |

写作时，不少厂商会把代码执行放在临时的云端容器里，也有编程智能体直接运行在用户本机的命令行中。具体做法各家不同、变化也快，但“动作总要落在某个具体环境里”这一点不会变。

运行环境对智能体有双重意义。一方面，它是**行动的舞台**：没有一个能执行命令的环境，“跑一遍测试”就只能停留在文字上。另一方面，它也是**观察的来源**：测试报错、文件内容、网页文字，都是环境反馈给智能体的信息，智能体靠它判断下一步。正因为环境里的动作会产生真实后果，人们常给它加一层隔离，这就是沙箱（sandbox），即一个与外界隔开、出了问题也不会殃及真实系统的受限空间。沙箱和权限的技术细节留到第七章再谈，这里先记住：**智能体能做多少事，上限往往由运行环境划定，而不只由模型能力划定。**

## 2.5.2 编排程序：让循环转起来的“调度员”

再来看第二个问题。大模型本身是一个“输入文字、输出文字”的函数，它不会自己醒来，也不会自己去敲命令。真正让智能体一圈圈运转起来的，是一段普通的软件，称为编排程序（orchestrator），有时也叫智能体运行框架或“外壳”（harness）。

把一次任务拆开看，编排程序大致在反复做这几件事：

1. **组装输入**：把系统提示词、用户任务、可用工具的说明、之前的对话和工具结果拼成一份完整的上下文，交给模型。
2. **解析输出**：读取模型的回复，判断它是在直接回答用户，还是在请求调用某个工具，比如“运行命令 `npm test`”。
3. **执行动作**：如果是工具请求，就在运行环境里真正执行，必要时先停下来请用户确认。
4. **回送结果**：把命令输出、报错信息等结果写回上下文，再次调用模型。
5. **判断停止**：模型宣布完成、达到步数或时间上限、出现无法处理的错误，或用户叫停时，结束循环。

可以把这想象成一家餐馆。模型是只在后厨思考菜单的主厨，他说“需要两个鸡蛋”，但自己不出门；编排程序就是跑堂兼采购，负责把顾客的要求递进去，把主厨的话变成实际行动，再把买回的东西和顾客的新意见带回来。主厨再聪明，没有这位跑堂，菜也上不了桌。

需要强调的是，编排程序本身**通常不是人工智能**，而是开发者写好的确定性代码。它不负责“想”，只负责“转”，但它决定了很多关键规则：给模型看多少历史、允许调用哪些工具、哪些动作要人工确认、最多跑多少步。同一个模型放进两套不同的编排程序里，表现可能差别很大。

## 2.5.3 两者如何配合：一次任务的完整画面

把前面几节的部件放在一起，回到开头改日期格式的例子：

- **模型**读取上下文，决定“先搜索项目里所有日期格式的写法”；
- **编排程序**识别出这是一个搜索工具请求，交给运行环境执行；
- **运行环境**在项目文件夹里完成搜索，返回结果；
- **编排程序**把结果放回上下文，再次唤醒模型；
- 如此往复，直到测试通过、模型给出总结，编排程序结束循环，把结果呈现给你。

| 部件 | 一句话角色 | 如果缺了它 |
|---|---|---|
| 模型 | 决定下一步做什么 | 没有判断，只剩固定脚本 |
| 指令 | 规定身份、目标和规矩 | 不知道该做什么、守什么规矩 |
| 工具 | 提供可用的动作 | 只能说，不能做 |
| 记忆 | 保存过程与知识 | 每一步都从零开始 |
| 运行环境 | 动作真正发生的地方 | 动作无处落地 |
| 编排程序 | 驱动循环、执行规则 | 部件之间无法串联 |

这张表也提醒我们一个常见误解：人们习惯说“AI 自己完成了任务”，但从系统角度看，完成任务的是**模型、程序和环境的组合**。模型提供判断，编排程序提供秩序，运行环境提供舞台和反馈。

## 2.5.4 小结：看见“幕后”的两个部件

使用智能体时，模型的回复最显眼，运行环境和编排程序却常常隐身在幕后。下次看到智能体的执行记录，不妨问两句：这一步是在哪里执行的，我的电脑、云端容器，还是某个网站？是谁决定要先征求我同意，又是谁决定它该停下来？能回答这两个问题，你就看清了智能体从“会说”到“会做”的那座桥。
