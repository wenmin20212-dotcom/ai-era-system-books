# 2.3 双手：工具、函数与外部服务

假设你对智能体说：“帮我查一下明天上海的天气，如果下雨，就在我的日历里把下午的户外跑步改到室内。”几秒钟后，它回复：“明天上海有小雨，已将 15:00 的跑步改为健身房训练。”

整个过程中，大语言模型本身并没有“看见”天气，也没有“碰到”你的日历。它不能联网，也不能改写任何文件。它只会读入文字、写出文字。真正去气象服务查询、去日历系统修改日程的，是另一组部件，也就是智能体的“双手”：工具（Tool）、函数（Function）与外部服务（External Service）。

## 2.3.1 为什么大脑需要双手

上一节讲到，大语言模型（Large Language Model，LLM）是智能体的“大脑”。这个大脑有三个天生的局限：

- **知识有截止时间**：训练数据停在某个时间点，它不知道今天的天气和股价。
- **只能产出文字**：它不能真的发邮件、建文件、点按钮。
- **精确计算不可靠**：让它心算一长串数字，可能出错。模型内部的原因，见第十八册《大语言模型》。

工具就是为弥补这三点而接上去的。可以这样类比：模型像一位坐在办公室里的顾问，见识广、会判断，但手边没有电话也没有电脑。工具相当于给他配了一部电话、一台计算器和一把办公室钥匙。顾问仍然负责想“该做什么”，具体动作由这些器具去完成。

## 2.3.2 工具是什么：一份“说明书”加一段“真程序”

在工程上，一个工具通常由两部分组成。

**第一部分是给模型看的说明书**，一般包括：

| 项目 | 例子 | 作用 |
|---|---|---|
| 名称 | `get_weather` | 让模型能指名调用 |
| 功能描述 | “查询某城市某天的天气预报” | 让模型判断何时该用 |
| 参数格式 | 城市（文字）、日期（年-月-日） | 规定调用时必须填什么 |

参数格式常用 JSON（JavaScript Object Notation，一种结构化的数据书写格式）来描述，好比一张有固定栏目的申请表。

**第二部分是真正执行的程序**。它由开发者事先写好，运行在模型之外，负责联网请求气象接口、读写日历数据库，再把结果交回来。

所谓“函数调用”（Function Calling），就是模型读完说明书后，输出一段格式规整的文字，例如“调用 get_weather，城市=上海，日期=明天”。外面的编排程序识别出这段文字，替它运行对应的程序，再把结果“小雨，18℃”作为新消息送回模型。从模型的角度看，它始终只是在写字和读字，“动手”这一步是由外部程序完成的。模型怎样“说出”一个动作，第六章 6.3 节会展开讲。

## 2.3.3 常见的几类“手”

工具种类繁多，按作用大致可以分成以下几类：

1. **信息获取类**：网页搜索、读取网页、查询数据库、读本地文件。负责把模型不知道的信息找回来。
2. **计算与代码类**：计算器、代码解释器（Code Interpreter，可以运行一段程序的环境）。负责精确计算和数据处理，例如把一张表格做汇总统计。
3. **操作与写入类**：发邮件、改日历、提交代码、在网页上填表。这类工具会真实地改变外部世界。
4. **界面操作类**：有些系统让模型通过截图“看”屏幕，再输出鼠标点击和键盘输入的指令，用来操作没有接口的软件。写作时，Anthropic、OpenAI 等公司都公开发布过这类“操作电脑”的能力，但仍处于发展阶段，速度和稳定性不如直接调用接口。
5. **外部服务类**：通过应用程序接口（Application Programming Interface，API，即软件之间约定好的对话方式）连接的地图、支付、企业内部系统等。

这几类工具的风险差别很大。查天气出错，结果只是答案不准；发错邮件或删错文件，往往很难撤回。所以第 4.4 节和第七章讲权限与沙箱时，会重点关注第 3 类工具。

## 2.3.4 工具设计的三条朴素原则

给智能体配工具，并不是越多越好。从各家公开的开发经验来看，有几条原则比较稳定，不容易过时：

- **描述要写清楚**：模型只能依靠说明书来判断用哪个工具。如果描述含糊，比如两个工具都叫“查询”，模型就容易选错。这和给新同事交代工作是一个道理。
- **数量要克制**：每份说明书都要占用模型的上下文空间，工具一多，既费成本又容易混淆。常见做法是按任务挑选一小组相关工具。
- **返回要精炼**：工具返回的结果会被送回模型。把一整个网页原样塞回去，模型反而抓不住重点。好的工具会先做筛选，只返回关键信息。

此外，同类工具在不同系统里各写一套，接入成本很高。于是业界出现了统一的工具接入协议，例如 Anthropic 在 2024 年底提出的模型上下文协议（Model Context Protocol，MCP），目的是让工具像 USB 设备一样即插即用。它的细节留到第 4.1 节和第 7.2 节再讲。

## 2.3.5 小结：手长在大脑之外

回到开头的天气与日历任务：模型判断需要先查天气，于是写出调用请求，由天气工具执行；看到返回“小雨”后，模型再决定改日程，由日历工具执行。在这个过程中，模型负责判断，工具负责执行，编排程序负责在两者之间传递消息。

理解了这一点，就不会把智能体想得太玄：它能做什么，很大程度上取决于给它接上了哪些工具、开放了多大的权限。另一方面，工具执行完以后，结果要放到哪里、能保留多久，模型下次还能不能想起来，这就是下一节要讲的“记忆”。
