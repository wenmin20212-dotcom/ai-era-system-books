# 7.1 智能体框架与开发工具

假设你在公司里负责一个小项目：让 AI 每天早上自动读取前一天的销售表格，查出异常的数据，写一段说明发到团队群里。你在聊天窗口里试过，模型确实能看懂表格、写出说明。可是一旦要让它“每天自己跑”，问题马上冒出来：表格从哪里读？出错了谁来重试？发消息的接口怎样接？每一步做了什么，事后怎么查？

这些问题和模型聪不聪明关系不大，它们属于工程问题。前面几章拆开过智能体的各个部件：模型、指令、工具、记忆、运行环境和编排程序。把这些部件组装成一台能稳定运转的机器，需要大量重复的“管道活”。智能体框架和开发工具就是为了把这部分活儿标准化而出现的。

## 7.1.1 框架是什么：一套预制好的“骨架和接头”

**智能体框架**（Agent Framework）指的是一类软件库或平台，它把搭建智能体时反复要写的代码预先写好，让开发者只需填入自己的任务逻辑。可以拿装修来类比：从零盖房子要自己打地基、砌墙、布水电；买一套精装公寓的毛坯框架，承重墙和管线已经就位，你只决定房间怎么布置。

一个典型的框架通常会提供下面几类“预制件”：

| 预制件 | 解决的问题 | 对应本书前文 |
|---|---|---|
| 模型接入层 | 用统一的写法调用不同厂商的模型 | 2.1 大脑 |
| 提示词模板 | 把系统提示词、角色和任务说明拼装成固定格式 | 2.2 指令 |
| 工具注册与调用 | 把一个函数登记为“工具”，自动生成说明并解析模型的调用请求 | 2.3 双手、6.3 工具调用 |
| 记忆模块 | 保存对话历史、做摘要压缩、接入向量检索 | 2.4 记忆、6.4 记忆管理 |
| 循环与编排 | 实现“推理—行动”循环，或按流程图调度多个步骤、多个智能体 | 6.1、4.3 |
| 日志与追踪 | 记录每一步的输入、输出、耗时和令牌消耗 | 5.5 成本流 |

可以看到，框架本身并不带来新的“智能”。它把前面讲过的那些结构和机制做成了可以复用的零件。理解了骨架，再看任何框架，都能认出它在哪一处帮你省了事。

## 7.1.2 三种常见的组织方式

不同框架的设计思路差别很大，但大致可以归成三种组织方式。

**第一种是链式或流水线式。** 把任务写成固定顺序的步骤：先检索，再总结，再输出。流程清楚、容易调试，适合步骤基本确定的任务，比如前面的销售日报。代价是灵活性低，遇到意外情况不会自己改道。

**第二种是图式或状态机式。** 把每一步看成图上的一个节点，节点之间的连线可以带条件，也允许回到前面的节点形成循环。这种方式能同时表达“固定流程”和“出错重试、人工审批后再继续”这类分支。写作时开源社区中有一些较流行的框架采用这种思路，例如 LangChain 团队推出的 LangGraph。

**第三种是对话式多智能体。** 定义几个各有角色的智能体，比如“研究员”“写作者”“审稿人”，让它们通过互相发消息协作完成任务。微软研究院发起的 AutoGen（现已进入维护模式，微软推荐改用其后继产品 Microsoft Agent Framework）、开源项目 CrewAI 等都以这种方式为主要特色。它贴近人的团队分工，好处是直观，难点是消息来回多了，成本和失控风险也会上升（参见 4.3 节与 5.5 节）。

这三种方式并不互斥，很多框架同时支持，开发者按任务特点挑选。

## 7.1.3 从代码库到“开箱即用”：开发工具的光谱

框架之外，还有一大类开发工具，按使用门槛大致排成一条光谱：

- **模型厂商的官方工具包。** 写作时，OpenAI、Anthropic、谷歌等公司都发布了各自的智能体开发包，例如 OpenAI 的 Agents SDK、Anthropic 的 Claude Agent SDK。它们与自家模型配合紧密，通常也支持接入通用工具协议（下一节详述）。
- **通用开源框架。** 不绑定某家模型，社区活跃，组件丰富，适合需要灵活组合的开发者。
- **低代码或可视化平台。** 用拖拽方块、连线的方式搭流程，不必写多少代码。国内外都有这类平台，适合业务人员快速做原型。
- **现成的智能体产品。** 比如编程智能体、带浏览器操作能力的助手，用户直接下达任务，不涉及搭建。

越往光谱下端越省事，越往上端越可控。管理者在引入时，常常需要在“快速上线”和“能看清、能改动每一步”之间权衡。

## 7.1.4 选框架时真正该看什么

框架更新极快，名字和功能几个月就可能变样，本书不推荐具体选择，只给出几条不易过时的判断标准：

1. **透明度。** 能否看到每一步发给模型的完整提示词和工具返回结果？封装太深的框架，出了问题很难定位。
2. **可观测性。** 有没有内置的追踪和日志，能否统计耗时与令牌消耗？
3. **控制点。** 能否方便地插入人工确认、权限检查和超时中止？这直接关系到第 7.3、7.5 节讨论的安全问题。
4. **可替换性。** 换一家模型、换一个工具，要改多少代码？是否支持开放的工具协议？
5. **任务匹配度。** 简单任务用重型多智能体框架，往往得不偿失。不少有经验的工程师的做法是：先用最朴素的循环写出来，确认真有需要，再引入框架。

最后一条值得多说一句。框架省下的是重复劳动，同时也会加进一层抽象。一个智能体的核心循环，本质上不过是“把上下文发给模型—解析它要调用的工具—执行—把结果放回上下文”，几十行代码就能写出雏形（第 9.2 节会带你动手试）。先理解这个内核，再用框架，才能在框架的便利和自己的掌控之间找到合适的位置。

## 7.1.5 小结

智能体框架把模型接入、提示词、工具、记忆、循环与日志这些部件做成了标准零件，开发工具则从代码库延伸到可视化平台和现成产品。它们解决的是“怎样把智能体可靠地装起来”。但零件要能互相插接，还需要统一的接口标准：工具怎样描述自己，上下文怎样传递。这正是下一节“工具与上下文协议”要回答的问题。
