# 7.2 工具与上下文协议：让工具即插即用

假设你在电脑上用一个编程智能体改代码，同时希望它能读公司内部的需求文档，再查一下项目管理系统里的任务状态。很多人第一次做这类配置时会发现，“让智能体连上某个系统”往往不是在聊天框里说一句话，而是要在设置文件里添加一个“服务器”，填上名称、启动命令或网址，有时还要授权一次。添加完成后，智能体的工具列表里就多出几项新能力。

这个过程背后的思路，和电脑接口从各式专用插头走向统一标准很相似。本节要讲的就是这种思路：用一套公共的**协议**（Protocol，即双方事先约定好的通信规则），把工具接入从逐个定制的手工活，变成即插即用的标准件。

## 7.2.1 没有协议时：M×N 的麻烦

第四章讲过，模型通过函数调用“说出”一个动作，再由编排程序真正去执行。问题在于，每种智能体应用描述工具、传递参数、返回结果的格式都可能不一样。如果有 M 个智能体应用，要接入 N 个外部系统（文件、数据库、日历、代码仓库……），最坏情况下需要写 M×N 份适配代码。每份代码各自维护，任何一方改版，都可能有一批接入失效。

协议的作用，是在中间放一层大家共同遵守的约定。智能体应用只需要实现一次“会说这套协议”，外部系统也只需要实现一次“按这套协议提供能力”，工作量就从 M×N 降到大约 M+N。互联网早已证明过这条路走得通：浏览器和网站之所以能互通，靠的正是 HTTP 这类公共协议，而不是两两谈判。

## 7.2.2 一个代表性例子：模型上下文协议

写作时，这一方向上影响较大的一个开放标准，是 Anthropic 公司在 2024 年 11 月发布并开源的**模型上下文协议**（Model Context Protocol，MCP）。该公司用 USB-C 接口作比方：不同设备用同一种接口连接，不同的工具和数据源也通过同一种协议接入智能体。此后，多家公司的智能体产品和开发工具陆续宣布支持这一协议。不过各产品的具体支持程度和配置方式变化较快，使用时应以对应产品的官方文档为准。

MCP 的基本结构可以用三个角色来概括：

| 角色 | 英文 | 做什么 | 类比 |
|---|---|---|---|
| 宿主 | Host | 用户直接使用的智能体应用，如桌面助手、编程工具 | 电脑本身 |
| 客户端 | Client | 宿主内部负责与某一个服务器保持连接的组件 | 电脑上的一个接口 |
| 服务器 | Server | 把某个外部系统的能力按协议暴露出来的程序 | 插上去的外设 |

服务器向智能体提供的内容主要有三类：**工具**（Tools），是可以执行的动作，例如“创建任务”“运行查询”；**资源**（Resources），是可以读取的数据，例如文件内容、数据库记录；**提示模板**（Prompts），是预先写好的任务说明，方便用户直接调用。这样划分的好处是“能做什么”和“能看什么”在接口层面就分开了，后面讲权限控制时更容易管理。

在通信层面，MCP 的消息采用 JSON-RPC 2.0 格式。JSON 是一种结构化文本格式，RPC 是“远程过程调用”（Remote Procedure Call）的缩写，意思是像调用本地函数一样请求另一个程序办事。服务器可以作为本机上的一个进程，通过标准输入输出与宿主通信；也可以部署在远端，通过 HTTP 访问。

## 7.2.3 即插即用是怎样发生的

把一个新服务器接进智能体，大致会经过以下几步：

1. **建立连接与握手**：客户端和服务器互相告知协议版本和各自支持的功能，类似两台设备插上后先确认“彼此会说哪种话”。
2. **能力发现**：客户端询问服务器“你有哪些工具”，服务器返回每个工具的名称、用途说明和参数格式。
3. **放入上下文**：宿主把这些工具说明交给模型，模型因此“知道”自己多了哪些能力。
4. **调用与返回**：模型决定使用某个工具时，宿主通过客户端发出请求，服务器执行后把结果送回，结果再进入下一轮推理。

关键在第 2 步。工具清单是运行时动态获取的，而不是写死在智能体程序里，所以新增一个服务器不需要修改智能体本身。这正是“即插即用”的含义。

## 7.2.4 协议解决了什么，没有解决什么

统一协议带来的是互通性，但它不会自动带来可靠性和安全性。有三点需要注意：

- **说明写得好不好，仍然决定用得好不好**。模型靠工具说明来判断何时调用、怎样填参数，说明含糊，调用就容易出错。
- **工具越多，上下文越挤**。每个工具的说明都要占用令牌，一次接入几十个服务器，既增加成本，也会干扰模型的选择。第五章讲的上下文流在这里同样适用。
- **第三方服务器就是第三方代码**。它返回的内容可能夹带恶意指令，它执行的动作可能越权。协议规定的是“怎么说话”，而“该不该信、能不能做”需要靠沙箱、权限和人工确认来把关，这是下一节和 7.5 节的主题。

另外，在“智能体连接工具”之外，业界也在探索“智能体连接智能体”的协议。例如谷歌公司在 2025 年提出了 Agent2Agent（A2A）协议，用于让不同来源的智能体互相发现并委派任务。这类标准仍在发展中，格局可能变化，但背后的逻辑不变：**把两两定制的连接，换成公共约定上的连接**。

理解了这一点，再看到任何新协议的名字，你都可以用同一组问题去拆解它：它连接的是谁和谁，约定了哪些消息，怎样发现对方的能力，又把安全问题留给了谁。
