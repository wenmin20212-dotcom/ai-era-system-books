# 6.1 行動作業系統的能耗博弈：從 EAS 排程到行程墓碑

拿起手機，連續滑十分鐘短影音，機身微微發熱，電量掉得飛快；把它丟在桌上一整晚，隔天早上電量卻只少了一點。這兩種狀態背後，是同一個「看不見的管家」在做決定：行動作業系統。它要回答兩個問題：**此刻的任務該交給哪顆核心去做？**以及**你看不見的那些應用程式，還有沒有資格繼續消耗電量？**前一個問題由排程器回答，後一個問題由背景管控機制回答。本節就沿著這兩條線，看看作業系統如何在效能與續航之間做精細的取捨。

## 6.1.1 為什麼「跑得快」不等於「好排程」

第三章介紹過，手機 SoC（系統單晶片，System on Chip）裡的 CPU 通常由「大核」和「小核」混搭組成。大核像一輛大排氣量跑車，爆發力強但油耗高；小核像一輛電動自行車，速度有限卻極其省電。

傳統電腦的排程思路比較樸素：哪顆核心閒置、哪顆核心效能高，就把任務往那裡放，追求「盡快完成」。但在手機上，這種思路會出問題。設想一個在背景同步通訊錄的小任務，如果把它丟給大核，大核需要提高電壓和頻率才能運作，能耗的增長遠遠超過任務本身的價值。電池容量有限，散熱空間又極其狹窄，手機的排程目標不能只是「快」，而必須是「**用最少的能量把事情辦好**」。

## 6.1.2 EAS：帶著「電費帳單」做決定的排程器

為了解決這個問題，ARM 與 Google 共同主導推出了 **EAS（能耗感知排程器，Energy Aware Scheduling）**，並將其納入 Android 所使用的 Linux 核心。

EAS 的核心，是內嵌在系統裡的一張**能量模型（Energy Model）**圖表。要理解它，先認識一個術語：**OPP（工作效能點，Operating Performance Point）**。每顆 CPU 核心並不是只有「開」和「關」兩種狀態，而是有一系列電壓與頻率的組合檔位，就像汽車的不同排檔。能量模型記錄的，就是**每個核心在每個電壓頻率檔位下的真實功耗，精確到毫瓦級**。

有了這張表，EAS 就像一位手裡拿著電費單的物業經理。每當一個新任務到達，它不會只問「誰最閒」，而是逐一試算：

> 如果把這個任務分配給核心 X，整個 SoC 增加的系統總能量消耗，是不是所有方案裡最低的？

這裡有兩個關鍵詞值得細細品味。

- **「全 SoC」**：EAS 看的是整顆晶片的總帳，而不是單一核心的局部帳。把任務塞進一顆已經在運作的小核，可能只需稍微提升它的檔位；而喚醒一顆沉睡的大核，則要額外付出「開燈」的代價。
- **「增加的能量」**：它比較的是邊際成本，也就是「多做這件事，要多花多少電」。

下面用一個簡化的情境對照幫助理解：

| 情境 | 粗放式排程的做法 | EAS 的思考方式 |
|---|---|---|
| 背景同步郵件 | 交給閒置的大核，迅速完成 | 小核低檔位即可勝任，總能耗更低，交給小核 |
| 滑動清單、開啟應用程式 | 平均分配 | 試算後發現小核需拉滿檔位且仍會卡頓，交給大核反而划算 |
| 多個輕任務同時到達 | 分散喚醒多顆核心 | 盡量集中到已喚醒的核心上，讓其餘核心繼續休眠 |

可以看出，EAS 並不是一味「偏愛小核」，而是用數據說話。能量模型越準確，排程的取捨就越合理，這也是晶片廠商需要為每款 SoC 精心校準這張表的原因。

## 6.1.3 背景的另一場戰爭：讓「隱身應用程式」真正停下來

排程器管的是「正在工作的任務如何分配」，但還有一個更隱蔽的耗電來源：那些你已經切走、卻仍在偷偷運作的應用程式。它們可能定時連網、重新整理資料，甚至反覆喚醒處理器，這類行為常被稱為「流氓喚醒」。一支手機裝了幾十個應用程式，如果每個都在背景「小動作不斷」，待機續航就會被蠶食殆盡。

兩大行動作業系統採用了思路相近、實作不同的方案：

**iOS 的墓碑機制。**當你把一個應用程式切到背景，iOS 會在短短數秒內將其執行緒徹底暫停。應用程式此時就像立了一塊「墓碑」：它的狀態被保留在記憶體中，介面、進度都還在，但不再獲得任何 CPU 時間。等你重新點開，它從墓碑中「復活」，看起來彷彿一直在原地等你。

**Android 的 cgroups 凍結。**Android 藉助 Linux 核心的 **cgroups（控制群組，Control Groups）** 機制，把程序依前景、背景等類別分組管理。應用程式退到背景後，系統可以向其發送 **SIGSTOP 訊號**，即一種讓程序立即暫停的核心指令，從而把它從 CPU 的執行佇列中切斷。被凍結的程序無法再自行喚醒處理器，流氓喚醒也就無從發生。

打個比方：墓碑機制和 cgroups 凍結，都像圖書館閉館時替每位讀者的書桌拍照存檔後請人離場。書本擺放不動，燈卻可以全部關掉；讀者回來時，桌面恢復原樣，繼續閱讀。

| 對比項目 | iOS 墓碑機制 | Android cgroups 凍結 |
|---|---|---|
| 觸發時機 | 應用程式切出後數秒內 | 應用程式退至背景後 |
| 實作手段 | 徹底暫停應用程式執行緒 | 透過控制群組發送 SIGSTOP，切斷執行佇列 |
| 核心效果 | 保留狀態，不占用 CPU | 杜絕背景流氓喚醒 |

當然，音樂播放、導航、下載等確實需要在背景執行的任務，系統會透過專門的權限和服務通道放行，而不是一刀切。

## 6.1.4 小結：省電是一門「算帳」的學問

把兩條線合起來看，行動作業系統的能耗管理可以概括為：**對前景任務精打細算，對背景應用程式嚴格管束**。EAS 依靠能量模型，在每一次任務分配時計算全域能耗的最佳解；墓碑機制與 cgroups 凍結，則讓不在你視線裡的應用程式真正安靜下來。這正是那支手機能在你手中流暢運作、又能在桌上安靜度過一夜的軟體根源。

不過，算帳再精明，也擋不住重負載下熱量的持續累積。當晶片溫度逼近極限時，系統還要動用另一套更強硬的自保手段，這就是下一節要討論的溫度牆與熱節流。
