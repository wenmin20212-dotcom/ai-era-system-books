# 7.4 软件安全：漏洞、补丁与安全开发

打开手机的“设置—系统更新”，或者留意一下应用商店里某个应用的更新说明，你常会看到一句话：“修复了若干问题，提升了安全性。”这句话很短，背后却是一条完整的链条：有人发现了代码里的缺陷，有人评估它有多危险，有人写出修复，再通过发布流程把修复送到你的设备上。软件安全不是在软件做完之后贴上去的一层保护膜，它贯穿编写、构建、运行和更新的每个环节。本节就沿着这条链条，看看漏洞从哪里来，补丁怎样到达你手中，以及工程团队怎样在开发阶段就减少漏洞。

## 7.4.1 漏洞是什么：被人利用的缺陷

前面几章讲过，软件就是按规则执行的代码。**漏洞**（Vulnerability）指的是代码、配置或设计中的缺陷，攻击者可以利用它让系统做出设计者没有打算让它做的事，比如读取别人的数据、冒充别人的身份、让服务瘫痪，甚至在服务器上执行任意命令。

可以用一栋办公楼打比方。普通的程序错误（Bug）好比电梯按钮偶尔失灵，让人不便；漏洞则好比后门的锁坏了，并且有人知道这一点。两者的区别不在于代码错得有多严重，而在于这个错误能不能被**有意利用**。

安全领域常用三个目标来衡量“被破坏了什么”，合称 CIA 三要素：

| 目标 | 中文含义 | 被破坏时的例子 |
|---|---|---|
| Confidentiality | 机密性：数据只给该看的人看 | 用户手机号、聊天记录被泄露 |
| Integrity | 完整性：数据不被未经授权地篡改 | 订单金额被改小、账户余额被修改 |
| Availability | 可用性：该用的时候能用 | 服务被大量恶意请求压垮，无法访问 |

## 7.4.2 几类常见漏洞：问题多出在“信任了不该信任的东西”

漏洞种类很多，但不少常见类型有一个共同根源：程序把外部输入当成了可信的内容。下面几类在公开的安全资料中反复出现，例如开放 Web 应用安全项目（OWASP）定期整理的 Web 应用风险清单。

- **注入**（Injection）：第 2.4 节讲过，应用通过 SQL 语句操作数据库。如果程序把用户在搜索框里输入的文字直接拼进 SQL 语句，攻击者就可以输入一段精心构造的文字，让数据库执行额外的命令。这就是 SQL 注入。常见防御办法是使用“参数化查询”，让数据库始终把用户输入当作数据，而不当作命令。
- **跨站脚本**（Cross-Site Scripting，XSS）：网页把用户提交的内容原样显示出来，如果其中夹带一段脚本，其他用户浏览时浏览器就会执行它，可能导致登录凭证被窃取。防御办法是在输出前对内容做转义处理。
- **访问控制失效**：第 3.4 节区分了“认证”和“授权”。如果服务端只检查“你是否登录”，不检查“这份订单是否属于你”，那么用户只要把网址里的订单编号改一个数字，就可能看到别人的订单。
- **内存安全问题**：用 C、C++ 这类需要程序员手动管理内存的语言写成的程序，可能出现缓冲区溢出，也就是写入的数据超出预留空间，覆盖了相邻的内存。多家大型软件厂商公开披露过，其严重漏洞中有相当大的比例与内存安全有关。这也是近年来 Rust 等内存安全语言受到关注的原因之一。
- **依赖中的漏洞**：第 7.1 节讲过，一个应用往往依赖成百上千个开源组件。其中任何一个有漏洞，都可能波及整个应用。

## 7.4.3 从发现到补丁：一个漏洞的生命周期

漏洞被发现之后，通常会经历一段相对规范的流程：

1. **发现**：发现者可能是厂商内部的安全团队、外部研究者，或者参与“漏洞赏金计划”的人。漏洞赏金计划由企业设立，向报告漏洞的人支付奖励。
2. **报告与编号**：广泛使用的公共漏洞编号体系叫 CVE（Common Vulnerabilities and Exposures，通用漏洞披露）。它给每个公开的漏洞分配一个形如“CVE-年份-序号”的唯一编号，方便全世界的人指称同一个问题。严重程度常用 CVSS（通用漏洞评分系统）打分，满分为 10 分。
3. **协调披露**：业界普遍做法是发现者先私下通知厂商，给对方一段修复时间，再公开细节，以免在补丁出现前就把攻击方法交给坏人。
4. **修复与发布**：开发者写出修复代码，经过第 5.4 节讲的构建、测试和发布流程，形成补丁。
5. **部署**：这是常被忽视的一步。补丁发布了，不等于漏洞消失了。服务端的修复由运营方部署后即可生效；手机应用、操作系统和路由器则要等用户真正完成更新。很多被大规模利用的漏洞，其实早已有补丁，只是大量设备没有更新。

在补丁出现之前就被利用的漏洞，叫“零日漏洞”（Zero-day），意思是厂商可以用来修复的时间为零。零日漏洞稀少且危险，因此在安全研究中备受关注。

## 7.4.4 安全开发：把安全“左移”

与其等漏洞被发现后再修补，不如在开发阶段就减少漏洞。在软件交付流程图上，越早的阶段画得越靠左，所以这种思路常被称为“安全左移”。它和第 6.5 节的测试思想一脉相承：缺陷发现得越早，修复成本越低。常见做法包括：

| 阶段 | 典型做法 |
|---|---|
| 设计 | 威胁建模：系统地设想“谁会攻击、从哪里攻击、想得到什么” |
| 编码 | 遵循安全编码规范；优先选用内存安全的语言和成熟的安全库 |
| 代码评审 | 在第 5.3 节的合并请求中专门检查权限校验、输入处理等环节 |
| 构建 | 静态应用安全测试（SAST），即不运行程序、直接扫描源代码；软件成分分析（SCA），即检查依赖中是否有已知 CVE |
| 测试 | 动态应用安全测试（DAST）和模糊测试（Fuzzing），后者向程序大量输入随机或畸形的数据，看它会不会崩溃 |
| 运行 | 最小权限原则、日志审计、及时打补丁 |

这些检查越来越多地被写进第 5.4 节讲的持续集成流水线：代码一提交，扫描就自动运行。有些团队会配置规则，发现高危问题时直接阻止合并。这种把开发（Dev）、安全（Sec）和运维（Ops）融为一体的做法，常被称为 DevSecOps。

还有一条朴素的原则叫**纵深防御**：不把安全寄托在单一环节上。防火墙、身份认证、权限检查、数据加密和日志监控层层设防，即使某一层被突破，后面还有阻拦。这和第 8.4 节将要谈到的“没有银弹”遥相呼应：安全没有一劳永逸的单一手段。

## 7.4.5 小结：安全是一种持续的过程

回到开头那句“提升了安全性”。现在你可以把它展开理解：某处代码存在被利用的可能，有人按规范报告了它，开发团队写出修复，再借助发布流程把修复送到你的设备上。你点下“更新”的那一刻，就是这条链条的最后一环。对普通用户来说，及时更新系统和应用、只从可信渠道安装软件、开启双重验证，就是参与软件安全最直接的方式。

漏洞的发现和修复，越来越多地借助自动化工具，AI 也开始在其中发挥作用：它既能帮助审查代码中的隐患，也可能写出带有隐患的代码。下一节我们就来看 AI 辅助编程给软件工程带来的新变化。
