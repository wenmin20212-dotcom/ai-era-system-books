# 7.1 开源软件与软件供应链

打开手机的“设置—关于本机”，往下翻，很多系统里都能找到一个叫“开源许可”或“法律信息”的入口。点进去，是一长串陌生的名字，后面跟着 MIT、Apache、GPL 之类的字样。这份清单说明，你手里这个应用并不是一家公司从零写出来的，它的大部分代码来自世界各地的开源项目。这些项目从哪里来，又怎样一层层流进你的手机，就是本节要讲的“软件供应链”。

## 7.1.1 开源：公开源代码，并约定怎样使用

开源软件（Open Source Software）指源代码公开、允许他人查看、修改和再分发的软件。“公开”只是一半，另一半是许可证（License），它是一份法律文本，规定别人可以怎样用这些代码。常见的许可证大致分两类：

| 类型 | 代表 | 核心要求 | 通俗理解 |
|---|---|---|---|
| 宽松型 | MIT、BSD、Apache 2.0 | 保留版权和许可声明等少量义务即可，可用于闭源商业产品 | “拿去用，记得写上我的名字” |
| 著佐权型（Copyleft） | GPL 系列 | 分发修改后的作品时，也要以相同许可证公开源代码 | “你可以用，但改进后要同样分享出来” |

手机里那份“开源许可”清单，正是为了履行这些许可证中“保留声明”的义务。对需要和软件团队打交道的管理者来说，许可证不是技术细节，而是合规问题：把 GPL 代码混进闭源产品后对外发布，可能带来法律风险。

开源能成为软件业的基础设施，原因很朴素：一个通用问题，比如解析日期、压缩图片、加密通信，没有必要每家公司各写一遍。全世界的开发者共同维护一份代码，发现问题的人更多，修复也更快。Linux 内核、各种编程语言的编译器与运行时、主流数据库和网页框架，许多都是开源项目。

## 7.1.2 供应链：依赖的依赖的依赖

第二章讲过，开发者通过包管理器（Package Manager）引入库，比如 JavaScript 生态的 npm、Python 的 pip。问题在于，你引入的一个库，自己又依赖别的库，后者再依赖更多的库。这种层层嵌套叫传递依赖（Transitive Dependency）。

可以把它类比成一盒超市里的饼干：品牌方只直接采购了面粉、黄油和包装盒，但面粉来自哪片麦田、黄油用了哪家牧场的牛奶，品牌方未必清楚。软件也一样。一个普通的网页项目直接声明的依赖可能只有几十个，展开后的传递依赖却可能达到数百甚至上千个。从开源作者写下代码，到包仓库托管，到开发者下载，到构建打包，再到发布到应用商店或服务器，这条链路就是软件供应链（Software Supply Chain）。链上任何一环出问题，最终都会落到用户手里。

## 7.1.3 三个真实事件，三种风险

几起公开报道过的事件，正好对应供应链上的不同薄弱点：

- **一个小包消失：left-pad（2016 年）。** npm 上一个只有十来行、用来在字符串左边补空格的小包被作者撤下，依赖它的大量项目随即构建失败。它暴露的是“可用性”风险：一个看似微不足道的零件，可能撑着许多项目。
- **一个普遍漏洞：Log4Shell（2021 年底）。** Java 世界里广泛使用的日志库 Apache Log4j 被发现存在严重漏洞（编号 CVE-2021-44228），攻击者构造一段特殊文本让程序记录下来，就可能远程执行代码。许多企业遇到的第一个难题不是修复，而是先弄清楚“我的哪些系统用到了 Log4j”。
- **一次蓄意投毒：xz 后门（2024 年）。** 有人以贡献者身份在开源压缩工具 xz 项目中长期参与维护、逐步取得信任，随后在发布包里植入后门。一位工程师在排查登录变慢时偶然发现了异常，问题在大范围扩散前被拦下。它暴露的是“信任”风险：很多关键开源项目实际只由一两位志愿者维护，精力有限，容易成为突破口。

## 7.1.4 怎样让供应链更可靠

针对这些风险，业界逐渐形成了一套做法，写作时较常见的有：

1. **锁定版本。** 用锁文件（Lock File）记下每个依赖的确切版本和校验值，保证每次构建拿到的是同一份代码，而不是悄悄变成新版本。
2. **软件物料清单（SBOM，Software Bill of Materials）。** 像食品配料表一样，列出一个软件包含的全部组件和版本。下一次再出现 Log4Shell 这样的漏洞，查清单就能知道哪些系统受影响。一些国家的政府采购规则已开始要求供应商提供 SBOM。
3. **自动扫描依赖。** 在持续集成流程中接入漏洞扫描工具，把依赖版本与公开漏洞数据库比对，发现问题自动提醒升级。
4. **签名与来源证明。** 对发布的软件包做数字签名，并记录它由哪份源代码、在什么环境下构建，防止中途被替换。
5. **回馈上游。** 企业为所依赖的开源项目出人出钱，减轻少数维护者的负担，本身就是在加固自己的地基。

回到那份“开源许可”清单：它既是一张致谢名单，也是一张风险地图。现代软件是“组装”出来的，享受共享成果的同时，也继承了每个零件的问题。理解这一点，再看下一节的云原生技术就更顺理成章：容器镜像同样是一层层叠起来的依赖，供应链的思路会在那里再次出现。
