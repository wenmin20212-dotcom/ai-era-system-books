# 7.3 网页与移动应用开发技术

同一家外卖平台，你可能在手机上用它的 App 点餐，在电脑浏览器里打开它的网页查订单，还可能在某个聊天软件里通过“小程序”下单。三个入口看起来差不多，背后却是三套不同的技术路线。本节就从这三个入口出发，看清网页与移动应用分别用什么技术做出来，以及团队为什么常常要在“一套代码”和“原生体验”之间反复权衡。

## 7.3.1 网页的三件套：结构、样式与行为

在电脑浏览器里打开任意网页，按 F12（苹果电脑上可用 Option+Command+I）打开开发者工具，你会看到一层层嵌套的标签。这就是网页的第一块基石：**超文本标记语言（HTML）**，它描述“页面上有什么”，比如标题、段落、按钮、图片。

第二块是**层叠样式表（CSS）**，它决定“看起来什么样”，包括颜色、字体、间距，以及屏幕变窄时布局怎样重新排列。同一个网页在手机和电脑上排版不同，靠的就是 CSS 中的“响应式设计”，即根据屏幕宽度套用不同的样式规则。

第三块是 **JavaScript（常缩写为 JS）**，它负责“能做什么”：点击按钮后弹出菜单、输入地址时自动补全、不刷新页面就加载出下一屏商品。

可以用盖房子来类比：

| 技术 | 类比 | 负责的问题 |
|---|---|---|
| HTML | 房屋的梁柱和房间划分 | 有什么内容 |
| CSS | 装修与软装 | 看起来什么样 |
| JavaScript | 水电和开关 | 怎样响应操作 |

这三者由浏览器直接理解和执行，不需要用户安装任何东西，这是网页最大的优势：打开链接就能用，更新时只要服务器换上新文件，所有用户下次打开就是新版本。

## 7.3.2 从“页面”到“应用”：前端框架与单页应用

早期网页每点一次链接，服务器就送回一整张新页面。今天的网页邮箱、在线文档却像桌面软件一样流畅，这得益于**单页应用（SPA，Single Page Application）**：浏览器只加载一次页面骨架，之后由 JavaScript 向服务器请求数据，再局部更新界面。

当界面复杂到成百上千个按钮、列表和弹窗时，手工逐个修改页面元素极易出错。于是出现了**前端框架**。写作时较常见的有 Meta 公司发起的 React、社区主导的 Vue，以及谷歌维护的 Angular。它们的共同思路是“组件化”和“数据驱动”：把界面切成一个个可复用的组件（如“商品卡片”“购物车角标”），开发者只描述“数据是什么样，界面就该是什么样”，数据变化时由框架自动计算需要更新的部分。这正是第六章讲过的抽象与模块化思想在界面上的落地。

单页应用也有代价：首次加载的 JavaScript 文件可能很大，搜索引擎收录其内容也可能不够及时、完整。因此许多团队又采用**服务端渲染（SSR，Server-Side Rendering）**，先由服务器生成好首屏 HTML，再交给浏览器接管交互，兼顾速度与体验。

## 7.3.3 原生应用：直接说操作系统的“母语”

手机上从应用商店下载的 App，大多是**原生应用（Native App）**，即使用平台官方提供的语言和工具开发。写作时，苹果 iOS 平台主要使用 Swift 语言（更早是 Objective-C），配合 Xcode 开发工具；安卓平台主要使用 Kotlin 语言（更早以 Java 为主），配合 Android Studio。

原生应用的好处在于能直接调用系统能力：相机、定位、蓝牙、通知推送、指纹与面容识别，动画也更流畅，离线可用。代价同样明显：

- **两套代码**：iOS 与安卓各写一遍，团队规模和维护成本明显增加；
- **发布受平台约束**：新版本通常要经过应用商店审核（见第四章 4.3 节），用户还得自己点更新；
- **安装门槛**：用户要先下载，占用手机空间。

## 7.3.4 跨平台与混合方案：一套代码，多处运行

为降低“两套代码”的成本，业界发展出几类折中方案：

| 路线 | 代表技术（写作时） | 基本原理 | 主要取舍 |
|---|---|---|---|
| 混合应用 | 在 App 中嵌入网页视图 | 用网页技术写界面，外面套一层原生“壳” | 开发快、可热更新，但流畅度较弱 |
| 跨平台框架 | Meta 的 React Native、谷歌的 Flutter | 一套代码分别生成或绘制两个平台的界面 | 复用率高，复杂功能仍需写原生代码 |
| 渐进式网页应用（PWA） | 浏览器标准 | 让网页可添加到桌面、离线缓存、接收通知 | 无需安装，但各平台支持程度不一 |
| 小程序 | 微信等国内超级 App 的平台方案 | 运行在宿主 App 提供的环境中 | 获客方便，但受宿主平台规则限制 |

值得注意的是，小程序是特定平台方的做法，各家的开发规范并不相同，不能当作通用标准。React Native 与 Flutter 的实现方式也不同：前者尽量调用平台原生控件，后者用自带的绘图引擎自己“画”出界面。

## 7.3.5 选择路线的判断框架

面对这么多选项，没有哪一种绝对最好。产品团队通常围绕几个问题做判断：

1. **用户从哪里来？** 靠搜索和分享链接获客，网页更合适；需要高频、长期使用，原生 App 更能留住人。
2. **需要多少系统能力？** 重度依赖相机、传感器或高性能图形的应用（如修图、游戏），倾向原生。
3. **团队有多大？** 小团队往往先用跨平台方案或网页验证需求，再逐步把关键页面改写为原生。
4. **更新要多快？** 网页和部分混合方案可随时上线，原生 App 需走审核流程。

不少成熟产品其实是“混搭”的：主框架原生开发，活动页、帮助中心用内嵌网页，方便运营人员频繁修改。下次打开一个 App 时，你不妨留意哪些页面切换特别顺滑、哪些页面加载时顶部出现了一条细细的进度条，后者很可能就是一张嵌在里面的网页。

无论走哪条路线，界面层最终都要通过第二章讲过的接口与后端对话，也都会暴露在网络之中，成为攻击者的入口。下一节，我们就转向软件安全，看漏洞是怎样产生，又是怎样被修补的。
