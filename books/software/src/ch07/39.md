# 7.2 云原生：容器、编排与服务治理

打开手机上的外卖应用，晚上六点到七点之间，下单的人可能是下午三点的好几倍。可你很少遇到“服务器满了，请明天再来”的提示。到了深夜，人少了，那些为高峰准备的机器也不会一直空转烧钱。前面几章讲过微服务、负载均衡和弹性伸缩，这一节要回答一个更具体的问题：成百上千个服务、成千上万个运行实例，是靠什么被打包、搬运、安置和照看的？当下业界常用的一组答案，被统称为“云原生”（Cloud Native）。

## 7.2.1 从“在我电脑上能跑”说起

软件团队里流传一句无奈的话：“在我电脑上明明能跑。”一个程序写好之后，要依赖特定版本的语言运行时、几十个库、某些配置文件，甚至某个系统设置。开发者的笔记本、测试服务器和线上服务器只要有一处不同，程序就可能出错。

集装箱运输提供了一个好类比。在集装箱普及之前，码头工人要把麻袋、木桶、散货一件件搬上船，每种货物的装法都不一样。标准集装箱出现后，港口和货轮不再关心箱子里装的是什么，只需要按统一的尺寸吊装、堆叠和运输。

**容器**（Container）就是软件世界的集装箱。它把程序连同它需要的运行时、库和配置一起打成一个标准包，这个包叫**镜像**（Image）。镜像放到任何装有容器运行环境的机器上，启动后的表现都基本一致。写作时最广为人知的容器工具是 Docker，镜像格式则已由开放容器倡议（OCI）组织做了标准化，所以不同厂商的工具大多可以互相通用。

容器和第三章以前提到的虚拟机有什么区别？可以用一张表对照：

| 对比项 | 虚拟机（VM） | 容器 |
|---|---|---|
| 隔离方式 | 模拟整台计算机，每台带自己的操作系统 | 共享宿主机的操作系统内核，只隔离进程、文件和网络视图 |
| 体积 | 通常以 GB 计 | 常见为几十 MB 到几百 MB |
| 启动速度 | 常见为几十秒到分钟级 | 常见为秒级甚至更快 |
| 隔离强度 | 较强 | 相对弱一些，需要额外的安全措施 |

容器之所以轻，是因为它借用了操作系统内核提供的隔离与资源限制能力。具体机制属于《操作系统》一册的内容，这里只需记住：容器像同一栋楼里隔开的房间，虚拟机像各自独立的小楼。

## 7.2.2 编排：谁来指挥一万个集装箱

有了集装箱，港口还需要调度系统：哪个箱子放哪个位置，哪艘船先装，起重机坏了怎么办。容器多到一定规模，同样需要一个“港口调度中心”，这就是**容器编排**（Container Orchestration）。

写作时最主流的编排系统是 Kubernetes，常简写为 K8s。它最初由谷歌发起并开源，设计上借鉴了谷歌内部集群管理系统的经验，现由云原生计算基金会（CNCF）托管。各大云厂商都提供基于它的托管服务。

Kubernetes 最核心的思想是**声明式管理**。运维人员不必逐条下命令“去 3 号机器启动一个订单服务”，而是写下期望的状态：“订单服务要一直保持 5 个副本运行，每个最多用 1 核 CPU。”系统会持续比较“期望状态”和“实际状态”，发现不一致就自动纠正。这就像设定好温度的空调：你只说要 26 度，它自己决定什么时候制冷、什么时候停。

在这个思想下，编排系统承担了几类日常工作：

- **调度**：根据各台机器的剩余资源，决定新容器放在哪里运行。
- **自愈**：某个容器崩溃或所在机器宕机，自动在别处重新拉起一个。
- **伸缩**：根据 CPU 使用率等指标增减副本数量，晚高峰多开，深夜收缩。
- **滚动更新**：发布新版本时逐个替换旧实例，出问题可以退回，这正是 5.4 节发布流在平台层面的落地。

## 7.2.3 服务治理：服务之间的“交通规则”

容器跑起来了，几百个微服务之间还要互相调用。订单服务要找库存服务，可库存服务的实例随时在增减、迁移，地址不断变化，它怎么知道该找谁？

**服务发现**（Service Discovery）解决的就是这个问题：服务启动时登记自己的位置，调用方通过一个稳定的名字去查找。好比你拨打公司总机号码，而不必记住每个员工换了几次的分机号。

除此之外，服务之间还需要一整套“交通规则”，统称**服务治理**：

- **超时与重试**：对方迟迟不回应时，不能无限等待。
- **熔断**（Circuit Breaker）：某个下游服务持续出错时，暂时停止调用它，避免故障沿调用链蔓延，就像家里电路过载时跳闸。
- **限流**：请求超过承受能力时有序拒绝一部分，保住整体不垮。
- **加密与鉴权**：服务之间的通信也要确认身份、防止窃听。

早年这些规则要写进每个服务的代码里。后来出现了**服务网格**（Service Mesh）的做法：在每个服务旁边配一个代理程序，形象地叫“边车”（Sidecar），由它统一处理流量转发、重试、加密和监控数据采集。Istio、Linkerd 是写作时常见的服务网格项目。这样业务开发者可以专注于写业务逻辑，把通信上的琐事交给基础设施。

## 7.2.4 云原生的代价与边界

云原生不是免费午餐。Kubernetes 本身就是一个复杂的分布式系统，概念多、配置多，一个小团队维护它可能比写业务代码还累。容器共享内核，隔离不如虚拟机彻底，镜像里带进来的第三方组件也构成 7.1 节讲过的供应链风险。服务网格多了一层代理，就多了一点延迟和一个可能出错的环节。

因此，业界常见的看法是：系统规模小、服务不多时，单体应用加几台服务器往往更划算；当服务数量、发布频率和流量波动都上来了，云原生这套工具的收益才明显超过成本。这与 8.4 节将讨论的“没有银弹”一脉相承：每一种技术都是在用一种复杂度换掉另一种复杂度。

回到晚高峰的外卖应用：标准化的镜像让服务可以快速复制，编排系统按声明自动调度和自愈，服务治理让几百个服务在混乱中保持秩序。下一节，我们把视线从服务器移回你手里的屏幕，看看网页和移动应用又是用哪些技术做出来的。
