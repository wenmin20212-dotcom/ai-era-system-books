# 2.5 接口与界面：应用编程接口与用户界面

打开手机上的外卖应用，你看到的是一排排店铺图片、一个搜索框、一个醒目的“去结算”按钮。你用手指点、划、输入，应用给你回应。可就在你点下“去结算”的那一刻，应用并没有自己算出配送费、查出优惠券、扣掉库存，它悄悄向远方的服务器发出了一条格式严格的“请求单”，又收回一份同样格式严格的“回执单”。

这里出现了两种“接口”：一种朝向人，叫用户界面；一种朝向程序，叫应用编程接口。前者让人能使用软件，后者让软件能使用软件。本节把这两种接口放在一起看，因为它们解决的是同一个问题：**两个互相不了解内部细节的一方，怎样按约定好的方式打交道。**

## 2.5.1 接口是什么：一份写清楚的“约定”

日常生活里，接口无处不在。墙上的插座就是一个接口：不管电是火电厂还是风电场发的，不管你插的是台灯还是电饭煲，只要插头形状、电压符合国家标准，就能用。插座把“发电、输电”的复杂世界藏在墙后，只露出几个孔。

软件里的接口（Interface）也是如此，它规定三件事：

- **能做什么**：提供哪些操作，比如“查询订单”“提交评论”；
- **怎么提要求**：需要给出哪些信息、按什么格式给；
- **会得到什么**：成功时返回什么，失败时又怎样告知。

至于对方内部怎么实现，接口并不关心，也不应该关心。这一点在第八章“信息隐藏”一节还会从原理上展开。

## 2.5.2 用户界面：人与软件之间的接口

用户界面（User Interface，UI）是软件朝向人的那一面。它经历过几种主要形态：

| 形态 | 英文与缩写 | 交互方式 | 常见场景 |
|---|---|---|---|
| 命令行界面 | Command-Line Interface，CLI | 键入文字命令 | 程序员的终端、服务器管理 |
| 图形用户界面 | Graphical User Interface，GUI | 鼠标、触摸点击窗口与按钮 | 电脑和手机上的大多数应用 |
| 语音与对话界面 | Voice / Conversational UI | 说话或用自然语言聊天 | 智能音箱、车载助手、AI 聊天应用 |

形态不同，本质相同：把人的意图翻译成程序能处理的操作，再把结果翻译成人能理解的信息。界面设计得好不好，常用“用户体验”（User Experience，UX）来衡量——按钮是否好找、出错时提示是否看得懂、等待时有没有进度反馈。

值得注意的是，界面只是软件很薄的一层“外壳”。同一个购物服务，可以同时有手机 App、网页、小程序几种界面，背后连到的却是同一套服务器逻辑。界面怎样被绘制、怎样响应点击，第三章“表现层”一节会细讲。

## 2.5.3 应用编程接口：程序与程序之间的接口

应用编程接口（Application Programming Interface，API）是软件朝向其他程序的那一面。它没有按钮和图片，只有一条条严格定义的调用规则。

API 有好几个层次：

1. **库和框架的 API**：上一节讲过的依赖库，会公开一批函数供你调用。比如一个处理日期的库提供“计算两个日期相差几天”的函数，你只需按要求传入两个日期。
2. **操作系统的 API**：应用要读文件、用摄像头、发通知，都得通过操作系统提供的接口申请，这也是手机会弹出“是否允许访问相机”的原因。具体机制留给本系列《操作系统》一书。
3. **网络 API**：应用通过网络调用另一台计算机上的服务，这是今天最常被提到的 API 形式。

以网络 API 为例，外卖应用查询订单的过程大致像这样：

- 应用向一个网址发出请求，例如“获取编号为某某的订单”；
- 请求里附带身份凭证，证明“我是这个用户”；
- 服务器返回一段结构化文本，常见格式是 JSON（JavaScript Object Notation，一种用“名称：值”成对书写数据的轻量格式），里面写着订单状态、金额、骑手位置等字段；
- 应用拿到这段文本，再把它画成你看到的页面。

写作时，网络 API 常见的设计风格有 REST（表述性状态转移，把数据看作一个个可用网址定位的“资源”）、GraphQL（由调用方声明自己需要哪些字段的查询语言）以及 gRPC（一种由 Google 发起、后来开源的高效远程调用框架，多用于服务器之间）。它们各有取舍，但都是在回答同一组问题：怎么命名操作、怎么组织数据、怎么报告错误。

## 2.5.4 两种接口的对照：一个软件的“两张脸”

把两类接口并排放着看，会更清楚：

| 对比项 | 用户界面（UI） | 应用编程接口（API） |
|---|---|---|
| 服务对象 | 人 | 其他程序 |
| 首要追求 | 好懂、好用、容错 | 精确、稳定、可预测 |
| 出错表现 | 一句提示语或一个弹窗 | 一个错误码和错误说明 |
| 变化频率 | 可以经常改版 | 一旦公开就要谨慎改动 |
| 说明书 | 新手引导、帮助页 | 接口文档 |

最后两行特别重要。界面改版，用户最多抱怨几句、适应几天；API 一旦被别人的程序依赖，随意修改就可能让成千上万个调用方同时出错。所以成熟的服务通常会给 API 标上版本号，新旧版本并存一段时间，并提前公告旧版本停用的时间。这种“对外承诺”的分量，正是 API 和界面最大的不同。

## 2.5.5 接口让软件可以拼装

为什么一个小团队也能做出带地图、支付、登录功能的应用？因为地图服务商、支付平台、身份认证服务都通过 API 把能力开放了出来。开发者不必自己画地图、建银行通道，只要按文档调用接口。很多公司把自己的 API 当作产品对外提供，这被称为“开放平台”。

这也带来一个提醒：调用别人的 API，就把对方的稳定性、收费规则和数据政策一并纳入了自己的系统。第一章所说的“第三方服务”边界，正是通过一个个 API 划出来的。
