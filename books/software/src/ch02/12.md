# 2.4 数据层：数据库、缓存与文件存储

打开手机上的聊天应用，往上翻，三个月前的对话还在；换一部新手机登录，聊天记录、头像、收藏的表情包又都回来了。再打开购物应用，订单列表、收货地址、浏览过的商品一样不少。这些东西不在你按下的按钮里，也不在屏幕上的图标里，而是存放在软件系统的“数据层”。上一节讲的库与框架决定了代码怎样搭起来，这一节要回答另一个问题：软件运行时产生和使用的数据，放在哪里，怎样放。

## 2.4.1 程序会忘，数据要记：为什么需要数据层

程序运行时，数据先放在内存里。内存读写很快，但有两个弱点：一断电或程序退出，内容就消失；容量也相对有限。软件系统真正有价值的东西，比如用户账号、订单、余额、照片，必须比任何一次程序运行活得更久。把数据可靠地保存下来、需要时又能快速找回，这项工作由数据层承担。

可以把一个软件比作一家餐馆。厨师（业务代码）在灶台上做菜，灶台（内存）上只放正在用的东西；冷库和仓库（数据库、文件存储）存放长期的货物；灶台边伸手就能拿到的调料架（缓存），放的是最常用的几样。三者分工不同，缺一个，餐馆都转不顺。

## 2.4.2 数据库：有规矩的“账本”

数据库（Database）是按一定结构组织、可以被程序高效查询和修改的数据集合。管理它的软件叫数据库管理系统（Database Management System，DBMS）。常见的有两大类。

**关系型数据库**把数据组织成一张张表，每张表像一个电子表格：一行是一条记录，一列是一个属性。例如“用户表”有用户编号、昵称、手机号，“订单表”有订单号、用户编号、金额。两张表通过“用户编号”关联起来。程序用一种叫结构化查询语言（Structured Query Language，SQL）的语言提问，比如“找出编号为 1001 的用户最近十笔订单”。MySQL、PostgreSQL、Oracle 都属于这一类。关系型数据库的长处是结构严谨，并且支持“事务”，能保证一组操作要么全做完、要么全不做——转账不会只扣钱不到账。事务的原理将在第六章详细讲。

**非关系型数据库**常被统称为 NoSQL，意思是“不只用 SQL”。它不强求固定的表格结构，形态多样：有的把数据存成一份份类似 JSON 的“文档”（如 MongoDB），有的只存“键—值”对（如 Redis），有的擅长表示人和人之间的关系网。它们往往更容易扩展到很多台机器上，适合结构多变或数据量极大的场景。

| 对比项 | 关系型数据库 | 非关系型数据库 |
|---|---|---|
| 组织方式 | 表格、行与列，结构预先定义 | 文档、键值、图等，结构较灵活 |
| 查询方式 | 主要用 SQL | 各有自己的接口，部分也支持类 SQL |
| 典型优势 | 数据一致性强，适合账务、订单 | 灵活、易横向扩展，适合海量或多变数据 |
| 典型场景 | 银行流水、电商订单、库存 | 用户画像、消息记录、实时排行榜 |

需要提醒的是，这种划分只是粗线条。写作时的情况是，不少关系型数据库也支持存储文档，不少 NoSQL 产品也加入了事务能力，两者界限在变模糊。选型时看的是数据的特点和业务对一致性的要求，而不是哪一类“更先进”。

## 2.4.3 缓存：把常用的东西放在手边

数据库通常把数据存在硬盘或固态硬盘上，每次查询都要经过解析、查找、读盘等步骤。如果一条热门新闻每秒被成千上万人打开，每次都去数据库里查，数据库很快就会不堪重负。

缓存（Cache）的思路很朴素：把最近或最常用的数据复制一份，放在读取更快的地方，通常是内存。下次再要，先查缓存，查到了（称为“命中”）就直接返回；查不到再去数据库，并顺手把结果放进缓存。前面提到的 Redis 就是写作时常被用作缓存的软件。

缓存无处不在，而且是分层的：

- **你的设备上**：浏览器会缓存看过的图片和网页文件，App 会把头像、列表先存在本地，所以断网时也能看到部分旧内容；
- **网络途中**：内容分发网络（Content Delivery Network，CDN）在各地部署节点，把视频、图片放在离你近的地方；
- **服务器端**：在数据库前面加一层内存缓存，挡住大部分重复查询。

缓存的代价是“可能不新鲜”。你改了昵称，好友那边一时还显示旧名字，往往就是缓存还没更新。什么时候让缓存过期、数据改了怎样同步，是工程师要反复权衡的问题。业内流传一句玩笑：计算机科学里最难的两件事之一，就是让缓存失效。

## 2.4.4 文件存储：照片、视频这样的“大件”

数据库擅长存储结构化的小块信息，比如名字、金额、时间。但一张几兆字节的照片、一段几百兆字节的视频，硬塞进数据库的表格里既笨重又低效。这类数据通常交给文件存储。

在单台电脑上，文件存储就是我们熟悉的文件夹和文件。到了云上服务，常见做法是**对象存储**（Object Storage）：每个文件作为一个“对象”，配一个唯一的标识，可以通过网址读取，存储容量可以近乎无限地扩展。亚马逊云科技的 S3、阿里云的 OSS 等都是这类服务。

于是一个典型的分工出现了：你在社交应用里发一张照片，照片本体被放进对象存储；数据库里只记下一行信息——谁发的、什么时间、配了什么文字，以及照片的存放地址。读取时，应用先从数据库拿到这行信息，再按地址去取照片。数据库当“目录”，对象存储当“仓库”。

## 2.4.5 三者如何配合

把三种存储放在一起看，一次“打开朋友圈”的过程大致是：应用先问缓存要最新动态列表；缓存没有，就去数据库查出动态的文字和图片地址，再写回缓存；屏幕上的图片则按地址从 CDN 或对象存储下载，并在手机本地缓存一份。

| 存储 | 存什么 | 主要特点 |
|---|---|---|
| 数据库 | 账号、订单、关系等结构化数据 | 可靠、可查询、可保证一致性 |
| 缓存 | 热点数据的副本 | 极快，但可能过时，可以丢失 |
| 文件/对象存储 | 图片、视频、文档等大文件 | 容量大、成本低，按地址读取 |

一个原则贯穿其中：**数据库是“真相的来源”，缓存只是加速用的副本。**缓存丢了可以重建，数据库丢了才是真正的事故。理解了这一点，就能明白为什么数据库要备份、要多份复制，而缓存可以随时清空。

数据存好了，但前端的 App、别的服务，以及屏幕前的你，又是通过什么方式来访问这些数据和功能的？这就是下一节要讲的接口与界面。
