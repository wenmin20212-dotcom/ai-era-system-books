# 2.3 库、框架与依赖：站在别人的代码上

打开你手机上常用的一个应用，进入“设置”，找到“关于”，再往下翻，很多应用都有一个名叫“开源许可”“第三方软件声明”或“开源组件”的入口。点进去，你可能会看到一份长得出奇的清单：几十个甚至上百个名字，每个名字后面附着一段英文许可证文本。

这份清单揭示了一个事实：你正在用的这个应用，大部分代码并不是这家公司自己写的。写作时的主流应用几乎都是这样。软件工程师常说自己“站在巨人的肩膀上”，这些巨人就是库、框架和它们背后的依赖网络。

## 2.3.1 库：随取随用的工具箱

**库**（Library）是一组写好的、可以被别的程序反复调用的代码。打个比方，你装修房子时不会自己炼钢打钉子，而是去五金店买现成的螺丝、合页和电钻。库就是程序员的五金店。

常见的库有这些用途：

- 处理日期和时间：闰年、时区、夏令时，自己写很容易出错；
- 压缩和解压图片，播放视频；
- 加密数据，校验密码；
- 发起网络请求，解析服务器返回的数据格式。

库的特点是“我来调用你”。程序员在自己的代码里决定什么时候、用哪个库、做什么事。库本身只是被动地等着被调用，就像电钻放在工具箱里，用不用、何时用，都由装修师傅说了算。

## 2.3.2 框架：先搭好的房屋骨架

**框架**（Framework）比库更大，也更有“主见”。它不只是提供工具，而是规定了整个程序的组织方式：代码放在哪里，按什么顺序执行，各部分怎样衔接。

继续用装修打比方：库是五金件，框架则像一套已经浇筑好梁柱、预留了水电管道的毛坯房。你可以决定墙刷什么颜色、厨房怎么布置，但承重墙的位置不由你定。

区分库和框架，业内有一句流传很广的说法：**你调用库，框架调用你。** 使用框架时，程序员写的是一个个“填空”的片段，比如“用户点击按钮时做什么”“页面打开时显示什么”。至于这些片段什么时候被执行，由框架决定。这种由框架掌握控制权的设计，被称为**控制反转**（Inversion of Control，IoC）。

| 对照项 | 库 | 框架 |
|---|---|---|
| 控制权 | 在程序员手里 | 在框架手里 |
| 规模 | 通常解决一类具体问题 | 规定整个应用的结构 |
| 替换难度 | 相对容易换成另一个 | 换框架往往等于大规模重写 |
| 类比 | 五金件、电钻 | 毛坯房的骨架 |

网页开发中常见的 React、Vue，后端开发中常见的 Spring、Django，都是写作时被广泛使用的框架或类框架工具。具体名字会变，库和框架这种分工方式不容易过时。

## 2.3.3 依赖：一张看不见的大网

当一个程序使用了某个库，我们就说它**依赖**（Dependency）这个库。麻烦在于，被依赖的库自己也会依赖别的库。你的应用依赖 A，A 依赖 B 和 C，C 又依赖 D……这样层层展开，就形成了一棵**依赖树**。其中你直接写明要用的叫“直接依赖”，被间接带进来的叫“传递依赖”。

一个只直接引用十几个库的项目，展开传递依赖之后，实际装进来的组件数量常常达到几百个，这在网页开发领域并不少见。前面那份长长的开源许可清单，正是这棵树的一部分投影。

手工管理这么多组件是不可能的，于是有了**包管理器**（Package Manager）。它像一位自动采购员：程序员在一个清单文件里写下“我需要哪些库、什么版本”，包管理器就会去公共仓库下载它们，并顺藤摸瓜把传递依赖也一并装好。不同语言生态各有自己的包管理器，例如 JavaScript 的 npm、Python 的 pip、Java 常用的 Maven。

## 2.3.4 版本号：依赖之间的约定

库会不断更新，怎样知道新版本会不会破坏你的程序？许多开源项目采用**语义化版本**（Semantic Versioning，SemVer）约定，版本号写成“主版本.次版本.修订号”，比如 2.4.1：

- **修订号**变了（2.4.1 → 2.4.2）：修了 bug，用法不变；
- **次版本**变了（2.4 → 2.5）：加了新功能，旧用法仍然可用；
- **主版本**变了（2 → 3）：有不兼容的改动，升级可能要改代码。

这只是一种约定，靠维护者自觉遵守，并不能强制保证。为了让每次安装结果完全一致，包管理器通常还会生成一个**锁文件**（Lock File），把整棵依赖树里每个组件的确切版本都记录下来。这样，今天在你电脑上能运行的程序，明天在同事电脑或服务器上装出来的也是同一套组件。

## 2.3.5 便利的另一面

依赖带来了巨大的效率，也带来了风险。2016 年，JavaScript 生态中一个名叫 left-pad 的小库被作者从 npm 仓库撤下。它只有十来行代码，功能是在字符串左边补空格，却被大量项目间接依赖，一时间许多项目无法正常构建。这个事件被广泛引用，用来说明依赖网络的脆弱：一个你从未听说过的小零件，可能决定你的整个系统能不能运转。

除了“零件突然消失”，还有“零件本身有缺陷”和“零件被人动了手脚”等问题。这些内容涉及开源生态与软件供应链安全，我们将在第七章专门展开。

一个软件系统，是自己写的少量代码加上大量借来的代码组装而成的。自己写的那部分决定了它与众不同的功能，借来的那部分决定了它能多快做出来，也决定了它会继承哪些别人的问题。看懂了这一点，再看那份开源许可清单，你看到的就是一张协作网络的缩影。下一节，我们转向这些代码共同服务的对象：数据，以及存放数据的地方。
