# 4.4 软件与人：开发、测试、运维、产品与用户

打开手机里的应用商店，找到你常用的一款应用，往下翻到“版本记录”。你会看到一串简短的说明：“修复了部分用户无法登录的问题”“新增夜间模式”“优化了图片加载速度”。每一行背后，都有一群人在协作：有人提出想法，有人写代码，有人找错误，有人保证服务器不宕机，还有成千上万的用户在用、在抱怨、在给出反馈。前面几节讲的都是软件内部各部分怎样连接，本节转向最容易被忽略的一层连接：软件和人。

## 4.4.1 一款应用背后的五种角色

一个软件系统从被构想到被使用，大致经过“要做什么、怎么做、做对了没有、怎样一直跑下去、用起来怎么样”五个环节。对应地，工程界形成了几类典型角色：

| 角色 | 主要关心的问题 | 典型工作成果 |
|---|---|---|
| 产品经理 | 做什么、为谁做、为什么值得做 | 需求文档、原型图、优先级列表 |
| 开发工程师 | 怎样用代码实现 | 源代码、技术设计、代码评审意见 |
| 测试工程师 | 实现得对不对、会不会出错 | 测试用例、缺陷报告、自动化测试脚本 |
| 运维 / 站点可靠性工程师 | 上线后能否稳定运行 | 部署方案、监控面板、故障处理记录 |
| 用户 | 好不好用、能不能解决问题 | 使用行为、评分评论、反馈与投诉 |

此外，设计师负责界面和交互，数据分析师解读用户行为，安全工程师关注漏洞，项目经理协调进度。小团队里一个人常常身兼数职，大公司里每个角色又会细分成更小的岗位。具体怎样分工，因公司和产品而异，上表只是常见的骨架。

这里的“站点可靠性工程”（Site Reliability Engineering，SRE）是谷歌公司最早系统提出并公开介绍的一种做法：用写软件的方式来做运维，把“系统可用率要达到多少”写成明确目标。后来许多公司借鉴了这套思路，但具体做法各不相同。

## 4.4.2 人与人之间也有“接口”

第二章讲过，模块之间通过接口交换信息。人和人之间的协作，同样需要约定好的“接口”，否则就会出现“我以为你要的是这个”的误会。

- **产品到开发**：需求文档和原型图是接口。写清楚“用户点击按钮后发生什么、出错时显示什么”，开发才不必靠猜。
- **开发到测试**：一个可运行的版本加上改动说明是接口。测试据此设计用例，发现问题后写成缺陷报告，退回给开发。
- **开发到运维**：部署脚本、配置清单和运行手册是接口。运维据此把软件放到服务器上，并知道出了问题去看哪里。
- **用户到团队**：评分、评论、客服工单、应用内的“意见反馈”按钮，以及经用户同意收集的使用数据，是用户把声音传回团队的通道。

一个有趣的现象是：软件的结构常常会映射出团队的结构。计算机科学家梅尔文·康威（Melvin Conway）在1960年代末提出一个观察，后人称为“康威定律”：设计系统的组织，其产出的系统结构往往会复制该组织的沟通结构。三个小组合作做一个编译器，很可能做出“三段式”的编译器。上一节讲到的微服务，在不少公司就与“一个小团队负责一个服务”的组织方式相互配合。这说明，软件的连接关系不只是技术选择，也是人的协作方式的投影。

## 4.4.3 从“扔过墙”到 DevOps

早年在不少组织里，开发和运维是两个隔得很远的部门。开发写完代码，像把包裹扔过一堵墙一样交给运维；软件在服务器上出了问题，运维又把问题扔回去。开发追求快速改变，运维追求稳定不变，双方目标天然冲突，常常互相埋怨。

2000年代后期，业界兴起了一种叫 DevOps 的理念，名字由开发（Development）和运维（Operations）拼合而成。它不是某个具体工具，而是一组做法和文化：

1. **共同负责**：谁写的服务，谁也要关心它上线后的表现，“你构建，你运行”是常被引用的说法；
2. **自动化**：把构建、测试、部署做成流水线，减少人工交接中的出错；
3. **小步快跑**：把大改动拆成频繁的小改动，每次出问题的范围更小、更容易回退；
4. **事后复盘不追责**：故障之后重点分析流程哪里有漏洞，而不是找人“背锅”，这样大家才愿意如实说出发生了什么。

测试工作也在发生类似变化。过去测试常常是开发完成后的独立阶段，现在越来越多的团队让开发自己编写自动化测试，测试工程师则更多地负责设计测试策略、搭建测试平台、探索那些自动化难以覆盖的情况。这些做法将在第五章的“代码流”“发布流”中具体展开。

## 4.4.4 用户：既是终点，也是起点

用户常被看作软件交付的终点，其实他们也是下一轮改进的起点。团队了解用户，大致有几条路：

- **直接反馈**：应用商店评论、客服记录、社区帖子；
- **行为数据**：在用户同意和法律允许的前提下，统计哪些功能常被使用、用户在哪一步放弃操作；
- **对照实验**：常称为 A/B 测试，让两组用户分别看到两种设计，比较哪种效果更好；
- **用户研究**：访谈、可用性测试，观察真实的人怎样使用产品。

这里有一条重要的边界：收集用户数据必须遵守隐私法规和平台规则。中国的《个人信息保护法》、欧盟的《通用数据保护条例》（GDPR）等都对收集范围、告知同意和数据保存提出了要求，应用商店也会审查应用的隐私声明。软件和人的关系，不只是技术和情感上的，也是法律上的。

## 4.4.5 小结：软件是人和代码共同组成的系统

回到开头那条“修复了部分用户无法登录的问题”。它可能起于用户的一条差评，经客服汇总成工单，由产品经理判断优先级，开发定位并修改代码，测试验证修复且没有引入新问题，运维把新版本逐步推给用户，最后再由监控和用户反馈确认问题真正消失。一行更新说明，串起了本节提到的所有角色。

理解这一点，对于和软件团队打交道的人尤其有用：当你提出一个“很简单”的需求时，它要经过的不只是几行代码，还有设计、评审、测试、发布和长期维护。下一节将对本章四种连接关系做一次骨架小结，之后进入第五章，跟随请求、数据、代码、发布和故障在这些连接中真正流动起来。
