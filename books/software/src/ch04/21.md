# 4.1 前端与后端：浏览器、App 与服务器的对话

打开手机上的外卖应用，首页很快出现附近的餐厅、优惠券和你上次点过的那家面馆。你划动屏幕，图片一张张加载出来；你点下“去结算”，几秒后弹出“下单成功”。整个过程像是在和手机本身打交道，其实手机只完成了一半工作。另一半发生在远处机房的服务器上。前者叫前端，后者叫后端。本节要看清的，是这两端各管什么，以及它们靠什么约定来对话。

## 4.1.1 一个餐厅的比喻：前厅与后厨

可以把一个应用想象成一家餐厅。

- **前端**（Front End）像前厅：桌椅、菜单、服务员。它负责让顾客看得见、点得了，把顾客的要求记下来送进去，再把做好的菜端出来。
- **后端**（Back End）像后厨和仓库：食材库存、菜谱、收银账本都在这里。顾客看不到它，但它决定了菜能不能做、价钱算得对不对。

对应到软件里，前端是运行在你设备上的那部分程序，包括浏览器里的网页和手机上安装的 App；后端是运行在服务器上的程序，连接着数据库，保管订单、账户、库存这些需要所有人共享、必须可靠保存的数据。

这样分工有一个根本原因：**数据和规则必须集中在一个可信的地方**。你的手机可能丢失、被改装、断网，如果“优惠券还能不能用”只由手机自己判断，任何人改一改本地程序就能无限领券。所以凡是涉及钱、权限和共享数据的决定，最终都要由后端拍板，前端只负责展示和收集。

## 4.1.2 两端各管什么

| 对照项 | 前端 | 后端 |
|---|---|---|
| 运行位置 | 用户的浏览器、手机、电脑 | 公司或云平台的服务器 |
| 主要职责 | 界面显示、响应点击与输入、初步校验 | 业务规则、数据存取、身份核验、对接第三方 |
| 常见技术（写作时的情况） | 网页用 HTML、CSS、JavaScript；App 用 Swift、Kotlin 或跨平台框架 | Java、Go、Python、Node.js 等语言及数据库 |
| 能否被用户控制 | 能，代码就在用户设备上 | 不能，用户只能通过接口访问 |
| 更新方式 | 网页刷新即更新；App 常需经应用商店 | 在服务器上部署，用户无感知 |

表中“能否被用户控制”一行最值得记住。前端的代码最终都要下发到用户设备上运行，懂行的人可以查看甚至篡改它。因此前端做的校验，比如“手机号必须是 11 位”，主要是为了体验，及时提示用户填错了；真正的把关必须在后端再做一遍。工程师常说“永远不要信任客户端”，说的就是这件事。

## 4.1.3 对话的语言：HTTP 请求与响应

前后端隔着网络，靠一种约定好的格式交流。今天网页和绝大多数 App 使用的是 **HTTP**（超文本传输协议，HyperText Transfer Protocol），通常加上加密层，即 **HTTPS**。浏览器地址栏里的小锁图标，表示这次对话经过了加密。

HTTP 的对话方式很简单：**前端发出请求，后端返回响应，一问一答**。一次请求大致包含：

1. **方法**：想做什么。常见的有 GET（获取，如“给我看餐厅列表”）和 POST（提交，如“我要下这个订单”）。
2. **地址**：找谁办。比如 `/api/orders`，表示订单相关的接口。
3. **头部**：附带说明。例如登录后得到的身份凭证，告诉后端“我是谁”。
4. **正文**：具体内容。例如订单里的菜品编号和数量。

后端处理完，返回一个**状态码**和内容。状态码是三位数字：200 表示成功，404 表示找不到，401 表示未登录或身份失效，500 表示服务器内部出错。你偶尔在网页上看到的“404 Not Found”，就是后端回的这句话直接露了出来。

响应的内容如今多用 **JSON**（JavaScript 对象表示法，JavaScript Object Notation）书写，一种人和机器都容易读的文本格式，形如 `{"orderId": "A1023", "status": "已支付"}`。前端拿到这段数据后，把它填进界面，变成你看到的“下单成功”。

这里接上了第二章讲过的应用编程接口（API）：后端公开一组接口，写明每个地址接受什么请求、返回什么数据；前端按这份“菜单”点菜。只要接口约定不变，前后端可以各自修改内部实现，互不干扰。这也是很多团队把前端工程师和后端工程师分成两组、并行开发的基础。

## 4.1.4 网页与 App：同一个后端，不同的前厅

同一家外卖平台，往往同时有网页版、苹果手机 App、安卓 App，可能还有小程序。它们的外观和技术各不相同，背后通常连着**同一套后端接口**。这就像一家餐厅开了堂食、窗口和外卖三种前厅，后厨只有一个。

两类前端的主要差别在于“界面从哪来”：

- **网页**：每次访问时，浏览器从服务器下载页面代码再运行，所以网站改版后你刷新就能看到新版本。
- **App**：界面代码大部分已经随安装包放在手机里，运行时主要向后端要数据。因此它启动后能先显示框架，再填入内容，而界面本身的大改动常要等你更新 App。

这也解释了一个日常现象：断网时打开 App，往往还能看到页面骨架和上次缓存的内容，只是数据刷不出来；网页在断网时则可能整页打不开。前者把“前厅”整个搬到了你手里，后者每次都要现场搭建。

## 4.1.5 对话不止一问一答

一问一答的模式有局限：后端无法主动开口。可外卖应用里，骑手位置在地图上实时移动，新消息会自己弹出来，这是怎么做到的？常见做法有几种：

- **轮询**：前端每隔几秒问一次“有新消息吗”，实现简单，但大部分询问是白问。
- **长连接**：例如 **WebSocket**（网页套接字），前后端建立一条持续打开的通道，后端有变化即可推送，适合聊天、实时位置等场景。
- **系统推送**：App 不在前台时，消息通常经由手机操作系统厂商提供的推送服务转达，例如苹果的 APNs。这属于平台提供的能力，具体机制随厂商而不同。

选哪种方式，取决于实时性要求、耗电和服务器压力之间的权衡，没有一种在所有场合都最好。

## 4.1.6 小结

前端与后端的划分，本质是把“与人打交道”和“守护数据与规则”分开放：前端贴近用户，追求流畅与好看；后端集中可信，追求正确与可靠。两者之间靠 HTTP 请求、响应和接口约定对话。理解了这层关系，你在应用里看到的转圈、报错、“请重新登录”，都能大致判断问题出在哪一端。下一节我们走进后端内部，会发现那个“后厨”本身也可能被拆成许多个小厨房，这就是从单体应用到微服务的演变。
