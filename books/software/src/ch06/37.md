# 6.6 本章骨架小结与实物探索任务

第五章我们跟着请求、数据、代码、发布和故障在系统里走了一圈，看到的是“流动”。这一章往下挖了一层：同样是点一下“支付”，为什么转账不会少一分钱，为什么几百万人同时刷新首页服务器还撑得住，为什么新版本上线前大家心里有底。答案都落在“机制”上。机制是系统在运行时反复使用的套路，看不见，却决定了软件稳不稳、快不快、对不对。

## 6.6.1 本章骨架回顾

可以把本章五节压缩成一张对照表，每一行回答一个“怎么做到的”问题：

| 机制 | 要解决的问题 | 核心做法 | 典型代价 |
|---|---|---|---|
| 抽象与模块化 | 系统太大，没人能装进脑子 | 按职责切块，只通过接口打交道，内部细节对外隐藏 | 切分不当会让模块间调用变多，改一处牵动多处 |
| 并发与异步 | 成千上万个请求同时到达 | 多线程、事件循环、消息队列，让等待时间不浪费 | 共享数据容易出现竞态条件，问题难以复现 |
| 事务与一致性 | 一组操作必须“要么全做，要么全不做” | 用事务保证原子性、一致性、隔离性、持久性（ACID）；跨服务时用补偿等方式逼近一致 | 加锁和协调会降低吞吐，分布式场景下只能权衡 |
| 缓存、负载均衡与弹性伸缩 | 访问量忽高忽低，热点数据被反复读取 | 把常用数据放近一点；把请求分给多台服务器；按负载自动增减实例 | 缓存可能读到旧数据；伸缩有延迟，需要预留余量 |
| 测试与质量保障 | 怎样在用户之前发现错误 | 单元测试、集成测试、端到端测试分层组织，自动化跑在持续集成里 | 测试只能证明“发现了错误”，不能证明“没有错误” |

把这五行串起来看，会发现一条共同的思路：**用结构换可控性**。模块化是空间上的切分，并发是时间上的交错，事务是给一组操作加边界，缓存与伸缩是给负载加缓冲，测试是给变化加防护网。每种机制都不是免费的，工程师的日常工作很大一部分就是在这些代价之间做选择。

还有三个容易混淆的点值得再强调：

- **并发不等于并行**。并发是“同时应付多件事”，并行是“同时执行多件事”。单核处理器也能并发，靠的是快速切换和不傻等。
- **一致性有不同强度**。银行余额通常要求强一致；朋友圈点赞数晚几秒更新，多数用户感觉不到，很多系统会选择最终一致来换取速度和可用性。
- **缓存是一份“副本”**。只要有副本，就要回答“原件变了，副本什么时候更新”。这是业界常说“缓存失效是计算机科学中最难的事情之一”的原因（这句话是流传很广的工程界说法，并非严格定理）。

## 6.6.2 实物探索任务

下面的任务只需要手机、电脑和浏览器，不需要写代码。

1. **观察缓存的痕迹**。在电脑浏览器里打开一个常用新闻网站，按 F12 打开开发者工具，切到“网络（Network）”面板，刷新一次，再刷新一次。比较两次请求中有多少条目标注了“来自缓存（from memory cache / disk cache）”，加载时间有什么差别。然后勾选“停用缓存（Disable cache）”再刷新，体会缓存省下了什么。
2. **寻找事务的边界**。回忆一次网购下单：从点“提交订单”到“支付成功”，中间哪些步骤必须同时成功？如果库存扣了而支付失败，你在页面上看到过什么提示（例如“订单已取消，库存已释放”）？把你观察到的步骤画成一条线，标出你认为“必须原子化”的那一段。
3. **感受异步**。在聊天应用里发一张大图片，注意发送过程中你仍然可以滑动聊天记录、输入文字。再找一个在加载时整个界面“卡住”的应用作对照。写下两者给你的感受差别，这就是异步与同步在体验上的区别。
4. **看懂一次弹性伸缩**。在抢票、秒杀或大型直播开始时，留意应用是否出现“排队中”“当前人数较多”的提示。这类提示往往是限流和排队机制在起作用，目的是在扩容跟上之前保护后端。记录你见到的提示文字。
5. **当一次测试员**。挑一个你常用的表单（如注册页），故意输入异常内容：超长名字、空格、表情符号、未来的生日。记下哪些被拦住、哪些被接受、提示语是否清楚。这正是测试中“边界值”和“异常输入”思路的日常版。

## 6.6.3 可以直接问 AI 的问题

把下面的问题原样交给你常用的 AI 助手，再要求它“用一个日常例子解释，并指出你不确定的地方”：

- “数据库事务的 ACID 四个特性分别防止了什么具体问题？请用两个人同时给同一个账户转账的场景逐条说明。”
- “网站使用缓存后，用户有时会看到旧数据。常见的缓存更新策略有哪些？各自适合什么场景、有什么风险？”
- “为什么说软件测试只能证明存在错误，而不能证明没有错误？这句话出自谁？实际工程中人们怎样在这个限制下提高信心？”

对 AI 的回答，留意它是否给出了出处，人名和年份要再自己核对一次。

## 6.6.4 从机制走向技术

本章讲的机制大多已有几十年历史，事务理论、模块化思想、测试方法在大型机时代就已成形。今天的变化在于，它们被打包进了新的工具和平台：容器与编排把伸缩变成几行配置，开源组件让模块可以跨公司复用，AI 开始参与写代码和写测试。下一章“关键技术”就从这里出发，看这些稳定的机制如何以新的技术形态出现在你每天使用的软件里。
