# 6.2 并发与异步：同时处理成千上万个请求

晚上八点，一家外卖平台进入高峰。你在手机上点下“提交订单”，几乎同一时刻，同一座城市里还有成千上万人在刷新菜单、查看骑手位置、付款。你的订单没有排在长队末尾苦等，几百毫秒后就收到了“下单成功”。服务器并没有成千上万颗处理器，它是怎样“同时”照顾这么多人的？答案藏在两个词里：并发与异步。

## 6.2.1 并发不等于并行：一个厨师和十个厨师

先分清两个容易混淆的概念。

- **并行（Parallelism）**：真的在同一瞬间做多件事。好比厨房里有十个厨师，每人炒一道菜。
- **并发（Concurrency）**：在一段时间里推进多件事，它们交替向前。好比一个厨师同时照看三口锅：这锅在炖，他去切那锅的配菜；那锅水还没开，他又回来给第一锅翻面。

计算机的处理器核心数量有限，一台服务器常见的是几个到上百个核心，而它要应对的请求可能是数千乃至更多。真正让它扛住流量的，主要是并发：在等待的空隙里去做别的事。

关键在于，一次网络请求的大部分时间其实都在“等”。以下单为例：

| 步骤 | 处理器在忙吗 |
|---|---|
| 解析请求、校验参数 | 忙，但很快 |
| 查询数据库里的库存 | 基本在等数据库回复 |
| 调用支付服务 | 基本在等网络回复 |
| 拼装结果返回给手机 | 忙，但很快 |

真正需要计算的时间往往只占一小部分，其余时间都在等待磁盘、数据库或其他服务。这类工作被称为 **I/O 密集型（输入/输出密集型）** 任务。如果处理器在等待时什么都不做，就像厨师盯着一锅没烧开的水发呆，浪费惊人。

## 6.2.2 第一种办法：多开几个“工人”——进程与线程

最直观的办法是多雇人。操作系统提供了两种“工人”：

- **进程（Process）**：一个运行中的程序实例，拥有自己独立的内存空间，像一个独立的厨房。
- **线程（Thread）**：进程内部的执行单位，同一进程的多个线程共享内存，像同一个厨房里的多个厨师。

早期许多网页服务器采用“一个请求一个线程”的模式：来一个请求，就派一个线程从头跟到尾。某个线程在等数据库时，操作系统会把处理器切换给别的线程。至于操作系统如何调度线程、如何切换，属于本系列《操作系统》的内容，这里只需知道：切换是有成本的。

这种模式写起来直观，代码按顺序一行行执行，符合人的思维习惯。但当并发请求达到数万级别，每个线程都要占用一定内存，频繁切换也消耗处理器时间，“多雇人”就开始吃力。业界把这类困境概括为“C10K 问题”，即单台服务器如何同时处理一万个连接，这是二十世纪末就被广泛讨论的经典话题。

## 6.2.3 第二种办法：不等，先去做别的——异步与事件循环

另一种思路是：少雇人，但绝不让人干等。这就是**异步（Asynchronous）**。

对照一下两种点餐方式。**同步**像在老式柜台排队：你点完餐，站在柜台前一直等到餐做好，后面的人都得等你。**异步**像奶茶店的取餐号：你点完拿个号就离开，店员接着服务下一位，饮料做好了叫号通知你。

在软件里，“叫号”由**事件循环（Event Loop）**完成。程序发出查询数据库的请求后，不原地等待，而是登记一句“结果回来后请执行这段代码”，然后立刻去处理别的请求。事件循环不断检查：哪个结果回来了，就去执行对应的后续代码。这样，一个线程就能周旋于大量连接之间。

这种模型有广为人知的代表。例如 Nginx 这类网页服务器以事件驱动架构处理大量连接；Node.js 让 JavaScript 以单线程事件循环的方式运行在服务器上；你的浏览器执行网页脚本时，也依靠事件循环来响应点击和网络回复。写作时，Python、C#、JavaScript 等许多主流语言都提供了 `async/await`（异步/等待）语法，让异步代码读起来接近顺序代码。

但异步也有代价。如果某段代码做了大量纯计算，比如压缩一张大图片，它会霸占唯一的线程，事件循环里排队的所有请求都被卡住。所以在实践中，系统常常把两种方式组合起来：用异步应对大量等待，把繁重计算交给单独的线程或进程。

## 6.2.4 同时做事的麻烦：竞态条件与锁

“同时”带来效率，也带来新问题。设想某款奶茶只剩最后 1 杯，两位顾客几乎同时下单，两个线程各自执行：

1. 读取库存：都读到“1”；
2. 判断库存大于 0：都通过；
3. 库存减一并写回：都写成“0”。

结果卖出了两杯，实际只有一杯。这种结果取决于执行先后顺序的错误，叫作**竞态条件（Race Condition）**。它最难对付的地方在于不稳定：测试一百次可能都正常，上线后在高峰时段偶然出现一次。

常见的应对办法有：

- **锁（Lock）**：像厨房里只有一把的“库存钥匙”，谁拿到谁操作，其他人等着。它简单有效，但锁用多了，大家都在排队，并发优势就被抵消；两方互相等待对方手里的钥匙，还会陷入**死锁（Deadlock）**。
- **原子操作（Atomic Operation）**：把“读取—判断—写回”合成一个不可分割的动作，要么整体完成，要么完全不做。
- **避免共享**：让每个工作单元只处理自己的数据，通过传递消息来协作，从根源上减少争抢。

库存扣减之所以敏感，是因为它关乎钱和货，涉及多步操作要么全成、要么全不成。这正是下一节“事务与一致性”要深入讨论的话题。

## 6.2.5 小结：在等待中创造效率

服务器能“同时”处理成千上万个请求，靠的不是无穷的硬件，而是对等待时间的精打细算：多线程让多个工人轮流干活，异步让少数工人从不空等，两者常被组合使用。代价是共享数据时可能出现竞态条件，需要锁、原子操作或避免共享来约束。理解了这一点，你就能明白为什么工程师听到“高峰期偶发错误”时，第一反应常常是：是不是并发出了问题？
