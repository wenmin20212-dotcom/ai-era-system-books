# 5.3 代码流：从一行修改到合入主干

你手机上的某个应用，前几天弹出提示：“修复了部分机型上图片无法加载的问题。”这一行更新说明的背后，可能只是一位工程师改动了几行代码。但这几行代码不能直接从他的电脑“飞”到你的手机上。它要先经过一条有规则、有检查、有记录的路径，才能并入团队共同维护的那份代码。这条路径就是本节要讲的**代码流**。上一节讲数据在系统里怎样流动，这一节讲另一种同样重要的流动：代码本身在团队中的流动。

## 5.3.1 一份代码，几百人同时改：版本控制登场

设想一个班级合写一本几百页的文集，几十个人同时修改同一份文档。如果大家各自拷贝、各改各的，最后很难合到一起：谁改了哪一段？两人改了同一句怎么办？改坏了能不能退回昨天的版本？

软件团队面对的是同样的问题，只是规模更大。大型软件的代码量常以百万行计，参与者可能多达成百上千人。解决办法是**版本控制系统**（Version Control System，VCS）。它像一台为代码设计的“时光机加档案馆”，记住每一次修改：改了什么、谁改的、什么时候改的、为什么改。

写作时最常用的版本控制工具是 **Git**。它最初由 Linux 内核的作者林纳斯·托瓦兹（Linus Torvalds）在 2005 年为管理内核开发而编写，后来成为开源世界和许多企业的事实标准。围绕 Git 还出现了 GitHub、GitLab、Gitee 等代码托管平台，提供网页界面、协作讨论和权限管理。这些平台的功能各有差异，下文讲的是它们共通的基本做法。

几个核心概念可以先用文集的类比理解：

| 术语 | 中文含义 | 文集类比 |
|---|---|---|
| 仓库（Repository） | 存放全部代码及其完整历史的地方 | 文集的总档案柜 |
| 提交（Commit） | 一次被记录下来的修改快照，附带说明 | 一次修订并签名注明理由 |
| 分支（Branch） | 从某一版本岔出去的独立修改线 | 复印一份草稿，在上面单独改 |
| 主干（Main/Trunk） | 团队公认的、可随时交付的那条主线 | 准备付印的正式稿 |
| 合并（Merge） | 把分支上的修改并回另一条线 | 把草稿上的修改誊回正式稿 |

## 5.3.2 一行修改的旅程：分支、提交、评审、合入

还是那个“图片无法加载”的问题。在多数采用 Git 的团队里，一行修改通常这样走：

1. **从主干拉出分支**。工程师基于最新主干创建一个分支，比如叫 `fix-image-loading`。在这里怎么改都不会影响别人。
2. **修改并提交**。他找到出错的代码，改好后在本机运行验证，然后做一次提交，写上说明：“修复某机型下图片路径拼接错误”。好的提交说明是写给半年后的同事看的。
3. **推送并发起合并请求**。他把分支推送到团队的代码托管平台，发起一个**合并请求**。GitHub 上称为 Pull Request（PR），GitLab 上称为 Merge Request（MR），意思一样：“我改好了，请大家看看，同意的话并入主干。”
4. **自动检查**。合并请求一发出，平台会自动触发**持续集成**（Continuous Integration，CI）：在干净的环境里重新构建程序、运行自动化测试、检查代码风格和已知安全问题。任何一项失败，页面上就会亮起红灯。
5. **代码评审**。同事阅读改动，逐行留言：“这里会不会在网络很慢时出问题？”“能不能补一个测试？”作者据此修改，再次提交。这一过程叫**代码评审**（Code Review）。
6. **合入主干**。自动检查全部通过、评审者批准后，修改才被合并进主干。至此，这行代码正式成为“团队的代码”，等待进入下一节要讲的发布流程。

## 5.3.3 冲突与集成：为什么要“小步快合”

两个人在各自分支上改了同一个文件的同一行，合并时 Git 无法替人判断该保留谁的版本，就会报告**合并冲突**（Merge Conflict），需要人来裁决。冲突本身不可怕，可怕的是分支离开主干太久。一个分支独自改了一个月，主干上同时进来几百个别人的修改，合并时冲突成片，谁也说不清哪种组合才是对的，业内常把这叫作“集成地狱”。

因此，许多团队倾向于**小步快合**：分支短命，修改粒度小，频繁并入主干。一些团队进一步采用**主干开发**（Trunk-Based Development），几乎所有人都直接围绕主干做小改动，尚未完成的功能用“功能开关”先藏起来。也有团队使用分支较多的流程，比如早年流行的 Git Flow。选择哪种方式取决于团队规模、发布节奏和产品形态，并没有通用的唯一答案。不同做法背后的原理是一致的：**集成越频繁，每次集成的风险越小。**

## 5.3.4 代码流里的制衡：自动化与人各管一段

为什么不让工程师改完直接推上主干？因为主干是所有人共享的基础，一处坏代码会同时拖累几百人的工作，最后还可能到达用户手里。代码流的设计，本质上是给修改设置了几道关口：

- **机器把关**：编译能否通过、测试是否全绿、格式是否规范、是否引入了已知有漏洞的依赖。这类检查标准明确、重复性高，交给机器又快又稳。
- **人把关**：设计是否合理、命名是否清楚、有没有漏掉边界情况、改动是否符合业务意图。这类判断依赖经验与上下文，机器目前还难以完全替代。
- **规则把关**：平台可以设置“主干受保护”，规定未经评审、检查未通过的修改不得合入。这样制衡就不再依赖个人自觉。

这些关口还留下了一份完整的记录。日后若发现某个版本出了问题，工程师可以沿着提交历史，查到是哪次修改、为何修改、谁批准的，必要时把那次修改单独撤回。对管理者来说，这份记录也是理解团队工作方式的窗口：评审是否敷衍、测试是否常年失败，都会在代码流里留下痕迹。

写作时，AI 辅助编程工具已经进入这条流程，有的在编辑器里帮人写代码，有的能自动生成合并请求或评审意见。但 AI 写出的代码同样要走分支、检查、评审、合入的路径，责任仍由提交和批准它的人承担，第七章会专门讨论这一变化。

## 5.3.5 小结

一行修改从工程师的电脑走到主干，要经过分支、提交、合并请求、自动检查、代码评审和合入这几站。版本控制让众人的修改可追溯、可回退；持续集成和代码评审分别从机器与人的角度为质量把关；小步快合则把集成风险拆小、摊薄。代码合入主干，只是走完了一半。它还要被构建成可安装的程序，分批送到真实用户面前，这就是下一节“发布流”要讲的内容。
