# 5.6 本章骨架小结与实物探索任务

前面五节，我们像跟踪快递包裹一样，盯住了软件系统里五种不同的“流动物”：一次请求、一份数据、一行代码、一个新版本、一次故障。它们走的路线不同，速度也不同。请求以毫秒计，代码修改以小时或天计，发布以天或周计。但它们有一个共同点：流动的路径都是工程师事先设计好的，每一段都有关口、记录和退路。看清这些流动，就能把第二到第四章介绍的组件和连接串成一张活的系统图。

## 5.6.1 本章骨架回顾

可以把本章内容压缩成一张对照表：

| 流动 | 流动的是什么 | 典型路径 | 关键关口 | 出问题时的退路 |
|---|---|---|---|---|
| 请求流 | 用户的一次操作 | 客户端 → 域名解析 → 网关/负载均衡 → 业务服务 → 数据库，再原路返回 | 认证、限流、超时设置 | 重试、降级、熔断 |
| 数据流 | 被写入的业务数据 | 写入主库 → 复制到从库/缓存/搜索索引 → 被读取或分析 | 事务提交、复制确认 | 备份恢复、对账修正 |
| 代码流 | 一次代码修改 | 本地分支 → 提交 → 合并请求 → 代码评审 → 自动测试 → 合入主干 | 评审、持续集成（CI） | 撤销提交（revert） |
| 发布流 | 一个可运行的新版本 | 构建制品 → 测试环境 → 灰度发布 → 全量 | 监控指标、发布审批 | 回滚到上一版本 |
| 故障流 | 一次异常及其处置 | 监控告警 → 响应与止损 → 定位根因 → 修复 → 复盘 | 告警阈值、值班机制 | 预案、回滚、扩容 |

围绕这张表，有几条要点值得记住：

- **请求流是“横向”的，代码流和发布流是“纵向”的。** 请求在一瞬间横穿系统的各层；代码则在较长时间里，从一个开发者的电脑一路走到所有用户的设备和服务器上。
- **数据往往有多份副本。** 为了速度和可靠，同一份数据会出现在主库、从库、缓存里。副本之间可能有短暂的不一致，这是第六章“事务与一致性”和第八章“CAP”要回答的问题。
- **每条流动都要“看得见”。** 日志、监控和追踪（第三章 3.5 节）是故障流的起点。没有它们，系统坏了也没人知道。
- **退路和前进路线同样重要。** 灰度发布、回滚、降级等手段都基于同一个认识：变更总会有风险，所以要让出错时的代价小一些，恢复快一些。
- **复盘的目标是改进系统，不是追究某个人。** 许多团队采用“不责备复盘”的做法。一次故障暴露的问题，最终要变成新的测试、告警或流程，回流到代码流和发布流中。

这些流动之所以能够顺畅运转，靠的是背后的机制：模块化、并发、事务、缓存、测试。下一章就要打开这些“发动机”。

## 5.6.2 实物探索任务

下面的任务不需要编程基础。只要有一台手机或电脑，就能亲眼看到本章讲的流动。

1. **追踪一次请求。** 在电脑浏览器中打开任意购物或新闻网站，按 F12（Mac 上按 Option+Command+I）打开开发者工具，切到“网络”（Network）面板后刷新页面。观察列表中出现了多少个请求，找出耗时最长的三个，看看它们分别请求的是图片、脚本还是数据接口。
2. **观察数据的“延迟一致”。** 在社交应用里发一条评论或修改头像，然后立刻换另一台设备，或者退出后重新登录查看。记录新内容是立刻出现，还是要等几秒才出现。想一想：这可能和数据的哪一段复制或缓存有关？
3. **翻看一个开源项目的代码流。** 访问 GitHub 等代码托管平台上的一个知名开源项目（写作时 GitHub 的常见入口是项目页面上的“Pull requests”标签），任选一个已合并的合并请求，看看它有几位评审者参与、讨论了几轮、自动检查显示的是绿色对勾还是红色叉号。
4. **记录应用的发布节奏。** 在手机应用商店里打开你最常用的三个应用，查看“版本历史”或“更新内容”，统计最近几次更新相隔多久，说明里提到的是新功能还是“修复已知问题”。
5. **阅读一份公开的故障报告。** 不少云服务商和互联网公司会公开发布故障复盘报告，也叫事后分析（postmortem）。找一篇来读，按“发现—止损—定位—修复—改进”五步画出时间线，标出哪一步花的时间最长。

## 5.6.3 可以直接拿去问 AI 的问题

- “我在浏览器开发者工具里看到一个请求的状态码是 304，耗时只有几毫秒，另一个是 200，耗时几百毫秒。请用通俗的话解释两者的区别，并说明这和缓存有什么关系。”
- “请以一个外卖下单为例，分别画出它的请求流、数据流和故障流，并指出三者在哪些环节会互相影响。”
- “灰度发布、蓝绿部署和金丝雀发布有什么异同？各自适合什么场景？请用对照表回答，并说明哪些说法是特定公司的做法。”

向 AI 提问时，不妨把自己在任务中实际看到的截图、状态码或报告原文一并贴上。AI 依据真实材料回答，比凭空泛泛而谈可靠得多。对它给出的具体数字和产品细节，也要保持核实的习惯。

到这里，系统已经“流动”起来了。下一章要回答一个更深的问题：成千上万的请求同时涌来，数据却不会算错，软件改了又改却依然可靠，这些究竟是靠什么机制做到的。
