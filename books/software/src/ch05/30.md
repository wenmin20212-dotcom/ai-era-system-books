# 5.5 故障流：一次故障怎样被发现、定位与修复

晚上八点，你在购物应用里点“提交订单”，转了十几秒的圈，最后弹出一行字：“服务繁忙，请稍后再试。”你刷新两次，第三次成功了。对你来说这只是一次小小的不顺；而在应用背后，很可能有一部值班手机已经响起，几位工程师正盯着同一张监控图，讨论“是哪一环出了问题”。

前面几节讲了请求、数据、代码和发布怎样流动。本节讲一种谁都不希望出现、却一定会出现的流动：**故障流**。它的起点是一个异常信号，终点是一份复盘报告和几项改进措施。中间的每一步，都有成熟的工程做法。

## 5.5.1 故障是常态：从“会不会坏”到“坏了怎么办”

一个中等规模的线上系统，往往由几十到上百个服务、多个数据库、缓存和第三方接口组成，运行在成百上千台机器上。硬盘会坏，网络会抖动，新发布的代码可能有缺陷，某个依赖的外部服务可能突然变慢。只要部件足够多，“某处正在出问题”几乎是每天的常态。

因此成熟的团队不追求“永不出错”，而是追求两件事：**尽快发现**，**尽快恢复**。业界常用几个时间指标来衡量：

| 指标 | 英文缩写 | 含义 |
|---|---|---|
| 平均发现时间 | MTTD（Mean Time To Detect） | 从故障发生到被察觉要多久 |
| 平均恢复时间 | MTTR（Mean Time To Recovery） | 从发现到服务恢复要多久 |
| 平均故障间隔 | MTBF（Mean Time Between Failures） | 两次故障之间平均隔多久 |

很多团队还会给服务定一个**服务等级目标**（SLO，Service Level Objective），比如“一个月内 99.9% 的请求成功”。按一个月约 43200 分钟算，0.1% 对应大约 43 分钟。这段允许出错的时间常被称为“错误预算”。预算快用完时，团队会放慢发布节奏，先修稳定性。

## 5.5.2 发现——信号从哪里来

故障被发现，通常有三条来源：

1. **监控告警**。第三章讲过的日志、指标和链路追踪在这里派上用场。比如“下单接口错误率五分钟内超过 1%”或“响应时间第 99 百分位超过 2 秒”，触发规则后，告警系统会通过短信、电话或即时通讯软件通知值班工程师（on-call）。
2. **主动探测**。有的团队会部署“拨测”程序，模拟真实用户每隔一段时间去登录、搜索、下单，一旦失败就报警。
3. **用户反馈**。客服工单突然增多、社交媒体上出现集中抱怨，也是信号。如果故障主要靠用户先发现，通常说明监控还有盲区。

告警设计本身也有讲究。规则太松会漏报；太紧又会让值班人员被大量无关紧要的告警淹没，产生“告警疲劳”，真正的问题反而被忽略。比较通行的做法是优先监控用户能感受到的症状，如错误率、延迟和成功率，而不是给每台机器的每个细节都设报警。

## 5.5.3 止血——先恢复，再找根因

值班工程师确认故障后，会按严重程度定级，影响面大的会拉起专门的应急沟通群，指定一名**事故指挥**（Incident Commander）统一协调。这一角色的做法源自消防等应急管理领域，被许多互联网公司借鉴。

这一阶段最重要的原则是：**先止血，后治病**。用户等不起工程师慢慢读代码，常见的止血手段有：

- **回滚**：如果故障出现在一次发布之后，最快的办法往往是退回上一个版本，也就是 5.4 节讲的回滚。经验上，相当比例的线上故障与变更有关，所以“最近改了什么”几乎总是第一个问题。
- **切流量**：把请求从出问题的机房或集群转到健康的那一边。
- **降级**：暂时关掉非核心功能，比如商品推荐、评论区，把资源让给下单和支付。
- **限流与熔断**：当某个下游服务已经扛不住时，主动拒绝一部分请求，或者暂时停止调用它，避免故障像多米诺骨牌一样扩散，这种现象叫“级联故障”。

本节开头那句“服务繁忙，请稍后再试”，很可能就是限流或降级在起作用。系统没有崩溃，而是有计划地少做一点。

## 5.5.4 定位——沿着线索往回追

服务恢复后，或者在止血的同时，工程师要回答“到底哪里坏了”。这像侦探破案，主要线索有三类：

- **指标**看“什么时候开始、影响多大”。把错误率曲线和发布记录、配置变更记录叠在一起看，时间点往往能说明问题。
- **链路追踪**看“卡在哪一环”。一次下单请求经过网关、订单服务、库存服务、支付服务，追踪数据能显示时间花在了哪一段。
- **日志**看“具体发生了什么”。报错信息、异常堆栈会指向某个函数，甚至某一行代码。

根因常常比表面现象深一层。比如表面是“下单超时”，往下查是“库存服务慢”，再往下是“数据库连接用光了”，最终原因可能是某条新加的查询没有走索引，在大促流量下拖垮了数据库。定位时要不停追问“为什么”，直到找到能修改的那一处。

## 5.5.5 修复与复盘——让同一个坑不踩第二次

真正的修复可能是改代码、加索引、扩容或修正配置，然后走完整的代码流和发布流，经过评审、测试和灰度后上线，而不是在线上随手修改。

最后一步是**事后复盘**（postmortem）。许多团队采用“不追责”（blameless）的复盘文化，这一做法在谷歌公开的《站点可靠性工程》（SRE，Site Reliability Engineering）一书中有系统介绍。它的出发点是：故障通常是系统性问题，比如缺少测试、告警不准、发布没有灰度，而不是某个人“不小心”。如果复盘变成追责，大家就会隐瞒信息，系统反而更脆弱。

一份典型的复盘报告包括：

1. 时间线：几点发生、几点发现、几点恢复；
2. 影响范围：多少比例的请求或用户受影响；
3. 根因分析；
4. 改进项：每一项写清负责人和完成期限，例如补一条告警、加一个测试、给数据库查询加上审查规则。

把故障流画成一条线：**信号 → 告警 → 定级 → 止血 → 定位 → 修复 → 复盘 → 改进**。最后一步又回到代码流和发布流，让系统比故障前多一层防护。这也是软件系统“演进”的一个重要来源：许多监控、测试和保护机制，都是在一次次真实故障之后补上的。
