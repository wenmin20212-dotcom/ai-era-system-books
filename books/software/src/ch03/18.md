# 3.4 身份认证与权限：确认你是谁、你能做什么

早上打开手机里的银行 App，你可能刷一下脸就进去了；下午在电脑上登录同一个账户，它却要你输入密码，再填一条短信验证码；进去之后，你能看自己的余额，却看不到别人的；公司里的财务同事能在报销系统里批准付款，你只能提交申请。这些日常体验背后，是软件系统里两件紧密相连但性质不同的事：**确认你是谁**，以及**决定你能做什么**。

## 3.4.1 两个问题，两个名字

工程上把这两件事分得很清楚：

| 概念 | 英文与缩写 | 回答的问题 | 生活类比 |
|---|---|---|---|
| 身份认证 | Authentication，常简写 AuthN | 你是谁？ | 进小区时保安核对你的门禁卡 |
| 授权（权限控制） | Authorization，常简写 AuthZ | 你能做什么？ | 门禁卡只能打开你家那栋楼的门 |

两者顺序固定：先认证，后授权。一个系统如果只做认证不做授权，就像所有住户的门禁卡都能打开所有房门；只做授权不做认证，则等于谁捡到卡都能冒充住户。很多安全事故，恰恰出在两者之一的疏漏上。

## 3.4.2 认证：凭什么相信你

系统无法直接"看见"你，只能检查你出示的凭证。常见的凭证大致分三类：

- **你知道的东西**：密码、PIN 码、密保问题答案。
- **你拥有的东西**：手机（接收短信验证码或运行验证器 App）、U 盾、硬件安全密钥。
- **你本身的特征**：指纹、面部、声纹等生物特征。

只用一类凭证称为单因素认证；同时要求两类及以上，称为**多因素认证**（Multi-Factor Authentication，MFA）。银行"密码 + 短信验证码"就是典型的双因素认证。它的道理很朴素：密码可能泄露，手机可能丢失，但两者同时落入同一个坏人手中的概率要小得多。

有一个容易误解的细节：负责任的系统**并不保存你的密码原文**。它保存的是经过**哈希**（Hash，一种单向的"搅碎"运算）处理后的结果，还会给每个密码加一段随机的"盐"（Salt）。你登录时，系统把你输入的密码用同样方式搅碎，比较结果是否一致。这样即便数据库被窃取，攻击者拿到的也只是难以还原的乱码。这也解释了为什么正规网站"找回密码"时只能让你重设，而不会把旧密码发给你——如果某个网站能把原密码发回来，说明它的存储方式值得警惕。

至于手机上的刷脸、指纹，写作时主流手机系统的通常做法是：生物特征只在本机的安全芯片区域里比对，比对通过后再由手机向服务器证明"主人已解锁"，指纹或面部数据本身一般不上传。近年兴起的**通行密钥**（Passkey）也沿用这一思路，用存在设备里的密钥代替密码，目前已有多家大型平台支持。

## 3.4.3 登录之后：系统怎样一直"记得"你

认证通过后，你接下来点的每一页、发的每一个请求，系统都要知道是你。总不能每次都重新输密码。常见做法是，登录成功后服务器发给你一张"临时通行证"：

- **会话**（Session）方式：服务器在自己这边记下"某编号对应某用户"，只把编号放进浏览器的 **Cookie**（浏览器替网站保存的一小段数据）里。之后每次请求都带上编号，服务器查表认人。
- **令牌**（Token）方式：服务器签发一段带数字签名的字符串，里面写明用户身份和有效期，常见格式是 **JWT**（JSON Web Token）。服务器只需验证签名真伪，不必查表，便于多台服务器共同处理请求。

两种方式都会设置有效期。这就是你长时间不操作后银行 App 会自动退出的原因：通行证越短命，被盗用后造成的损失窗口越小，代价是用户要更频繁地重新登录——这是安全与便利之间典型的取舍。

你常见的"用微信登录""用 Apple 账号登录"，则是把认证这件事委托给第三方。背后通常采用 **OAuth 2.0** 授权框架及在其上扩展的 **OpenID Connect**（OIDC）协议：你在第三方那里确认身份并同意授权，第三方给应用一张有限范围的凭证，应用自始至终拿不到你在第三方的密码。这正呼应了第一章所说的软件系统边界——一部分职能被放到了系统之外的第三方服务里。

## 3.4.4 授权：把"能做什么"写成规则

确认了身份，下一步是判断每个操作是否允许。最常见的模型是**基于角色的访问控制**（Role-Based Access Control，RBAC）：不直接给每个人分配权限，而是先定义角色，再把人放进角色。

| 角色 | 提交报销 | 审批报销 | 修改系统设置 |
|---|---|---|---|
| 普通员工 | ✓ | | |
| 部门经理 | ✓ | ✓ | |
| 系统管理员 | | | ✓ |

公司来了新人，只需给他分配"普通员工"角色，而不必逐项勾选几十个权限。当规则更细时——比如"经理只能审批本部门、金额在一定额度以下的报销"——就需要结合用户属性、数据属性和环境条件来判断，这类做法称为**基于属性的访问控制**（Attribute-Based Access Control，ABAC）。

设计授权时有一条公认原则：**最小权限原则**，即只给完成工作所必需的最小权限。手机系统询问"是否允许此 App 访问你的相册"，也是这一原则在操作系统层面的体现。

还有一个关键的工程要点：**授权检查必须在服务端完成**。前端界面把"删除"按钮藏起来，只是改善体验；真正的把关要在后端每次处理请求时重新核对身份与权限。否则，懂技术的人绕过界面直接向服务器发请求，就可能看到别人的订单、改掉别人的数据。在公开的安全风险排行中，"访问控制失效"长期位居前列，原因大多就在这里。

## 3.4.5 小结

认证解决"你是谁"，靠的是凭证与多因素组合；会话和令牌让系统在一段时间内记住你；授权解决"你能做什么"，靠角色、属性和最小权限原则，并且必须由服务端把关。它们和业务逻辑一起，构成系统可信运行的基础。但规则写好了，并不等于系统就不会出问题——有人试图越权、登录接口突然变慢、某台服务器悄悄出错，这些都需要被及时发现。下一节，我们来看让系统"看得见"的日志、监控与告警。
