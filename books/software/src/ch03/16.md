# 3.2 业务逻辑层：把规则写成代码

打开购物应用，把一件标价 199 元的外套放进购物车，再领一张“满 200 减 30”的优惠券，结算页提示你“还差 1 元可用券”。你又加了一双 9.9 元的袜子，总价变成 208.9 元，优惠券立刻生效，实付 178.9 元。同一时刻，页面还告诉你“预计后天送达”“该商品不支持七天无理由退货”。

这些提示的背后没有店员在算账，是一层专门负责“按规则办事”的代码在工作。上一节讲的表现层负责把信息呈现出来、接收你的点击；至于这些信息怎样算出来、你的操作是否被允许，由**业务逻辑层**（Business Logic Layer，也常叫“领域层”）决定。

## 3.2.1 什么是“业务规则”

“业务”一词听起来像商业术语，在软件里它的意思更宽：**这个软件所服务的那件现实事务，本身有哪些规矩**。

- 购物应用的规矩：满减怎样计算，库存不足能不能下单，订单多久不付款自动取消。
- 银行应用的规矩：单日转账有没有上限，余额不足时拒绝交易。
- 打车应用的规矩：起步价加里程费加时长费，高峰时段怎样调整价格。
- 学校选课系统的规矩：先修课没通过不能选，同一时段的两门课不能同时选。

这些规矩原本写在合同、制度和店员的经验里，软件要做的是把它们**翻译成精确、无歧义、机器能执行的代码**。业务逻辑层就是存放这些翻译结果的地方。

## 3.2.2 从一句话规则到一段代码

“满 200 减 30”看上去一句话就说完了，真正写成代码时，开发者必须回答一连串问题：

| 自然语言里的模糊处 | 代码必须给出的明确答案 |
|---|---|
| “满 200”包不包括运费？ | 只算商品金额，还是含运费 |
| 正好 200 元算不算“满”？ | 用“大于等于”还是“大于” |
| 能否和会员折扣叠加？ | 先打折再减，还是先减再打折 |
| 退掉一件商品后怎么办？ | 不满 200 时，优惠是否按比例收回 |
| 金额出现小数怎么办？ | 精确到分，四舍五入还是截断 |

这张表说明了业务逻辑层最难的地方：**难点往往不在技术，而在规则本身**。人与人沟通可以说“差不多”，计算机只认“是”或“否”。所以这一层的代码通常由开发者和产品经理、业务人员反复对齐后才定下来，很多软件缺陷也不是程序“算错了”，而是一开始就把规则理解错了。

一个典型的业务操作，在这一层里大致按如下步骤走：

1. **校验**：输入是否合法，比如数量不能是负数，收货地址不能为空。
2. **判断**：根据规则决定能不能做，比如库存是否足够、优惠券是否过期。
3. **计算**：算出结果，比如应付金额、预计送达时间。
4. **改变状态**：把订单从“待支付”改为“已支付”，扣减库存。
5. **通知**：把结果交给其他部分，比如给用户发消息、通知仓库发货。

其中第 4 步要动用数据，具体怎样把数据可靠地存下来，交给下一节讲的持久化层。

## 3.2.3 状态与流转：订单的一生

业务逻辑里有一个很常用的思路，叫**状态机**（State Machine）：把一件事物可能处于的状态列出来，再规定状态之间允许怎样转换。

以网购订单为例，常见的状态流转是：

> 待支付 → 已支付 → 已发货 → 已签收 → 已完成
> 待支付 →（超时或用户取消）→ 已取消
> 已签收 →（申请退货）→ 退货中 → 已退款

状态机的价值在于**明确禁止不合理的跳转**。“已取消”的订单不能再发货，“待支付”的订单不能直接退款。若没有这样的约束，一个按钮的误触或一次网络重复请求，就可能让一笔没付钱的订单被发出货去。你在应用里看到某些按钮是灰色的、点不了，往往就是状态机在表现层留下的投影：当前状态下这个操作不被允许。不过，按钮变灰只是界面上的提示，真正的把关必须在业务逻辑层再做一次。

## 3.2.4 为什么规则要放在“一个地方”

业务规则能不能散落在各处？比如在手机 App 里算一遍价格，在网页里再算一遍，在服务器上又算一遍。工程实践给出的答案是：**关键规则应当集中在服务端的业务逻辑层，由它做最终裁决**。理由有三：

- **安全**：手机和浏览器上的代码在用户手里，可以被查看甚至篡改。如果价格只在客户端计算，懂行的人就可能把 178.9 元改成 1.789 元再提交。服务端必须重新计算、重新校验。
- **一致**：同一条规则只写一份，网页、App、小程序调用的都是它，才不会出现“App 里能用券、网页上不能用”的矛盾。
- **易改**：规则会变。今天“满 200 减 30”，下个月可能改成“每满 100 减 15”。规则集中在一处，修改时只动一处，测试也只测一处。

客户端仍然可以做一些预先计算和检查，让你不必每次都等服务器回应，体验更顺畅，但那只是“预览”，以服务端为准。

有些系统会进一步把变化频繁的规则从代码里抽出来，写成配置或交给专门的**规则引擎**（Rule Engine）管理，让运营人员不改代码也能调整活动参数。这是不少电商、金融系统的常见做法，并非所有软件都需要。规则越稳定、越简单，直接写在代码里反而越清楚。

## 3.2.5 小结：软件的“价值”住在这一层

界面可以改版，数据库可以更换，服务器可以从机房搬到云上，只要业务规则没变，这个软件“做的事”就没变。从这个意义上说，业务逻辑层承载的是软件存在的理由：它把一个组织的制度、经验和承诺，变成了每秒可以准确执行成千上万次的代码。

规则判断完毕、状态已经改变，接下来的问题是：这些改变怎样才能在断电、宕机之后依然不丢？这就是下一节“数据持久化”要回答的。
