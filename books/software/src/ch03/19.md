# 3.5 日志、监控与告警：让系统看得见

深夜，你在外卖应用里点了“提交订单”，屏幕转了几圈，弹出一行字：“网络开小差了，请稍后再试”。你看到的只是一句提示，可在服务端，这一次失败已经被记了下来：几点几分、哪台服务器、调用了哪个服务、等了多久、错误代码是什么。几分钟后，如果同样的失败越来越多，某位值班工程师的手机就会响起来。

软件不像汽车，坏了会冒烟、会有异响。它的内部运转看不见、摸不着。日志、监控与告警，就是工程师给软件装上的“仪表盘”和“行车记录仪”。业界常把这种“从外部判断系统内部状态”的能力叫作**可观测性**（Observability）。

## 3.5.1 日志：系统的行车记录仪

**日志**（Log）是程序在运行过程中主动写下的一条条文字记录。最朴素的一条日志大致长这样：

```
2026-10-27 23:41:05 ERROR order-service 用户下单失败：库存服务响应超时（3000毫秒）
```

它通常包含几个要素：时间、级别、来源、事件描述。其中“级别”用来区分轻重，常见的分法如下：

| 级别 | 含义 | 生活类比 |
|---|---|---|
| DEBUG（调试） | 开发时排查用的细节 | 草稿纸上的演算 |
| INFO（信息） | 正常发生的重要事件，如“用户登录成功” | 日记里的流水账 |
| WARN（警告） | 有异常苗头但还能运行 | 汽车油量灯变黄 |
| ERROR（错误） | 某个操作失败了 | 发动机故障灯亮起 |

早期的日志写成一行行自由文字，人读起来方便，机器却难以统计。现在许多系统改用**结构化日志**，即把每条记录写成“字段名—值”的格式，比如 `{"level":"ERROR","service":"order","latency_ms":3000}`，这样就能直接查询“过去一小时订单服务有多少条超时错误”。

日志的价值在于细节：出事之后，它能回答“当时到底发生了什么”。但它也有代价。一个大型应用每天产生的日志可能多达 TB（万亿字节）级别，存储和检索都要花钱。另外，日志里绝不能随手写进密码、身份证号这类敏感信息，否则记录本身就成了泄密源头。

## 3.5.2 监控：系统的仪表盘

日志像记录仪，逐条记事；**监控**（Monitoring）更像仪表盘，把大量事件汇总成随时间变化的数字，称为**指标**（Metric）。工程师最常盯的几类指标，有一套广为流传的归纳，出自谷歌公开出版的《SRE：Google 运维解密》一书，叫“四大黄金信号”：

- **延迟**：一个请求从发出到得到回应要多久；
- **流量**：每秒有多少请求进来；
- **错误率**：失败请求占多大比例；
- **饱和度**：CPU、内存、连接数等资源用掉了多少。

这四个数字画成曲线挂在大屏幕上，工程师一眼就能看出系统是否“发烧”。比如晚饭高峰时流量曲线陡升是正常的，但如果流量平稳而延迟突然翻倍，就说明某处出了问题。

当一个请求要穿过十几个服务时（第四章会讲到微服务），只看单个服务的指标还不够。于是有了**链路追踪**（Tracing）：给每个请求贴一个唯一编号，它经过哪个服务、在每一站停留多久，都记在这个编号下，最后拼成一张完整的“行程单”。日志、指标、追踪三者合在一起，常被称为可观测性的“三大支柱”。

## 3.5.3 告警：会叫醒人的规则

有了仪表盘，总不能让人二十四小时盯着屏幕。**告警**（Alert）就是一组预先写好的规则：当某项指标越过阈值，就通过短信、电话或办公软件通知值班人员。例如：“过去五分钟内下单错误率超过 1%，立即通知。”

告警最难的不是“报”，而是“报得准”。规则定得太松，真故障漏掉了；定得太紧，半夜接连响起几十条无关紧要的提醒，工程师很快就会麻木，这被称为“告警疲劳”。因此成熟团队通常遵循几条经验：

1. 告警要对应“用户受到影响”，而不只是“某台机器 CPU 高了”；
2. 每条告警都应有明确的处理办法，否则就该降级为普通记录；
3. 分级通知：严重的打电话，一般的发消息，轻微的只记录。

许多团队还会事先约定**服务等级目标**（SLO，Service Level Objective），比如“99.9% 的请求在 1 秒内完成”，告警围绕这个目标来设计，避免各说各话。

## 3.5.4 三者如何配合

把三者串起来看，就是一条清晰的链条：

> 监控发现“哪里不对”→ 告警通知“该有人管了”→ 日志和追踪帮助回答“为什么不对”。

回到开头那单失败的外卖：错误率指标上升触发告警，工程师打开追踪记录，发现请求卡在库存服务；再查库存服务的日志，看到数据库连接已经用满。问题从模糊的“下单失败”被一步步缩小到具体原因。

要注意，这套能力不是软件写完之后再贴上去的，而是在写代码时就要设计好：在哪里打日志、暴露哪些指标、请求编号如何传递。看不见的系统无法管理，这正是本章所讲的各个功能层之外，那条贯穿所有层次的“观察线”。至于故障被发现之后怎样定位、修复和复盘，我们留到第五章的“故障流”一节再完整走一遍。
