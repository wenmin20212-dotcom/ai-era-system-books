# 5.3 查询流：一次搜索请求的完整旅程

在手机浏览器里输入“附近 修自行车”，按下回车，不到一秒，屏幕上出现了地图、店铺列表和几条网页链接。从手指离开屏幕到结果出现，这串文字走完了一段长长的路：它离开手机，穿过网络，进入数据中心，被拆开、改写、分发给成百上千台机器，再被汇总、排序、装进页面送回来。上一节讲的索引流是在搜索之前“备好货”，本节要跟着这一次请求，把这段往返旅程按站点走一遍。

需要先说明：各家搜索引擎的内部流程并不公开。下面描述的是信息检索教材、公开论文和开源系统（如 Elasticsearch）中可以确认的通用结构，具体到某一家公司的细节，会单独标明或说明属于推测。

## 5.3.1 第一站：从搜索框出发

旅程其实在按回车之前就开始了。你每敲一个字，搜索框下方的联想词就会刷新，这是浏览器在不断向服务器发送小请求，取回“查询自动补全”（Query Auto-Completion）的候选。真正按下回车后，浏览器会把查询词连同一些附加信息打包成一个网络请求，常见的附加信息包括：

- 界面语言和大致地区（决定“附近”指哪里、结果用什么语言）；
- 设备类型（手机还是电脑，影响页面布局）；
- 是否开启安全搜索等设置；
- 在用户允许的情况下，位置或登录状态等信息。

这个请求先经过域名解析（DNS，Domain Name System，把网址翻译成服务器地址），再被送往离你较近的数据中心入口。大型搜索服务通常在多地部署机房，入口处的负载均衡（Load Balancing）设备会把海量请求分摊到不同服务器上，避免某一台被挤垮。

## 5.3.2 第二站：查询理解——先把问题“读懂”

请求到达后，第一件事不是去翻索引，而是弄清楚用户想要什么。第二章讲过查询处理的组成，这里只看它在流程中的位置。对“附近 修自行车”，系统可能依次做：

1. **规范化**：统一大小写、全角半角，去掉多余空格；
2. **分词**：切成“附近 / 修 / 自行车”；
3. **纠错与改写**：如果你打成“修自行吃”，可能提示正确写法；还可能补充同义表达，如“自行车维修”“单车修理”；
4. **意图识别**：判断这是一个“找本地服务”的查询，而非想了解自行车维修原理。

意图判断会直接改变后面的路线。被识别为本地需求，系统就会同时去查地图和商户数据；如果查询是“今天天气”，可能直接调用天气数据源。很多系统会把一次查询同时发给多个“垂直”数据源——网页、图片、新闻、地图、视频——这种做法在公开资料中常称为聚合搜索（Federated / Aggregated Search）。

## 5.3.3 第三站：分发与检索——成百上千台机器同时翻目录

整个网页索引太大，一台机器装不下，于是被切成许多“分片”（Shard），分散在大量服务器上，每个分片还有多个副本。这部分架构在第七章细讲，这里抓住流动的形态即可：

| 环节 | 做什么 | 类比 |
|---|---|---|
| 分发（Scatter） | 把改写后的查询同时发给所有分片 | 图书馆馆长把同一张找书单发给每个书库 |
| 本地检索 | 每个分片查自己的倒排索引，圈出候选并粗排 | 每个书库管理员挑出自己库里最像的几十本 |
| 汇总（Gather） | 收集各分片的候选，合并成一份名单 | 馆长把各书库交上来的书摆到一张桌上 |

这种“分散—汇总”模式是分布式检索的经典结构。它带来一个现实问题：总耗时取决于最慢的那个分片。因此工程上会设置超时，某个分片迟迟不回应，就先用其他分片的结果凑出答案；还会给同一请求向多个副本发送备份请求，谁先回来用谁。谷歌工程师在公开文章《The Tail at Scale》中专门讨论过这类“长尾延迟”问题。

## 5.3.4 第四站：精排与组装——把名单变成页面

汇总后的候选可能有成千上万条，接下来按“漏斗”逐层收窄：先用计算量小的方法（如第六章将讲的 BM25 等相关性分数）筛掉明显不相关的，再对剩下的几百条用更复杂的学习排序模型精细打分，综合相关性、权威性、新鲜度、地理距离等信号。越往后，候选越少，模型越重。

排好序后，还要“装修”结果页：

- 为每条网页生成摘要，并把你搜的词加粗；
- 插入地图卡片、知识卡片或直接答案；
- 在标明“广告”的位置放置广告结果（广告来自另一套竞价系统，第四章已讨论）；
- 去掉重复或过于相似的结果，保证多样性。

如果是 AI 搜索产品，这一站还会多出一步：把排在前面的若干网页片段交给大语言模型，生成一段带引用的回答。这正是第四章介绍的检索增强生成（RAG，Retrieval-Augmented Generation）在查询流中的落点。

## 5.3.5 第五站：返程与留痕

页面组装完毕，经网络回到你的手机，浏览器把它渲染出来。公开资料中常见的说法是，主流网页搜索力求把服务端处理控制在零点几秒的量级，许多常见查询还会直接命中缓存（Cache），即最近有人搜过、结果尚未过期，就直接复用，省去整条检索链路。

旅程并未就此结束。你点了哪条结果、是否很快返回重新搜索，这些行为会以日志形式记录下来（具体记录什么、保存多久，各家隐私政策规定不同）。它们是下一节“反馈流”的源头。

## 5.3.6 小结：一条往返的流水线

把全程串起来，一次查询流可以概括为：

### 5.3.6.1 输入与联想 → 网络传输与负载均衡 → 查询理解 → 分发到各分片检索 → 汇总 → 多级排序 → 结果页组装 → 返回与记录日志

这条流水线的设计原则很朴素：先读懂问题再找答案，能并行的尽量并行，先粗后细地筛选，赶不上时间的环节宁可舍弃。理解了它，你就会明白为什么同一个词在不同地点、不同设备上搜，结果会有差异。而那些被记录下来的点击，又将沿着另一条通道流回系统——这就是下一节要追踪的反馈流。
