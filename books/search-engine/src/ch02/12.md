# 2.4 查询处理：弄清你到底想找什么

打开手机上的搜索框，输入“苹果多少钱”，你想知道的是水果摊上一斤苹果的价格，还是最新款苹果手机的售价？再试试输入“北京天气”，结果页最上方通常直接出现一张天气卡片，而不是一串网页链接。搜索框只接收到几个字，系统却要从这几个字里猜出你的真实需求。完成这件事的部件，就是查询处理模块。

如果把爬虫和索引比作图书馆的采购员和编目员，查询处理就像柜台后面的咨询员：读者递过来一张字迹潦草、只写了半句话的纸条，咨询员要先认清字、理解意思，再决定去哪几排书架找。

## 2.4.1 从一串字符到一组检索词

用户输入的内容叫作查询（Query）。它进入系统时只是一串字符，要经过几道基础加工，才能变成索引能“听懂”的形式：

1. **规范化**：统一全角与半角、大写与小写，去掉多余空格和标点。“ＩＰｈｏｎｅ”和“iphone”应当被当作同一个词。
2. **分词**：中文没有空格，系统要把“北京大学生活动中心”切成合适的词语。切成“北京大学 / 生活 / 动 / 中心”还是“北京 / 大学生 / 活动中心”，检索结果会完全不同。这里用到的分词方法与2.2节文档处理所用的方法应保持一致，否则查询切出的词和索引里存的词对不上，就会找不到。
3. **停用词处理**：“的”“了”“是”这类词几乎每篇文档都有，单独检索意义不大，系统常会降低它们的作用。不过并非一律删除，比如歌名“我的未来不是梦”，去掉虚词就面目全非了。

经过这几步，一句自然语言被转换成若干个检索词（Term），交给检索系统去倒排索引里查找。

## 2.4.2 修补与扩展：用户的输入并不完美

真实的查询常常带着错别字、拼音、简写和口语。查询处理模块会在这一阶段做几类“修补”：

| 处理类型 | 典型场景 | 系统的做法 |
|---|---|---|
| 拼写纠错（Spelling Correction） | 输入“搜素引擎” | 提示“您要找的是不是：搜索引擎” |
| 拼音转换 | 输入“sousuo yinqing” | 识别为对应汉字 |
| 同义词扩展 | 搜“电脑卡顿” | 同时匹配“计算机运行慢” |
| 缩写展开 | 搜“北大” | 关联“北京大学” |
| 查询联想（Query Suggestion） | 只输入“搜索” | 下拉框推荐完整的常见查询 |

公开资料中常见的说法是，纠错和联想主要依靠大量历史查询的统计：很多人输错后又改成同一个正确写法，系统就能学到这种对应关系。具体某家搜索引擎用了哪些数据和模型，大多没有公开，这里只介绍通用思路，第七章7.2节会进一步展开。

## 2.4.3 识别意图：同样几个字，想要的东西不同

比纠错更难的是判断用户“为什么搜”。信息检索研究中有一种被广泛引用的分类，把网页搜索的意图分为三类：

- **导航型**：想去某个特定网站，比如搜“中国铁路12306”，用户要的就是官网入口。
- **信息型**：想了解某个知识，比如“光合作用的过程”。
- **事务型**：想完成某个操作，比如下载软件、购买商品、查快递。

此外，系统还会识别查询中的**实体**（人名、地名、产品名等）以及时间、地点等限定条件。“附近的川菜馆”里的“附近”意味着要结合位置信息；“2026年高考日期”带着明确的时效要求。意图判断的结果会影响后续步骤：导航型查询优先给出官网，天气、汇率、计算这类查询可能直接触发答案卡片，带有新闻性质的查询则会更看重时效。

回到开头的“苹果多少钱”。系统无法读心，常见做法是根据大多数用户的点击习惯判断主流意图，同时在结果中照顾少数意图，例如前几条以手机价格为主，也夹带水果行情。这种做法在工程上常被称为结果的**多样化**。

## 2.4.4 改写之后，交给下游

经过规范化、分词、纠错、扩展和意图识别，原始查询被改写成一份更丰富的“检索指令”，里面通常包括：

- 主要检索词及其重要程度；
- 补充的同义词和相关词；
- 识别出的意图类别与实体；
- 时间、地点、语言等限定条件。

这份指令会被发往检索与排序系统：检索系统据此从索引里圈出候选文档，排序系统再结合意图信息决定先后顺序。需要说明的是，近年来不少搜索系统在查询处理中引入了语义模型，能把查询理解为一个整体含义，而不只是一组关键词。这一变化将在第六章语义检索部分详细介绍。

## 2.4.5 小结：读懂需求是找对答案的前提

查询处理位于用户和索引之间，负责把含糊、简短、带错误的输入，翻译成系统可执行的检索请求。如果这一步理解错了，后面的检索再快、排序再精，也只是在错误的方向上努力。下一节我们将看到，拿到这份检索请求之后，排序系统如何把成千上万个候选结果排出先后，并组织成你看到的结果页面。
