# 7.2 查询理解技术：纠错、联想与意图识别

在搜索框里慢慢敲下“北京天汽”，还没按回车，下拉框里已经出现“北京天气”“北京天气预报15天”；按下回车，结果页顶部可能还会提示“以下是‘北京天气’的结果”，并直接给出今明两天的气温卡片。短短几个字，系统做了三件事：猜你还没打完的话（联想），改你打错的字（纠错），判断你其实想要一张天气卡而不是一堆网页（意图识别）。第二章 2.4 节介绍过查询处理在系统中的位置，本节把这三项技术拆开，看它们各自靠什么工作。

## 7.2.1 查询联想：从“前缀”到“补全候选”

查询联想（Query Auto-Completion，QAC），也叫搜索建议，在你每敲一个字时就要给出候选，留给它的时间通常只有几十毫秒量级。它的基本结构可以分成两步：

1. **候选生成**：系统事先把大量历史查询整理成一种按前缀组织的数据结构，最常见的是前缀树（Trie，又称字典树）。就像查纸质字典时先翻到“北”字部，再找“北京”，前缀树沿着已输入的字符一路往下走，就能取出所有以此开头的候选。
2. **候选排序**：同一个前缀可能对应成千上万条历史查询，需要挑出最可能的几条。公开研究中常用的信号包括：查询的历史热度、近期是否突然变热（比如节假日、突发新闻）、用户所在地区、设备类型，以及同一次会话里前面搜过什么。

中文输入还多一层难度：用户可能直接用拼音或拼音首字母输入，比如敲“bjtq”，系统要先把它映射回“北京天气”。这一步与输入法的工作原理相近。

联想不只是省几下按键，它还在悄悄“规范”用户的表达：很多人顺手点了建议词，查询就从五花八门的说法收敛到少数常见写法，后面的检索和排序因此更容易。也正因为影响大，各家搜索引擎在公开政策中通常会说明，会过滤涉及暴力、色情、对个人的诽谤等不当建议。

## 7.2.2 拼写纠错：在“噪声”里还原本意

查询纠错（Query Spelling Correction）要回答一个问题：用户敲下的字符串，最可能是在想打哪个词？信息检索教材中经典的思路是**噪声信道模型**（Noisy Channel Model）：把用户脑中正确的词想象成一条消息，经过“手指打字”这条有噪声的信道，变成了屏幕上的错误字符串。纠错就是反推原消息，综合两个因素：

| 因素 | 回答的问题 | 举例 |
|---|---|---|
| 错误模型 | 正确词有多大可能被打成这个样子 | “天气”拼音输入时误选同音字“天汽”很常见 |
| 语言模型 | 这个正确词本身有多常见、放在上下文里通不通 | “北京天气”远比“北京天汽”常被搜索 |

英文纠错常用**编辑距离**（Edit Distance）衡量两个词相差多少次增、删、改、换位操作，例如 “serach” 与 “search” 只差一次相邻字母互换。中文的错误类型不同：拼音输入带来同音字错误（“在”与“再”），五笔或手写输入带来形近字错误，因此中文纠错系统通常要分别建立音近、形近的混淆字表。

搜索引擎的纠错有一个独特的数据来源：用户自己改错。如果大量用户搜了“天汽”后几秒钟内又改搜“天气”，这一对“改写记录”就是极有价值的纠错样本。公开论文和教材中常把这类查询日志作为训练纠错模型的重要依据；至于某家搜索引擎具体如何使用，内部细节大多未公开。

纠错还有分寸问题。系统把握大时可能直接替换并提示“已显示××的结果”，把握小时只显示“您是不是要找”。新出现的人名、品牌名、网络用语最容易被误改，所以纠错必须为“看起来像错字的正确新词”留出余地。

## 7.2.3 意图识别：同样两个字，想要的不一样

搜“苹果”的人，可能想买手机，想看水果营养，也可能想查苹果公司股价。意图识别（Query Intent Classification）要判断查询背后的需求类型。信息检索领域广为引用的一种粗分方法来自 Andrei Broder 在 2002 年发表的论文，把网页搜索查询分为三类：

- **导航型**：想去某个特定网站，如“中国铁路12306”；
- **信息型**：想了解某方面知识，如“光合作用的过程”；
- **事务型**：想完成某个操作，如下载、购买、订票。

实际系统的分类远比这细，常见维度还包括：是否有地域需求（“附近的药店”）、是否有时效需求（“台风最新消息”）、属于哪个垂直领域（医疗、购物、旅游）。识别结果会直接改变后续流程：时效需求高就优先新近网页，地域需求就调用地图服务，天气、汇率这类需求就直接返回结构化卡片（见 3.4 节）。

意图识别的技术路线大致经历了三个阶段：早期依赖人工规则和词表（如出现“下载”就判为事务型）；之后用统计机器学习，以查询词、点击过的网页类别等为特征训练分类器；近年普遍引入预训练语言模型，让系统更好地理解短查询中的语义。还有一种朴素而有效的思路是“看用户怎么点”：如果搜“苹果”后多数人点进了手机官网，这个查询的主要意图就偏向品牌。歧义很大时，系统往往不强行选一个，而是在结果页里混排几种意图的结果，这种做法常被称为结果多样化。

## 7.2.4 三者如何串起来：查询改写

纠错、联想和意图识别并不孤立，它们共同服务于一个更大的目标——**查询改写**（Query Rewriting），即把用户原话变成更适合检索系统执行的形式。除了纠错，改写还包括：

- **同义扩展**：搜“电脑卡顿”时也匹配写着“计算机运行慢”的网页；
- **实体识别与规范化**：把“鲁迅的《呐喊》”中的作者和书名识别为两个实体；
- **去除或降权无关词**：“请问怎么煮米饭啊”中的“请问”“啊”对检索帮助不大。

一次搜索中，它们大致按这样的顺序发挥作用：

> 输入中 → 联想补全 → 回车 → 纠错 → 分词与实体识别 → 意图识别 → 同义扩展与改写 → 送入检索与排序

要注意，这是公开资料中常见的逻辑顺序，真实系统中各步骤可能并行、合并或反复调用，具体实现因系统而异。

## 7.2.5 小结：在“说”与“找”之间搭桥

查询理解处理的是一个根本矛盾：用户的表达短、随意、常出错，而索引里的文档用的是另一套措辞。联想在你还没说完时帮你把话说清，纠错把说错的话还原，意图识别弄明白你说这话想干什么，查询改写再把这一切翻译成检索系统能执行的指令。它们都大量依赖历史查询与点击这类集体行为数据，这也解释了为什么常用查询总是被理解得更准，而冷门、新颖的查询更容易“答非所问”。下一节将转向开源世界，看 Lucene 与 Elasticsearch 这样的工具如何让任何人都能搭起一套具备这些基本能力的搜索系统。
