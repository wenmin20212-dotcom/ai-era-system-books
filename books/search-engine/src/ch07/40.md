# 7.3 开源搜索技术：Lucene 与 Elasticsearch 等

在购物网站的搜索框里输入“降噪耳机”，左侧立刻出现“品牌”“价格区间”的筛选项；在公司内部文档系统里搜索一份合同，几毫秒就跳出结果。这些搜索框背后，很多并不是各家公司从零写起的，而是建立在一批公开源代码的搜索软件之上。网页搜索巨头的核心系统大多不公开，**开源搜索**（Open Source Search）却让任何人都能看到一个真实可用的搜索引擎是怎样搭起来的。本节就借这扇敞开的窗口，把前面讲过的倒排索引、BM25、分片与副本落到具体软件上。

## 7.3.1 一个“发动机”和几辆“整车”

开源搜索世界里最常被提到的名字是 **Lucene**。它是一个用 Java 编写的搜索程序库，由道格·卡廷（Doug Cutting）最初开发，后来成为 Apache 软件基金会的项目。Lucene 本身不是一个打开就能用的网站，而是一套“发动机”：负责建倒排索引、存储文档、执行查询、计算相关性得分。

在这台发动机上，人们组装出了不同的“整车”：

| 名称 | 定位 | 与 Lucene 的关系 |
|---|---|---|
| Lucene | 搜索程序库 | 核心引擎本身 |
| Solr | 独立的搜索服务器 | Apache 项目，基于 Lucene |
| Elasticsearch | 分布式搜索与分析服务 | 由 Elastic 公司主导开发，基于 Lucene |
| OpenSearch | 分布式搜索与分析服务 | 由亚马逊云服务发起、从 Elasticsearch 早期版本分叉而来，现由社区基金会维护（写作时情况） |

此外还有不依赖 Lucene 的项目，例如用 Rust 编写的 Tantivy、面向站内即时搜索的 Meilisearch 等。各项目的许可协议和归属曾有过调整，选用前应以其官方网站的最新说明为准。

需要强调：这些工具常用于站内搜索、日志分析、电商检索等场景，规模通常远小于全网网页搜索。大型网页搜索引擎是否、在多大程度上使用它们，属于未公开信息，不宜推测。

## 7.3.2 Lucene 内部：把教科书原理装进文件

打开 Lucene 的设计，你会认出第六章的许多老朋友。

- **分析器**（Analyzer）：文档和查询进入系统前，先经过分词、转小写、去停用词等处理。中文需要额外的中文分词插件，否则可能被切成一个个单字——这正是第二章“分词”在工程中的样子。
- **倒排索引与压缩**：每个词对应一个文档编号列表，编号以差值方式压缩存储，以减少磁盘和内存占用。
- **相关性打分**：在 Lucene 较新的版本中，默认打分模型是 BM25；更早的版本使用基于 TF-IDF 的经典模型。
- **段**（Segment）：这是 Lucene 很有特色的设计。新加入的文档不会去改动已有索引，而是写成一个新的小“段”；每个段一旦写好就不再修改。查询时同时查所有段再合并结果；后台则不断把小段**合并**（Merge）成大段。删除文档时也只是打上“已删除”标记，等合并时才真正清除。

为什么要“只增不改”？可以类比图书馆：每天到的新书先放在临时书架上，定期再整理进总目录，而不是每来一本书就重印整本目录。不可修改的段便于缓存、便于并发读取，也不怕写到一半出错。代价是新文档要等新段“打开”后才能被搜到，Elasticsearch 把这个间隔称为**刷新**（Refresh），默认约为一秒，因此被称作**近实时搜索**（Near Real-Time Search）。这与第五章“更新流”的取舍一脉相承：越追求新鲜，系统开销越大。

## 7.3.3 Elasticsearch：把单机引擎变成集群

Lucene 擅长在一台机器上管好一份索引，Elasticsearch 和 Solr 的分布式模式（SolrCloud）则解决“数据装不下、请求扛不住”的问题，正好对应 7.1 节讲的结构：

1. **索引被切成若干分片**（Shard），每个分片本质上就是一个独立的 Lucene 索引；
2. 每个分片可以有**副本**（Replica），分布在不同机器上，一台宕机时副本顶上，同时分担查询；
3. 一次查询先发到协调节点，再分发给相关分片并行检索，各自返回前若干名，最后汇总排序——这就是“分散—汇聚”的查询流。

使用者通过 HTTP 接口、以 JSON 格式提交文档和查询，不必写 Java 代码。除全文检索外，它还支持按字段精确过滤、聚合统计（例如“各价格区间各有多少件商品”），这就是购物网站筛选栏背后常见的实现方式之一。

## 7.3.4 跟上语义检索的潮流

6.5 节讲到的向量检索也已进入开源搜索。写作时，Lucene 已支持存储嵌入向量，并用 HNSW（Hierarchical Navigable Small World，分层可导航小世界图）做近似最近邻搜索；Elasticsearch、OpenSearch、Solr 也都提供了向量字段和相应查询。许多团队把关键词检索（BM25）与向量检索结合起来，形成**混合检索**（Hybrid Search），再交给大语言模型生成答案——这正是 4.4 节检索增强生成在中小规模场景下的常见搭法。此外，也有 Milvus 等专门的开源向量数据库，与上述全文搜索引擎形成互补。

## 7.3.5 小结：开源让原理“看得见”

开源搜索的价值不只在于省钱，更在于透明：分析器、倒排索引、BM25、段合并、分片副本，每一层都能读到源代码和文档，原理与实现可以一一对照。它也提醒我们边界所在——开源工具展示的是通用做法，不能代替各家商业搜索引擎未公开的具体算法。下一节，我们把目光从文字转向图片、声音和视频，看看搜索如何走向多模态。
