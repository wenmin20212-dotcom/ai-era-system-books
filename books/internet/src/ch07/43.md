# 7.6 本章骨架小结与实物探索任务

还是那个熟悉的场景：你在浏览器里按下回车，网页一眨眼就出来了。读完第七章，同样这一秒，你看到的东西应该多了几层。地址栏里那个安全连接标志背后，可能跑着 QUIC 和 HTTP/3；你的手机可能同时拿着一个 IPv4 地址和一个 IPv6 地址；页面上的图片多半不是从网站的“老家”来的，而是从离你几十公里外的缓存节点取的；运营商机房里那些路由器，有一部分可能正按控制器下发的规则转发流量。网速变慢的时候，你也知道该先用什么工具去量，不必只能干着急。

本节先把这五项关键技术串成一副骨架，再布置几项动手任务，最后给出几个可以直接拿去问 AI 的问题。

## 7.6.1 本章骨架：五项技术，回应五个老问题

第七章的五节表面上各讲各的，其实都在回应前面几章留下来的问题。地址不够怎么办？连接太慢怎么办？内容太远怎么办？网络太僵怎么办？出了故障怎么查？每项技术各答一题。

| 关键技术 | 回应的老问题 | 核心思路 | 与前文的连接 |
|---|---|---|---|
| IPv6（互联网协议第 6 版） | IPv4 约 43 亿个地址不够分 | 把地址扩展到 128 位，减少对 NAT 的依赖 | 3.1 寻址、5.2 NAT |
| QUIC 与 HTTP/3 | TCP+TLS 建连握手次数多，一个包丢了会拖住后面的数据 | 在 UDP 之上重做传输层，加密握手合并进来，多路流彼此独立 | 6.2 TCP、6.5 TLS |
| 内容分发网络（CDN） | 源站离用户远，热门内容反复长途搬运 | 把内容复制到边缘节点，用 DNS 或任播把用户引到近处 | 2.5 服务器、5.4 内容流 |
| 软件定义网络（SDN）与网络虚拟化 | 设备各自为政，配置分散，改起来慢 | 控制平面与数据平面分离，集中编程；在一套物理网上切出多张逻辑网 | 3.3 路由、6.3 BGP |
| 网络测量与故障排查 | 网络对用户是个黑箱，“慢”和“断”说不清 | 用 ping、traceroute 和持续监控测出时延、丢包和路径 | 8.2 排队论（下一章） |

用一句话串起来：**互联网的基本架构几十年没有推倒重来，靠的是在边缘和上层不断加新技术，同时尽量不改动中间那根“细腰”——IP。** IPv6 是唯一直接动了细腰的一项，所以它的过渡用了几十年还没走完，至今和 IPv4 长期并存。QUIC 绕开了难以改动的 TCP，在 UDP 上重新实现可靠传输。CDN 没碰协议，只调整了内容放在哪里。SDN 改的是网络由谁来管、怎么管。测量技术则让前面这些改变可以被看见、被验证。

本章还有几条要记住的边界：

- **具体部署情况变化快。** 各国 IPv6 普及率、支持 HTTP/3 的网站比例、CDN 节点数量都在逐年变化，书中只讲结构和原理。需要最新数字时，可以查谷歌等公司公开的 IPv6 统计页面、APNIC 等地区互联网注册机构的测量报告，或 W3Techs 一类第三方统计网站，并注意数据的发布时间。
- **测量结果不等于真相。** 很多路由器会限制对 ping 的回应速度，或者干脆不回应；traceroute 中途某一跳显示星号，不一定说明那里出了故障。测量数据都需要结合上下文解读。
- **SDN 主要用在云数据中心、大型互联网公司的自有广域网和企业分支互联（SD-WAN）里。** 家用路由器一般不涉及它。数据中心的细节，留给本系列的《数据中心》和《云计算》两册。

## 7.6.2 实物探索任务

以下任务只用你自己的设备和公开网站，全部是只读的观察，不会影响任何人的网络。

**任务 1：看看你有没有 IPv6 地址。** 在电脑或手机的网络设置里查看当前连接的详细信息，找有没有以“2”或“3”开头、用冒号分隔的长地址。然后分别连家里的 Wi-Fi 和手机流量，比较两次的结果。也可以打开一个公开的 IPv6 测试网站，看它给出的评分。记下结论：你家的宽带和你的手机网络，各自有没有开通 IPv6？

**任务 2：找出走 HTTP/3 的网站。** 在电脑版 Chrome 或 Edge 浏览器中按 F12 打开开发者工具，切到“网络（Network）”面板，在列标题上右键勾选“协议（Protocol）”，然后刷新几个常用的大网站。协议一栏显示“h3”的请求用的就是 HTTP/3，显示“h2”或“http/1.1”的用的是较老的版本。数一数各有多少，再想想：为什么同一个网页里，有的请求用 h3，有的不用？

**任务 3：追踪一张图片的来处。** 还是在“网络”面板里，点开页面上的一张大图片，查看它的响应头（Response Headers）。留意 server、via、x-cache、age 这类字段，看能不能认出它来自哪一家 CDN，以及是否命中了缓存（例如出现 HIT 字样）。注意，各家 CDN 使用的字段名称不统一，这本身就是一个可以记下来的发现。

**任务 4：在不同时段测一测时延。** 在电脑的命令行里对同一个常用网站执行 ping，分别在早上和晚上九点左右各测一次，每次各记约 20 个结果。比较平均时延和波动幅度。再执行一次 traceroute（Windows 系统中的命令是 tracert），数一数大约经过多少跳，看时延从哪一跳开始明显变大。下一章 8.2 节讲排队论时，会用到你在这里记下的数据。

**任务 5：画一张“我家网络的分层图”。** 拿一张纸，从下往上画：光猫、路由器、你的设备，以及它们各自拿到的地址（IPv4 和 IPv6）；再往上画运营商网络、可能经过的 CDN 节点，最后是源站。在每一层旁边标出本章讲到的哪项技术在这里起作用。

## 7.6.3 可以直接问 AI 的问题

1. “这是我在家里用 traceroute 访问某网站的完整输出（附上结果，可以先把自己的公网 IP 抹掉）。请逐跳解释每一行的含义，指出哪几跳可能属于我的运营商、哪几跳属于 CDN，并说明中间出现星号可能有哪些原因。”
2. “请用不超过五百字比较 TCP+TLS 1.3 与 QUIC 建立连接的过程，各需要几次往返？在丢包率较高的手机网络里，为什么 QUIC 往往表现更好？请注明依据的是哪些 RFC 文档。”
3. “如果我是一家小网店的运维人员，在决定是否启用 IPv6 和 HTTP/3 时，应该检查哪些事项？请按‘先查什么、再改什么、最后怎样验证’的顺序列出清单。”

AI 给出回答后，记得回到本书的骨架上去对照：它说的是原理，还是某家厂商的具体做法？有没有给出可以核实的出处？

## 7.6.4 小结与过渡

本章讲的是互联网怎样一边保持原有架构，一边持续更新自己。不过还有一个问题没有回答：为什么这种在边缘加新技术、尽量不动中间的做法能一直行得通？为什么晚上九点的 ping 值会变高？下一章“原理溯源”会从端到端原则、排队论、图论和网络效应这几个方面来解释。
