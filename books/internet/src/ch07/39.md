# 7.2 QUIC 与 HTTP/3：让网页更快

在地铁里刷手机，信号时好时坏；从家里走到楼下，手机从 Wi-Fi 切换到蜂窝网络。这时你可能注意到，有些 App 的视频会卡一下再继续，有些则几乎无感。差别的一部分就藏在传输协议里。前面几章讲过，网页长期依靠 TCP 加 TLS 加 HTTP 这套组合来传输。QUIC 和 HTTP/3 换掉了这套组合的底座，目标是让网页更快、切换网络时更平稳。本节说明它们解决了什么问题，又是用什么办法解决的。

## 7.2.1 老组合的三处“慢”

回顾第六章：打开一个 HTTPS 网页，浏览器先和服务器做 TCP 三次握手，再做 TLS 握手协商密钥，之后才能发出第一个 HTTP 请求。这套做法有三个问题。

1. **握手轮次多。** TCP 握手要花一个往返时间（RTT，Round-Trip Time）。TLS 1.2 还要再花两个往返，TLS 1.3 减到一个。如果服务器在大洋彼岸，一个往返常在一两百毫秒量级，几个往返叠加起来，用户就能感觉到等待。
2. **队头阻塞（Head-of-Line Blocking）。** HTTP/2 允许在一条 TCP 连接里同时传多个文件，比如图片、脚本、样式表，每个文件走一条“流”。但 TCP 只认一条有序的字节流。只要其中一个数据包丢了，后面所有数据都得等它重传，哪怕后面那些数据属于别的文件、本来已经到了。这好比单车道上一辆车抛锚，后面所有车都得停。
3. **连接绑死在地址上。** TCP 连接由“源 IP、源端口、目的 IP、目的端口”这四个值确定。手机从 Wi-Fi 换到蜂窝网络，IP 地址变了，旧连接就作废，只能重新握手。

这些问题很难在 TCP 内部修改。TCP 由操作系统内核实现，网络中间还有大量防火墙、NAT 设备认得 TCP 的老格式。一旦改动报文格式，就可能被这些中间设备丢弃，这种现象叫“协议僵化”（ossification）。

## 7.2.2 QUIC：在 UDP 之上重建传输层

QUIC 最初由谷歌公司设计并在自家浏览器和服务中试验，后来交给互联网工程任务组（IETF）标准化，2021 年以 RFC 9000 等一组文档发布。它的名字在标准里不再是缩写，就叫 QUIC。

QUIC 的做法是把数据装进 UDP 报文。UDP（User Datagram Protocol，用户数据报协议）很简单，只负责送达，不保证顺序和可靠性。中间设备大多允许 UDP 通过，所以 QUIC 在多数网络中可以直接部署，不必改造现有设备。可靠传输、拥塞控制、加密这些功能，QUIC 自己在 UDP 之上重新实现，而且通常放在应用程序里运行，不放在内核里。这样浏览器和服务器更新软件时，协议也能跟着改进，不必等操作系统升级。

下面对照 QUIC 针对上面三个问题的设计：

| 问题 | 老组合（TCP+TLS+HTTP/2） | QUIC + HTTP/3 |
|---|---|---|
| 建连握手 | TCP 1 个往返 + TLS 1～2 个往返 | 传输与加密合并，首次连接约 1 个往返；曾连过的服务器可尝试 0-RTT |
| 丢包影响 | 一个包丢失，所有流都要等 | 各流独立排序，丢包只影响所在的那条流 |
| 切换网络 | IP 变化即断开，需要重连 | 用连接 ID 标识连接，可迁移到新地址 |
| 加密 | TLS 在 TCP 之上，头部信息明文 | TLS 1.3 内置，大部分头部也加密 |

## 7.2.3 三项关键机制

**合并握手。** QUIC 把 TLS 1.3 的密钥协商直接写进自己的握手过程（RFC 9001），传输参数和加密参数一次谈妥。如果浏览器以前访问过这台服务器，还可以用上次保存的信息在第一个报文里就带上请求数据，这叫 0-RTT。0-RTT 有一个代价：这类早期数据可能被别人截获后重复发送（重放），所以标准建议只用于重复执行也无害的请求，例如普通的页面读取。

**流的独立。** QUIC 在一条连接里原生支持多条流，每条流各自编号、各自保持顺序。一张图片的数据包丢了，只有这张图片的流需要等待重传，同时传输的脚本和文字照常交给浏览器。前面那条单车道，现在变成了多车道。

**连接迁移。** 每条 QUIC 连接有一个连接 ID（Connection ID）。手机换了网络、IP 变了，只要报文里的连接 ID 没变，服务器就知道还是原来那位客户。经过地址验证后，双方可以接着传数据，不必重新握手。

## 7.2.4 HTTP/3：跑在 QUIC 上的 HTTP

HTTP/3（RFC 9114）在语义上和 HTTP/1.1、HTTP/2 一样，请求方法、状态码、头部这些内容都没有变。变化在于它把“多路复用”这件事交给 QUIC 的流来做，自己不再管理。HTTP/2 原来的头部压缩算法依赖严格的顺序，在流彼此独立的环境里会重新带来阻塞，所以 HTTP/3 另配了一套 QPACK 压缩方案（RFC 9204）。

浏览器怎么知道某个网站支持 HTTP/3 呢？常见做法是先用 HTTP/2 访问，服务器在响应里通过 Alt-Svc 头部告诉浏览器“我还有 HTTP/3 可用”。浏览器下一次访问时再改走 QUIC。另一种做法是在 DNS 的 HTTPS 记录里提前公布。如果 UDP 被某个网络屏蔽，浏览器会退回 TCP，所以用户一般不会察觉到这个过程。

写作时，主流浏览器和大型内容分发网络普遍已经支持 HTTP/3。公开测量资料显示，它在全球网页流量中已占相当比例，具体占比因统计方法不同而差异较大。

## 7.2.5 收益与代价

QUIC 的收益主要体现在高延迟、易丢包、经常切换网络的场景，比如移动网络和跨洲访问。在稳定的有线网络里，它和 TCP 的差距往往不明显。

它也有代价。在用户态完成加密和收发，服务器的 CPU 开销通常比内核里经过多年优化的 TCP 更高。另外，报文大部分都被加密，运维人员很难像以前那样在中间抓包分析，这也是第 7.5 节要讨论的测量难题之一。另有部分企业网络出于管理需要会封锁 UDP 443 端口。

你可以打开浏览器的开发者工具，在“网络”面板里显示“协议”一列，就能看到哪些资源走的是 h3。QUIC 说明了一件事：TCP 本身不变，也可以在端点之间重建传输层，让整套组合继续演进。下一节的内容分发网络，正是把 HTTP/3 部署到你身边的主要力量之一。
