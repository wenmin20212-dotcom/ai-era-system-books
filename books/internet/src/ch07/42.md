# 7.5 网络测量与故障排查：ping、traceroute 与监控

晚上九点，视频突然卡成幻灯片，网页转圈打不开。多数人的第一反应是重启路由器，有时管用，有时不管用。问题可能出在手机和路由器之间，也可能出在运营商的线路上，还可能是对方网站本身出了故障。网络工程师面对同样的情况，会先做测量，再下判断。这一节介绍几件最常用的测量工具，以及隐藏在它们背后的原理。这些工具都是只读的诊断手段，用来看清自己的网络，与攻击无关。

## 7.5.1 ping：向远方喊一声，听回声

ping 这个名字借用了声呐的“回声”。你在电脑的命令行里输入 `ping` 加一个网址，电脑就会向目标发送一种特殊的小数据包，叫作“回显请求”（Echo Request），对方收到后回一个“回显应答”（Echo Reply）。这两种报文属于互联网控制报文协议（ICMP，Internet Control Message Protocol），它是 IP 协议的“随行通信员”，专门传递诊断和差错信息，IPv4 版本的规范是 RFC 792。

ping 的输出里有两个数字最值得关注：

- **往返时延（RTT，Round-Trip Time）**：一来一回花了多少毫秒。家里电脑 ping 自家路由器，一般在几毫秒以内；ping 同城的服务器，常见是十几到几十毫秒；跨越大洋的线路，常见在一百多毫秒甚至更高。光在光纤里的传播速度大约是真空光速的三分之二，所以距离本身就决定了一个下限，再好的网络也快不过物理。
- **丢包率**：发出十个包，回来几个。偶尔丢一两个未必是问题，持续丢包则说明某一段链路拥塞或者质量不好。

需要提醒的是，ping 不通不一定代表网站坏了。出于安全考虑，许多服务器和防火墙会选择不回应 ICMP 请求。这时网页可能照常打开，ping 却一直“请求超时”。ping 是一种线索，不能当作判决书。

## 7.5.2 traceroute：把一路经过的站点逐个点名

ping 只告诉你两端之间“通不通、快不快”，却不告诉你中间经过了谁。traceroute（在 Windows 中叫 `tracert`）解决的就是这个问题，它能把数据包沿途经过的每一台路由器列出来。

它利用了 IP 包头里的一个字段：生存时间（TTL，Time To Live）。第三章讲过，每经过一台路由器，TTL 就减 1，减到 0 时路由器丢弃这个包，并回一条 ICMP“超时”消息给发送者。这个设计原本是为了防止数据包在路由环路里无限打转，traceroute 则巧妙地借用了它：

1. 先发一个 TTL=1 的包，第一台路由器把它丢弃并回报，于是你知道了第一跳是谁；
2. 再发 TTL=2 的包，得到第二跳；
3. 依次递增，直到包抵达目的地。

输出结果中的每一行是一跳，通常带有路由器地址和三次测量的时延。读结果时有几条经验：

| 现象 | 常见含义 |
|---|---|
| 某一行显示 `* * *` | 该路由器不回应或限速回应，后面若恢复正常，多半不是故障 |
| 某一跳起时延突然大增并一直保持 | 可能进入了长距离链路（如跨海），或此处开始拥塞 |
| 只有中间某一跳时延高，后面又降下来 | 通常是那台路由器处理诊断报文的优先级低，不代表转发慢 |
| 从某一跳往后全部无回应 | 故障或过滤可能就在这附近 |

还要记得，互联网的去程和回程路径常常不一样（这与第六章讲的 BGP 各自选路有关），traceroute 只能看到去程这一半。

## 7.5.3 由近及远：一套排查思路

工具只是手段，排查靠的是思路。最实用的方法是沿着本书的结构“由近及远、分段排除”：

- **先看终端**：别的网站能不能打开？换一台设备是否正常？如果只有一台设备有问题，就先查它自身。
- **再看家庭网络**：ping 路由器的地址（常见是 192.168.x.1 这一类私有地址）。若丢包或时延忽高忽低，问题多在 Wi-Fi 信号或路由器本身。
- **然后看名字解析**：网址打不开，但直接用 IP 地址能通，问题可能出在 DNS。可以用 `nslookup` 查询域名对应的地址，必要时更换 DNS 服务器做对照。
- **再看运营商与远端**：traceroute 到目标，观察从哪一跳开始异常。如果是出了家门的第一两跳就出问题，可以联系宽带运营商；如果是目标网站附近的问题，你能做的往往只有等待。

这套顺序的价值在于每一步都把可能性砍掉一半，比凭感觉“到处重启”更快、更可靠。

## 7.5.4 从一次测量到持续监控

个人用户偶尔 ping 一下就够了，网站和运营商则需要一刻不停地观察。网络监控大致分为两类：

- **主动测量**：主动发出探测流量，例如定时 ping、定时访问网页并记录加载时间。前面提到的测速网站也属于这一类。一些研究机构和组织会在全球部署大量探针，持续测量互联网的连通性，例如欧洲区域互联网注册机构 RIPE NCC 运营的 RIPE Atlas 项目。
- **被动测量**：不额外发包，而是统计设备上已有的真实流量。路由器可以按“流”汇总记录，谁和谁通信、用了多少字节；设备也可以通过简单网络管理协议（SNMP，Simple Network Management Protocol）等方式上报端口流量和错误计数。

运维团队把这些数据汇总成曲线和告警规则，例如“某条链路利用率持续超过某个阈值就通知值班人员”。第五章讲到的流量潮汐，正是靠这类监控画出来的。

从按下回车时的一个小小 ping，到覆盖全球的探针网络，测量让看不见的互联网变得可以观察。它也是本章各项关键技术落地时共同的底座：IPv6 部署得怎么样、QUIC 有没有提速、CDN 节点是否健康，最终都要靠测量来回答。
