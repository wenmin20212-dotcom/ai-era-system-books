# 6.5 HTTPS 与 TLS：加密连接怎样建立

在浏览器地址栏里，大多数网址都以“https://”开头，旁边还有一个小锁形状的图标（不同浏览器在写作时的样式不同，有的已改为一个“调节”图标，但点开后仍能看到“连接是安全的”之类的说明）。点开它，你会看到网站的证书信息：颁发给谁、由谁签发、有效期到哪天。这个小图标背后，是一套在你点下回车后几十毫秒内完成的协商过程。上一节我们看到，DNS 把名字变成了地址；TCP 在 6.2 节里建立了可靠的连接。但光有可靠还不够：数据包要穿过家里的路由器、运营商的设备、交换中心和别人的骨干网，沿途任何一个环节都有可能“看到”或“改动”内容。HTTPS 要解决的，正是“在一条你无法控制的路上，安全地说悄悄话”。

## 6.5.1 明文时代的三个隐患

HTTPS 是“超文本传输安全协议”（HTTP Secure）的缩写，本质上是“HTTP 跑在 TLS 之上”。TLS 即“传输层安全协议”（Transport Layer Security），前身是 SSL（安全套接层，Secure Sockets Layer）。今天的 SSL 各版本都已被标准文档宣布弃用，但“SSL 证书”这个叫法仍在日常中流传。

如果只用普通 HTTP，网页内容以明文在网上传递，会面临三类问题：

| 隐患 | 生活类比 | TLS 提供的对应能力 |
|---|---|---|
| 被偷看 | 明信片谁都能读 | 机密性：内容加密 |
| 被篡改 | 信在途中被人改了几个字 | 完整性：任何改动都能被发现 |
| 被冒充 | 寄信人其实是骗子 | 身份认证：用证书证明“我就是这个网站” |

三者缺一不可。只加密而不认证身份，就可能与一个冒充者建立了“非常安全”的加密通道，等于把秘密锁进保险箱后交给了小偷。

## 6.5.2 两种钥匙：对称加密与非对称加密

理解 TLS，先要分清两类密码学工具。

**对称加密**：双方用同一把钥匙加密和解密，速度快，适合大量数据，常见算法如 AES。难点在于：素不相识的两方，怎样在被人监听的线路上约定同一把钥匙？

**非对称加密**（公钥密码）：每一方有一对钥匙，公钥可以公开，私钥自己保管。用公钥“锁上”的东西只有私钥能打开；用私钥做的“签名”任何人都能用公钥验证。它解决了“陌生人如何建立信任”的问题，但计算开销大。

TLS 的思路是取长补短：先用非对称技术完成身份认证和密钥协商，再用协商出来的对称密钥加密真正的网页数据。常用的密钥协商方法叫“密钥交换”，例如基于椭圆曲线的迪菲-赫尔曼（ECDHE）。它的巧妙之处在于：双方各自公开一部分数值，就能各自算出同一个秘密，而旁观者即使看到全部公开数值也算不出来。打个不严格的比方：两人各往一桶公共颜料里加入自己的秘密颜色再交换，最后两边调出同样的颜色，旁人却无法把颜色拆回原样。

## 6.5.3 证书与信任链：谁来证明“你就是你”

服务器怎样证明自己就是 example.com？靠**数字证书**。证书里写着域名、服务器的公钥、有效期，以及签发机构的签名。签发机构叫**证书颁发机构**（Certificate Authority，CA）。

浏览器和操作系统里预装了一批“根证书”，这是信任的起点。验证时形成一条**信任链**：

1. 网站证书由某个“中间 CA”签名；
2. 中间 CA 的证书由“根 CA”签名；
3. 根 CA 的证书已预装在你的设备里，被直接信任。

浏览器逐级核对签名、检查域名是否匹配、证书是否过期或被吊销。任何一环出错，就会弹出“您的连接不是私密连接”之类的警告。这个警告值得认真对待：在公共 Wi-Fi 下遇到它，最稳妥的做法是不要继续访问，更不要输入密码。

此外还有“证书透明度”（Certificate Transparency，RFC 6962 等）机制：CA 签发的证书要记入公开可审计的日志，让错签或滥签更容易被发现。按公开资料，Let's Encrypt 等免费 CA 的出现和自动化签发工具的普及，是近十年 HTTPS 迅速普及的重要原因之一。

## 6.5.4 一次 TLS 1.3 握手

写作时主流的版本是 TLS 1.3（RFC 8446，2018 年发布），较旧的 TLS 1.2 仍在部分系统中使用。在 TCP 三次握手完成之后，TLS 1.3 的完整握手大致如下：

1. **ClientHello**：浏览器说明自己支持哪些加密算法，附上自己的密钥交换参数，并在“服务器名称指示”（SNI）字段里写明要访问的域名——一台服务器上常常托管着许多网站，需要靠它挑出对应的证书。
2. **ServerHello 及后续**：服务器选定算法，送回自己的密钥交换参数。此时双方已能算出共享密钥，于是服务器后面发送的证书、证明自己持有私钥的签名、握手完成消息，都已经是加密的。
3. **Finished**：浏览器验证证书和签名无误，发出自己的完成消息，紧接着就可以发送加密的 HTTP 请求。

相比 TLS 1.2 需要两个来回，TLS 1.3 只需一个来回；对近期访问过的网站，还可以借助“会话恢复”甚至“0-RTT”提前发送数据（0-RTT 存在重放风险，标准对其使用有限制）。TLS 1.3 还删除了一批老旧、不安全的算法，取消了静态 RSA 密钥交换，完整握手一律采用具备“前向保密”的（EC）DHE 密钥交换：即使服务器私钥日后泄露，过去录下的通信也无法被解密。

需要注意 HTTPS 保护的边界：它加密的是内容，但你连接的 IP 地址、通信时间和数据量仍然可见；SNI 中的域名在 TLS 1.3 中默认仍是明文，相关的加密方案（ECH）在写作时仍处于逐步部署阶段。这个标志也只说明“通道安全、对方确实持有该域名的证书”，并不保证网站本身可信——钓鱼网站同样可以申请到合法证书。

## 6.5.5 从握手到下一章

回头看一次网页访问：DNS 找到地址，TCP 建立连接，TLS 再握一次手，然后 HTTP 请求才真正出发。每多一个来回，就多一份延迟，在跨洋链路上尤其明显。这正是下一章 QUIC 与 HTTP/3 的出发点：把传输和加密的握手合并起来，让“安全”和“快”不再互相拖累。
