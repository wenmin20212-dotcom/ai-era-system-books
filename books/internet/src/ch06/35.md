# 6.4 DNS 的层级、缓存与解析过程

在浏览器地址栏输入一个网址，按下回车。第一次打开某个网站，有时会感觉“卡”了一下才开始加载；同一个网站再打开一次，几乎立刻就有反应。这短短的停顿里，常常有一件事在发生：电脑正在向网络打听这个名字对应哪个 IP 地址。第三章讲过，域名系统（Domain Name System，DNS）负责把名字变成地址。本节进一步拆开它的运行机制：名字为什么分层管理，一次查询怎样一级一级问下去，缓存怎样让第二次查询变快，以及这套系统靠什么防范被人冒充。

## 6.4.1 一棵倒过来的树：DNS 的层级结构

DNS 的名字空间是一棵倒置的树。以 `www.example.com.` 为例，从右往左读：

| 层级 | 例子 | 由谁负责 |
|---|---|---|
| 根（root） | 最右边那个通常省略的“.” | 根服务器系统，由多家机构共同运营 |
| 顶级域（Top-Level Domain，TLD） | `.com`、`.cn`、`.org` | 各顶级域的注册管理机构 |
| 二级域 | `example.com` | 域名持有者，通过注册商注册 |
| 更下层的名字 | `www.example.com` | 持有者自己设置 |

每一层只管自己那一段，并把下一层的管理权**授权**（delegation）出去。根只知道 `.com` 归哪些服务器管，不知道 `www.example.com` 在哪里；`.com` 的服务器知道 `example.com` 由哪几台服务器负责，也不知道具体主机的地址。真正掌握最终答案的，是 `example.com` 自己的**权威域名服务器**（authoritative name server）。

这种设计和邮政地址很像：国家、省、市、街道逐级划分，没有哪个邮局需要记住全世界每一户人家的位置。分层授权让 DNS 管得过来，也不必依赖某一台中心服务器。DNS 的基本规范见 RFC 1034 和 RFC 1035，均发布于 1987 年，至今仍是这套系统的基础。

关于根服务器，有一个常见误解，说“全世界只有 13 台根服务器”。准确的说法是：根服务器有 13 个名字（a 到 m），每个名字背后靠**任播**（anycast）技术部署在世界各地的大量实例上，公开资料中的实例总数在一千以上的量级。离你最近的那一个实例会回应你的查询。

## 6.4.2 一次完整的解析：递归与迭代

普通用户的设备并不亲自去问根服务器，这些工作交给**递归解析器**（recursive resolver）完成。它通常由宽带运营商提供，家里的路由器通过 DHCP 把它的地址分给手机和电脑；也有人改用公共 DNS 服务。整个过程分两段：

1. **终端 → 递归解析器（递归查询）**：你的电脑说“请把 `www.example.com` 的地址直接告诉我”，然后等结果。电脑里负责发出这个请求的程序叫“存根解析器”（stub resolver）。
2. **递归解析器 → 各级权威服务器（迭代查询）**：
   - 问根：“`www.example.com` 在哪？”根答：“我不知道，去问 `.com` 的服务器，地址在这里。”
   - 问 `.com`：答：“去问 `example.com` 的权威服务器。”
   - 问 `example.com` 的权威服务器：答：“`www.example.com` 的 IPv4 地址是……”
3. 递归解析器把结果交回你的电脑，浏览器这才开始建立连接。

可以把它理解为前台代办：你只对前台说一句话，前台替你跑完好几个部门。答案里常见的记录类型有：A 记录（IPv4 地址）、AAAA 记录（IPv6 地址）、CNAME（别名，指向另一个名字，内容分发网络常用这种方式接管流量）、NS（指明由哪台服务器负责）、MX（邮件服务器）。

## 6.4.3 缓存与 TTL：快的秘密，也是慢的来源

如果每次都从根问起，根服务器和顶级域服务器会不堪重负，用户也要等很久。DNS 的效率主要来自**缓存**：浏览器、操作系统、家用路由器、递归解析器都可能把查到的结果暂存起来。

缓存能存多久，由记录自带的**生存时间**（Time To Live，TTL）决定，单位是秒，由域名持有者在权威服务器上设定。常见取值从几十秒到一天不等：经常调整线路的网站设得短，稳定的记录设得长。递归解析器还会缓存“`.com` 归谁管”这类中间信息，所以大多数查询根本不需要再问根服务器。查不到的结果也会缓存一段时间，叫作否定缓存（RFC 2308）。

缓存带来两个后果：

- **快**：第二次访问往往在本机或解析器内部就得到答案，耗时从几十毫秒降到接近零。
- **慢**：网站更换服务器地址后，各地缓存要等 TTL 到期才会更新。这就是运维人员常说的“DNS 生效需要时间”。DNS 并没有一个统一的“广播更新”动作，新旧答案会在一段时间内同时存在。

## 6.4.4 脆弱点与防护：DNSSEC 与加密 DNS

早期 DNS 查询通常使用 UDP、以明文传输，也不带签名，因此存在两类风险：

| 风险 | 原理 | 防护手段 |
|---|---|---|
| 伪造应答、缓存投毒 | 冒充权威服务器抢先返回假答案，被解析器缓存后影响大量用户 | 源端口与查询编号随机化；**DNSSEC**（DNS 安全扩展，RFC 4033 等）用数字签名逐级验证答案真伪 |
| 被窃听或篡改 | 途中设备能看到你在查哪些网站 | **DoT**（DNS over TLS，RFC 7858）、**DoH**（DNS over HTTPS，RFC 8484）对终端到解析器这一段加密 |

需要注意两种技术的分工：DNSSEC 保证答案“是真的”，不负责保密；DoT/DoH 保证传输过程“不被偷看”，但无法证明权威服务器给出的内容没有被伪造。两者解决的是不同问题。写作时，DNSSEC 在各顶级域和网站中的部署程度并不均衡；不少主流浏览器和操作系统已支持加密 DNS，具体默认设置因产品和版本而异。

对普通用户来说，最实用的防范方法是：使用可信的解析服务，及时更新路由器固件，并修改路由器的默认管理密码。家用路由器的 DNS 设置一旦被人改掉，家里使用默认设置的设备都可能被引向错误的地址。

## 6.4.5 小结

DNS 用分层授权解决“管得过来”的问题，用递归加迭代的查询方式解决“问得到”的问题，用缓存和 TTL 解决“问得快”的问题，再用 DNSSEC 和加密传输弥补早期设计在安全上的不足。打开网页前那一下停顿，就是这套全球分布式数据库在为你工作。拿到 IP 地址之后，浏览器要和服务器建立一条加密连接，这就是下一节要讲的 TLS。
