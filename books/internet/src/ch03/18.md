# 3.4 可靠传输：丢包、重传与拥塞控制

晚上八点，你在手机上打开一个网页，页面一行行出现，图片清清楚楚，没有缺一块、错一个字。可是就在同一时刻，你家路由器的 Wi-Fi 正受到邻居信号的干扰，小区出口的链路被成百上千户人家同时挤占，某台远方的路由器因为缓存满了，正把来不及处理的数据包直接丢掉。网络本身并不保证每个包都能送到，可你看到的网页却是完整的。这中间的落差，就是“可靠传输”要填补的。

## 3.4.1 网络为什么会丢东西

上一节讲到，路由器只负责“尽力而为”（Best Effort）地把数据包往下一跳送，既不保证送到，也不保证出了问题一定告诉发送方。丢包的常见原因可以归成几类：

| 原因 | 发生在哪里 | 日常表现 |
|---|---|---|
| 排队溢出 | 路由器、交换机的缓存 | 晚高峰网速变慢、视频卡顿 |
| 无线信号差错 | Wi-Fi、蜂窝网络 | 离路由器远时网页加载断断续续 |
| 线路或设备故障 | 光缆、端口、板卡 | 某些网站突然打不开 |
| 包损坏被校验丢弃 | 任何链路 | 用户通常感觉不到，由重传掩盖 |

其中最常见的是第一种：数据包像车流一样到达路由器，出口一时处理不过来，就先在缓存里排队；队伍排满，后来的包只能被丢弃。这一现象背后的数学规律，第八章“排队论”一节会专门展开。

除了丢失，数据包还可能**乱序**（后发的先到，因为走了不同的路）和**重复**（同一个包被送了两次）。一个可靠的传输机制必须同时处理这三件事。

## 3.4.2 把可靠性放在两端：TCP 的思路

互联网的做法是：中间的路由器保持简单，把“保证送到”的责任交给通信两端的计算机。承担这份责任的主要协议叫**传输控制协议**（Transmission Control Protocol，TCP），最早的标准是 1981 年发布的 RFC 793，现行版本整合在 RFC 9293 中。浏览网页、收发邮件、下载文件，大多跑在 TCP 之上。

可以把 TCP 想象成寄一套编了页码的书稿：

1. **编号**：发送方给每一段数据标上序号（Sequence Number），接收方据此把乱序到达的内容重新排好，并识别出重复的部分。
2. **确认**：接收方收到后回一个确认（Acknowledgment，ACK），意思是“到第几页为止我都收到了”。
3. **校验**：每个数据段带有校验和（Checksum），内容出错就当作没收到。
4. **重传**：发送方迟迟等不到某段的确认，就认为它丢了，再发一次。

这样，下层网络哪怕丢、乱、重，到了应用程序手里的仍是一串完整、有序的数据。

## 3.4.3 什么时候该重传

重传的难点在于“等多久”。等太短，包其实还在路上就重发，白白浪费带宽；等太久，用户就要盯着空白页面干着急。

TCP 用两种方式判断丢包：

- **超时重传**：发送方持续测量数据往返一趟所需的时间，即往返时延（Round-Trip Time，RTT），并据此动态计算一个超时时间（RTO，计算方法见 RFC 6298）。超过这个时间仍无确认，就重传。往返国内网站的 RTT 通常在几毫秒到几十毫秒，跨洋访问则常在一两百毫秒量级，所以超时时间不能是一个固定值。
- **快速重传**：如果接收方连续收到了第 5、6、7 段，却唯独缺第 4 段，它会反复发出“我只收到第 3 段为止”的确认。发送方看到连续三个这样的重复确认，不必等超时，立刻补发第 4 段。

这就像快递员发现收件人连续三次说“还差 4 号包裹”，便马上补寄，而不是干等一周再说。

## 3.4.4 拥塞控制：别把路堵死

光会重传还不够。设想晚高峰时，所有人的电脑都发现丢包，于是都拼命重发——网络只会更堵，丢得更多，最终谁也传不动。这种情况在 1986 年前后的早期互联网上真实发生过，被称为“拥塞崩溃”。此后，研究者范·雅各布森（Van Jacobson）等人提出了拥塞控制算法，成为 TCP 的标准组成部分（现行规范见 RFC 5681）。

核心思想是：**把丢包当作网络拥挤的信号，主动放慢**。发送方维护一个“拥塞窗口”，表示不等确认最多能连续发出多少数据：

- **慢启动**：连接刚建立时窗口很小，每收到确认就扩大，大约每个 RTT 翻一倍，快速摸索可用带宽。
- **拥塞避免**：到达一定程度后改为每个 RTT 只增加一点，小心试探。
- **遇到丢包就减速**：发现丢包后把窗口大幅缩小，常见做法是减半。

这种“缓慢加、快速减”的策略，让成千上万条连接在没有中央指挥的情况下，自发地分享同一条线路。下载文件时速度先是爬升、再在某个水平上下波动，正是这个过程的外在表现。

拥塞控制算法仍在演进。写作时，许多操作系统默认使用名为 CUBIC 的算法（RFC 9438）；谷歌提出的 BBR 则尝试通过测量带宽和时延而非单纯依赖丢包来判断拥塞，已在部分服务中使用。具体选用哪种，取决于操作系统和服务商的配置，并非全网统一。

## 3.4.5 不是所有应用都要“绝对可靠”

可靠是有代价的：等待重传意味着延迟。对于视频通话、在线游戏，迟到半秒的旧画面不如直接跳过。这类应用常使用**用户数据报协议**（User Datagram Protocol，UDP），它只负责送出、不做确认和重传，把取舍交给应用自己决定。

| 对比项 | TCP | UDP |
|---|---|---|
| 是否保证送达与顺序 | 是 | 否 |
| 是否有拥塞控制 | 内置 | 需应用自行处理 |
| 典型用途 | 网页、邮件、文件下载 | 实时音视频、DNS 查询、游戏 |

值得一提的是，新一代的 QUIC 协议也构建在 UDP 之上，却在自身内部重新实现了可靠传输和拥塞控制，第七章会专门介绍它。

回到开头那个完整显示的网页：它的每一个字节，都可能经历过编号、确认、超时、重发与减速。正是两端计算机这份不声不响的“对账”工作，让一张并不可靠的网络，交出了可靠的结果。数据既然能完整送达，接下来要问的就是：网页、邮件、视频这些应用，又是怎样利用这条通道为我们提供服务的。
