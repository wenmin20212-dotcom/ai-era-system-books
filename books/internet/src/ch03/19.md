# 3.5 应用服务：网页、邮件、即时通信与视频

早上出门前，你可能在几分钟里做了这些事：在浏览器里查天气，在邮箱里回一封工作邮件，在聊天软件里给家人发一张照片，再在地铁上刷几段短视频。四件事用的是同一部手机、同一条网络，但它们“说话的方式”各不相同。前面几节讲的寻址、命名、路由和可靠传输，都是为了把数据送到对的地方；真正让你感受到“上网”的，是跑在这些基础功能之上的应用服务。本节就来看看，网页、邮件、即时通信和视频，各自是怎样利用下面这套基础设施的。

## 3.5.1 网页：一问一答的 HTTP

当你在地址栏输入网址并按下回车，浏览器做的事情可以概括为“向服务器提一个问题，等它给出答案”。这套问答规则叫作超文本传输协议（HyperText Transfer Protocol，HTTP）。一次典型的请求大致是：“请把某某路径下的页面给我”；服务器的回答则带有一个状态码和页面内容。你可能见过的“404”，就是服务器回答“找不到这个页面”的状态码。

今天的网页很少只是一个文件。一个新闻首页往往需要几十到上百个资源：页面骨架（HTML）、样式表（CSS）、脚本（JavaScript）、图片和字体。浏览器拿到骨架后，会根据里面的引用继续发出请求，最后把它们拼成你看到的画面。为了保护传输内容，现在的网站普遍使用 HTTPS，也就是在 HTTP 外面套一层加密的 TLS 连接，不少浏览器地址栏里的小锁图标表示的就是这一点。TLS 的握手过程留到第六章细讲。

HTTP 本身也在演进。下表是三代版本的简要对照，具体细节在第七章展开：

| 版本 | 下层传输 | 主要特点 |
|---|---|---|
| HTTP/1.1 | TCP | 文本格式，一条连接上的请求基本要排队处理 |
| HTTP/2 | TCP | 二进制分帧，一条连接里可以同时跑多个请求 |
| HTTP/3 | QUIC（基于 UDP） | 减少连接建立的等待，丢包时多个请求之间不互相拖累 |

不管版本怎样变化，“客户端请求、服务器响应”这个基本模式始终没有变。

## 3.5.2 邮件：像寄信一样的“存储转发”

电子邮件比网页还要古老，它的设计思路很像邮政系统。你点“发送”后，邮件并不是直接飞进对方手机，而是先交给你所用邮件服务商的发信服务器，再由它按照简单邮件传输协议（Simple Mail Transfer Protocol，SMTP）转交给对方邮件服务商的服务器，存放在对方的“邮箱”里。收件人什么时候打开客户端，客户端才会用 IMAP（Internet Message Access Protocol，互联网消息访问协议）或较早的 POP3（Post Office Protocol 3，邮局协议第三版）把信取回来。

这里有两个值得注意的细节：

- **发信服务器怎样知道对方邮箱在哪里？** 靠域名系统。每个邮件域名都可以登记一种专门的 MX（Mail Exchange，邮件交换）记录，指明“发给这个域名的信，请交给哪台服务器”。上一节讲的 DNS，在这里又派上了用场。
- **为什么邮件允许“慢一点”？** 因为它采用存储转发：对方服务器暂时联系不上时，发信服务器会先把信留着，过一段时间再重试。所以邮件不追求实时，追求的是“最终送达”。

现在很多人用网页或手机应用收发邮件，表面上走的是 HTTPS，但服务商之间传递邮件，仍然以 SMTP 为基础。

## 3.5.3 即时通信：一直“挂着”的长连接

微信、QQ、Telegram 这类即时通信应用要做到“对方刚发，你就收到”。难点在于：你的手机通常躲在家用路由器或运营商的地址转换设备后面，外面的服务器不能随时主动找到它。常见的解决办法是由手机主动和服务器建立一条长期保持的连接，并定时发一点很小的“心跳”数据，让这条连接和沿途的地址转换记录不被清除。有新消息时，服务器就顺着这条已经打通的连接推送下来。

不同公司的即时通信软件大多使用各自的私有协议，具体做法并不公开统一。公开标准方面，有 XMPP（Extensible Messaging and Presence Protocol，可扩展消息与存在协议）等，部分系统曾经采用过。语音和视频通话对延迟更敏感，常用 UDP 承载实时媒体，并可能尝试让两台设备直接通信，打不通时再由服务器中转。这种“点对点”和“中转”的取舍，第四章还会再讨论。

另外，手机系统为了省电，通常不允许每个应用都自己挂着连接。苹果和谷歌的手机系统都提供统一的推送通道，由系统维持一条连接，替各个应用接收通知。这是写作时主流手机操作系统的普遍做法。

## 3.5.4 视频：切成小块、按需挑选

视频是今天互联网流量中占比很高的一类，公开的行业报告中常见“占大头”的说法。在线点播视频（比如看剧、看短视频）通常不是一口气下载完整文件，而是把视频切成每段几秒钟的小片段，并且同一内容准备了高、中、低多种清晰度。播放器一边播放，一边估算当前网速，再决定下一段要哪种清晰度。这种做法叫自适应码率流（Adaptive Bitrate Streaming），常见的标准方案有 HLS（HTTP Live Streaming，由苹果公司提出）和 MPEG-DASH（国际标准化组织制定）。你在地铁里看到画面突然变糊又慢慢变清，就是播放器在根据网络状况调整清晰度。

这些片段本质上就是一个个普通的 HTTP 文件，因此可以被缓存在离你很近的内容分发网络节点上，这正是第二章提到 CDN 的意义所在。直播则对延迟要求更高，会尽量缩短片段长度，或采用专门的低延迟传输方式。

## 3.5.5 小结：同一张网，四种“性格”

把四类应用放在一起看，差别就很清楚了：

| 应用 | 最在意什么 | 典型做法 |
|---|---|---|
| 网页 | 打开快、内容完整 | HTTP 请求响应，加密传输 |
| 邮件 | 最终送达 | SMTP 存储转发，DNS 的 MX 记录 |
| 即时通信 | 实时到达 | 长连接加心跳，服务器推送 |
| 视频 | 播放不卡 | 分段、多清晰度、就近缓存 |

它们共用同一套地址、域名、路由和传输能力，只是在最上层按照自己的需要组合这些能力。这也体现了互联网设计中的一个重要思路：网络本身只负责尽力把数据送到，至于怎样把数据变成网页、邮件或视频，交给两端的应用去决定。这种分工方式，正是下一章“分层模型”要讨论的主题。
